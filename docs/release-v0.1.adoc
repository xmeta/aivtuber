= v0.1 Release Checklist and Evidence Record
:toc:
:toclevels: 2

This document operationalizes GitHub issue #97, the minimum usable live-stream release gate.

It defines *how to collect release evidence*.
It does not claim that the current repository already satisfies v0.1, and it does not replace subsystem acceptance criteria.

== 1. Release decision principle

The v0.1 question is:

> Can an operator start the production runtime, connect the selected live adapters, admit content, produce a useful reaction through the intended routing hierarchy, remain bounded/degraded under failure, retain emergency control, and shut down cleanly?

A release candidate is acceptable only when the exercised production profile has coherent end-to-end evidence.

Do not substitute "all unit tests pass" for product-level release evidence.
Do not substitute one successful live demo for deterministic CI/replay/failure evidence.

== 2. Evidence classes

=== 2.1 Deterministic CI / local reproducible evidence

Expected to be runnable without live billable providers:

* toolchain/lockfile validation;
* schema/security fixtures;
* Rust workspace checks;
* deterministic replay benchmark;
* deterministic failure/fallback scenarios;
* bounded logical-time soak where applicable.

=== 2.2 Scheduled/manual provider conformance

Harness and fixtures for this class were delivered by #66 (completed); collecting the live/scheduled evidence for the release gate is a #97 activity.

May require controlled credentials or test environments:

* VTube Studio protocol/auth compatibility;
* OBS compatibility;
* configured Thinking/TTS provider health;
* authentication/permission failures;
* timeout/cancellation normalization;
* provider/version identity.

These probes must not perform destructive/public actions against unrelated real channels.

=== 2.3 Local live-smoke evidence

A bounded 30-60 minute operator-observed session using the selected v0.1 production profile.

The live smoke validates system composition and operability.
It does not define statistical performance targets by itself.

=== 4.2 Cached reaction path

* [x] admitted event reaches the production Rust composition root;
* [x] exact/cached route produces the expected bounded Performance Asset;
* [x] audio dispatch succeeds or degrades explicitly;
* [x] avatar dispatch succeeds or degrades explicitly;
* [x] route/correlation identity is observable.

This is the cheapest end-to-end production path and should remain usable even when generative providers are unavailable.

=== 4.3 Template route

* [x] valid Template routing no longer maps to silence solely because the route is absent;
* [x] output remains subject to the normal public-output/security boundary;
* [x] unsupported/missing template content has a typed fallback.

Primary owner: #54.

=== 4.4 Reflex/Jev degradation

Exercise at least:

* normal bounded reflex decision;
* provider timeout;
* provider unavailable;
* invalid/malformed decision where supported by fixtures.

Verify:

* [x] scheduler/motor loop does not freeze;
* [x] deterministic fallback is selected;
* [x] fallback reason is observable;
* [x] stale provider result cannot override the newer decision.

Evidence: #173/#174 adds `late_success_after_deadline_becomes_deterministic_timeout_fallback`. Its mock transport deliberately ignores the supplied timeout, returns a valid HTTP 200 only after the absolute Jev deadline, and proves the late result is normalized to `Timeout` / deterministic `Fallback` with no accepted returned model, selected candidate, or provider answers.

=== 4.5 Generative / TTS degradation

Exercise controlled failure or mock fault for:

* Thinking provider timeout/unavailable;
* TTS timeout/unavailable;
* cancellation while generation is pending.

Verify:

* [x] performer remains responsive;
* [x] cheaper route/non-verbal/silence fallback is explicit;
* [x] stale/cancelled generated output is not dispatched later;
* [x] operator stop/mute remains available.

=== 4.6 Bounded retained state

For the selected v0.1 profile, collect available high-water/plateau evidence for retained state such as:

* scheduler active/terminal state;
* generated L0 assets;
* working/adaptation memory;
* rate-limit/source state;
* telemetry/diagnostic retained history;
* provider queues.

Do not invent a numeric release threshold before #51/#58/#71 establish the relevant contract/baseline.

The release gate instead requires:

* [x] all exercised long-lived state has an explicit configured bound;
* [x] no observed process-lifetime collection grows without ownership/retention policy;
* [x] any unresolved growth is linked to a blocking issue.

=== 4.7 Operator emergency control

Verify independently of normal content/model health:

* [x] stop;
* [x] mute;
* [x] recovery/resume if included in the selected profile (unmute is intentionally restart-only in this profile, issue #56);
* [x] operator command cannot be forged through public content;
* [x] emergency control remains usable while a provider is slow/unavailable (verified with providers entirely unavailable);
* [x] emergency control remains usable under content backlog/saturation scenario where safely testable.

A failure here is a no-go for the affected production profile.

=== 4.8 Diagnostics / health visibility

The operator must be able to identify at least:

* selected production profile;
* runtime/build identity;
* adapter connection/degradation state;
* current provider identity where relevant;
* bounded queue/high-water or equivalent health information needed to diagnose stalls;
* fallback/error reason for the exercised failures.

Do not require raw prompts/replies or secrets in a support artifact.

=== 4.11 30-60 minute local live smoke

Use controlled content/test accounts where appropriate.

Suggested sequence:

. Start from the documented production profile.
. Confirm initial adapter/provider health.
. Exercise several cached reactions.
. Exercise at least one Template response.
. Exercise normal reflex/Jev routing where enabled.
. Exercise one generative response where enabled.
. Trigger or simulate a safe provider degradation.
. Verify fallback while the performer continues operating.
. Verify operator mute/stop during non-idle activity.
. Resume/restart only if the selected profile supports it.
. Continue normal mixed events long enough to observe queue/retention behavior.
. Perform clean shutdown.
. Inspect diagnostic/telemetry evidence for unexplained errors or growth.

Record notable incidents, even if recovered automatically.

Executed record (2026-10-02, section 12): 34 minute 32 second live run on the cached profile with real VTube Studio (`ws://127.0.0.1:8001`) and OBS (`ws://127.0.0.1:4455`) connected. Sequence coverage: documented production profile start; initial adapter health all `None`; 27 cached reactions queued across four reactions; mixed events for the full duration; real (not simulated) provider degradation when VTube Studio repeatedly dropped the daemon's session -- the avatar adapter degraded explicitly (`avatar_error=Some("Unavailable: VTube Studio reconnect backoff active until ...")`) and recovered to `None` while the performer path kept operating; operator `mute`/`stop` during non-idle activity (mute latched, the event-while-muted did not dispatch, `stop` recorded an `operator_stop` cancellation); clean stdin-EOF shutdown with exit 0 and no orphaned processes; diagnose bundle inspected -- every retained collection bounded, no unexplained growth. Incidents: (1) repeated VTS-side session drops (`ObjectDisposedException` in VTube Studio's own log, roughly every 60 seconds) -- recovered automatically by adapter reconnect backoff; the daemon did not freeze (the pre-#175 unbounded-read defect that froze the daemon on an unresponsive peer was filed as #175 and fixed in a97983b before this run); (2) the `smile_soft` hotkey was absent from the model loaded during a fresh-session probe (VTS APIError 202) -- hotkey availability is model-dependent and dispatch degrades explicitly instead of failing silently; (3) the live-smoke debug binary was built without `AIVTUBER_GIT_REVISION`/`AIVTUBER_RUSTC_VERSION`, so its diagnose bundle reports those two identity fields as unknown -- build identity for the run is established by the commit and rebuild command, and the stamped fresh-clone RC binary verified the identity wiring end-to-end. Template/reflex-Jev/generative routes are disabled in the cached profile and were not exercised live; they remain covered by the automated gate (sections 4.3-4.5).

== 8. Go / no-go rules

A release decision must be explicit.

=== GO

Use when:

* #97 criteria are met for the selected profile;
* required CI/replay/failure evidence is green or understood within documented non-blocking variance;
* no unresolved release-blocking security/operator/boundedness issue remains;
* live smoke completed without unexplained release-blocking incidents;
* limitations are documented.

=== NO-GO

Use when a release-blocking defect/invariant failure is known, especially:

* operator emergency control failure;
* privileged-control/trust bypass;
* stale/cancelled public output escaping its fence;
* exercised retained state is known unbounded without an accepted temporary release restriction;
* runtime freezes on a required degraded path.

=== DEFER

Use when evidence is incomplete rather than known-bad.

Do not convert missing evidence into an implicit GO.

== 9. Relationship to later stages

Stage 2+ adds stronger measurement, engagement intelligence, natural performance, and multimodal capabilities.

Those stages can change future release criteria, but they are not retroactively required for the minimum v0.1 profile unless #97 is explicitly amended.

Future numeric SLO/error-budget gates belong to #58/#71 after measured baselines exist.

== 13. Post-decision main stability -- replay-benchmark quiescence flake (#177) RESOLVED

The GO decision in section 12 stands and is not reopened here. This section records a

=== What happened

After the RC-20261001-3 decision, `main` turned red in the `Replay benchmark smoke` step of
`Rust checks` (run 36888486710 at `d5c181a`) with:

[source,text]
----

##[error]Process completed with exit code 1.
----

The same commit had passed every `pull_request` run, so the failure was intermittent and
load-dependent rather than a deterministic regression. This violates the section 4.9/4.10
criterion ("replay/benchmark and failure/soak checks remain green") on `main` itself, which
is the branch the release is cut from.

=== Root cause and fix

The bounded generation worker released `in_flight` before publishing its completion to the
composition thread, so `pending == 0 && in_flight == 0` was observable while a finished
result was still unpublished or undrained. The benchmark's wait loop consumed exactly that
predicate and stopped waiting too early. A first fix attempt was rejected in review for
leaving two further holes (the `pending -> in_flight` dequeue gap, and source ordering across
separate relaxed atomics), both of which are now closed.

`crates/app/src/lib.rs` now models outstanding generation work as a three-state machine
(queued -> in-flight -> awaiting drain) where each transition claims the new state before
releasing the old one, and the state counters plus the snapshot loads are `SeqCst` so
claim-before-release is a real ordering guarantee rather than an accident of source order.
`GenerationExecutionSnapshot::is_quiescent()` is the single predicate shared by operator
health, retention, the support bundle, the benchmark wait, and tests. The benchmark wait
additionally searches the whole observation log instead of only its tail, and waits on a
wall-clock budget with yield-then-backoff polling.

Fixed by #179 (`c23b8a7` + `977b19f`), merged as `60b99bc`. Tracked as #177; the follow-up
gate-calibration finding is #180.
