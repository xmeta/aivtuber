= Supply-chain policy (cargo-deny)

Issue: #100 · Policy file: `deny.toml` · CI job: `supply-chain` in `.github/workflows/ci.yml`

== 1. What the gate checks

`cargo deny --locked check` runs four checks against the locked dependency graph:

* *advisories* — known https://rustsec.org/[RustSec] advisories fail the build.
* *licenses* — only the permissive licenses listed in `deny.toml` (`allow`) are accepted. Copyleft (GPL/AGPL) is rejected. Workspace crates are not published (`publish = false` inherited via `[workspace.package]`), so their own license expressions are not gated.
* *bans* — duplicate crate versions are reported as warnings; wildcard version requirements from external crates are denied (intra-workspace path dependencies are allowed). Known `std`-replacement and duplicate findings should be resolved by upgrading rather than skip-listing.
* *sources* — only crates.io is accepted as a registry; unknown git sources and registries are denied.

`--locked` guarantees the gate never mutates `Cargo.lock`.

== 2. Local commands

[source,bash]
----
cargo deny --locked check          # all four checks
cargo deny --offline check         # without network (uses cached advisory db)
cargo deny check licenses          # a single check
----

The advisory database is fetched on first run; CI fetches it automatically.

== 3. Advisory handling policy

When a RustSec advisory appears:

1. Check whether a patched version exists. If yes, upgrade in a normal PR (`cargo update -p <crate>`), let CI run the gate, and record the upgrade in the PR description.
2. If there is no actionable fix (unmaintained transitive dependency, no patched release, or the fix is incompatible with toolchain constraints), add a *temporary exception* to `deny.toml` under `[advisories] ignore`, then document it here.

An advisory with a fix is never ignored; an advisory without a fix may be ignored only through the procedure below.

== 4. Temporary exception procedure

Every exception in `[advisories] ignore` (or a licenses/bans exception) must carry:

* *reason* — why the finding cannot be fixed right now;
* *owner* — the maintainer or issue tracking it;
* *revisit condition* — the event that removes the exception (patched release available, crate dropped from the graph, toolchain upgrade).

Example entry in `deny.toml`:

[source,toml]
----
[advisories]
ignore = [
    # RUSTSEC-2026-0123: unmaintained transitive dep of <crate>, no patch.
    # Owner: @maintainer · Tracked: #NNN · Revisit: when <crate> releases the fix.
    { id = "RUSTSEC-2026-0123", reason = "no patched release; see #NNN" },
]
----

Exceptions are re-reviewed when the dependency graph changes (dependency-upgrade PRs must confirm each still-applies exception) and at least when a revisit condition fires. An exception without a revisit condition is invalid and should be rejected in review.

== 5. Dependency-upgrade PRs

A PR that changes `Cargo.lock` must:

* pass `cargo deny --locked check`;
* add or remove exception entries together with the reason/owner/revisit fields;
* note the license/source impact of any newly introduced crate in the PR description, per the adoption record in `docs/reuse-first.adoc` section 5.

== 7. Tooling installed by CI but absent from every lock file

`cargo deny` audits resolved graphs. It cannot see a binary that CI installs at
runtime, because nothing in the repository records it.

* *`cargo-fuzz` 0.13.2* — installed in `.github/workflows/fuzz.yml` with
  `cargo +nightly install cargo-fuzz --version 0.13.2 --locked`. It is a
  build-time driver, not a runtime dependency, and never links into a
  production binary: it only invokes the targets under `fuzz/`, which
  `crates/scheduler/tests/workspace_contract.rs` keeps out of the workspace
  graph and the workspace lock.
* *owner* — the property/fuzz workstream (#146, #147).
* *reason for the pin* — an unpinned `cargo install cargo-fuzz` would let a CI
  run compile a different toolchain version each week, with no lock file to
  diff against. The explicit `--version` plus `--locked` makes the install
  reproducible in the same spirit as `--locked` in cargo-deny.
* *revisit condition* — if `fuzz/` is removed, or the workflow moves to a
  prebuilt binary with a checksum, or `cargo-fuzz` enters a lock file, revisit
  this entry and either drop the pin or promote it into `deny.toml` scope.
* *assertion* — `scripts/validate.mjs` fails if `fuzz.yml` installs cargo-fuzz
  without an explicit `--version`, so this pin cannot be quietly removed.

The nightly channel used by that workflow is intentionally outside
`scripts/validate-toolchain-pins.mjs`, which enforces a single Rust channel
across `ci.yml`. That validator is deliberately unmodified: the pull-request
gate stays stable-only, and the scheduled workflow is asserted separately by
`scripts/validate.mjs` (nightly declared explicitly, no `pull_request`
trigger).

== 8. Renderer npm bundle (`renderer/local-avatar`)

Issue: #219 (S3) · Decision: ADR-0003 decision 8 · CI job: `renderer` in `.github/workflows/ci.yml`

`cargo deny` audits resolved Rust graphs only. The local VRM renderer is a separate npm project with its own `package.json` and `bun.lock` under `renderer/local-avatar/`; the root `package.json` and `bun.lock` are untouched. Its dependencies are therefore gated by the checks below, not by `cargo deny`.

=== Policy

* *Exact pins.* Every entry in `dependencies` and `devDependencies` is an exact version (no ranges, no tags). The renderer's `package.json` pins the same `packageManager` Bun as the root, and the `renderer` job pins the same `bun-version`, which `scripts/validate-toolchain-pins.mjs` already enforces for every `bun-version:` in `ci.yml`.
* *Frozen lockfile, no install hooks.* CI installs with `bun install --frozen-lockfile --ignore-scripts`. Do not refresh `bun.lock` implicitly. Regenerate it only with the pinned Bun (an older Bun cannot read a newer lockfile format; 1.3.14 writes `lockfileVersion` 1) and in a PR that says why.
* *No CDN.* The bundle is built locally (`bun run build`); the page loads nothing from another origin, which the host's CSP (`default-src 'self'`) also enforces. `dist/` is not committed.
* *Production dependencies* (what ships in the bundle) are `three` and `@pixiv/three-vrm`. A new production dependency needs the adoption record from `docs/reuse-first.adoc` section 5 in the PR.
* *License allowlist.* `bun run check:licenses` (`renderer/local-avatar/scripts/check-licenses.mjs`, no dependencies) reads the installed `node_modules/*/package.json` and fails on any license outside `MIT`, `ISC`, `BSD-2-Clause`, `BSD-3-Clause`, `Apache-2.0`, `0BSD` (SPDX `OR` = any allowed, `AND` = all allowed). The runtime closure (what ships in the bundle) is held to the allowlist with no exceptions. Build/test-only tooling may carry an explicit exception in the script, each with a reason.
* *Advisory audit.* `bun audit` (Bun 1.3.14 supports it) queries the npm advisory database for the locked tree, any severity, runtime and build tooling alike. Exceptions follow the same reason / owner / revisit procedure as section 4, recorded in this section, passed with `bun audit --ignore=<GHSA id>`, and re-reviewed whenever `bun.lock` changes.

=== Current validation (2026-11)

39 installed packages, 15 in the runtime closure (`three` 0.187.0, `@pixiv/three-vrm` 3.5.5 and its 6 `three-vrm-*` and 7 `types-*` packages), all `MIT`. `bun audit` reports no vulnerabilities.

Active license exception (build/test only):

* `lightningcss` (and its platform binary package), `MPL-2.0`. *Reason:* transitive dependency of Vite, used at build time to transform CSS; file-level weak copyleft, used unmodified, never copied into or linked with `dist/`. *Owner:* #219. *Revisit:* if it enters the runtime closure (the script then fails), or when Vite drops it.

Active advisory exceptions: none.

=== Tooling installed by the `renderer` job but absent from every lock file

* *Chromium for Playwright.* Installed by `node node_modules/playwright-core/cli.js install --with-deps chromium`; the browser build is determined by the exact-pinned `playwright-core` (1.65.0) and cached by the hash of `bun.lock`. It is test tooling only and never ships. *Owner:* #219. *Revisit:* when Playwright is bumped.

It is never committed; its license is the VRM metadata embedded in the file (see "Model and rights" in `docs/vts-obs-adapters.adoc` section 6).

== 9. sherpa-onnx (feature `sherpa-stt`, issue #92 S3b)

The optional local Japanese speech-to-text worker wraps the official `sherpa-onnx` crate 2.0.1 (k2-fsa, Apache-2.0; `sherpa-onnx-sys` 2.0.1, Apache-2.0) behind the off-by-default `sherpa-stt` cargo feature of `aivtuber-adapters`. Reuse mode: *wrap* (decision Q4 of the S3a decisions on #92; the fallback, an owned `libloading` FFI, was not needed because the scoped exceptions below are accepted by `cargo deny`). Without the feature nothing here is compiled, downloaded or linked.

=== Scoped license exceptions

The crate's build script pulls in two crates whose licenses are not in the global `allow` list. Both are permissive, both are build-time only (they reach the graph through `sherpa-onnx-sys` -> `zip` -> `bzip2`/`ppmd-rust`, archive extraction inside the build script) and neither can be switched off. They are *scoped exceptions*, pinned to the exact crate version, not global allowlist additions: any other crate under these licenses is still rejected.

[cols="2,2,3",options="header"]
|===
|Crate |Exception in `deny.toml` |Reason and revisit condition

|`libbz2-rs-sys` 0.2.6
|`bzip2-1.0.6`
|The bzip2 / libbzip2 license (BSD-style permissive). Build-time only. Revisit when `sherpa-onnx-sys` drops `zip`/`bzip2` from its build dependencies, or when the crate version changes (the exception names the version, so an upgrade reopens the review).

|`ppmd-rust` 1.5.2
|`MIT-0`
|Licensed `CC0-1.0 OR MIT-0`; the `OR` is satisfied by `MIT-0` alone, so `CC0-1.0` is deliberately not allowed. Build-time only. Same revisit condition.
|===

cargo-deny evaluates the default feature set, so these two exceptions report as "not encountered" warnings in the default `cargo deny --locked check` and are exercised by `cargo deny --locked --features sherpa-stt check`, which the `speech-stt` CI job runs. (`cargo deny --all-features check licenses` fails today for an unrelated reason: the `native-audio-spike` feature's `symphonia` crates are MPL-2.0. That is not changed here.) Cargo.lock gains 29 package entries (25 new crate names, nearly all build-time), and no existing entry is removed or re-versioned.

=== The crate's unchecked download path must never run

The `sherpa-onnx-sys` build script downloads prebuilt libraries from GitHub over HTTPS and *verifies no checksum* unless `SHERPA_ONNX_LIB_DIR` or `SHERPA_ONNX_ARCHIVE_DIR` is set. Rules:

* Every build, test or lint of `aivtuber-adapters` with `--features sherpa-stt` sets `SHERPA_ONNX_ARCHIVE_DIR` to a directory produced by `node scripts/fetch-sherpa-onnx.mjs lib <dir>`, which downloads the pinned archive for the platform and verifies its SHA-256 before it is allowed to exist under its final name. The pins: `sherpa-onnx-v2.0.1-linux-x64-shared-lib.tar.bz2` `532c45bb...` and `sherpa-onnx-v2.0.1-win-x64-shared-MT-Release-lib.tar.bz2` `afa4de3c...` (both downloaded and hashed here, and equal to the digests GitHub publishes). The CI job `speech-stt` does this before any cargo step. Local builders: the same script, then export the variable; do not build the feature without it.
* No default job enables the feature, so no default build downloads anything. Never use `--all-features` in CI for this reason.
* The engine libraries (`sherpa-onnx-c-api` and `onnxruntime`, plus `onnxruntime_providers_shared` on Windows) are pinned by SHA-256 inside the worker and checked by the sidecar before it spawns the worker and by the worker at start. The platform table is Windows x64 and Linux x64; other platforms are refused.

=== Models: provenance, licenses, no redistribution

We do not redistribute weights and never commit them. The operator fetches them with `node scripts/fetch-sherpa-onnx.mjs model <name> <dir>` (pinned revision, every file SHA-256 checked); the worker verifies the same pins at every start (`crates/adapters/src/speech_stt/pins.rs`, asserted equal to the script by a unit test). The transcript lines record `engine.model_id` and a bundle digest of the pinned files.

* *ReazonSpeech k2-v2 int8 (default, Q2).* Hugging Face `reazon-research/reazonspeech-k2-v2`, revision `291488c8151be24d7da4bf7af26e533fad96e407`, the four `*.int8.onnx`/`tokens.txt` files. Weights Apache-2.0 per the model card (published by the corpus publisher's own project; training recipe icefall, Apache-2.0). *Training-data provenance (Q1, accepted with conditions):* trained on the ReazonSpeech corpus (Japanese TV broadcasts), which is gated and whose card makes dataset access conditional on agreeing to use the data solely for the purpose of Article 30-4 of the Japanese Copyright Act (information analysis, which covers training). That is a term for accessing the dataset and is not stated as a restriction on the released weights. Conditions: we do not redistribute weights (the operator fetches them), and this provenance stays recorded here. Revisit if Reazon or the model card publishes a restriction on the weights, or if the project starts bundling model files.
* *NVIDIA parakeet-tdt_ctc-0.6b-ja (selectable, `parakeet-ja`).* The sherpa-onnx int8 CTC export `sherpa-onnx-nemo-parakeet-tdt_ctc-0.6b-ja-35000-int8.tar.bz2` (archive SHA-256 `4b0a800ef29f4f4c8667339bf6f60d5bfdc2852ddc9dc5741aea65b6f8d1306b`; a third-party conversion of `nvidia/parakeet-tdt_ctc-0.6b-ja`). *License CC-BY-4.0: attribution required.* Whoever selects or distributes it must keep this notice: "Contains NVIDIA parakeet-tdt_ctc-0.6b-ja (NVIDIA, CC-BY-4.0, https://huggingface.co/nvidia/parakeet-tdt_ctc-0.6b-ja), converted to ONNX by the sherpa-onnx project (k2-fsa)." Trained on ReazonSpeech (model card dataset list): same Article 30-4 note as above.
* Other candidates evaluated in EXP-0002 (SenseVoice, Moonshine ja, Nemotron streaming, whisper.cpp, Vosk) are not adopted and not pinned.
