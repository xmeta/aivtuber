= Supply-chain policy (cargo-deny)

Issue: #100 · Policy file: `deny.toml` · CI job: `supply-chain` in `.github/workflows/ci.yml`

== 1. What the gate checks

`cargo deny --locked check` runs four checks against the locked dependency graph:

* *advisories* — known https://rustsec.org/[RustSec] advisories fail the build.
* *licenses* — only the permissive licenses listed in `deny.toml` (`allow`) are accepted. Copyleft (GPL/AGPL) is rejected. Workspace crates are not published (`publish = false` inherited via `[workspace.package]`), so their own license expressions are not gated.
* *bans* — duplicate crate versions are reported as warnings; wildcard version requirements from external crates are denied (intra-workspace path dependencies are allowed). Known `std`-replacement and duplicate findings should be resolved by upgrading rather than skip-listing.
* *sources* — only crates.io is accepted as a registry; unknown git sources and registries are denied.

`--locked` guarantees the gate never mutates `Cargo.lock`.

== 2. Local commands

[source,bash]
----
cargo deny --locked check          # all four checks
cargo deny --offline check         # without network (uses cached advisory db)
cargo deny check licenses          # a single check
----

The advisory database is fetched on first run; CI fetches it automatically.

== 3. Advisory handling policy

When a RustSec advisory appears:

1. Check whether a patched version exists. If yes, upgrade in a normal PR (`cargo update -p <crate>`), let CI run the gate, and record the upgrade in the PR description.
2. If there is no actionable fix (unmaintained transitive dependency, no patched release, or the fix is incompatible with toolchain constraints), add a *temporary exception* to `deny.toml` under `[advisories] ignore`, then document it here.

An advisory with a fix is never ignored; an advisory without a fix may be ignored only through the procedure below.

== 4. Temporary exception procedure

Every exception in `[advisories] ignore` (or a licenses/bans exception) must carry:

* *reason* — why the finding cannot be fixed right now;
* *owner* — the maintainer or issue tracking it;
* *revisit condition* — the event that removes the exception (patched release available, crate dropped from the graph, toolchain upgrade).

Example entry in `deny.toml`:

[source,toml]
----
[advisories]
ignore = [
    # RUSTSEC-2026-0123: unmaintained transitive dep of <crate>, no patch.
    # Owner: @maintainer · Tracked: #NNN · Revisit: when <crate> releases the fix.
    { id = "RUSTSEC-2026-0123", reason = "no patched release; see #NNN" },
]
----

Exceptions are re-reviewed when the dependency graph changes (dependency-upgrade PRs must confirm each still-applies exception) and at least when a revisit condition fires. An exception without a revisit condition is invalid and should be rejected in review.

== 5. Dependency-upgrade PRs

A PR that changes `Cargo.lock` must:

* pass `cargo deny --locked check`;
* add or remove exception entries together with the reason/owner/revisit fields;
* note the license/source impact of any newly introduced crate in the PR description, per the adoption record in `docs/reuse-first.adoc` section 5.

== 7. Tooling installed by CI but absent from every lock file

`cargo deny` audits resolved graphs. It cannot see a binary that CI installs at
runtime, because nothing in the repository records it.

* *`cargo-fuzz` 0.13.2* — installed in `.github/workflows/fuzz.yml` with
  `cargo +nightly install cargo-fuzz --version 0.13.2 --locked`. It is a
  build-time driver, not a runtime dependency, and never links into a
  production binary: it only invokes the targets under `fuzz/`, which
  `crates/scheduler/tests/workspace_contract.rs` keeps out of the workspace
  graph and the workspace lock.
* *owner* — the property/fuzz workstream (#146, #147).
* *reason for the pin* — an unpinned `cargo install cargo-fuzz` would let a CI
  run compile a different toolchain version each week, with no lock file to
  diff against. The explicit `--version` plus `--locked` makes the install
  reproducible in the same spirit as `--locked` in cargo-deny.
* *revisit condition* — if `fuzz/` is removed, or the workflow moves to a
  prebuilt binary with a checksum, or `cargo-fuzz` enters a lock file, revisit
  this entry and either drop the pin or promote it into `deny.toml` scope.
* *assertion* — `scripts/validate.mjs` fails if `fuzz.yml` installs cargo-fuzz
  without an explicit `--version`, so this pin cannot be quietly removed.

The nightly channel used by that workflow is intentionally outside
`scripts/validate-toolchain-pins.mjs`, which enforces a single Rust channel
across `ci.yml`. That validator is deliberately unmodified: the pull-request
gate stays stable-only, and the scheduled workflow is asserted separately by
`scripts/validate.mjs` (nightly declared explicitly, no `pull_request`
trigger).

== 8. Renderer npm bundle (`renderer/local-avatar`)

Issue: #219 (S3) · Decision: ADR-0003 decision 8 · CI job: `renderer` in `.github/workflows/ci.yml`

`cargo deny` audits resolved Rust graphs only. The local VRM renderer is a separate npm project with its own `package.json` and `bun.lock` under `renderer/local-avatar/`; the root `package.json` and `bun.lock` are untouched. Its dependencies are therefore gated by the checks below, not by `cargo deny`.

=== Policy

* *Exact pins.* Every entry in `dependencies` and `devDependencies` is an exact version (no ranges, no tags). The renderer's `package.json` pins the same `packageManager` Bun as the root, and the `renderer` job pins the same `bun-version`, which `scripts/validate-toolchain-pins.mjs` already enforces for every `bun-version:` in `ci.yml`.
* *Frozen lockfile, no install hooks.* CI installs with `bun install --frozen-lockfile --ignore-scripts`. Do not refresh `bun.lock` implicitly. Regenerate it only with the pinned Bun (an older Bun cannot read a newer lockfile format; 1.3.14 writes `lockfileVersion` 1) and in a PR that says why.
* *No CDN.* The bundle is built locally (`bun run build`); the page loads nothing from another origin, which the host's CSP (`default-src 'self'`) also enforces. `dist/` is not committed.
* *Production dependencies* (what ships in the bundle) are `three` and `@pixiv/three-vrm`. A new production dependency needs the adoption record from `docs/reuse-first.adoc` section 5 in the PR.
* *License allowlist.* `bun run check:licenses` (`renderer/local-avatar/scripts/check-licenses.mjs`, no dependencies) reads the installed `node_modules/*/package.json` and fails on any license outside `MIT`, `ISC`, `BSD-2-Clause`, `BSD-3-Clause`, `Apache-2.0`, `0BSD` (SPDX `OR` = any allowed, `AND` = all allowed). The runtime closure (what ships in the bundle) is held to the allowlist with no exceptions. Build/test-only tooling may carry an explicit exception in the script, each with a reason.
* *Advisory audit.* `bun audit` (Bun 1.3.14 supports it) queries the npm advisory database for the locked tree, any severity, runtime and build tooling alike. Exceptions follow the same reason / owner / revisit procedure as section 4, recorded in this section, passed with `bun audit --ignore=<GHSA id>`, and re-reviewed whenever `bun.lock` changes.

== 9. sherpa-onnx (feature `sherpa-stt`, issue #92 S3b)

The optional local Japanese speech-to-text worker wraps the official `sherpa-onnx` crate 2.0.1 (k2-fsa, Apache-2.0; `sherpa-onnx-sys` 2.0.1, Apache-2.0) behind the off-by-default `sherpa-stt` cargo feature of `aivtuber-adapters`. Reuse mode: *wrap* (decision Q4 of the S3a decisions on #92; the fallback, an owned `libloading` FFI, was not needed because the scoped exceptions below are accepted by `cargo deny`). === Scoped license exceptions

The crate's build script pulls in two crates whose licenses are not in the global `allow` list. Both are permissive. Both reach the graph through `sherpa-onnx-sys` -> `zip` -> `bzip2`/`ppmd-rust` (archive extraction inside the build script), which cannot be switched off. Since #294 S2 `libbz2-rs-sys` is also linked at run time by `aivtuber-setup` (the pure-Rust bzip2 decoder for the `.tar.bz2` model archives); `ppmd-rust` is not. They are *scoped exceptions*, pinned to the exact crate version, not global allowlist additions: any other crate under these licenses is still rejected.

=== The crate's unchecked download path must never run

The `sherpa-onnx-sys` build script downloads prebuilt libraries from GitHub over HTTPS and *verifies no checksum* unless `SHERPA_ONNX_LIB_DIR` or `SHERPA_ONNX_ARCHIVE_DIR` is set. Rules:

* Every build, test or lint of `aivtuber-adapters` with `--features sherpa-stt` sets `SHERPA_ONNX_ARCHIVE_DIR` to a directory produced by `node scripts/fetch-sherpa-onnx.mjs lib <dir>`, which downloads the pinned archive for the platform and verifies its SHA-256 before it is allowed to exist under its final name. The pins: `sherpa-onnx-v2.0.1-linux-x64-shared-lib.tar.bz2` `532c45bb...` and `sherpa-onnx-v2.0.1-win-x64-shared-MT-Release-lib.tar.bz2` `afa4de3c...` (both downloaded and hashed here, and equal to the digests GitHub publishes). The CI job `speech-stt` does this before any cargo step. Local builders: the same script, then export the variable; do not build the feature without it.
* No default job enables the feature, so no default build downloads anything. Never use `--all-features` in CI for this reason.
* The engine libraries (`sherpa-onnx-c-api` and `onnxruntime`, plus `onnxruntime_providers_shared` on Windows) are pinned by SHA-256 inside the worker and checked by the sidecar before it spawns the worker and by the worker at start. The platform table is Windows x64 and Linux x64; other platforms are refused.

=== Loaded libraries are the verified libraries

The worker links the engine as shared libraries, so the OS loader resolves them before `main`. The check is only meaningful if the loader loads exactly the files that are verified, so both are tied to the directory of the executable:

* The libraries must sit *beside* `speech-stt-worker`. On Windows the loader searches the application directory first. On Linux `crates/adapters/build.rs` links the worker with `-Wl,--disable-new-dtags,-rpath,$ORIGIN`: a `DT_RPATH`, which the loader consults before `LD_LIBRARY_PATH` (a `DT_RUNPATH` would come after it), so the environment cannot substitute other libraries; the sherpa-onnx libraries carry their own `$ORIGIN` rpath for `libonnxruntime`. (A `rustc-link-arg` from the dependency's build script does not reach our binary, hence our own build script, scoped to this one binary.) Neither `PATH` nor `LD_LIBRARY_PATH` is relied on.
* The worker verifies the libraries in `current_exe()`'s directory, never an operator-supplied directory, and exits with code 2 and a clear message if they are missing from it or do not match. The sidecar resolves `--stt-worker` to a real path (no `PATH` lookup, symlinks followed), verifies the libraries beside that file, and spawns exactly that path.
* A missing library cannot be reported by the worker: the loader refuses first (`error while loading shared libraries`, exit 127). A tampered one is refused by the worker (exit 2). The `speech-stt` CI job shows both, plus that a tampered set on `LD_LIBRARY_PATH` is ignored.
* *Residual risk:* the loader runs the libraries' initializers before our hash check runs, so a tampered library executes once before the worker refuses it. The sidecar's pre-spawn check covers the supervised path. This is acceptable only because whoever can write beside the binary can already replace the binary itself; the pin guards against wrong, corrupt or silently updated libraries, not against an attacker with write access to the install directory. Static linking (the crate's `static` feature) would remove the shared-library question but was not chosen (a 123 MB static archive per platform, per EXP-0002 section 7, and a second verified archive flavour in CI); revisit if the install directory cannot be trusted.

== 11. Release archives and the first-run command (issue #294 S1, S2)

Workflow: `.github/workflows/release.yml`. Assembly: `scripts/package-release.mjs`. Smoke: `scripts/smoke-release-archive.mjs`. Static inputs: `packaging/` (`about.toml`, `about.hbs`, `RELEASE-README.txt`, `ENGINE-LIBRARIES-NOTICE.txt`). The reuse decision (plain Actions matrix; cargo-dist reference only; cargo-about adopted for notices) is recorded in `docs/reuse-first.adoc`, "Release packaging record".

=== What is built and from what

* *Triggers.* A tag matching `v*` (builds, smoke-tests, creates a *draft* GitHub release with the archives and `SHA256SUMS`; a person publishes it) and `workflow_dispatch` (a dry run: the same build and smoke, artifacts only, nothing released). The workflow never runs for pull requests. Only the `publish` job has `contents: write`, and it refuses a tag whose commit is not reachable from `main`.
* *Targets.* Windows x64 (`windows-latest`) and Linux x64 (`ubuntu-22.04`, the oldest hosted image, for a low glibc floor). macOS is not built.
* *Locked, verified inputs.* Every cargo step uses `--locked`; the renderer uses `bun install --frozen-lockfile --ignore-scripts`; `SHERPA_ONNX_ARCHIVE_DIR` is the output of `node scripts/fetch-sherpa-onnx.mjs lib` (SHA-256 verified), so the crate's unchecked download path (section 9) never runs. There is no build cache: a release is built from the tag's sources and the verified engine archive alone. `cargo deny --locked --features silero-vad,mic-capture,sherpa-stt,sherpa-tts check` runs in the job, before the build, with the scoped exceptions of section 9.
* *Contents.* `aivtuber-app`, `aivtuberctl`, `aivtuber-setup`, `speech-vad-sidecar`, `speech-stt-worker`, `local-tts-sidecar`, `twitch-chat-ingress`, `youtube-chat-ingress`; the pinned engine libraries beside them (copied from the verified archive, only the file names pinned in `speech_stt::pins`); the renderer page at `renderer/local-avatar/dist`; the starter reaction pack; `README.txt`; licence files. No Node script ships any more (S2): `aivtuber-setup` embeds the pins. The Cargo feature set is the one the quickstart builds (`silero-vad,mic-capture,sherpa-stt,sherpa-tts`).
* *C runtime (Windows, 2026-11-12).* A clean Windows image has no Visual C++ runtime, and a first archive exited 0xC0000135 because `aivtuber-setup.exe` imported `VCRUNTIME140.dll`. Every Windows release build now sets `RUSTFLAGS=-C target-feature=+crt-static` (the job `env` in `release.yml`, release only; dev and CI builds are unchanged), so the Rust programs link the C runtime statically. The pinned engine DLLs are the `shared-MT-Release` build of sherpa-onnx v2.0.1: their import tables were read (`node scripts/pe-imports.mjs`) and `sherpa-onnx-c-api.dll` imports only `kernel32.dll` and `onnxruntime.dll`; `onnxruntime_providers_shared.dll` only `kernel32.dll`; `onnxruntime.dll` only `advapi32.dll`, `api-ms-win-core-path-l1-1-0.dll`, `dbghelp.dll`, `dxgi.dll`, `kernel32.dll` and `setupapi.dll` (all part of Windows). None needs `vcruntime140.dll`, `vcruntime140_1.dll` or `msvcp140.dll`, so *no Microsoft Visual C++ redistributable file is bundled*. The smoke job fails if any shipped `.exe` or `.dll` imports `vcruntime*`, `msvcp*`, `concrt*`, `vcomp*`, `mfc*` or `api-ms-win-crt-*`. If a future engine pin needs the runtime, ship the DLLs it imports app-local beside the engine-loading programs, copied from the runner's Visual Studio redistributable folder (`VC\Redist\MSVC\<version>\x64\Microsoft.VC14x.CRT`, found with `vswhere`, no download) under Microsoft's app-local deployment terms (https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files), and record the source, version and basis here and in `ENGINE-LIBRARIES-NOTICE.txt`.
* *Visual C++ runtime for llama.cpp (Windows, 2026-11-12, this is the case above).* The setup fetches the pinned llama.cpp b12224 Windows zip (not bundled). Scanning every `.exe` and `.dll` of both pinned Windows zips (Vulkan and CPU) with `scripts/pe-imports.mjs` shows `llama-server.exe` and the ggml/llama DLLs importing exactly `vcruntime140.dll`, `vcruntime140_1.dll` and `msvcp140.dll` (plus the universal CRT `api-ms-win-crt-*`, part of Windows 10 and later, and `libomp.dll`, which the zip ships itself); none of the three is in the zip. The first Sandbox run that reached `start` failed with 0xC0000135 for that reason. *Decision:* ship those three files app-local in the Windows archive under `runtime\msvc`, with `runtime\msvc\REDIST-VERSION.txt` (redistributable version, source folder, SHA-256 of each file) and a section in `THIRD-PARTY-NOTICES.txt` (`packaging/MSVC-RUNTIME-NOTICE.txt`). The release job runs `scripts/collect-msvc-runtime.mjs`, which locates the runner's Visual Studio with `vswhere` and copies the files from `VC\Redist\MSVC\<newest version>\x64\Microsoft.VC14x.CRT` (the newest runtime is backward compatible); nothing is downloaded. *Basis:* Microsoft permits app-local deployment of the Visual C++ redistributable files listed as redistributable (https://learn.microsoft.com/cpp/windows/redistributing-visual-cpp-files; the set is chosen from the imports as https://learn.microsoft.com/cpp/windows/determining-which-dlls-to-redistribute describes; the files are unmodified and distributed only as part of this application). The list lives in `packaging/local-profile-pins.json` (`llama.windows_runtime_dlls`), is read by the smoke test, and `aivtuber-setup local` copies the files from `runtime\msvc` beside `llama-server.exe` (never overwriting a different file; a missing file in the archive is an error naming it; a source checkout without `runtime\msvc` only warns). The files are not code-signed by us; they carry Microsoft's own signature. Revisit when the llama.cpp pin changes: re-scan the new zips and update the list.
* *Never bundled:* model weights, voice files, avatar models, generated audio. `package-release.mjs` refuses a `.vrm`/`.gguf`/`.onnx`/`.bin` file in the page build, and the smoke test fails on any model-like file anywhere in the archive. This keeps the section 9 and 10 position that weights are fetched by the operator with their licence and disclosure handling intact.
* *Checksums.* `SHA256SUMS` is computed over the final archives in the `checksums` job (after the smoke jobs pass) and published beside them. The `tar.gz` is reproducible (sorted entries, fixed owner and mtime, `gzip -n`; `SOURCE_DATE_EPOCH` or 0); the zip is not byte-reproducible (bsdtar stores file times), so the published checksum is of the released bytes.

=== The pin manifest and the first-run command (S2)

* *One source for every download pin.* `packaging/local-profile-pins.json` holds, for each third-party download of the local profile, the HTTPS URL, the exact size in bytes and the SHA-256, plus the licence and disclosure text that `aivtuber-setup local` prints. It is read by the Rust command (embedded with `include_str!`, so a shipped binary has no loose file to swap), by `scripts/fetch-local-profile.mjs`, `scripts/fetch-sherpa-onnx.mjs` and `renderer/local-avatar/smoke/fetch-model.mjs`. The scripts contain no digest or download host (asserted by `tests/fetch-local-profile.test.mjs` and by a unit test in `crates/setup`). The runtime pins the sidecars verify at every start (`speech_stt::pins`, `speech_tts::pins`) stay in the adapters crate and are asserted equal, digest and size, to the manifest by unit tests in both crates. Changing a pin means editing one file and the Rust runtime pin if it is a model file; a test fails if they disagree. Adding or bumping a third-party download still follows the review rules of sections 9 and 10 (licence, provenance, digest of the downloaded bytes).
* *Model profiles (#318).* `profiles` in the manifest names the selectable llama-server setups. `default` uses the top-level `llm` pin (Gemma 4 E4B QAT UD-Q4_K_XL since #340: `unsloth/gemma-4-E4B-it-qat-GGUF` at revision `8c5a9e4fd5482e2be20fe0bf013b4c262a8f4265`, 4,215,695,776 bytes, Apache-2.0; replaces Qwen3-4B-Instruct-2507 Q4_K_M); `perception` pins `Qwen3VL-4B-Instruct-Q4_K_M.gguf` (2,497,281,664 bytes) and `mmproj-Qwen3VL-4B-Instruct-Q8_0.gguf` (453,974,304 bytes) from `Qwen/Qwen3-VL-4B-Instruct-GGUF` at revision `1cd86afb9a95c410a6038ab3b40d8b578c892266`. The digests were taken from the repository's published LFS metadata at that revision and equal the SHA-256 of the files downloaded for EXP-0004. *Licence:* the model card metadata for that revision says `apache-2.0`; the licence text itself was not separately read (the repository carries none beside the README), and the weights are not redistributed by this project. The disclosures are per profile (`applies_to` `profile:<name>`). A test asserts every profile resolves, has exactly one disclosure and its assets are Apache-2.0-tagged HTTPS pins. No dependency changed.
* *What `aivtuber-setup` may do on the network.* HTTPS only, to the hosts in the manifest (GitHub releases and raw, Hugging Face). Plain HTTP is accepted only for a loopback host and only through a test-only configuration field that no command-line option or environment variable reaches. Redirects are followed by hand, at most five, and every hop is re-checked, so an HTTPS URL can not redirect to HTTP. A file is fetched in `Range` segments appended to `<file>.part` with a per-segment timeout; the manifest size is an exact cap (more bytes than pinned is refused, fewer is a failure); retries are bounded; only a file whose SHA-256 equals its pin is renamed to its final name, and a mismatch deletes the partial file. The program sends no credential, no user identifier and no request body.
* *Archive extraction.* In process, no `tar`/`unzip`: `.zip`, `.tar.gz` and `.tar.bz2`. An entry name must be relative with plain components (no `..`, root, drive, `\`, `:`); nothing is written through an existing link; a link entry is allowed only on Unix, only to a single plain sibling file name in the same directory (no separator, `.` or `..`, so link chains can not escape); hard links, devices and other entry types are refused; entry count and expanded bytes are capped per archive (`max_extracted_bytes` in the manifest). Tests cover traversal, absolute names, escaping links, writing through a link and expansion bombs.
* *Dependencies.* `crates/setup` adds *no new package*: `bzip2` 0.6.1, `flate2`, `tar`, `zip` 9.5 (deflate only), `ureq` 3.4 (the HTTP client the adapters already use, rustls), `sha2`, `getrandom`, `clap`, `serde`, `url` were already in `Cargo.lock` (through `sherpa-onnx-sys`'s build script, the adapters and the app). The only `Cargo.lock` change is the new workspace member entry. `libbz2-rs-sys` is the one crate whose licence exception (section 9) now also covers a run-time dependency. `cargo deny --locked check` passes.
* *Secrets.* The env file holds a random 256-bit pseudonym key and a random 128-bit control secret generated from the operating system's randomness; it is created owner-only on Unix, never overwritten without `--force`, and never printed or logged.
* *Signing.* `aivtuber-setup` is unsigned like the other programs (section 11, known limitations).

=== Licence notices in the archive

* *Rust crates:* `cargo about generate --locked --workspace --features <release features> -c packaging/about.toml packaging/about.hbs`, for the two target triples, build and dev dependencies excluded. cargo-about only generates the notice file; the policy gate stays cargo-deny, and `packaging/about.toml` mirrors the `deny.toml` allow list plus the two scoped exceptions, so generation fails on a licence cargo-deny would also reject.
* *Engine libraries:* `packaging/ENGINE-LIBRARIES-NOTICE.txt` (sherpa-onnx Apache-2.0; ONNX Runtime MIT, with the licence text). *Known gap:* the sherpa-onnx library archive carries no licence files, and ONNX Runtime embeds further permissive components whose notices are published upstream in its `ThirdPartyNotices.txt`; the notice file points there rather than copying a text that is not pinned here. Revisit if a pinned copy of those notices is added to the engine pin set.

=== Known limitations

* *Not run end to end on a clean machine by CI.* The release smoke test runs `aivtuber-setup` offline (`--dry-run`, `--offline`, `start --dry-run`); the real downloads, extraction and starter audio were run from a development machine against the real hosts. A clean Windows VM run from a downloaded archive remains the #294 acceptance check.
* *Unsigned binaries.* No Authenticode signing and no notarisation. Windows SmartScreen may warn; the published checksums are the integrity channel. Signing needs a certificate (cost, identity and key custody) and is a later decision under #294.
* Linux archives depend on the system `libasound2` and `libssl3` and on a glibc no older than the build host's.
* The engine libraries are loaded from the install directory and checked by SHA-256 (section 9's residual risk applies unchanged).
