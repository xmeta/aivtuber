= Reuse-First Library and Reference-Implementation Matrix
:toc:
:toclevels: 3

This document records the first candidates to evaluate before aivtuber contributors implement generic infrastructure from scratch.

It is not a dependency lock-in list.
A candidate may be adopted directly, wrapped, partially reused, used only as a reference, benchmarked first, or rejected.

The issue or PR that introduces a dependency still owns final due diligence.
See #100 for supply-chain policy and CI gates; the enforced policy lives in +deny.toml+ (cargo-deny) with the exception procedure in +docs/supply-chain.adoc+.

== 1. Decision rule

Prefer:

[source,text]
----
aivtuber-specific policy / authority / replay semantics
        +
mature library for the generic mechanism
----

Do not outsource project-owned semantics merely because a library offers a convenient default.

Before custom infrastructure is added, check license, maintenance, transitive/runtime cost, async/runtime assumptions, security advisories, determinism/replay impact, bounded-state behavior, provider lock-in, and fallback/removal cost.

For baseline product dependencies, also require a path that does not depend on paid third-party software or billable SaaS. Hosted/commercial services may be optional adapters, but a generic mechanism is not an acceptable baseline choice if the only viable deployment requires an external paid account.

Record the result as one of:

* +adopt+
* +wrap+
* +sidecar+
* +partial reuse+
* +reference only+
* +benchmark first+
* +reject+
* +custom+ (only with a short reason why earlier reuse modes do not fit)

=== First-run setup command record (#294 S2)

[source,text]
----
Problem:     A streamer with only the release archive needs the pinned models and engine pieces
             fetched, verified, extracted, configured and started without Node, Bun or Cargo.
Candidate 1: scripts/fetch-local-profile.mjs + scripts/fetch-sherpa-onnx.mjs (project, Node).
Decision:    wrap the pins, replace the runtime. The pins move to one manifest
             (packaging/local-profile-pins.json) that the scripts keep reading; the Rust command is the
             archive user's path. Node would be an install requirement on the target machine.
Candidate 2: cargo-dist installers / a generic installer builder (Velopack, WiX, Inno Setup).
Decision:    reference only (see the S1 record): they install programs but do not own our verified
             fetch-and-license step, and signing/installer choice is a separate #294 decision.
Candidate 3: HTTP and archive crates for the Rust command.
Decision:    adopt ureq 3.4 (already the HTTP client of crates/adapters), plus tar, flate2, bzip2 0.6
             (pure Rust) and zip 9.5 (deflate only). All were already in Cargo.lock, so no new package
             enters the supply-chain gate. reqwest/hyper rejected: a second HTTP stack and an async
             runtime for a sequential downloader. Shelling out to tar/unzip/curl rejected: absent or
             different on target machines (the Git Bash tar problem of the fetch scripts) and it moves
             the traversal and size checks outside our tests.
Custom:      the download loop (Range segments, size-exact cap, SHA-256 gate, manual redirect checks),
             the safe extractor and the setup flow, because the project-owned rules are the point: HTTPS
             only, exact pinned sizes, no partial file at its final name, no writes outside the
             destination. None of the adopted crates provides these policies.
Revisit:     if the pin count grows past a manifest a person can review, or an installer is chosen (#205).
----

----

             without a terminal, over the existing control surfaces and with no new authority.
Candidate 1: the project's own loopback server (crates/adapters/src/local_avatar/server.rs).

Custom:      the Host/Origin/secret rules, the typed queues to the composition thread and the fixed chat
             envelope, because they are the project's authority and trust boundary (security threat

=== Release packaging record (#294 S1)

[source,text]
----
Problem:     Ship prebuilt Windows x64 / Linux x64 archives of the local profile (app, VAD/STT/TTS
             sidecars, engine libraries beside the executables, renderer page build, licences,
             SHA256SUMS) so a streamer needs no Rust/Node/Bun.
Candidate 1: cargo-dist (axodotdev/cargo-dist, Apache-2.0; active, v0.34.0 released 2026-11-02).
Decision:    reference only (not adopted). Evaluated from its documentation and release state; not trialled.
Why not:     (a) Its unit is one archive per Cargo package. Ours must merge two packages
             (aivtuber-app and aivtuber-adapters) into one archive, so every file beyond one
             package's binaries would ride on its generic `include` of repository paths.
             (b) The deliverable is not just binaries: the verified engine libraries (fetched by our
             pinned script, not the crate's unchecked download), the Vite page build, notices and
             README must be assembled between build and archive. That is exactly the part cargo-dist
             leaves to injected "build setup" steps, which would hold the real logic anyway.
             (c) It generates and owns the workflow file (a regeneration check, plus its own action
             pins), which conflicts with pinning every third-party action to a commit SHA in a file
             we review by hand. (d) The features it adds (installers, Homebrew/npm publishing, update
             receipts) are out of S1 scope (installers are a separate decision, see #294).
Candidate 2: plain GitHub Actions matrix: first-party artifact actions plus the preinstalled `gh` CLI.
Decision:    adopt. `scripts/package-release.mjs` (assembly, ~250 lines, Node only) and
             `scripts/smoke-release-archive.mjs` are project-owned; they embed our verification rules.
             The release is created with `gh release create` rather than a third-party release
             action, so the only third-party actions are those CI already uses
             (dtolnay/rust-toolchain, oven-sh/setup-bun, taiki-e/install-action), plus
             actions/{checkout,setup-node,upload-artifact,download-artifact}. All are pinned to a
             commit SHA in release.yml.
Candidate 3: cargo-about (EmbarkStudios, MIT OR Apache-2.0, v0.9.3 2026-10-26) vs `cargo deny` licence listing.
Decision:    adopt cargo-about for the third-party notice file only. cargo-deny stays the policy gate
             (it decides allowed/denied, but does not produce licence texts); cargo-about reads the same
             Cargo.lock for the same feature set and produces the texts, with `packaging/about.toml`
             mirroring deny.toml's allow list. Installed as a pinned prebuilt binary by
             taiki-e/install-action; recorded in docs/supply-chain.adoc section 11.
License:     all tools above are permissive; none links into a shipped binary.
Determinism: the Linux tar.gz is made reproducible (sorted, fixed owner and mtime, gzip -n). The zip is
             bsdtar's and carries file times; the SHA256SUMS describe the released bytes either way.
Fallback:    delete release.yml; nothing else depends on it.
Revisit:     when installers, signing/notarisation or macOS are decided (#205 or a later #294 slice),
             re-evaluate cargo-dist or an installer builder with new evidence.

== 3. Areas intentionally kept project-owned

The following are not generic mechanisms to outsource wholesale:

* scheduler priority, reservation, safe-interrupt, and cancellation semantics;
* non-serializable authenticated control and memory-write capabilities;
* source trust/plane classification;
* public-output security gate;
* replay ordering and deterministic fallback decisions;
* Jev/LLM recommendation-to-policy boundary;
* moderation recommendation vs privileged execution;
* deadline classes, attention policy, and stale-command policy;
* benchmark/evaluation result meaning and product guardrails.

A library may implement a lower-level primitive used by these systems, but it must not become the authority for these semantics.

== 4. Reference implementations

=== 4.1 Open-LLM-VTuber

Study sentence segmentation, early first response, speech interruption, segmented TTS, and live voice interaction.
Use it to identify tested patterns and failure cases, not as a reason to weaken aivtuber's atomic Performance Asset and output-gate requirements.

=== 4.2 AIRI

Study Live2D/VRM behavior, auto blink, auto look-at, idle eye movement, motion mapping, attention UX, plugin capability negotiation, and control/data-plane separation.
Use it primarily as behavior/UX/architecture evidence unless a package independently fits a provider-neutral Rust boundary.

=== 4.3 Neuro SDK

Study dynamic registration of bounded high-level actions, scene/turn-scoped action windows, context updates that do not require a reply, separate realtime voice transport, and explicit speech lifecycle events.
Adopt those patterns only through aivtuber-owned authority and verification: an action being accepted/dispatched is never proof that the requested outcome completed.

== 6. Revisit policy

Revisit a decision when #58 identifies a different bottleneck, provider behavior changes, a crate becomes unmaintained or receives an unmitigated advisory, dependency/runtime cost becomes material, deterministic/replay requirements change, or #66 conformance disproves an assumption.

Do not repeatedly re-evaluate a previously rejected candidate without new evidence.
