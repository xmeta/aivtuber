= Reuse-First Library and Reference-Implementation Matrix
:toc:
:toclevels: 3

This document records the first candidates to evaluate before aivtuber contributors implement generic infrastructure from scratch.

It is not a dependency lock-in list.
A candidate may be adopted directly, wrapped, partially reused, used only as a reference, benchmarked first, or rejected.

The issue or PR that introduces a dependency still owns final due diligence.
See #100 for supply-chain policy and CI gates; the enforced policy lives in +deny.toml+ (cargo-deny) with the exception procedure in +docs/supply-chain.adoc+.

== 1. Decision rule

Prefer:

[source,text]
----
aivtuber-specific policy / authority / replay semantics
        +
mature library for the generic mechanism
----

Do not outsource project-owned semantics merely because a library offers a convenient default.

Before custom infrastructure is added, check license, maintenance, transitive/runtime cost, async/runtime assumptions, security advisories, determinism/replay impact, bounded-state behavior, provider lock-in, and fallback/removal cost.

For baseline product dependencies, also require a path that does not depend on paid third-party software or billable SaaS. Hosted/commercial services may be optional adapters, but a generic mechanism is not an acceptable baseline choice if the only viable deployment requires an external paid account.

Record the result as one of:

* +adopt+
* +wrap+
* +sidecar+
* +partial reuse+
* +reference only+
* +benchmark first+
* +reject+
* +custom+ (only with a short reason why earlier reuse modes do not fit)

== 3. Areas intentionally kept project-owned

The following are not generic mechanisms to outsource wholesale:

* scheduler priority, reservation, safe-interrupt, and cancellation semantics;
* non-serializable authenticated control and memory-write capabilities;
* source trust/plane classification;
* public-output security gate;
* replay ordering and deterministic fallback decisions;
* Jev/LLM recommendation-to-policy boundary;
* moderation recommendation vs privileged execution;
* deadline classes, attention policy, and stale-command policy;
* benchmark/evaluation result meaning and product guardrails.

A library may implement a lower-level primitive used by these systems, but it must not become the authority for these semantics.

== 4. Reference implementations

=== 4.1 Open-LLM-VTuber

Study sentence segmentation, early first response, speech interruption, segmented TTS, and live voice interaction.
Use it to identify tested patterns and failure cases, not as a reason to weaken aivtuber's atomic Performance Asset and output-gate requirements.

=== 4.2 AIRI

Study Live2D/VRM behavior, auto blink, auto look-at, idle eye movement, motion mapping, attention UX, plugin capability negotiation, and control/data-plane separation.
Use it primarily as behavior/UX/architecture evidence unless a package independently fits a provider-neutral Rust boundary.

=== 4.3 Neuro SDK

Study dynamic registration of bounded high-level actions, scene/turn-scoped action windows, context updates that do not require a reply, separate realtime voice transport, and explicit speech lifecycle events.
Adopt those patterns only through aivtuber-owned authority and verification: an action being accepted/dispatched is never proof that the requested outcome completed.

For a new dependency or custom replacement, record at least:

----

Why:

Determinism / replay impact:

Fallback / removal plan:

----

For small utility crates this can be a short issue/PR section.
For high-consequence runtime/provider changes, use #61's decision/assumption process.

== 6. Revisit policy

Revisit a decision when #58 identifies a different bottleneck, provider behavior changes, a crate becomes unmaintained or receives an unmitigated advisory, dependency/runtime cost becomes material, deterministic/replay requirements change, or #66 conformance disproves an assumption.

Do not repeatedly re-evaluate a previously rejected candidate without new evidence.
