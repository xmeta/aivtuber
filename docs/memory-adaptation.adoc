= Memory and Adaptation Runtime
:toc:

== 1. Scope

Roadmap Phase 5 is implemented by +crates/adaptation+ and the production composition in +crates/app+.

The design keeps three responsibilities separate:

* +SecurityRuntime+ owns authority for durable memory writes.
* +AdaptationEngine+ owns deterministic memory/adaptation policy and replay metadata.
* +AssetStore+ owns validation, compatibility checks, generated-asset persistence, and invalidation.

Neither model output nor serialized authorization claims can directly create durable memory or persist a generated asset.

== 2. Bounded working memory

+WorkingMemory+ stores normalized entries with:

* source event id and source name;
* source class and trust level;
* a pseudonymous actor id when an actor exists;
* normalized claim and optional topic;
* creation and expiry timestamps;
* retention class;
* the deterministic write-gate decision.

Working memory has explicit bounds for entry count, working TTL, durable TTL, claim bytes, and topic bytes. Expired entries are removed during compaction. If the capacity bound is exceeded, the oldest remaining entries are removed deterministically.

Viewer/topic retrieval is local and deterministic. Actor matching requires both the actor id and its source/provider namespace — a query that names an actor without its namespace carries a filter that cannot be evaluated and fails closed with no matches rather than silently widening to every actor; matching prefers the resulting pseudonymous viewer identity, then topic, then recency, with insertion order (the same retained timeline `TemporalBefore` derives from) as the stable tie break for equal record times, so link construction and retrieval can never disagree on which same-tick write came later.

Raw actor ids are not stored in +MemoryEntry+.

=== 2.1 Keyed actor pseudonymization

+ActorPseudonymizer+ uses HMAC-SHA-256 with a deployment secret that is separate from Event Envelopes, replay metadata, model context, telemetry, and operator-control credentials. The MAC domain includes a fixed aivtuber domain tag, the configured key version, the source/provider namespace, and the raw actor id using length-prefixed fields. The complete 256-bit MAC is retained as hexadecimal text; it is not truncated to the former 64-bit identifier.

Production requires +AIVTUBER_MEMORY_PSEUDONYM_KEY_HEX+ containing exactly 32 bytes as 64 hexadecimal characters. +AIVTUBER_MEMORY_PSEUDONYM_KEY_VERSION+ defaults to +v1+ and is non-secret. There is no production zero/default key fallback. Tests and deterministic tooling pass explicit test-only key material directly to +WorkingMemory+.

Key rotation intentionally breaks historical linkability: changing either key material or key version produces a different pseudonym. The key version is embedded in the pseudonym so operators can identify which generation produced a retained record without exposing the key. Existing records are not silently relinked across rotations; deployments that require continuity must perform an explicit offline migration under their own retention/privacy policy.

== 3. Durable memory gate

Short-lived working memory may contain untrusted public content. Durable retention is different.

+ProductionApp::remember_durable_memory+ first calls +SecurityRuntime::authorize_memory_write+. The runtime returns a non-serializable +MemoryWritePermit+ only for an allowed system source or authenticated +memory.admin+ authority.

Public chat without that permit is rejected before +WorkingMemory::remember_durable+ can be called.

A permit records the source event id, source, source class, trust level, optional actor, the deterministic gate decision, and the source event's own claim text (its payload `text`) — the binding a consumer needs to tell the event's verified claim from an unrelated sentence supplied beside the permit. The claim is retained content, not diagnostic metadata: the permit's debug representation reports only whether the event carried one and prints a redaction marker in place of the text, so ordinary debug/tracing output cannot disclose it. The permit remains non-serializable, and the stored entry converts the actor to the configured pseudonym before retention.

=== 3.1 Epistemic classes and crystallization

Every retained entry carries a versioned epistemic class (+MemoryEpistemicClass+, vocabulary +memory-epistemic-v1+) alongside its provenance/trust, in addition to the durable-write authority the gate already enforces:

* verified fact;
* viewer claim;
* performer experience;
* observation;
* persona opinion.

The class is derived **once at write time** from the source class and trust level the security runtime already assigned to the source event and from whether the retained claim *is that event's own claim text* (its payload `text`) — never from claim text alone, retrieval rank, model output, or link structure. It is stored on the entry and never recomputed, so retrieval, ranking, and temporal/graph linkage cannot change a claim's class. The vocabulary version (+memory-epistemic-v1+) is stored **on each entry**, not stamped from the current process constant, so an artifact written under an older vocabulary is identifiable instead of being presented as derived under the present one. The retrieval view serializes the class and reports the entry's own stored version. Those classes describe provenance/epistemic status; they are not authorization and never feed a gate.

The derivation fails closed and binds verification to the specific claim. +VerifiedFact+ is reachable from exactly one combination — a *trusted* system-plane source **whose event carried that claim**. A permit proves the event was authorized, not the content of a sentence supplied separately alongside it, so a trusted system permit writing an unrelated claim is an +Observation+, not a fact. The binding is judged on the **full** text of both sides, after the same normalization and *before* the storage byte truncation: a claim the event actually carried is not downgraded because normalization rewrote its case or whitespace, and content appended to the event's claim cannot inherit its provenance by matching a truncated prefix. A +VerifiedFact+ whose own claim exceeds the storage byte bound is **rejected** before storage rather than stored truncated, because dropping the negation or qualifier that bounded it would make the retained copy assert something the runtime never observed; weaker classes (+ViewerClaim+, +PerformerExperience+, +Observation+, +PersonaOpinion+) assert nothing and keep the truncation semantics. This is deliberately stricter than the write gate, which also admits semi-trusted system sources: a semi-trusted system write is admitted but classified as an observation, so the store can never mint facts the runtime did not verify. Public chat and donations are a +ViewerClaim+ at any nominal trust, trusted performer speech is +PerformerExperience+, authenticated operator content is a +PersonaOpinion+ (an asserted opinion, not an independently verified fact), and every other source is an unasserted +Observation+.

Public content MUST NOT self-promote from claim/observation to verified fact. Model repetition, summarization, retrieval rank, or temporal/graph linkage alone is insufficient verification; the class is a write-time fact about provenance and claim binding, so nothing downstream can raise it.

Likewise, short-lived conversation/thread context is not automatically durable memory. Any future "crystallization" from active context into a retained atomic memory still passes the existing non-serializable +MemoryWritePermit+ gate and retention policy.

Temporal links between retained memories follow the bounded model in section 10: node deletion/expiry deterministically removes every link that touched the node, and edge metadata never carries claim content.

== 4. Generated-asset promotion

Generated assets initially live in L0 after the complete LLM/TTS/compiler pipeline succeeds.

+AdaptationEngine+ records generated-asset usage and explicit positive/negative quality labels. +PromotionPolicy+ contains deterministic thresholds for:

* minimum uses;
* minimum quality labels;
* minimum positive quality ratio;
* negative-label invalidation threshold;
* recent-variant anti-repetition window.

The policy produces one of:

* +keep_hot+;
* +promote+;
* +invalidate+.

Promotion is never triggered by generated text itself. A production host must explicitly supply quality labels and call +ProductionApp::apply_generated_asset_adaptation+.

== 5. Persistence and rollback

+AssetStore::persist_generated_descriptor+ is intentionally a storage primitive, not a policy engine.

Before writing L1 it requires:

* a complete validated Performance Asset;
* +provenance.generated=true+;
* compatibility with the current compiler/voice/avatar/viseme/motion runtime.

The descriptor is written through a temporary file and renamed only after the bytes are flushed. Existing L1 ids are not overwritten.

+AssetStore::invalidate_generated_asset+ removes only assets whose persisted or hot provenance identifies them as generated. Static pack assets cannot use this invalidation path.

Promotion therefore preserves the original model/TTS/routing provenance and the compatibility identity already present on the generated asset.

== 6. Replay and audit metadata

Every adaptation policy evaluation yields an +AdaptationDecisionRecord+ containing:

* monotonically increasing decision sequence;
* asset id and stable asset identity;
* decision and deterministic reason;
* usage/quality feedback snapshot;
* policy version and the complete threshold snapshot;
* seed.

The record has a stable JSON serialization boundary. The same asset, seed, policy, and feedback produce byte-equivalent decision records.

Working-memory compaction also records the timestamp and counts of expired/capacity removals.

== 7. Anti-repetition and deterministic variation

+AdaptationEngine::select_variant+ excludes recent ids for the semantic group when alternatives exist, sorts candidates by stable asset id, and uses the recorded seed plus event sequence for deterministic selection.

Performance Asset variation itself remains bounded by the existing asset schema/validator. Adaptation does not widen those bounds.

== 8. Calibration

The hardening retention soak additionally carries the link store's current and
high-water edge counts in every state snapshot and growth finding, so a
long-running soak that lets links grow — or stops pruning them — fails the same
plateau check every other bounded subsystem is held to. Because every durable
slot also writes one working entry, the probe refuses as configuration any node
window that cannot hold the working entry, the supersession target, and the new
durable entry together (fewer than 3 slots): a run that could never retain a
link must not report zero links as a clean link-store probe. That rule belongs
to the *core* probe alone, so it lives in a separate
+SoakConfig::validate_link_probe+ — the scenario soak shares only the common
+SoakConfig::validate+ bounds and a one- or two-entry window stays a valid
scenario experiment. The same probe validation refuses runs too short to reach
the second durable write that mints the first supersession edge, and pins the
projected retained supersession chain against +memory_links_limit+; the durable
cadence (+SoakConfig::durable_every+) derives from the window *and* the link
budget, so the chain fits the store instead of exhausting it mid-run — an
accepted configuration always completes, and its link-growth checks always
describe links that were really minted (issue #105 review round 6). The same honesty
rule applies to workload shape: the scenario fault soak only records working
memory, so its workload can never mint a link and its reports omit the
`memory_links` growth findings entirely rather than pass a bound that reads zero
because the subsystem was never exercised — the raw counters stay in the state
snapshots as observations, and the scenario store is still constructed with the
configured `memory_links_limit` so the reported and enforced bounds cannot
diverge (issue #105 review round 4).

== 10. Bounded episodic links (issue #105)

+WorkingMemory+ retains a small versioned link vocabulary, +memory-link-v2+, between retained entries. Three kinds exist today:

* +temporal_before+ — derived deterministically at write time: the new entry links to the newest retained same-topic durable entry *in logical record order* (+created_at_ms+), walking older ones within the per-write budget. Insertion order is never the basis — a backfilled write can carry an earlier record time than one already stored — and an entry recorded *after* this write is not its predecessor at all, so a temporal edge can never contradict the record times retrieval ranks by. The spine is therefore *predecessor-only*: under out-of-order writes it may be disconnected (a backfill inserted between two records links back to older records but is not added as the successor of the newer one), while every edge it does emit stays directionally valid. No model output is involved.
* +supersedes+ — declared by the caller through +remember_durable_superseding+, the permit-gated durable path, reachable from the composition root as +ProductionApp::remember_durable_memory_superseding+. Every declared target is resolved *before* anything is stored to exactly one still-live retained durable node; a target that is absent, unknown, working-only, expired at the write timestamp, ambiguous (one source event id retained more than once), or recorded *after* the superseding write refuses the whole write, so nothing is stored and no link is minted — a claim may not replace evidence from its own future, or a backfill would mark a logically later claim stale. Declaring one target twice declares it once: the per-write budget counts the edges a write creates, not the strings it was handed.

* +caused_by+ — also declared by the caller, through the same permit-gated durable path (+remember_durable_with_evidence+, reachable from the composition root as +ProductionApp::remember_durable_memory_with_evidence+). The claim being written is the effect; each declared target is a retained claim that brought it about, and it resolves under exactly the same rules as a supersession target: absent, unknown, working-only, expired at the write timestamp, ambiguous, or recorded after the write refuses the whole write, so nothing is stored and no edge is minted. Only one direction is stored — the other reading of the same evidence, "the target resulted in this claim", is the same edge seen from its other endpoint — because a second kind would spend two units of the per-write budget on one fact and could disagree with the first after partial eviction.

The vocabulary is versioned (+memory-link-v2+) rather than extended in place: v2 adds the causal kind, so the change is replay-visible and an artifact written under v1 simply carries no causal edges, rather than being reinterpreted by a reader that infers the vocabulary from which kinds appear.

A link carries only its endpoint node ids, kind, and creation timestamp. The endpoint is +MemoryEntry::memory_id+, a monotonic per-insertion identity: a source event id is neither unique among retained entries nor durable identity (the scheduler may legitimately replay one), so it is never a link endpoint and deletion prunes by node identity — removing one of two copies that share an event id cannot keep the other copy's edges alive or inherit its staleness. The link never carries claim, topic, or actor content, so edge metadata cannot become a covert archive of deleted (or live) content (see docs/security-threat-model.adoc section 8). Serialized link artifacts — the store snapshot and each retrieval view — carry +vocab_version+, the vocabulary they were produced under, so a replay identifies which vocabulary shaped a record instead of inferring it from field presence. The store snapshot is filtered to the edges visible at its read timestamp (both endpoints retained and alive there), so persisting or replaying it can never keep relation metadata for content retention already removed (issue #105 review round 11).

Bounds, both validated positive and owned by the #51 unified retention policy:

* +max_links+ (default 2,048; +AIVTUBER_MEMORY_MAX_LINKS+) caps the store-wide edge count. Insert-compact evicts entries first, then the edge cap is enforced deterministically, oldest edge first.
* +max_links_per_memory+ (default 8; +AIVTUBER_MEMORY_MAX_LINKS_PER_WRITE+) is the per-write creation budget and the per-entry retrieval cap, so a single entry's neighborhood can never fan out.

Both must hold +max_links >= max_links_per_memory+: the store has to be able to hold one maximum-size write, otherwise the store bound would drop an explicit supersession that the very same write just had accepted — which is not historical edge eviction but a lost caller-owned fact. The configuration is refused at startup instead, and the core hardening link probe refuses a soak link limit below the same per-write budget as configuration rather than failing at construction; a linkless scenario experiment is exempt from that minimum — its store aligns the per-write budget down to its smaller reported link bound, so tiny positive link bounds stay valid for runs that never mint a link (issue #105 review round 9). The same budget also bounds the write's *input*: one call's raw relation declaration list (supersession and causal together) may restate targets only up to a fixed multiple of +max_links_per_memory+, and the deduplication buffer never grows past the budget itself, so duplicates keep counting once without an unbounded scan or allocation before the cap is applied (issue #105 review round 6). When the store is over its bound, only derived temporal edges are shed (oldest first) — a temporal edge is re-derived from record time on the next write in that topic, an explicit supersession or causal edge is not. Explicit evidence is never dropped: a write whose supersession edges would not fit alongside the ones already retained is refused *before* anything is stored ("stores nothing, mints nothing"), so an accepted configuration can no longer discard the last evidence for a still-retained stale claim and hand it back as current, nor lose the caller's account of why a claim exists. The fit is judged over the edges this write would *leave retained*, not the raw store: an edge whose endpoint is already expired at the write timestamp — or is the node this insertion itself capacity-evicts — is dead evidence the write's own compaction removes anyway, so it never blocks a supersession that fits once that compaction has run (a valid update must not wait for an unrelated write to free logically dead capacity). The same projection governs the edges this write *adds*: a new supersession edge counts against the store only when its target survives that compaction, because the insertion's own front-pop can evict the oldest node — even one just named as a target — and the fresh edge is pruned with it in the same write, so an evicted target consumes no capacity the store will never spend. Only a write whose supersession edges would displace evidence that stays retained is refused; its remedy is a larger +max_links+ or letting retention expire the earlier endpoints first.

Only permit-gated memory enters the graph: links are created exclusively inside the +MemoryWritePermit+ durable path, so public chat and generated/model output cannot mint links or authority.

Compaction and deletion prune links by node identity: an edge survives only while both endpoint nodes are retained. Staleness is decided over the **full** retained edge set recorded at or before the read timestamp, never over the capped presentation view — a supersession that fell past the per-entry cap still marks its target stale — and the superseding node must itself already be recorded and live at the read timestamp, so an expired-but-not-yet-compacted memory can neither authorize an update relation nor keep a claim marked. Retrieval is time-indexed throughout: a node or edge recorded *after* the read timestamp does not exist for the query, so direct matches, the staleness verdict, the bounded view, and the one-hop expansion all stay inside the read timestamp and a replay-time query can never act on evidence from its own future (issue #105 review round 10). The same liveness rule applies to the view itself: a link is shown only while **both** endpoints are live, so an expired node leaves no dangling relation behind (physical removal remains compaction's job). The bounded view is deterministic and leads with the caller-owned evidence — supersessions newest-first by record time (the higher node id — the later insertion — breaking ties, so the per-entry cap can never truncate the latest correction behind an older one, even when two corrections share a record time; issue #105 review round 12), then causal edges newest-first by the same ordering rule, then temporal spine edges in creation order — before the cap cuts it. Supersession leads causation because staleness is decided from it; the derived spine trails because it is the only kind the next write in the topic can rebuild. Retrieval via +relevant_linked+ joins that view with the ranked matches and then resolves the live nodes one link away from them — a supersession that changed topic brings the claim it replaces back into the result — with expansion filling only the space the query limit still leaves, never displacing a direct match, so the caller's limit stays the bound. Direct matches and the hop both keep the query's actor scope: with an actor and a topic supplied, a ranked match can arrive through the topic alone, so another viewer's same-topic claim is refused at every step; the derived temporal spine connects every durable entry sharing a topic, so an actor-scoped query would otherwise receive another viewer's claim as context; topic is deliberately not required, because following a claim to what replaced it is the point of the hop, and neither verdicts nor edge metadata (node ids only) are narrowed by scope. Short-lived thread context (#80) is never persisted as links.

== 11. Retained memory in the thinking request (issue #105)

A generated reply is enriched at the composition root with bounded retained memory, so a claim the runtime already admitted can shape phrasing without a raw transcript ever crossing the thinking boundary.

* *Scope* — `WorkingMemory::context_for` returns the current actor's own retained claims plus the *shared* ones. Sharing is decided per source class, never by "has no actor": a `chat.message` and an `operator.command` are both valid envelopes without an `actor_id`, so an unattributable public claim and an operator's private record would otherwise look identical to shared knowledge. `System`, `Game`, `Stream`, and `Timer` observations and the performer's own `Speech` are shared (attributable to the runtime rather than to a person); `PublicChat`/`Donation` are somebody's words and are in scope only for that same actor; `Operator` is private and stays out of generation entirely, because a privacy *label* is not an egress authorization. A shared claim attributed to another actor is refused too. An event that carries no actor gets the shared set only.
* *Supersession* — a claim an explicit supersession replaced is not evidence of the present: it is dropped from the context and its live correction is promoted into the same rank bucket, so a correction that moved to another topic cannot be cut behind the claim it replaced. Only a supersession whose replacement is itself alive at the read timestamp counts — an expired correction cannot keep the old claim current either.
* *No new authority* — retrieval only reads the store. Nothing on this path mints a claim, promotes a class, creates a link, or buys a durable write; a recall path that could do any of those would be a second write gate.
* *Provenance* — each item is a `ThinkingContent` with `source: memory`, the retained claim's source class, trust level, and privacy class, the source event id, and `epistemic_class` set to the class the entry was classified under. A `memory` item without a class is refused at the domain boundary and a non-memory item cannot carry one, so generation always knows whether it was handed a verified fact or a viewer claim.
* *Budget* — the current event's own text is charged first, then claims in rank order until `MAX_THINKING_CONTEXT_BYTES`; `MAX_THINKING_CONTEXT_ITEMS` and `MAX_THINKING_TEXT_BYTES` bound the list and each item. A claim that does not fit is dropped whole: shortening it would present a claim the runtime never admitted as if it had — the defect #231 fixed for the store, one layer up.
* *Determinism and failure* — ranking is topic match first, then logical record time, with node id breaking ties, so an unchanged retained state yields an identical request context. If an enriched request still fails validation the context is cleared and the reply proceeds; retrieval enriches a reply and is never a precondition for one.
* *Curated slot* — a caller-supplied curated context (operator curation) is not displaced by retrieval.
* *One rule, two callers* — the scope/supersession/rank half lives in `WorkingMemory::context_for`, the byte/item half in `aivtuber_app::retained_memory_context`, and nothing else assembles memory content for a request. The composition root calls it per generated reply and the evaluation in section 12 calls the same function, so a measured result cannot come from a parallel implementation.

== 12. Measured long-range evaluation (issue #105)

Section 11 is a contract; this section is its measurement. The cases are data (`examples/memory-long-range/cases.json`, fixture schema `memory-eval-v1`), not Rust code, so the identical inputs can be handed to an external memory sidecar and both sides can emit the same report shape. They are synthetic, privacy-safe versions of the issue's scenario classes: preference change, a correction that moved topic (with and without the item bound in play), goal -> attempt -> result, a contradiction that is not an update, record time inverting event time, expiry keeping the newer linked claim, another viewer's same-topic claim, budget pressure, an oversized claim, retention plateau, an empty actor scope, and a cause/effect pair that must arrive together.

A fixture case declares its claims, their explicit update and causal evidence, the query, and what it expects: `must_deliver`, `must_not_deliver`, `stale` (a subset of the refused claims), `expected_temporal_errors`, optionally the exact `expected_delivery_order`, and optionally `expected_retained_causal_spans`. A claim declares `caused_by` (section 10) the same way it declares `supersedes`, and the runner writes it through `remember_durable_with_evidence` — the identical permit-gated path the runtime uses — so a fixture cannot store evidence the gate would have refused. `text_bytes` tiles a short ASCII seed to a known byte length, so a byte-budget case stays readable instead of carrying a multi-kilobyte literal. A fixture that could not be compared — unknown schema version, repeated claim id, an expectation naming a claim that does not exist, a claim both required and refused — is refused with its case named, never measured ambiguously.

The runner calls `retained_memory_context`, the same function the composition root calls for every generated reply, so a number cannot describe a re-implementation. Every claim enters through the real `authorize_memory_write` gate first.

The report is versioned `memory-long-range-eval/v1`, names the fixture version it measured, and is byte-identical across runs, so two revisions — or a sidecar adapter that emits this shape — can be compared rather than described. A violation is reported with its evidence and makes the CLI exit non-zero; it never stops the remaining cases, so one breach does not hide the rest.

Measured against `main` at `f1796da4` (the #253 merge), 14 cases:

* current-fact correctness 1.0, stale-memory use 0, absent violations 0, truncated claims 0;
* temporal-order errors 2. The store keeps *record* time, so a claim recalled out of event order can still be delivered ahead of a later event. This is the class a timeline-aware sidecar would have to fix: retrieval alone cannot, because the event timestamp is not retained;
* the request bounds hold where they bind: 12 of 12 items in the limit case, 7,038 of 8,192 bytes in the budget case, and the largest retained state in the suite is 14 entries / 69 links, inside the configured bounds. The plateau case stops growing at its own 4 entries / 6 links;
* one rule is measured instead of left implicit: topic is a *rank*, not a filter. An in-scope claim on another topic is still delivered behind the topic match, so the precision cost of the current rule is visible in the `topic_mismatch_ranks_lower` case rather than inferred;
* causal edges (`caused_by`, section 10) are now measured instead of described: `causal_reason_travels_with_its_effect` declares one, and `retained_causal_spans` is 1 — the effect and the cause both reach generation, and the edge that says so is read back from the store's own link view instead of from the fixture's declaration, so the count falls to 0 when the edge was never retained, the cause was evicted, or the budget cut one of the pair. An earlier revision of this section measured the declaration plus the delivered set, which could only report the fixture's intent back and would have stayed 1 with the link gone (issue #105 review round 13); the store half is now pinned by regression tests that read the retained link's endpoints back and require the lost-edge case to fail its pin rather than merely report a smaller number. A causal edge still never changes which claim is current, so it cannot show up in staleness or correctness; what the metric can show is that the relation survives retrieval. The revisit condition the earlier revision named is therefore discharged for delivery; whether a causal edge should also *rank* a claim higher remains unmeasured, because nothing in the current ranking reads links.

=== 12.1 Measuring an external memory service

The same fixture is handed to a memory service through the provider-neutral port in `aivtuber-domain` (`MemorySidecar`: open a scope, retain a claim, recall within a scope, retire a claim, close the scope). `aivtuber-adapters` implements that port for Hindsight; `memory-sidecar-eval` drives it. The boundary is split so a number can only describe the service's retrieval:

* *Admission stays the project's* — every claim enters through the real `authorize_memory_write` gate before the service is told about it. A service cannot buy an admission the project would not grant.
* *Retention policy stays the project's* — the project's entry bound, its durable TTL, and its explicit supersession evidence decide what the service may keep: the runner retires claims the store would have evicted, expired, or replaced, so the candidate is measured holding the memory the project would have kept rather than everything it was ever told. Retirement is not deletion; it is the instruction that the claim must stop being recalled, which is exactly what the runtime needs.
* *Retrieval is the service's* — ranking, matching, and order are the thing under test, and the runner does not re-rank what the service answered.
* *Acceptance stays the project's* — scope, liveness, and identity are re-checked against the project's own records, and the request budget is applied by `aivtuber_app::bounded_prefix`, the same rule the runtime's own context path applies. An item the project refuses never reaches generation; it is recorded in `refused_items` with the reason (`out_of_scope`, `removed`, `unknown`) as evidence of what the service widened or kept.
* *Relations stay the project's too* — the port hands a service claims, not the `caused_by` relations between them, so a service keeps no project edge and its own `retained_causal_spans` reads 0 by construction. What the comparison asks of a service instead is `causal_pairs_delivered`: whether the answer carried the reason back together with the event it explains.

=== 12.2 Boundary corrections found by reviewing the first sidecar run

The review of the run that first used this boundary found six places where 12.1's rules were stated but not enforced. Each is a case where a service could have widened what the project owns, or where a measurement could have been contaminated by the run before it:

[cols="1,3"]
|===
|Weakness |What the code does now

|A failing case left its scope open
|`run_sidecar_case` closes the scope on the failure path as well as the success path. When the close is the second failure, both survive in `MemoryEvalError::SidecarCleanup`: the measurement failure says why the run stopped, the cleanup failure says what it may have left behind. A scope left open keeps the project's claims in the service, and the next run would measure them as its own answer.

|Opening a scope ignored a failed clear
|Only `404` — the scope that does not exist yet — is tolerated. A `403`, a `500`, or a timeout stops the open before the scope is created, because a scope that could not be cleared may still hold an earlier run's claims.

|Two case ids could name one scope
|The case id is hex-encoded instead of sanitised, so `case_a`, `case-a`, and `Case_a` no longer collapse into one scope whose open would clear another case's claims. The CLI also namespaces each run by process id and start time, so two runs against one deployment do not clear each other's scopes.

|`limit` was validated but not applied
|The adapter truncates the service's answer to `query.limit`; the bound is the caller's, and a service that ignores it cannot spend more of the request budget than the caller allowed.

|A recall with no actor answered other actors' claims
|The adapter drops what the query did not ask for: `actor: None` keeps only unscoped claims, `actor: Some(k)` keeps `k`'s claims and the unscoped ones that are shared with every viewer. The service's tag filter is a hint; the adapter is where the port's scope rule is enforced.

|A claim recorded after the read stayed recallable
|The runner retires it on the service before the recall rather than only dropping its local handle: memory the project would never show must not consume the service's ranking or answer budget ahead of a claim that is live.
|===

The verdict is `rejected`, and the reasons are the cases:

* `topic_shifted_correction_under_limit` — the service returned a competing claim the case refuses (`evt-c1`) and dropped `evt-enjoy`, the claim the supersession promoted. The case requires 12 claims and the item bound is 12, so which claims a ranking returns decides membership, and semantic similarity to the request's topic ranks the correction — filed under a new topic — last.
* `budget_pressure_drops_whole` — the service answered `evt-o3` ahead of `evt-o1`. Both are 3,000 bytes, so the same 7,038-of-8,192-byte budget admits the claim the case refuses and refuses the one it requires.
* `oversized_claim_skipped_whole` — the service returned the 4,224-byte claim the runtime drops whole (over `MAX_THINKING_TEXT_BYTES`), and answered with a shortened rendering of the text it had stored. That is the shortened-claim class: the project would present text it never admitted, so the metric is what stops the service's prose from becoming the project's record.

The service got the authority boundary right: no out-of-scope claim was returned and no retired claim came back, so `refused_items` is empty and every zero-tolerance scope and removal check passed. What it fails is retrieval quality and text fidelity, which is the comparison's actual question; keeping the runtime's own store is the supported verdict, not a formality.

This closes the Hindsight half of the issue's comparison. Graphiti is still unmeasured: it needs its own adapter over the same port plus a running deployment, and the rule that will judge it is already executable.

Run it four ways:

* `cargo test -p aivtuber-app --test memory_long_range_eval -- --nocapture` prints the report and asserts every case measures cleanly;
* `cargo run -p aivtuber-app --bin memory-long-range-eval -- examples/memory-long-range/cases.json target/memory-runtime.json` writes the report artifact and exits non-zero on any violation, which is what a comparison run should consume;
* `cargo run -p aivtuber-app --bin memory-sidecar-eval -- examples/memory-long-range/cases.json http://localhost:8888 target/memory-sidecar.json` measures a service (bearer token from `AIVTUBER_MEMORY_SIDECAR_TOKEN`, never from the command line) and emits the same schema;
* `cargo run -p aivtuber-app --bin memory-eval-compare -- examples/memory-long-range/cases.json target/memory-runtime.json target/memory-sidecar.json --out target/memory-verdict.json` judges a candidate report against the runtime's (`memory-eval-compare/v1`) under the case document both measured, and exits non-zero for a rejected candidate or an incomparable pair. The fixture is an input rather than a version string because the causal declarations live there and nowhere in a report.

The verdict rule is exactly the sentence this section states: `Improvement` when the candidate beats `temporal_order_errors` or `current_fact_correctness` and regresses nothing, `Rejected` when it leaks a superseded, refused, or shortened claim, answers with an item the project has to refuse, or breaks a request bound, `NoImprovement` otherwise — and a win never rescues a leak, because the zero-tolerance checks are decided per case, not on the average. A refusal is not a delivered-memory leak (the item never reached generation), but it still rejects the candidate: a project that has to filter its memory service's answers forever is not better off for adopting it. `causal_pairs_delivered` — the fixture's declared cause/effect pairs whose two members both came back — is reported per case and in the totals for both sides. It is re-derived by the comparison from the case document and each side's delivered set, never read from a report's own causal count, because a sidecar keeps no project edge and such a number would describe a store the comparison was not handed. It is a metric the comparison shows rather than one it scores: a candidate cannot be adopted on causal coverage alone, because the rule that decides adoption is unchanged.

A candidate report is never trusted on its declared totals. Each case row carries the claims it required (`must_deliver`) and the claims it refused (`refused_claims`), so correctness, `stale_memory_use`, and `absent_violations` are re-derived from the delivered list and the aggregates are re-derived from the case rows. `retained_causal_spans` is summed the same way, and each case row is bounded by the fixture: a count above the declared pairs that case's delivered set supports is refused, because an answer can return both members of at most the pairs the case declares and a store can retain at most the pairs its claims declared — an invented count beside a delivery that supports none is refused rather than shown. A report whose numbers disagree with its own records — or which covers a different set of cases, is not about the fixture's cases in the fixture's order, names another fixture document, or carries another schema — is refused as *incomparable*: "not verifiable" must not be reported as a measurement.
