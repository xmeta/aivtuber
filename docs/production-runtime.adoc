= Production Rust composition runtime

Issue #34 adds the first executable Rust composition root under +crates/app+.

The production path composes existing subsystems instead of duplicating them:

[source,text]
----
serialized EventEnvelope
        |
        v
SecurityRuntime content ingress
        |
        v
RoutePlanner
   | deterministic intent / cached asset
   | or ReflexPipeline -> explicit LLM route
        |                         |
        |                         v
        |                  GenerativePipeline
        |                  ThinkingEngine
        |                         |
        |                  SecurityRuntime::publish_text
        |                         |
        |                  TtsEngine -> complete PerformanceAsset
        |                         |
        |                  AssetStore::insert_hot
        |_________________________|
                  |
                  v
CachedPerformer
        |
        +--> compatibility-checked AssetStore
        +--> deterministic Scheduler
        |
        v
scheduled audio/avatar commands
        |
        +--> ProcessAudioPlayer
        +--> VtsAvatarOutput
----

OBS remains an independent control adapter. Its availability never owns scheduler state.

== Runtime invariants

* Raw stdin is byte-bounded and queue-bounded before +SecurityRuntime+; hostile line size or producer rate cannot create an unbounded pre-runtime buffer.
* Content bytes always pass through +SecurityRuntime::admit_content_bytes+.
* Operator/control events cannot enter the content ingress path.
* Cached playback uses the existing +CachedPerformer+ scheduler, not a second application scheduler.
* A production semantic index is built from the compatibility-checked `AssetStore` snapshot and precomputed versioned embeddings; index build/rebuild performs no scheduler/frame-path network I/O.
* A reflex-selected asset id is resolved by +AssetStore::resolve+ before playback. When retrieval supplied an asset identity, the current `AssetIdentity::stable_key()` must still match or playback is rejected as stale.
* Adapter commands are dispatched only while their scheduler generation is still live.
* Commands older than +AIVTUBER_MAX_DISPATCH_LATENESS_MS+ are dropped.
* Failed audio/avatar commands are not requeued. Reconnecting an adapter therefore cannot replay an already-due stale command.
* Authenticated emergency stop operates on the same scheduler used by cached/generated playback, purges pending commands, and cancels active generation independently of model/network availability.
* Generated public text always passes through +SecurityRuntime::publish_text+ before TTS. The current policy contains known control-plane command text and redacts configured secrets; it is not a general content-moderation classifier. Suppressed output never reaches TTS, and typed capability enforcement remains independent of text filtering.
* Every attempted LLM call is retained in the production audit with source event id, deterministic routing reason, and provider/model identity; prompt and generated reply text are excluded.
* Only complete, validated, runtime-compatible generated assets enter +AssetStore::insert_hot+; partial text/audio never reaches reusable asset or scheduler state.
* Generated assets are scheduled by the same +CachedPerformer+ / +Scheduler+ instance as cached assets, preserving one monotonic timeline for audio/visemes/avatar commands.
* Working memory is explicitly bounded by entry count, TTL, claim bytes, and topic bytes; raw viewer actor ids are replaced before storage with source-namespaced HMAC-SHA-256 pseudonyms under a deployment-only key.
* Durable memory writes require a non-serializable +MemoryWritePermit+ from +SecurityRuntime::authorize_memory_write+; public chat without that gate cannot become durable memory.
* Generated-asset promotion is explicit and deterministic: production records generated use, accepts quality labels separately, and only +apply_generated_asset_adaptation+ can promote or invalidate through the validated AssetStore path.
* Higher-priority generation cancellation uses the scheduler's shared +priority_for_event+ mapping.
* Serialized control events remain data only: content ingress rejects them and cannot use them to cancel/stop privileged runtime work.
* Operator control (issue #56) terminates in +LocalControlIngress+ on its own local-socket transport; the presented secret is verified in constant time before any +AuthenticatedControl+ is minted, every privileged action is capability-checked, and accepted/rejected actions are audited. The control endpoint never shares the untrusted content queue.
* VTube Studio and OBS connection failure is degraded state, not scheduler failure.

== Burst selection and deferred replies (issues #78, #75)

+aivtuber_reflex::BurstEngine+ is the deterministic micro-batcher for normal-priority admitted chat. It is a pure, caller-clocked library: quiet chat is never delayed, control/system-plane events bypass it, bursts are batched under hard count/byte/window/queue bounds, and every admitted comment gets one terminal outcome. With +AIVTUBER_CHAT_BURST_MODE=true+ (default off) the app composes it into +process_content_bytes+ together with a bounded deferred-reply inbox: a selected reply waits while the performer is busy (busy state comes only from the scheduler/speech lifecycle, the generation runtime and the operator mute flag, never from chat) and is revalidated, or expired, before it dispatches. Operator stop cancels everything held. Contract, configuration and metrics: +docs/jev-routing.adoc+ section 12.

== Runtime retention

Long-running production state is governed by the shared +RuntimeRetentionPolicy+. Safe defaults, subsystem classification, logical-time eviction rules, observability, and the high-volume plateau verification are documented in +docs/runtime-retention.adoc+.

== Executable

Run the daemon from the repository root:

[source,shell]
----
export AIVTUBER_MEMORY_PSEUDONYM_KEY_HEX='<64 hex characters / 32 random bytes>'
# Optional non-secret rotation label; default is v1.
export AIVTUBER_MEMORY_PSEUDONYM_KEY_VERSION='v1'
cargo run -p aivtuber-app
----

Optional performer memory writer (#306, ADR-0008 Q1): +AIVTUBER_MEMORY_WRITER+ (default off) enables the permit-gated post-turn writer that retains stream-level performer facts (commitments, running jokes, segment recaps) from committed public output only, never viewer-attributed content. +AIVTUBER_MEMORY_WRITER_MAX_LIVE_ENTRIES+ (default 32, 1 to 128) bounds the live entries. Counters are logged as +memory_writer_metrics+. See +docs/memory-adaptation.adoc+ section 13.0.

The actor pseudonymization key is mandatory for the production composition root and is independent of the operator-control secret. Generate and store it as deployment secret material; do not place it in fixtures, replay metadata, logs, or model context. Rotating key/version intentionally breaks historical actor correlation unless records are explicitly migrated.

The process reads one Event Envelope JSON document per stdin line. Raw stdin is bounded before `SecurityRuntime`: the pre-runtime channel uses `sync_channel` with capacity equal to `SecurityRuntimeConfig::content_queue_limit`, and the line reader retains at most `max_envelope_bytes + 1` bytes while determining whether a record is oversized. An oversized record is drained through its newline and dropped; a record arriving while the raw queue is full is also dropped rather than blocking the reader. Both outcomes are exposed through `RawIngressMetricsSnapshot` and reported by the executable. Valid records retain input order.

Because the producer uses non-blocking `try_send`, a saturated raw queue cannot leave the stdin producer blocked on the application consumer during shutdown. The raw record-size limit is derived directly from `SecurityRuntimeConfig::max_envelope_bytes`, so the pre-runtime and runtime envelope limits cannot silently diverge. With the current default `SecurityRuntimeConfig`, this means a 64 KiB raw-record limit and a 1024-record pre-runtime queue.

The process advances the scheduler from a monotonic process clock and services due output commands on a short polling interval.

The starter pack contains descriptors and viseme metadata only. Audio binaries remain external to Git. Materialize the referenced files below the configured audio root before testing real playback.

== Ingress ceiling and Twitch chat (issue #257)

The stdin content ingress accepts what envelope validation accepts. A record declares its own `source_class`, `plane` and `trust_level`, and the runtime only checks that the declaration is self-consistent. `source` is chosen by the producer and is never evidence of where a record came from, so the operator, not the record, sets a ceiling on the ingress channel:

[cols="1,2,1"]
|===
|Variable |Meaning |Default

|`AIVTUBER_INGRESS_MAX_TRUST`
|Highest `trust_level` the pipe may declare: `untrusted`, `semi_trusted` or `trusted`.
|`trusted` (no change)

|`AIVTUBER_INGRESS_SOURCE_CLASSES`
|Comma-separated allow-set of `source_class` values, for example `public_chat`.
|all (no change)
|===

A record above the ceiling is rejected whole, audited as `rejected_ingress_policy`, and counted (`ContentAdmitDecision::RejectedIngressPolicy`; the total is printed when stdin closes). It is never rewritten or clamped, so a mislabelled producer is visible. An unrecognised value fails startup instead of silently widening the ceiling.

=== Twitch chat sidecar

`twitch-chat-ingress` (`crates/adapters`) is a separate read-only process. It uses the `twitch-irc` crate with the anonymous `justinfan` login: no OAuth, no credentials, and no send call exists in the binary. Provider types stay in `crates/adapters/src/twitch_chat.rs`; the output is the existing Event Envelope, one JSON line per chat message, so no wire contract is added.

[source,sh]
----
export AIVTUBER_INGRESS_MAX_TRUST=untrusted
export AIVTUBER_INGRESS_SOURCE_CLASSES=public_chat
cargo run --locked -p aivtuber-adapters --bin twitch-chat-ingress -- --channel somechannel \
  | cargo run --locked -p aivtuber-app
----

Options: `--channel` (repeatable, at most 8), `--queue N` (writer queue, default 256), `--stall-secs N` (rebuild the connection after this much silence, default 600), `--stats-secs N`, `--duration-secs N` (exit after N seconds). Diagnostics and counters go to stderr; stdout carries records only.

* *Trust.* Every record is `chat.message` / `public_chat` / `content` / `untrusted` with no `authorization`, whatever the message says. The ceiling above is what makes the app enforce that. Badges, emotes, channel and message id are carried in `payload` as audit data only; nothing reads a badge to decide anything, so a viewer claiming to be a moderator or broadcaster gains no capability and still cannot write memory.
* *Viewer identity.* `actor_id` is the numeric Twitch user id. Login and display name are not emitted. Pseudonymization happens in the app (`ActorPseudonymizer`, deployment key, applied when working memory is written); the sidecar never holds that key. Do not `tee` the pipe to a file you intend to keep: the raw numeric id is on the pipe.
* *Bounds.* Network messages go through a bounded writer queue; when it is full the newest record is dropped and counted (`dropped_queue_full`). Records or payloads over 64 KiB / 16 KiB are dropped and counted (`dropped_oversize`); the limits match `SecurityRuntimeConfig` defaults and a test pins them together. Reconnect uses capped exponential backoff, 1 s doubling to 60 s (`SIDECAR_RECONNECT`); `twitch-irc` also rate-limits new connections itself.
* *Deleted and cleared messages.* `CLEARMSG` and `CLEARCHAT` are counted (`messages_deleted`, `chats_cleared`) and not forwarded: the wire format has no retraction event, and a record already piped cannot be recalled.
* *TLS.* Connections use the platform TLS stack (`native-tls`: Schannel on Windows, OpenSSL on Linux).

Tests: `cargo test --locked -p aivtuber-adapters --lib twitch` (mapping fixtures, bursts, backoff) and `cargo test --locked -p aivtuber-app --test twitch_ingress_e2e` (stdin path, ceiling, forged message). A live run needs network access and is manual: `--duration-secs 120` against a busy public channel, piped into the app with the ceiling set.

=== YouTube Live chat sidecar (issue #293)

`youtube-chat-ingress` (`crates/adapters`) is a second read-only ingress with the same shape as the Twitch one: a separate process, the existing Event Envelope on stdout, one JSON line per record, no new wire contract. Provider types stay in `crates/adapters/src/youtube_chat.rs`. It uses the official YouTube Data API v3 only; there is no innertube or other unofficial path.

[source,sh]
----
export YOUTUBE_API_KEY=...            # never a command-line argument
export AIVTUBER_INGRESS_MAX_TRUST=untrusted
export AIVTUBER_INGRESS_SOURCE_CLASSES=public_chat,donation
cargo run --locked -p aivtuber-adapters --bin youtube-chat-ingress -- --video-id <11-char id> \
  | cargo run --locked -p aivtuber-app
----

Pass exactly one of `--video-id` (resolved once through `videos.list?part=liveStreamingDetails`, field `activeLiveChatId`, 1 quota unit) or `--live-chat-id`. Other options: `--min-poll-ms N` (operator floor, default 5000), `--queue N`, `--stats-secs N`, `--duration-secs N`, `--include-backlog` (see below), `--api-base URL` (tests only; HTTPS or loopback HTTP). Diagnostics and counters go to stderr; stdout carries records only. Exit code 2 means misconfiguration (missing or invalid key, unknown chat, other non-retryable 4xx); 0 means the run deadline passed, stdout closed, or the chat ended.

==== Setup: API key

. In the Google Cloud console create or choose a project and enable *YouTube Data API v3* (APIs and Services, Library).
. Create an *API key* (APIs and Services, Credentials). Restrict it to the YouTube Data API v3. If the sidecar runs from a fixed address, add an IP restriction.
. Put it in the `YOUTUBE_API_KEY` environment variable of the sidecar process only. The key is public-data read access; it cannot post, moderate or read private data. No OAuth is used.

The key is sent in the `x-goog-api-key` request header, so it is never part of a URL; it is wrapped in a type with redacted `Debug` and has no `Display`; and it is scrubbed from transport error text. The sidecar never prints it or any response body, only the HTTP status and a short `error.errors[].reason`.

==== API facts the design rests on

Checked against the Google documentation on 2026-11-10:

* `liveChatMessages.list` (https://developers.google.com/youtube/v3/live/docs/liveChatMessages/list): 5 quota units per call; `part=snippet,authorDetails`; `maxResults` 200 to 2000 (the sidecar asks for the minimum, 200); the response carries `nextPageToken`, `pollingIntervalMillis` (how long to wait before the next call) and, only when the stream is offline, `offlineAt`. Errors used: `liveChatEnded` (403), `liveChatNotFound` (404), `rateLimitExceeded` (403).
* Message resource and `snippet.type` values (https://developers.google.com/youtube/v3/live/docs/liveChatMessages): `textMessageEvent`, `superChatEvent`, `superStickerEvent`, `newSponsorEvent`, `memberMilestoneChatEvent`, `membershipGiftingEvent`, `giftMembershipReceivedEvent`, `chatEndedEvent`, `tombstone`, `userBannedEvent`, `sponsorOnlyModeStartedEvent`, `sponsorOnlyModeEndedEvent`, `pollDetails`, `giftEvent`.
* `liveChatMessages.streamList` (https://developers.google.com/youtube/v3/live/streaming-live-chat) exists and accepts an API key, but it is a *gRPC* server-streaming RPC to `youtube.googleapis.com:443` (proto `StreamList`), with no REST streaming form. It costs 5 units per call like `list`. It is not used: it would add a gRPC/protobuf stack (tonic, prost, generated protos) and its supply-chain surface for a latency gain of a few seconds that chat reactions do not need. Revisit if chat latency becomes a measured problem; the poller is behind a small `YoutubeHttp` trait and the mapper is independent of the transport.
* Quota (https://developers.google.com/youtube/v3/determine_quota_cost): the default allocation is 10,000 units per day per Cloud project; `liveChatMessages.list` costs 5 and `videos.list` costs 1. The daily quota resets at midnight Pacific Time.

==== Quota math

Each poll costs 5 units, so a stream consumes `5 * duration / interval`. The sidecar waits `max(pollingIntervalMillis, --min-poll-ms)` between calls, never less than the interval the API returns:

[cols="1,1,1,1"]
|===
|Effective interval |Calls in 2 h |Units (2 h) |Share of 10,000/day

|5 s (default floor)
|1,440
|7,200 (+1 for `videos.list`)
|72 %

|6 s
|1,200
|6,000
|60 %

|10 s
|720
|3,600
|36 %
|===

One 2-hour stream at the default floor fits the default daily quota; a second stream the same day, or a shorter interval, does not. If `pollingIntervalMillis` is larger than the floor (the API's value wins) the cost is lower. To run longer or more than once per day, raise `--min-poll-ms` or request a quota extension from Google. These numbers are arithmetic from the documented costs, not a measurement; no live stream has been run.

==== Behaviour and bounds

* *Trust.* Every text message is `chat.message` / `public_chat` / `content` / `untrusted` with no `authorization`, exactly as for Twitch. `isChatOwner`, `isChatModerator`, `isChatSponsor` and `isVerified` are carried as `payload.author_flags` for audit only; nothing reads them, so a viewer who is the channel owner or a moderator gains no capability, and still cannot write memory. The `AIVTUBER_INGRESS_*` ceiling is what makes the app enforce this.
* *Viewer identity.* `actor_id` is the author's channel id. Display name and avatar URL are not emitted. Pseudonymization happens in the app (`ActorPseudonymizer`, namespaced by `source`, which is the constant `youtube:live-chat`) when working memory is written; the sidecar never holds that key. Do not `tee` the pipe to a file you intend to keep.
* *Paid events.* `superChatEvent` and `superStickerEvent` map to the existing `chat.donation` kind (`source_class=donation`, `plane=content`, `trust_level=untrusted`, never `semi_trusted`): `payload.amount` (`amountMicros / 1,000,000`), `currency`, `message` (the comment, or the sticker alt text), `paid_kind`, optionally `tier` and `amount_display`. Because the class is `donation`, the operator must list it in `AIVTUBER_INGRESS_SOURCE_CLASSES` (as in the example above); with `public_chat` alone the app rejects each one as `rejected_ingress_policy` and counts it, which is the safe default.
* *Membership events.* `newSponsorEvent`, `memberMilestoneChatEvent`, `membershipGiftingEvent` and `giftMembershipReceivedEvent` are *not* emitted: the domain has no membership event kind and this change adds none. They are counted (`membership_unmapped`). Future work: a membership kind in `schemas/event-envelope.schema.json` and the domain types, then a mapping here.
* *Other items.* Tombstones (deleted messages), bans, sponsor-mode changes, polls and gifts are counted as `not_chat`; as with Twitch deletions, a record already piped cannot be recalled.
* *Backlog.* The first poll returns messages already in chat. They are marked seen and counted (`skipped_backlog`) but not emitted, so a mid-stream start does not answer old chat; `--include-backlog` emits them.
* *Bounds.* Message text over 500 characters (YouTube allows 200), a record over 64 KiB or a payload over 16 KiB is rejected whole, never truncated, and counted (`dropped_oversize`); the record and payload limits match `SecurityRuntimeConfig` and a test pins them. Items with a missing id, text, author or timestamp are counted (`dropped_malformed`). A response that is not valid JSON is counted (`malformed_responses`) and backed off. Message ids are deduplicated in a set of 4,096 ids, oldest evicted first (`duplicates`). A response over 2 MiB is refused. The writer queue is bounded as for Twitch (`dropped_queue_full`). Sequence numbers are a logical counter and are not consumed by rejected items.
* *Backoff.* 5xx and transport errors: 2 s doubling to 2 min. Quota or rate-limit 403 (`quotaExceeded`, `dailyLimitExceeded`, `rateLimitExceeded`, `userRateLimitExceeded`) and 429: 1 min doubling to 15 min. Success resets the schedule. While backing off no chat flows but the performer keeps running; the app never waits on this process.
* *Ending.* `liveChatEnded`, a `chatEndedEvent` item, or `offlineAt` in a response stops the sidecar cleanly with a final stats line.
* *Redirects and TLS.* No redirects are followed; remote hosts require HTTPS, plain HTTP is allowed for loopback only (the test server). Proxy environment variables are honoured for the real API host and ignored for loopback.

== Speech observations (issue #92, S1)

`schemas/speech-observation.schema.json` is the contract for raw speech-activity edges and an optional turn-end score from a VAD or turn provider. It carries no audio, PCM or transcript text, and no source class, plane, trust or priority field: the receiving ingress assigns them. A microphone speaker, including the operator's own, is always `speech` / `content` / `untrusted` (`SpeechObservationProvenance`); it cannot mint authority, and priority comes from configuration.

Observations do not ride the stdin `EventEnvelope` pipe. An envelope kind would send them through the content queue and the scheduler's `Conversation` priority, and a signal is not content. They enter `SpeechObservationTracker::ingest_bytes` (size-bounded, schema-validated), which first applies the same operator ceiling as the stdin ingress (`IngressPolicy::admits_declared`): if `AIVTUBER_INGRESS_SOURCE_CLASSES` excludes `speech`, every batch is rejected and counted before parsing. The S2 sidecar uses a separate child-process pipe (see Speech sidecar below), never the stdin content pipe, and the same policy applies to it.

* *Stale rejection.* An activity edge older than `max_age_ms` (160), a turn-end score older than `turn_end_max_age_ms` (400), or any observation past its `expires_at_ms` is rejected and counted by reason (`stale_age`, `expired`, `future_dated`, `out_of_order`, `speaker_capacity`). Ordering uses observed time, never arrival, and nothing blocks.
* *Raw edges.* No debounce: a 32 ms fragment is an edge and restarts the silence clock (ADR-0005).
* *Bounded state.* At most 64 speakers; idle speakers are evicted after a logical-time TTL.
* *Fallback.* `fallback_turn_signal(state, now, config)` is a pure function that reports `turn_end_eligible` after 800 ms of silence. `SpeakerView` says why it applies (`no_turn_end_provider`, `unsupported_language`, `turn_end_stale`). Language is declared by configuration, never inferred. A speaker still active after 60 s without an edge is `activity_stale`. No floor decision is made here; `FloorAction` is #81.
* *Metrics.* `SpeechObservationMetrics` (observation age, rejects by reason, speaker high water, fallback signals per silence episode, provider unavailable) appears as `RuntimeRetentionSnapshot::speech` when `ProductionApp::with_speech_observations` is composed; it is absent by default.
* *Replay.* `examples/speech-observations/replay/*.json` run through `SpeechReplayFixture` with logical time and no microphone or model; `cargo test --locked -p aivtuber-runtime speech`.

== Perception observations (issue #90, S1a)

`schemas/perception-observation.schema.json` is the contract for derived screen observations (a closed scene class with closed-vocabulary labels, or one caption of at most 240 bytes); see ADR-0007 and `docs/domain-contract.adoc` section 4.2. `PerceptionTracker` (`crates/runtime/src/perception.rs`) is the ingress. In S1a it was a library component only; S1b composes it behind `AIVTUBER_PERCEPTION` (next section). The default is off.

* *Untrusted.* Plane `content`, trust `untrusted`, no source class; a payload with any trust, plane, source class, priority or authorization field is invalid.
* *Opt-in.* `enable_source(&AuthenticatedControl, alias, now_ms)` needs the dedicated `perception.control` capability (not `obs.control`) and an alias in `PerceptionConfig::source_privacy_floors` (empty by default, so nothing can be enabled). With nothing enabled, `ingest_bytes` refuses before parsing.
* *Bounds.* 16 KiB per batch, 8 observations per batch, at most 8 allowlisted and 2 enabled sources (defaults), latest observation per (source, kind) and a text-free diagnostic ring of 8. Observation age limit 10 s (unmeasured), validity at most 30 s, label vocabulary at most 64 tokens.
* *Rejections* are counted per reason in `PerceptionMetrics` (`disabled`, `future_dated`, `stale_age`, `expired`, `out_of_order`, `redaction_failed`, batch `oversize`/`invalid`/`disabled`) with disagreement, out-of-vocabulary label, redaction and age counters; no caption text is in any metric.
* *Consumers.* `scene_snapshot` (closed vocabulary only), `resolve_scene` (source hierarchy) and `thinking_caption_item` (one untrusted, delimited, at most 512 byte item). The caption never reaches memory, TTS or Reflex.
* *Replay.* `examples/perception-observations/replay/*.json` through `PerceptionReplayFixture`; `cargo test --locked -p aivtuber-runtime perception`.

== Live screen perception (issue #90, S1b)

Opt-in and off by default at every level: the profile switch, the operator enable, and the runtime's own suspension. Needs the `local` profile, a loopback obs-websocket and a loopback multimodal `llama-server` (Qwen3-VL-4B-Instruct Q4_K_M with its projector, `--parallel 2`). **It requires about 12 GB of VRAM next to the local stack**; on an 8 GB card the model spills silently (EXP-0004c) and the runtime latency probe will suspend perception. ADR-0007 has the design; `docs/local-profile-quickstart.adoc` has the setup.

[cols="2,1,4"]
|===
|Variable |Default |Meaning

|`AIVTUBER_PERCEPTION` |`false` |Compose the perception path (requires `AIVTUBER_MODE=local`). It starts `off`.
|`AIVTUBER_PERCEPTION_OBS_SOURCE` |required |The one OBS source to capture. The operator's real name; observations only ever carry the alias.
|`AIVTUBER_PERCEPTION_ALIAS` |`game-main` |Alias for that source in observations and the tracker allowlist.
|`AIVTUBER_PERCEPTION_VLM_ENDPOINT` |required |Loopback chat-completions URL of the multimodal server. A non-loopback host is a startup error.
|`AIVTUBER_OBS_ENDPOINT`, `AIVTUBER_OBS_PASSWORD` |`ws://127.0.0.1:4455` |Shared with the OBS stream output; perception opens its own session. Must be loopback.
|`AIVTUBER_PERCEPTION_MODEL` |`qwen3-vl-4b-instruct-q4_k_m` |Provenance label in observations.
|`AIVTUBER_PERCEPTION_LANGUAGE` |`ja` |Caption language, `ja` or `en`.
|`AIVTUBER_PERCEPTION_IMAGE_WIDTH`, `_HEIGHT`, `_IMAGE_FORMAT` |`768`, `432`, `png` |Size OBS downscales to (8 to 4096) and container (`png` or `jpeg`).
|`AIVTUBER_PERCEPTION_CADENCE_MS` |`10000` |Time from one capture finishing to the next. Floor 5000; a lower value is an error.
|`AIVTUBER_PERCEPTION_GATE_SETTLE_MS` |`750` |How long Thinking and speech must have been idle before a capture starts.
|`AIVTUBER_PERCEPTION_CAPTION_DEADLINE_MS` |`3000` |A model call slower than this is late: dropped, and three in a row suspend perception.
|`AIVTUBER_PERCEPTION_PROBE_INTERVAL_MS` |`60000` |Period of the latency probe (it also runs once at start).
|`AIVTUBER_PERCEPTION_PROBE_CEILING_MS` |`150` |A probe slower than this, or over twice the start baseline, suspends perception (spill).
|`AIVTUBER_PERCEPTION_VALIDITY_MS` |`20000` |Observation validity, at most 30000.
|===

* *Control.* `aivtuberctl perception-on` and `perception-off` go through the authenticated operator endpoint, which holds `perception.control` only when perception is composed. `aivtuberctl status` prints a `perception` line: `status` (`off`, `probing`, `active`, `suspended`), `suspend_reason` (`start_probe_failed`, `start_probe_spill`, `latency_spill`, `slow_captions`, `repeated_failures`), availability, the last probe time and counters including how often a capture yielded to Thinking or speech. A suspended path stays off until `perception-on`. Disabling takes effect before the next capture and drops everything retained.
* *Privacy.* Frames are held in memory for one model call and are never written to disk or logged; only counters and the bounded tracker state exist. The model and OBS endpoints are loopback only. Captions are untrusted data: URLs and secret shapes are removed, the caption is at most 240 bytes, and it can reach Thinking only as one delimited untrusted item (not yet wired; S2).
* *Failure.* The model, OBS or the probe failing degrades to "no observations" and a visible status; the deterministic performer is never involved. The capture runs on its own thread, never in the frame or motor loop.

== Speech sidecar (issue #92, S2)

`speech-vad-sidecar` (crates/adapters, `src/bin/speech-vad-sidecar.rs`) turns a local microphone, or `--input-wav`, into `speech-observation` batches on stdout, one JSON line per raw speech edge. The app spawns it as a child process when `AIVTUBER_SPEECH_SIDECAR` is set; it is off by default.

Pipeline: capture (cpal) -> mono -> rubato sinc resample to 16 kHz -> 512-sample (32 ms) frames -> Silero VAD v6 probability -> start/end hysteresis (0.5 / 0.35, the EXP-0001 values) -> raw edge -> stamp on the runtime timeline -> bounded stdout writer. There is no debounce and no minimum-speech filter (ADR-0005): one frame above the start threshold is an edge. No turn-end score is emitted (Smart Turn is not adopted); `language` is declared with `--language`, never inferred.

=== Build and run

[source,sh]
----
# Fetch the pinned model once (sha256 is checked again at every start).
curl -L -o silero_vad_op18_ifless.onnx \
  https://raw.githubusercontent.com/snakers4/silero-vad/v6.2.3/src/silero_vad/data/silero_vad_op18_ifless.onnx
sha256sum silero_vad_op18_ifless.onnx   # 7671cd04b004e9076da0d4a7b1a5aec36adf161c39230c1cb94a4fd5db6bbd28

cargo build --release --locked -p aivtuber-adapters --features silero-vad,mic-capture --bin speech-vad-sidecar
export AIVTUBER_SPEECH_SIDECAR=target/release/speech-vad-sidecar
export AIVTUBER_SPEECH_SIDECAR_ARGS="--model silero_vad_op18_ifless.onnx --language ja"
cargo run --locked -p aivtuber-app      # reads content on stdin as usual
----

* `AIVTUBER_SPEECH_SIDECAR_ARGS` is split on whitespace and passed without a shell (paths with spaces are not supported; at most 32 arguments). `AIVTUBER_SPEECH_SIDECAR_RESYNC_MS` (default 5000, 250 to 60000) sets the steady-state clock re-sync. The child's environment has every `AIVTUBER_*` variable removed.
* Sidecar flags: `--model`, `--language` (required), `--speaker-id` (default `mic-local`), `--input-device NAME` (substring match; `--list-devices` prints names to stderr), `--input-wav FILE [--pace realtime|max]`, `--preroll-ms` (default 300, at most 2000), `--start-threshold` / `--end-threshold`, `--clock sync|local`, `--sync-timeout-ms`, `--duration-secs`, `--stats-secs`, `--clock-probe-ms` (model-free clock measurement mode).
* `mic-capture` is a separate feature because cpal needs ALSA development headers on Linux. Without it `--input-wav` still works. The default workspace build compiles neither feature.
* Manual smoke and clock measurement: `cargo run --release --locked -p aivtuber-app --bin speech-sidecar-check -- --wide --duration-secs 30 -- <sidecar and its flags>` prints every edge with its signed lag (`now_ms - observed_at_ms`) and the tracker metrics. `--wide` widens the tracker limits to 1 s so every edge is measured.

=== Runtime model decision (adopt tract; ort not needed)

Silero VAD v6.2.3 runs through `tract-onnx` 0.23.10 (pure Rust, MIT OR Apache-2.0, no build-time network, no native library). The standard `silero_vad.onnx` cannot be loaded by tract (it analyses both branches of the sample-rate `If` node and fails on the 8 kHz branch), so the pinned asset is the same release's `silero_vad_op18_ifless.onnx` (16 kHz only, no `If`; MIT, snakers4/silero-vad tag v6.2.3, sha256 `7671cd04b004e9076da0d4a7b1a5aec36adf161c39230c1cb94a4fd5db6bbd28`). Measured on 9 EXP-0001 inputs (3 Common Voice ja clips, 3 clean and 3 noisy synthesized streams; 1620 frames), maximum absolute difference of per-frame probability against onnxruntime 1.31.1 running the standard v6 model: ifless export on onnxruntime 4.8e-7, tract on the ifless export 8.7e-7, 0 of 1620 frames differing at the 0.5 threshold. (The probabilities were printed to six decimals, so the true differences are smaller.) tract takes about 0.14 ms per 32 ms frame on the development host (release build of the probe, 130 frames in 18.8 ms), the same order as the 0.22 ms onnxruntime figure in EXP-0001. Decision: adopt (tract, project-owned frame/edge logic). Fallback, if a later Silero export tract cannot load: `ort` with dynamic loading of an operator-installed, pinned onnxruntime (no build-time download). Scores are Silero v6 only: the sherpa-onnx release asset (a v4 export) behaved badly under noise in EXP-0001 and must not be substituted. The model file is never committed; `provider_version` records the model release, the export and the runtime (`silero-vad-v6.2.3-ifless-tract-0.23.10`) because both can move scores.

=== Privacy

* Audio stays in process memory. The sidecar opens no file for writing and no socket; the only output is the observation lines (edges, times, an optional frame confidence), which cannot carry samples. `--input-wav` only reads.
* The only audio kept beyond the frame being scored is `PreRoll`, a bounded in-memory ring of the most recent 16 kHz mono samples (`--preroll-ms`, default 300, hard cap 2000). It is the hook the S3b transcription reads to recover onset the VAD reports late (EXP-0001: 12.7% of clean utterances had onset lag above 100 ms). Nothing reads it in S2 or when no STT worker is configured, it is cleared on a capture gap, and its `Debug` output shows lengths only. With `--stt-worker` the segment feeder copies from it into the worker pipe (see Speech transcripts below).
* Tests that need a WAV generate synthetic signals in memory and write them under the cargo test temp directory; no recorded audio and no model is committed.

=== Timeline and clock mapping

The app writes `{"clock_sync":{"runtime_now_ms":N}}` (its own monotonic `now_ms`) to the child's stdin at spawn, every 50 ms for the first 10 s (a line written at spawn is read only after the child starts and loads its model, so the first lines are stale by the startup time; measured 11 to 18 ms with no model, longer with one), then every `AIVTUBER_SPEECH_SIDECAR_RESYNC_MS`. The sidecar keeps `offset = runtime_now - local_receipt_time` over its last 8 syncs and uses the maximum, because pipe delay only ever lowers a sample. Capture positions are mapped to local time by the least-delayed recent chunk arrival (a min filter over the last 256 callbacks), which also tracks drift between the audio device clock and the monotonic clock. Without a first sync the sidecar exits instead of stamping (`--clock local` is for standalone runs). When stdin closes the sidecar exits.

Measured (A-SPEECH-OBS-001): see the assumption entry. Stamp-to-arrival lag of a model-free probe edge, after the warm-up, median 0.3 ms and maximum 0.9 ms in repeated runs (one run showed a single 25 ms scheduling outlier); the lag includes the pipe latency, so it upper-bounds the offset error. Real edges lag their stamp by about 38 ms (32 ms frame start plus the 10 ms capture chunk, then inference), against the 160 ms activity age limit. Not measured: acoustic and device-buffer latency before the callback runs, which needs a loopback rig; the sidecar stamps at callback arrival. The floor therefore sees edges slightly later than the sound, and never earlier.

=== Failure and bounds

* The child's stdout is read by a dedicated thread through the same bounded line reader as the stdin ingress (`pump_bounded_records`; lines over 16 KiB are drained and dropped, at most 64 lines queued, newest dropped and counted). Each poll ingests at most 64 lines, so a flooding child cannot starve the loop.
* The app counts `provider_unavailable` once and stops expecting observations when the child exits, closes stdout, cannot be started, or sends 32 consecutive rejected lines (garbage, or batches refused by the operator ingress ceiling, which applies to `speech` exactly as in S1). There is no automatic restart. A silent child is not a failure: silence is normal. A child that hangs without exiting is not detected (the sidecar has no heartbeat; recorded as a limitation; the STT worker child it supervises does have one, see Speech transcripts below).
* Inside the sidecar: the audio callback uses a bounded channel and counts dropped chunks; a drop closes any open segment, resets the model, resampler and clock, and restarts the stream, so a gap is never spliced. Output goes through a 64-line bounded writer (drop-newest, counted); a closed stdout ends the process.

== Speech transcripts (issue #92, S3b)

The speech sidecar can supervise a second child, `speech-stt-worker` (crates/adapters, `src/bin/speech-stt-worker.rs`), that turns the VAD's speech segments into Japanese partial and final transcripts. It is off by default, behind the off-by-default `sherpa-stt` cargo feature, and nothing in the default build, the default CI gates or the default tests downloads or needs a model.

```text
mic -> 16 kHz -> Silero edges ----------------------------------> sidecar stdout (speech-observation, unchanged)
                  |
                  +-> SegmentFeeder (PreRoll >= 300 ms, tail, min speech) --pipe--> speech-stt-worker
                                                                                        |  sherpa-onnx offline recognizer, CPU
sidecar stdout <-- relayed speech-transcript lines + {"stt":{...}} status <-- stdout <--+  one JSON line per revision + heartbeat
        |
        v
app: SpeechSidecar::poll_with_transcripts -> SpeechTranscriptTracker (untrusted content)
```

* *Contract.* `schemas/speech-transcript.schema.json` (positive and negative fixtures in `examples/speech-transcripts`, fixture to Rust and Rust to schema parity): `segment_id`, `revision`, `kind` (`partial`|`final`), `text` (at most 1000 characters, no control characters), the declared `language`, `covered_audio_ms`, `observed_at_ms` (runtime timeline, the end of the covered audio), `engine` (`model_id` and a SHA-256 bundle digest) and `complete` (false on every partial). There is no trust, plane, source class or priority field, and no audio or word timings; extra fields are refused.
* *Trust.* The runtime assigns the classification, and it is constant: source class `speech`, plane `content`, trust `untrusted`, even for the operator's own microphone. The operator ceiling `AIVTUBER_INGRESS_SOURCE_CLASSES` is applied before parsing, as for observations. Transcript text is data: a transcript that says "ignore your rules" is surfaced verbatim as untrusted content and changes nothing (`hostile-text` replay fixture).
* *Partial versus final (decision Q6).* A partial is reduced by `SpeechTranscriptTracker` to a `FloorHold` observation (revision, covered audio, the character count of the latest revision, age) that may extend or hold the speaker's floor. Its text is neither retained nor exposed, so a partial cannot start a reply, reach Reflex or Thinking, or be persisted. Only a final leaves the tracker, as a `SurfacedFinal` in a bounded queue (`take_finals`); an empty final closes the segment and is not surfaced.
* *Revisions (Q10).* A revision supersedes and never appends. A duplicate or lower revision (`stale_revision`), an older segment or a revision that covers less audio (`out_of_order`), anything after the final (`after_final`), an over-age partial (1500 ms) or final (10 s) (`stale_age`) and a future-dated one (`future_dated`) are rejected and counted. Bounds: 16 speakers with one open segment each, 8 pending finals (drop-newest, counted), 1000 characters of text, idle open segments abandoned after 45 s, idle speakers evicted after 5 min.
* *Text (Q9).* The worker emits the engine's text unmodified. A text that violates the wire bounds is counted (`texts_rejected`) and replaced by an empty final, never rewritten. Display or projection normalisation belongs to the consumer under ADR-0004, so replay keeps the raw text.
* *Nothing persists and nothing is minted.* No type in the tracker is serializable except the metrics, none carries a privileged-control capability or a durable-memory permit, and `Debug` output of transcripts, finals and audio frames shows lengths only. The app logs only the length of a surfaced final.
* *Routing finals into conversation (S3c, off by default).* With `AIVTUBER_SPEECH_CONVERSATION=true` the app loop turns each final into one `speech.input` envelope and passes it to `process_content_bytes`, the entry point stdin and Twitch chat use, so there is no second request path: the runtime parses and validates it, refuses non-content planes, applies the `AIVTUBER_INGRESS_*` ceiling, the payload cap, the per-source token bucket and the bounded content queue, and the router builds the typed Reflex/Thinking request from the admitted envelope. Source class, plane and trust come from the runtime-assigned provenance, never from the text. The payload is exactly `text` and the declared `language`, so a spoken sentence cannot supply the `intent`, `template_id` or `topic` keys the routers read, and `authorization` is always absent: a final cannot mint a privileged-control capability or a durable-memory permit, even when the operator is the speaker. Text is passed through unmodified (Q9); ADR-0004 governs *output* speech projection and does not apply to input. Event ids and the `observed_at` stamp derive from a counter and the transcript's runtime-timeline millisecond, so a replay is identical. Bounds: at most `AIVTUBER_SPEECH_CONVERSATION_MAX_FINALS_PER_TICK` (default 4, 1 to 16) finals per loop pass (the rest wait in the tracker's bounded queue) and `AIVTUBER_SPEECH_CONVERSATION_MAX_TEXT_CHARS` (default 400, 1 to 1000) characters; an over-long final is dropped whole, never truncated. Drops are counted (`speech_conversation_metrics`: `dropped_oversize`, `dropped_blank`, `dropped_by_runtime` for ingress-policy, rate, size or queue refusals, `route_errors`). The setting requires `AIVTUBER_SPEECH_STT_WORKER`; without it the app refuses to start. Without the setting finals are drained and only their length is logged. A partial still only produces `FloorHold`; with `AIVTUBER_SPEECH_FLOOR` (below) the floor gate reads it, and it can only delay a reply. Replay fixtures: `examples/speech-conversation/replay`, driven by the app's `speech_conversation_tests` with no microphone or model. A reply to a second utterance while the same cached asset is still playing or cooling down is refused by the scheduler exactly as it is for chat (`route_errors`).

The loop calls `ProductionApp::service_chat_burst` after it drains operator requests, and logs a `chat_burst:` counters line (admitted, dispatched, held, deferred pending/offered, expired, superseded, erased, operator-cancelled, revalidation-refused, evicted, actor-capped, not-selected, shed and an invariant-violation total that must stay 0) plus a `chat_burst: deferred reply` line per reply dispatched from the inbox (event id and chosen asset only; viewer text is never logged). Section 12.6 of `docs/jev-routing.adoc` has the contract.
* `AIVTUBER_SPEECH_FLOOR` (default off), `AIVTUBER_SPEECH_FLOOR_TAKE_TURN_SILENCE_MS` (default 800, 700 to 1000), `AIVTUBER_SPEECH_FLOOR_MAX_DEFER_MS` (default 10000, 1000 to 60000), `AIVTUBER_SPEECH_FLOOR_MAX_DEFERRED` (default 8, 1 to 32): the deterministic conversational-floor gate (#81 S1, ADR-0005). Needs `AIVTUBER_SPEECH_CONVERSATION`; without it the app refuses to start. With it, a final is routed only when `FloorPolicy` (crates/scheduler) answers `take_turn` for its speaker: the user is not speaking (raw VAD edges), has been silent for the take-turn silence, no fresh partial transcript holds the floor, and the performer is not speaking. Otherwise the final waits in a queue bounded by count (the oldest is dropped on overflow) and by age (a final that waited longer than the max defer is dropped, never answered over the user); drops and deferrals are counted and logged as `speech_floor_metrics`. A partial can only delay a reply; only a final can be routed. Missing evidence (no VAD tracker, a speaker never heard, a lost `end` edge past the fallback bound) degrades to the unchanged behaviour (routed at once) and is counted as `fallback_take_turn`. The policy also implements the stale-feed rule (ADR-0005 D6) but the app does not report VAD feed liveness yet, so that rule is dormant in the composition. The gate has no handle to the scheduler, any output or operator control: operator stop never passes through it. S1 records a `yield` decision when a user run reaches 400 ms over a speaking performer but executes nothing (fade-stop barge-in, backchannels and phrase-level interrupt points are later slices; the last needs #83). Replay fixtures: `examples/speech-floor/replay`, driven by the app's `speech_floor_tests` with no microphone or model.
* *Feed liveness (#81 S2, ADR-0005 D6; automatic with `AIVTUBER_SPEECH_FLOOR`).* The edge stream is silent in a quiet room, so a stalled feed cannot be told from silence without a heartbeat. With the floor on, the app adds `--feed-heartbeat-ms 64` to the sidecar's arguments (an explicit `--feed-heartbeat-ms` in `AIVTUBER_SPEECH_SIDECAR_ARGS` wins; `0` turns it off, and the flag is off by default so nothing else sees the line). The sidecar then writes `{"vad":{"heartbeat":{"seq":N}}}` at most once per interval and only right after a chunk of audio went through the scorer, so a stalled microphone, a hung scorer or a dead process stops it. It is not part of the `speech-observation` batch (no observation, time or authority in it; routed by its top-level `vad` key like the `stt` status line, strict parser in `speech_vad::heartbeat`, a malformed beat counts as a rejected line and never toward the 32-invalid degrade). The app ages the newest beat by its own receipt time, so a wrong cross-process clock mapping can neither hide a stall nor fake one, and passes it to the floor as `feed_age_ms`. Until a first beat arrives the freshness rule stays dormant (the S1 behaviour). Once beats have arrived: a feed older than `observation_stale_ms` (160) makes costly decisions wait (`stale_observation`, replies stay deferred, a speaking performer holds); a feed older than `vad_loss_ms` (5000) degrades the floor to the text-only path (`vad_unavailable`), so a reply is released, not held forever, and the performer is never frozen. The release needs the deferred final to still be inside `AIVTUBER_SPEECH_FLOOR_MAX_DEFER_MS` (default 10000); with a shorter max defer than 5 s a stale-feed reply is dropped and counted rather than released.
* *Barge-in (#81 S2, ADR-0005 S-3; off by default).* `AIVTUBER_SPEECH_BARGE_IN=true` (requires `AIVTUBER_SPEECH_FLOOR`, otherwise the app refuses to start) and `AIVTUBER_SPEECH_BARGE_IN_FADE_MS` (default 120, 0 to 150; 0 asks for a hard stop). Each loop tick `ProductionApp::service_barge_in` evaluates the floor for every tracked speaker while an audio performance is playing. Only a *confirmed* `yield` / `user_barge_in_confirmed` acts: raw VAD activity for `barge_in_confirm_ms` (400) over the performer, on a fresh feed that has reported liveness at least once. A tentative run, a stale or dead feed, a partial transcript, any model or Jev output, and a feed that never beat all do nothing; the transcript hold is not even an input to the performer-speaking branch of the policy. The effect, once per user speech run: (1) the scheduler cancels the audio-channel performances the user's speech may preempt (`Scheduler::stop_speaking_for`: the same rank rule as `schedule`, so a better-ranked reaction and a performance declared non-interruptible are left alone and the decision is recorded as `nothing_to_stop`; no wait for an interrupt point, because stopping publishes nothing), playing and reserved ones counted separately; (2) their pending audio and avatar commands are purged; (3) `AudioOutput::stop(fade_ms)` is called; (4) the avatar gets a `Reset` through its normal output (executed directly, because the cancelled generation is no longer live and a scheduled command would be dropped). There is no new privileged route and operator stop does not pass through here. The decision is in the floor's bounded decision ring (logical `at_ms`, only confirmed yields are sequenced there) and in a 32-entry `BargeInRecord` ring with counters; `speech_barge_in:` log lines carry counts and times only.

* Sidecar flags (also usable by hand): `--feed-heartbeat-ms N` (0 = off, the default; 16 to 1000), `--stt-worker PROGRAM`, `--stt-model`, `--stt-model-dir`, `--stt-threads`, `--stt-preroll-ms` (default 300, at least 300), `--stt-tail-ms` (500), `--stt-min-speech-ms` (250), `--stt-max-segment-ms` (25000, split below the worker's 30 s cap), `--stt-startup-timeout-ms` (60000), `--stt-heartbeat-timeout-ms` (5000), `--stt-drain-ms` (8000), `--stt-wait-ready-ms` (for `--input-wav` only: wait for the model before reading the file), `--stt-arg ARG` (raw passthrough to the worker, for test doubles). The pipeline's pre-roll ring grows to the pre-roll plus the minimum speech plus 300 ms when STT is on.
* The pre-roll hook S2 left unread is read here: a segment opens once the speech span reaches the minimum (a cough never reaches the worker), starts `--stt-preroll-ms` before the first start edge (EXP-0001 onset lag p90 was 112 to 144 ms, EXP-0002 6.5), continues across a pause shorter than the tail and closes when the tail runs out. Raw VAD edges still go out unchanged and undebounced.

=== Worker behaviour

* stdin is 16 kHz mono PCM framing plus segment `START`/`AUDIO`/`END` control (`speech_stt::protocol`); the reader checks every length against its tag before allocating. stdout is one `speech-transcript` JSON line per revision and a heartbeat line (`{"heartbeat":{...}}`, about 1 s, first one after the model loaded). Diagnostics go to stderr.
* Partial re-decode of the open segment happens at most every 500 ms of new audio, and a partial is emitted only when its text changed. If the decoder is busy the request is dropped, never queued (`partials_dropped_busy`); the final always wins: a partial in flight for a segment that ended is discarded, and the final is queued (at most 2 waiting). A segment is force-finalized at 30 s; later audio of that segment is dropped until its end.
* A decode runs on its own thread, never on the reader, the coordinator or the audio path. The engine cannot cancel a decode, so one that runs past `--decode-deadline-ms` (default 10 s) ends the worker with exit code 3, which the supervisor reports as `decode_deadline_exceeded`.
* Pins: the worker refuses to start unless every model file matches the SHA-256 and size pinned in the binary (`speech_stt::pins`), and unless the engine libraries beside it match their pins. The sherpa-onnx libraries are linked as shared libraries and must sit beside the worker executable (Windows: application directory; Linux: `DT_RPATH $ORIGIN` from `crates/adapters/build.rs`, so `LD_LIBRARY_PATH` cannot override it). The worker verifies the libraries in `current_exe()`'s directory, which are the very files the loader used, and the sidecar resolves `--stt-worker` to a real path and verifies the libraries beside it *before spawning that path*, which is the check that can still prevent a load. The loader runs library initializers before the worker's own check; see docs/supply-chain.adoc for the residual risk. Pinned platforms: Windows x64 and Linux x64 (anything else is refused).
* Privacy: the open segment's audio (at most 30 s) and the decode job copies live in memory only; the worker opens no file for writing and no socket; model files are only read.

=== Failure policy (same as S2, plus a heartbeat)

The sidecar supervises the worker; the first failure is final, the worker is killed, no restart is attempted, and the app is told once through a `{"stt":{"state":"unavailable","reason":"..."}}` line on the sidecar's stdout (a `ready` line is sent at the first heartbeat). The VAD edges and the deterministic floor fallback keep working without any transcript (decision Q3: a crash, OOM or hang in a 0.5-1 GB model must not take them down).

* Reasons: `worker_failed_to_start` (missing binary, or the pinned libraries do not match), `worker_exited`, `decode_deadline_exceeded` (exit code 3), `worker_closed_output`, `worker_stdin_closed`, `invalid_lines` (32 consecutive lines that are not valid transcripts), `heartbeat_missing` (no heartbeat within 5 s once running, or 60 s to load). The heartbeat closes the hung-child limitation S2 recorded, for this child only; the sidecar itself still has none.
* The app degrades only the *transcript path* (`SpeechSidecar::transcript_path`, counted once in `SpeechTranscriptMetrics::provider_unavailable`) on that status line, or on 32 consecutive transcript lines its tracker rejected. A sidecar that exits degrades both paths as in S2.
* Backpressure: the pipe to the worker is a bounded queue (512 frames, about 5 s of 10 ms chunks). A refused frame damages the open segment (its remaining audio is not sent and its end carries the skip flag, so the worker closes it with an empty final and never decodes spliced audio); a refused start skips the segment; segments are skipped, not queued, while the worker is still loading. All are counted.
* The app routes each sidecar line by its top-level key (`stt`, `transcripts`, otherwise an observation batch as before). Transcript lines are counted and ignored when no transcript tracker is composed. `{"stt":...}` is a health line like the stdin `clock_sync` line, not part of either normative schema.

== Local Japanese speech output (issue #220, S2b)

The `local` profile can speak with no paid or remote service. `local-tts-sidecar` (crates/adapters, `src/bin/local-tts-sidecar.rs`) is a loopback HTTP server over the official `sherpa-onnx` crate running Supertonic 3 int8 on the CPU. *Supervised child or a separate process?* Supervised is the documented path (decision Q3, the S3b pattern): with `AIVTUBER_TTS_SIDECAR` set, the app spawns the sidecar, waits for its ready line, owns its lifetime (it exits when the app does, even if the app is killed, because its stdin closes) and *derives* the listen address, path and audio root from `AIVTUBER_TTS_ENDPOINT` and `AIVTUBER_AUDIO_ROOT`, so the two processes cannot disagree about where a WAV file is. A sidecar you start yourself works too (`AIVTUBER_TTS_ENDPOINT` alone; give it the same `--audio-root`), and is the right choice when you want to restart the voice without restarting the app.

* `AIVTUBER_TTS_SIDECAR` (the executable; unset means off, the default). Local profile only, with `AIVTUBER_GENERATIVE_ENABLED=true` and a loopback `http://` `AIVTUBER_TTS_ENDPOINT` that has a port; anything else is a startup error. The libraries beside the executable are checked against their SHA-256 pins *before* it is spawned.
* `AIVTUBER_TTS_SIDECAR_MODEL_DIR` (required): the directory printed by the fetch script. The sidecar re-verifies every file against the pins at each start and refuses an unpinned directory (exit 2).
* `AIVTUBER_TTS_SIDECAR_SPEAKER_ID` (default 0, 0 to 9): the voice. Voice choice is configuration only, never request or model output. `AIVTUBER_TTS_SIDECAR_THREADS` (default 4), `AIVTUBER_TTS_SIDECAR_READY_TIMEOUT_MS` (default 60000: a cold first model load measured 6.6 s, a warm one about 1 s).
* `AIVTUBER_TTS_SIDECAR_AMPLITUDE_VISEMES` (default false): the mouth track, below.
* `AIVTUBER_TTS_SIDECAR_ARGS`: extra sidecar flags, whitespace separated (`--synth-deadline-ms`, `--max-text-chars`, `--max-cache-mb`, and so on); a flag the app derives is refused.
* A supervised sidecar records `backend=local-tts-sidecar`, `model_alias=supertonic-3-int8` and the model bundle digest as the model version in TTS provenance, unless `AIVTUBER_TTS_BACKEND_NAME`, `_MODEL_ALIAS` or `_MODEL_VERSION` say otherwise. Set `AIVTUBER_VOICE_MODEL` to a name that identifies the voice (for example `supertonic-3-int8-sid0`) so generated assets and your cached ones agree.
* `AIVTUBER_TTS_TIMEOUT_MS` (default 15000) still bounds the adapter; the sidecar's own synthesis deadline defaults to 12 s.
* `AIVTUBER_PHRASE_MODE` (`auto` default, `phrase` or `buffered`; #83 S1): `phrase` commits a generated reply one complete, gated, synthesized phrase at a time and plays phrase 1 while phrase 2 is synthesized (docs/generative-fallback.adoc, "Phrase mode"); `buffered` keeps one commit per reply; `auto` follows the composition profile. `AIVTUBER_PHRASE_TTS_TIMEOUT_MS` (default 12000) bounds the synthesis of one phrase, not of the whole reply, so a long reply no longer exceeds it as a whole; keep it at or below `AIVTUBER_TTS_TIMEOUT_MS`. The first phrase is also bounded by the interaction deadline. Startup prints which mode is active, and the loop logs `phrase_metrics` and one `phrase_response` line per phrased reply (commit order, gaps, how it ended).
* `AIVTUBER_THINKING_STREAM` (`off` default, `on`; #83 S2): in phrase mode the OpenAI-compatible Thinking adapter requests `"stream": true` and feeds the server-sent-event deltas (Responses `response.output_text.delta` or Chat Completions `choices[0].delta.content`, `[DONE]`/`response.completed`) into `phrase-seg-v1` incrementally, so phrase 1 is gated, synthesized and committed while the model is still writing. Requires phrase mode (startup error otherwise). Bounds: `AIVTUBER_THINKING_STREAM_IDLE_MS` (default 10000, silence between chunks), `AIVTUBER_THINKING_STREAM_MAX_REPLY_CHARS` (default 4096), `AIVTUBER_THINKING_STREAM_MAX_MS` (default 120000, whole stream wall clock including synthesis and lookahead waits); events are capped at 16 KiB and the stream body at 1 MiB. Differences from buffered phrase mode: there is no whole-reply gate before phrase 0 (each phrase is still gated, projected, gated again and re-checked at commit before it is committed); a provider failure after phrase 0 ends the reply with a typed `stream_failed` partial end (committed phrases stand, the incomplete remainder is never spoken); a failure before phrase 0 is the usual visible fallback (#291); the last phrase is `final` only when it is cut at end of stream. It is off by default because it has been verified against a stub SSE server only, not a real llama-server (see the pull request for #83 S2).

=== What the sidecar guarantees

* *Loopback only.* It refuses to bind a non-loopback address, checks that the `Host` header names this machine (a DNS-rebinding page cannot reach it) and requires `Content-Type: application/json`.
* *Explicit language and seed.* `lang=ja` and a seed derived from the text are passed to the engine on every call; the engine's defaults (English, a fresh random seed) cannot occur. The same reply is the same audio, byte for byte, across processes (measured). The file name is a content address of text, language, seed, voice, steps, speed and the model bundle, so the same request reuses the file and cache and replay keys are stable.
* *`style` is ignored and reported.* Supertonic has no style: the field is accepted, never an error, and every success carries `X-TTS-Style-Applied: false` (counted in the request log).
* *Bounded.* Body 16 KiB (413), text 500 characters (422), 4 simultaneous connections, a per-request read deadline (408), one synthesis at a time (a second is refused at once with 503, which the adapter maps to `Overloaded`; nothing queues), a synthesis deadline (504, the late result is discarded), and 256 MiB of generated audio (oldest removed first). Log lines carry counts and timings, never the text.
* *WAV files* are written through a temp file and an atomic rename under `AIVTUBER_AUDIO_ROOT/generated/`; the reference is `audio://generated/<digest>.wav`, which `ProcessAudioPlayer` resolves under the same root with its existing traversal rules.

=== Text that is not spoken, and how words are read (ADR-0004, issue #222 S1)

Before the TTS request, the generative pipeline projects the gated display text to speech text in two deterministic stages. The display text, and the asset compiled from it, are never changed; the output gate sees the display text, then the projected text when it differs, then the display text again last (the app commits only when the gate's last decision is for the display text). In phrase mode each phrase is projected on its own.

*Stage 1, deletion (D-5).* URLs (`http://`, `https://`, `ftp://`, `www.`), emoji (with their joiners and selectors) and parenthesised kaomoji such as `(´▽`)` are not spoken. Measured in EXP-0003: every engine speaks a URL as letter noise (6 s of audio for one link) and drops or misreads emoji. If a reply has nothing left to speak (only emoji or a link) the result is the typed non-verbal fallback, with no TTS call.

*Stage 2, reading lexicon.* A bounded, versioned, project-owned list of `surface -> reading` entries is applied to the stage 1 output, so a reading can never bring back a URL or an emoji. It exists because EXP-0003 measured the shipped engine misreading `YouTube`, `Twitter` and `VTuber`. There is no morphological analyzer in this stage (ADR-0004 D-1): numbers, counters and ordinary kanji are left to the TTS engine, and so is every word the lexicon does not list.

* *Starter lexicon.* `crates/generative/data/default-speech-lexicon.json`, compiled into the binary: about 45 streamer and tech words (YouTube, YouTuber, Twitter, `Twitter/X`, VTuber, Twitch, OBS, Discord, AI, LLM, TTS, GPT, OpenAI, VRM, BGM, SNS, ...). Every entry's `source` is `self-authored`: the readings were written for this project, and no third-party dictionary was copied.
* `AIVTUBER_SPEECH_LEXICON`: path of an operator lexicon (same format) merged *over* the starter lexicon, for the persona's name, community words and corrections. `AIVTUBER_SPEECH_LEXICON_DEFAULTS=false` (default true) drops the starter lexicon, which is also the rollback to display text for the words it covers. A missing file, malformed JSON or a bound violation is a *startup error* that names the entry (`AIVTUBER_SPEECH_LEXICON: speech lexicon entries[3].reading: ...`); the app never starts speaking without a lexicon the operator asked for. The file is read once at start; restart to change it. Startup prints `speech lexicon: <n> entries, projection <identity>`.
* *Authority.* Only the operator can add or change entries (an environment path read at start). Chat, Jev, the LLM and the TTS provider cannot; a model-suggested correction is a proposal for the operator to put in the file.
* *Format* (`schemas/speech-lexicon.schema.json`, fixtures in `examples/speech-lexicons/`):
+
[source,json]
----
{
  "schema_version": "0.1.0",
  "lexicon_id": "my-persona",
  "revision": "2026-11-10.1",
  "entries": [
    {"surface": "Claude", "reading": "クロード", "source": "operator"},
    {"surface": "AI", "reading": "アイ", "source": "operator", "case_sensitive": true, "note": "this persona is named Ai"}
  ]
}
----
* *Bounds* (a file that violates one is rejected whole): at most 2048 entries and 131072 bytes per file; `surface` 1 to 32 characters without control characters or surrounding whitespace; `reading` 1 to 64 hiragana, katakana or `ー` characters (so an entry can change how a word sounds and never what is said); `source` 1 to 64 and `note` at most 128 characters; unique surfaces (compared ignoring ASCII case); at most 4 layers merged. Text longer than 4096 characters is projected by stage 1 only.
* *Matching.* Longest match first. ASCII letters match case-insensitively unless the entry sets `"case_sensitive": true`; fullwidth Latin (`ＹｏｕＴｕｂｅ`) matches its halfwidth surface. An entry whose first (last) character is an ASCII letter or digit only matches when the character before (after) it is not an ASCII letter, digit or `_`, so `AI` is read in `AIの話` and `(AI)` and not in `MAIL`, `RAINBOW` or `AIs`; add an entry such as `AIs` when you want the plural. Entries that start or end with Japanese characters or symbols match anywhere.
* *Precedence.* Layers are merged starter first, operator file after; an operator entry replaces the starter entry with the same surface (ignoring ASCII case). Within one file, order does not matter.
* *Identity.* `rules:<rules version>|lexicon:<id@revision;...>+<sha256>` where the hash covers the effective merged entries (surface, reading, case flag), not the file bytes, so line endings and entry order do not change it and any changed reading does. It is recorded in `compatibility.speech_projection` of every generated asset (performance asset schema 0.2.0, below), and the startup line and `GenerationTrace.speech_projection` carry it.
* *Metrics.* The loop logs `speech_projection: replies=.. lexicon_hits=.. projection_passthrough_latin=..` when they change. `projection_passthrough_latin` counts Latin words of two or more letters that no entry covered and that therefore went to the TTS as written: it is the list of words to add next. Counts only, never text.

*Asset schema 0.2.0 (ADR-0004 D-3).* Generated assets now carry `speech.speech_text` (what was sent to TTS) and `compatibility.speech_projection` (the identity above). Schema 0.1.0 assets stay readable and are not rewritten; they cannot carry the new fields (the schema and the Rust validator both reject that), and a reader that only knows 0.1.0 will refuse a 0.2.0 asset, so upgrade readers first. The default compiler version was spelled with the schema version constant; the two are now independent (`DEFAULT_COMPILER_VERSION` stays `0.1.0`), so the bump does not make cached assets incompatible. *Staleness (D-4):* a recorded projection that differs from the current one makes an asset *stale but playable*: `AssetCompatibility::speech_projection_is_stale` says so and `check` does not turn it into an incompatibility. Lazy re-synthesis and operator-forced invalidation are described next (S2).

*Stale audio is renewed lazily; the operator can force it (ADR-0004 D-4, issue #222 S2).* When a generated asset recorded under another projection is played, it is played anyway (the meaning is unchanged), `projection_stale_played` is counted, and one bounded, deduplicated re-synthesis request is queued (at most 32 outstanding). A single worker re-runs TTS for it off the composition thread, from the display text the asset already carries and with no model call: the output gate sees display, projected and display again, exactly as for a fresh reply. The renewed asset keeps its id and replaces the old one in the hot cache and, when it was persisted, in the local descriptor store. A failure (gate now refuses, TTS error, timeout) is counted as `resynthesis_failed`, leaves the stale asset playable and is not retried until the projection changes, so a broken TTS cannot cause a retry storm. Assets that recorded no projection (schema 0.1.0, recorded takes) and assets that are not generated are never re-synthesized.

`AIVTUBER_SPEECH_INVALIDATE` (comma-separated lexicon surfaces, operator configuration read once at start, like the lexicon) is for when a wrong reading must stop immediately, for example a name: every generated asset whose display text contains the surface (ASCII case-insensitive) and whose audio was not produced under the current projection (including assets with no recorded projection) is forced to *must re-synthesize*. A forced asset is not played until it has been re-synthesized (the reply is dropped like any other playback error), and its next use asks again if the first attempt failed. Startup prints `speech invalidate "<surface>": scanned=.. forced=.. skipped_not_generated=.. truncated=..`. The scan reads at most 4096 assets and at most 256 may be forced at once; an asset already produced under the current projection is left alone, so leaving the variable set across restarts is harmless. There is no chat, model or provider path to this setting; it is deliberately not an operator-socket command (that would need a new control capability, a wire change).

*Speech lifecycle (ADR-0004 D5, `schemas/speech-lifecycle.schema.json`, fixtures in `examples/speech-lifecycle/`).* The scheduler records, for every item on the audio channel, `prepared`, `committed`, `started`, `boundary` (declared safe points inside a unit; the end is `finished`), `finished` and `cancelled` with a reason (`operator_stop`, `muted`, `preempted`, `superseded`, `barge_in`, `scheduler_rejected`, `stale_or_late`, `generation_cancelled`, `output_failure`, `shutdown`, `gate_rejected`), how far the unit had got (`reached`) and, for a started unit, `spoken_ms`. A TTS "synthesis done" is only `prepared`; a unit whose command failed, was muted or was dropped as late is `cancelled`, never `finished`, even though the performer's own timeline keeps running. `basis` says how the fact was observed: `logical_timeline` is not evidence of audible output; `output_accepted` means the audio adapter accepted the command (a backend-return proxy); `output_drained` is reserved for adapters that can report a drain (none does yet). Events carry the asset id, the scheduler generation, the phrase index and `final_phrase`, the SHA-256 of the text sent to TTS and the projection identity, never the text. On the streamed (phrased) path a phrase is `final_phrase` only when it was cut at the end of the stream; a reply cut short therefore never reports a final phrase, and the authoritative end of a reply stays the phrase response record's `Completed`. The queue of events is bounded (1024; a boundary is dropped first, then the oldest) and drops are visible as `seq` gaps and in `speech_lifecycle.dropped`; a consumer re-synchronizes from the snapshot (live units plus queued events). The counters (`emitted`, `dropped`, `rejected`, per-phase totals, `late_output_reports`) and the freshness counters are part of `retention_snapshot`.

*Known limitations, not handled yet:* symbols such as `&`, `%`, `#`, `@`, kaomoji that contain letters or digits, bare domains without a scheme or `www.`, any word the lexicon does not list (the engine reads it its own way), and anything that needs context to read (homographs).

Fixture tests: `examples/tts-projection/handling-set.json` (the EXP-0003 handling set plus the brand-word items; `expected` is the stage 1 result and `expected_speech` the stage 1 and 2 result, written by hand) and `cargo test --locked -p aivtuber-generative speech_lexicon`.

=== Mouth movement

Supertonic returns no visemes. Amplitude-driven mouth movement is the accepted first slice (decision Q7). With `AIVTUBER_TTS_SIDECAR_AMPLITUDE_VISEMES=true` the sidecar derives a coarse open/closed track from the audio envelope (one viseme, `aa`, whose weight follows the loudness; `neutral` when quiet; at most one cue per 80 ms and only when the weight moves) and writes it to `$AIVTUBER_PACK_ROOT/viseme/generated/<digest>.json` in the existing viseme-track format, returning it as `viseme_ref`. The app's `LocalVisemeStore` resolves it like any other track. Text-derived visemes stay with ADR-0004 / #222. Point `AIVTUBER_PACK_ROOT` at a directory you own (the repository's example pack is not a place to write generated files). Off, a generated reply moves the avatar through its expression and gesture tracks only.

=== Optional VOICEVOX backend (issue #295)

`AIVTUBER_TTS_BACKEND=voicevox` swaps the voice, not the contract. The app starts the `local-tts-sidecar` HTTP server in process, on an ephemeral loopback port, with a VOICEVOX synthesizer behind it, and the normalized-HTTP TTS adapter posts to it exactly as it posts to the Supertonic sidecar. VOICEVOX's own DTOs (the `audio_query` JSON, speaker ids, the engine's WAV) exist only in `crates/adapters/src/speech_tts/voicevox.rs`; the bridge calls `POST /audio_query?text=..&speaker=..` and then `POST /synthesis?speaker=..` on the engine, which the operator runs as a separate loopback process (never linked or bundled).

* Settings (`crates/app/src/voicevox_bridge.rs`): `AIVTUBER_VOICEVOX_ENDPOINT` (loopback `http://` origin; the same host check as the local profile's other endpoints), `AIVTUBER_VOICEVOX_SPEAKER` (required, no default character), `AIVTUBER_VOICEVOX_CREDIT` (required, printed at start), `AIVTUBER_VOICEVOX_TIMEOUT_MS` (total synthesis budget, default 12000) and `AIVTUBER_VOICEVOX_AMPLITUDE_VISEMES`. Local profile with `AIVTUBER_GENERATIVE_ENABLED=true` only; it is exclusive with `AIVTUBER_TTS_ENDPOINT` and `AIVTUBER_TTS_SIDECAR`. A missing speaker, a missing credit or a non-loopback engine is a typed startup error naming the variable.
* Bounds: the text length (500 characters, the server's cap), the engine's query JSON (2 MiB) and WAV (8 MiB), one budget for both engine calls, no redirects, no proxy, one synthesis at a time. Errors never carry the text or the URL.
* Failure: engine unreachable, non-2xx, malformed answer or timeout end as a 5xx from the bridge, which the adapter maps like any sidecar failure; the generated reply takes the visible non-verbal fallback (#291). The engine is not probed at start, so starting the app before the engine is fine.
* Credits and terms, and what is and is not deterministic: `docs/local-profile-quickstart.adoc`, "Optional voice: VOICEVOX".
* Tests: `cargo test --locked -p aivtuber-adapters --lib voicevox` (the two-step API, bounds, strict WAV parsing, failures against a fake engine on loopback) and `cargo test --locked -p aivtuber-app --lib voicevox` (settings, and the whole local path through the real adapter and bridge in buffered and phrase mode, including that the engine only receives projected text and that engine failures play the visible fallback). No engine is needed.

=== Failure and degradation

The deterministic performer never waits on the voice. After start-up the app does not wait on the sidecar at all:

* *Cannot start or never ready* (missing binary, a library or model that does not match its pin, a bad model directory): one line `tts_sidecar: unavailable: ...`, and the app runs on; every generated reply takes the typed non-verbal fallback.
* *Exits or crashes mid-run:* reported once (`tts_sidecar: exited; ...`); the TTS engine is gated on a liveness flag, so each later reply degrades at once with `Unavailable` instead of waiting out a connect timeout (a closed loopback port takes about two seconds to refuse on Windows). No restart is attempted; restart the app (or a sidecar you started yourself) to retry.
* *Busy, slow or hung:* 503 `Overloaded`, 504 or the adapter timeout, all the existing typed fallbacks (generation runs on the bounded worker, never on the composition thread).

== Generative fallback configuration

The executable constructs the production `GenerativeRuntime` only when `AIVTUBER_GENERATIVE_ENABLED=true`. Enabling it requires `AIVTUBER_OPENAI_API_KEY` (or, for a loopback-only endpoint, the explicit `AIVTUBER_OPENAI_AUTH=unauthenticated-loopback` policy) and `AIVTUBER_TTS_ENDPOINT`; endpoint/model/timeouts and optional TTS credentials are documented in `docs/generative-fallback.adoc`. The runtime compatibility values used by generated assets are the same compiler/voice/avatar/viseme/motion values used by the production `AssetStore`.

A `PlaybackRoute::Generate` is produced by the reflex composition when Jev executes the LLM route. Generation is submitted to the bounded `GenerativeRuntime` worker and returns immediately to the composition loop; `tick()` drains completed immutable results, revalidates publication/cancellation state, and only then mutates the hot asset store or scheduler. Slow providers therefore do not stop scheduler advancement or adapter maintenance. The default execution boundary has one in-flight provider job and eight queued jobs; saturation deterministically uses the preselected cached/non-verbal fallback rather than spawning unbounded work. A completed result that has been handed over but not yet drained is still counted as outstanding work, so health, retention, and benchmark waits never observe a false idle state (issue #177).

== Composition profiles (issue #55)

`AIVTUBER_MODE` names the active route graph explicitly. The mode — not disconnected environment flags — determines which planner, semantic index, Jev adapter, template pack, and generative runtime are composed. Startup prints a non-secret summary line (`composition profile: profile=... fingerprint=...`), and the fingerprint is recorded in benchmark result documents (`configuration.runtime_profile`) so base/head comparisons compare like-for-like compositions.

Profiles:

* `cached` (default) — exact/preselected cached playback via `IntentRoutePlanner` only. No semantic retrieval, Jev, templates, or generation.
* `reflex` — semantic retrieval + Jev + curated template decisions via `ReflexRoutePlanner` with the starter template pack. No generative fallback.
* `full` — the reflex route graph plus the LLM/TTS generative fallback.
* `local` (#220) — zero-paid-dependency composition: explicit `intent` events take the deterministic cached path (`LocalRoutePlanner`), free-text chat/donation/speech goes to the Thinking engine, everything else is `Silent`. No Jev, semantic retrieval, or templates. Every provider endpoint (Thinking and TTS) must be loopback; when Thinking fails, or its reply is refused, the route's fallback group `reaction.neutral` plays a speechless expression-and-nod reaction from the starter pack through the avatar output, and the daemon logs `generation_fallback: reason=...` (docs/generative-fallback.adoc, #288). Generated text still passes the same output gate, TTS, compilation, and scheduler path as `full`.

Profiles fail fast on misleading configurations before composition:

* `reflex`/`full` without `AIVTUBER_JEV_API_KEY` refuse to start instead of silently degrading.
* `full` without a fully configured generative backend (`AIVTUBER_GENERATIVE_ENABLED=true` plus thinking/TTS endpoints) refuses to start; use `reflex` for the documented degraded fallback.
* `cached` with a configured generative backend is rejected as misleading — either select `full` or remove the configuration.
* `local` without a configured generative backend refuses to start (it would silently do nothing for free text), and refuses any Thinking or TTS endpoint that is not loopback (`127.0.0.0/8`, `::1`, `localhost`).

Minimal commands:

[source,shell]
----
# cached (default; no extra credentials needed)
cargo run -p aivtuber-app

# reflex
export AIVTUBER_MODE=reflex
export AIVTUBER_JEV_API_KEY='<jev key>'
cargo run -p aivtuber-app

# full
export AIVTUBER_MODE=full
export AIVTUBER_JEV_API_KEY='<jev key>'
export AIVTUBER_GENERATIVE_ENABLED=true
export AIVTUBER_OPENAI_API_KEY='<thinking key>'
export AIVTUBER_TTS_ENDPOINT='https://tts.example/v1'
cargo run -p aivtuber-app
----

The step-by-step operator guide for the whole local path (assets, build, every variable, loopback verification, licences, troubleshooting, measurements) is link:local-profile-quickstart.adoc[the local profile quickstart]. Local profile with a `llama.cpp` `llama-server` on loopback (see `docs/generative-fallback.adoc` for the authentication policy and `docs/provider-conformance.adoc` for the verified server/model):

[source,shell]
----

export AIVTUBER_MODE=local
export AIVTUBER_GENERATIVE_ENABLED=true

Startup prints `thinking: endpoint=<origin> auth=<policy> backend=<name>` (origin only, never a path, query, or key) next to the profile line, so the Thinking location and authentication mode are observable; model alias/version and backend name are recorded in generation audit and asset provenance.

== Operator control (issue #56)

The daemon can expose a local, authenticated operator control endpoint for emergency stop/mute and a health/status snapshot. It is enabled by default on the endpoint name +aivtuber-operator-control+ and can be renamed with:

[source,shell]
----
export AIVTUBER_CONTROL_ENDPOINT='aivtuber-operator-control' # optional
----

The transport is an interprocess local socket: a named pipe under the `\\.\pipe\` namespace on Windows and a Unix domain socket on Unix-like systems. It is local-machine scope by construction and cannot be accidentally exposed to the network (no TCP is involved).

Authentication uses +AIVTUBER_CONTROL_SECRET+ (exactly 32 UTF-8 bytes; if unset, the daemon generates a random session secret). Operator clients present the same secret. If the daemon runs with VTube Studio enabled, the value is shared with the avatar adapter boundary by design.

Actions:

[cols="1,3,2"]
|===
|Action |Effect |Authority

|+status+
|Adapter health, mute state, content queue depth, scheduler item count, generation activity. Contains no secret material.
|Secret verification only (constant time); no control authority is minted.

|+stop+
|Stops and cancels current and queued performer work through +SecurityRuntime::handle_control_with_scheduler+, ends audio that already started (+AudioOutput::stop(0)+, hard stop) and resets the avatar to neutral.
|+performer.stop+ capability.

|+mute+
|Latches the operator mute state; scheduled audio and avatar dispatch is suppressed while muted. Like +stop+, it also ends audio that already started and resets the avatar to neutral.
|+performer.mute+ capability.
|===

*Ending started audio (#277).* +stop+ and +mute+ call +AudioOutput::stop(0)+ and an avatar +Reset+ with no feature flag: it works with the speech floor, barge-in and speech features off, with the content queue saturated, and with the model provider failed. The result per output is in the response detail and in an audit record (+operator_audio_stopped+ or +operator_audio_stop_unconfirmed+), for example +stopped 1 items; audio_stop=hard_stopped avatar_reset=ok+:

* +ProcessAudioPlayer+ kills and reaps its playback processes: +hard_stopped+ (or +nothing_playing+).
* An output with no stop primitive reports +unsupported+; already started audio plays out and the record says so. An output whose stop fails reports +failed+.
* The stop runs on a worker thread and the handler waits at most 100 ms (+AUDIO_STOP_BOUND+). A stuck backend yields +unconfirmed+ and cannot wedge the control handler; the app keeps dispatching without blocking on that output, and repeated stops do not pile up workers.

Full guarantees: docs/security-threat-model.adoc section 6.1.

*Memory erase (issue #305).* Retained viewer memory can be erased on request. The library entry point is +ProductionApp::erase_memory_operator+, which requires the authenticated +memory.admin+ capability, takes an actor +(source namespace, raw actor id)+ and/or up to 32 retained memory ids, and returns an +ErasureReport+ that lists what was removed and every remnant the runtime cannot prove erased (sidecar copies, Hindsight +retire+, generated assets, spoken output, provider and audit logs, backups). It is RAM-only and not yet an +aivtuberctl+ action; the operator socket grants +performer.stop+ and +performer.mute+, plus +perception.control+ only when live screen perception is composed (#90). Viewers can ask to be forgotten by sending exactly +!forgetme+ in public chat; only their own pseudonym is erased, at most once per 60 seconds, and the line is consumed before routing. Each erase writes an audit record (+erase_erased+, +erase_noop+ or +erase_ratelimited+) without claim text or raw ids. Details: docs/memory-adaptation.adoc section 13.1 and ADR-0008.

*Unmute is intentionally not supported.* Mute is a latching emergency state: resuming output requires restarting the daemon with a verified configuration. This is a deliberate choice so a compromised operator session cannot silently re-enable output.

CLI client (clap-based):

[source,shell]
----
export AIVTUBER_CONTROL_SECRET='0123456789abcdef0123456789abcdef'
cargo run -p aivtuber-app --bin aivtuberctl -- status
cargo run -p aivtuber-app --bin aivtuberctl -- stop
cargo run -p aivtuber-app --bin aivtuberctl -- mute
----

Security properties:

* Operator commands never enter the untrusted content queue; they are applied directly on the runtime thread through the same emergency path as operator hotkeys.
* Privileged actions pass through +LocalControlIngress::authenticate+ (constant-time secret comparison, action allowlist, scoped capability minting) before reaching the scheduler; content events cannot forge control authority (ingress rejects any serialized +OperatorCommand+ / authorization metadata).
* Requests are token-bucket rate-limited (burst 16, refill 8/s); the endpoint has its own bounded queue so saturated content ingress, blocked generation workers, or disconnected adapters cannot starve emergency control.
* The secret is never written to logs, telemetry, audit records, or status output. Audit records use the shared redactor.
* Transport failure (listener error, dropped connection) cannot corrupt scheduler/runtime state: requests are applied atomically on the runtime thread and connections are stateless.

== Support bundle / diagnostics (issue #68)

`aivtuberctl diagnose` captures a bounded, privacy-safe support bundle over the same local operator endpoint as `status`. Authentication is the same constant-time secret verification (no control authority is minted), so generating a bundle cannot stop, mute, or otherwise disturb the runtime.

[source,shell]
----
export AIVTUBER_CONTROL_SECRET='0123456789abcdef0123456789abcdef'
cargo run -p aivtuber-app --bin aivtuberctl -- diagnose > support-bundle.json
----

The bundle is a single versioned JSON document (`schema_version` in the manifest, currently `0.1.0`) containing:

* runtime/build/config identity: git revision (best effort), rustc/OS/arch, composition profile, non-secret config fingerprint, asset pack/compiler versions, semantic retriever identity, provider/model **names** (never keys or endpoints);
* adapter health (redacted error text; endpoint URLs are masked as `[ENDPOINT]`);
* bounded resource counters from #51/#52/#53 (queue depths, scheduler active/terminal counts, hot-cache occupancy, audit/telemetry/trace retention, generation worker counts);
* the most recent incident references (correlation ids only) with their redacted #65 causal timelines (one line per stage, no payloads);
* bounded redacted audit summaries (category + decision codes only, newest last);
* a manifest with generation timestamp and a SHA-256 of the bundle body for integrity comparison.

Identity sources (issue #167):

* `composition_profile` and `config_fingerprint` are the daemon's live values — the same ones printed by the startup `composition profile:` line — so an attached bundle is attributable to the composition that produced it. An app composed outside the daemon reports `unknown` for both.
* `git_revision` and `rustc_version` are best-effort compile-time values read from `AIVTUBER_GIT_REVISION` and `AIVTUBER_RUSTC_VERSION` when the binary is built. The default build path does not set them, so they report `unknown` unless the builder provides them. To build an attributable release binary:

[source,shell]
----
AIVTUBER_GIT_REVISION="$(git rev-parse HEAD)" \
AIVTUBER_RUSTC_VERSION="$(rustc --version)" \
cargo build --locked --release
----

Privacy model — the exporter is allowlist-based:

* it serializes explicit typed fields only; it never dumps environment variables, configuration files, payloads, transcripts, durable memory, or viewer identifiers;
* payloads and actor ids never enter causal traces or the correlation registry, so they cannot reach the bundle through them;
* every audit record has already passed the shared secret redactor at write time, and adapter error text is redacted again at export time;
* bundle generation is synchronous local work over already-retained state: no external provider calls, no unbounded history retention, and no scheduler/control mutation, so it works while providers are down and never blocks emergency control.

Bounds: causal timelines default to 8 and audit summaries to 32; both are clamped to 256 and configurable via `SupportBundleBuilder`. The correlation registry on `SecurityRuntime` retains at most 128 references.

Reproducibility workflow: follow link:after-action-review.adoc[After-Action Review and Regression Learning]. Attach the bounded bundle JSON to the incident issue when appropriate. The correlation ids inside map 1:1 to `trace_for_correlation` lookups in a replay; the identity section decides whether two bundles are comparable (same profile fingerprint and compiler version) before comparing counters.

Limitations: the bundle is evidence, not a replay artifact. It does not include private conversation text by design, so some behavioral incidents will need a separate minimal reproduction case.

== End-to-end interaction deadlines

Every admitted content event receives a trusted runtime deadline class derived from its normalized `EventKind`; untrusted payload fields do not choose or extend the class. Operator commands remain on the independent authenticated control path and do not enter this content-deadline policy.

The current classes are `high_priority`, `strong_reaction`, `conversation`, `commentary`, and `background`. `InteractionDeadlinePolicy` owns their budgets and the minimum useful budget required before starting generation. The default 30-second values are conservative safety ceilings that preserve existing behavior; they are not latency SLO targets and should be calibrated by #58 before tightening production profiles.

One interaction budget spans routing and provider work. Retrieval time is subtracted before Jev admission. OpenAI-compatible Thinking, normalized HTTP TTS, and Jev each receive an effective timeout no larger than both their provider-specific maximum and the remaining interaction budget. If too little useful budget remains before generation, production selects the already-determined cached/non-verbal fallback without entering the provider worker. A generation completion that arrives after the useful deadline is discarded at the composition-thread commit fence and cannot insert a hot asset or schedule playback.

The immediate interaction deadline is distinct from any future deferred-response expiry (#75): missing the immediate useful-time budget vetoes immediate work, but does not by itself define whether a separately retained deferred item is still contextually valid.

== Generative resource budgets (issue #69)

The generative resource budget is a provider-neutral admission policy that sits **before** generation submit: a denial never allocates provider work that must then be cancelled. It is disabled by default — existing deployments keep identical behavior until it is enabled explicitly.

[source,shell]
----
export AIVTUBER_BUDGET_ENABLED=1
export AIVTUBER_BUDGET_INTERVAL_MS=60000
export AIVTUBER_BUDGET_MAX_CONCURRENT_GENERATIONS=2
export AIVTUBER_BUDGET_MAX_LLM_CALLS=30
export AIVTUBER_BUDGET_MAX_TTS_CALLS=30
# Optional finer-grained ledgers:
export AIVTUBER_BUDGET_MAX_LLM_UNITS=200000
export AIVTUBER_BUDGET_MAX_TTS_CHARS=20000
# Optional cost ceiling (requires a pricing input version):
export AIVTUBER_BUDGET_MAX_COST_MILLIUNITS=500
export AIVTUBER_BUDGET_PRICING_INPUT_VERSION=pricing-2026-09
# Share of every call budget reserved for high-priority deadline classes:
export AIVTUBER_BUDGET_RESERVE_PERCENT=25
# Whether #64 shadow evaluation spends billable budget (default: no):
export AIVTUBER_BUDGET_CHARGE_SHADOW=0
----

Semantics:

* all ledgers roll over `AIVTUBER_BUDGET_INTERVAL_MS` using the runtime's logical clock, so recorded decisions replay identically;
* priority comes **only** from the trusted #67 deadline class (`high_priority`/`strong_reaction` may spend the reserved share); untrusted content fields can never promote priority;
* on denial the request degrades deterministically — reuse → semantic/template → cached/non-verbal → safe silence — exactly like other fallbacks, with a typed reason (`concurrent_budget_exhausted`, `llm_call_budget_exhausted`, `tts_call_budget_exhausted`, `llm_unit_budget_exhausted`, `tts_char_budget_exhausted`, `cost_budget_exhausted`) that stays distinct from #67 deadline exhaustion and #121 `capacity_saturated`;
* granted reservations settle with observed TTS usage at commit time and release automatically on stale/cancelled completions, so enforcing the budget never strands provider work or leaks in-flight slots;
* #64 shadow evaluation does not consume billable budget unless `AIVTUBER_BUDGET_CHARGE_SHADOW=1`;
* operator emergency control (stop/mute/diagnose) runs on the independent authenticated control path and is budget-independent by construction.

Accounting is observable in three places: the support bundle's `resources.generative_budget` section (six bounded budget-type records with limit/consumed/remaining/rejected_or_degraded), the telemetry `budget_denial_reason` column, and the `budget_denied` audit records with typed reasons.
