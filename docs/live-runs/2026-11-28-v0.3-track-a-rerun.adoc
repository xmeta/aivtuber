Notes on the table:

* *Disposition accounting.* Of the `64` chat inputs, `52` had a first phrase: `43` direct, `8` deferred and `1` crowd carrier (the crowd carrier took the deferred path, so the raw `path` notes show `9`). `12` were unvoiced policy outcomes. `0` lost. The `64` raw ingress records were all enqueued with `0` dropped, `0` oversize and `0` read errors.
* *Latency method.* p50/p95 reproduce the supported `aivtuberctl log summary` values (built from `main` `56db814`); p99 is nearest-rank over the same per-turn eligible observations (`ceil(p * n)`), with the counts shown. For small `n` (deferred `8`, crowd `1`) p95/p99 are effectively the maximum. Logical accepted-audio is not physical speaker onset; visible acknowledgement was not observed (avatar disconnected).
* *Quiet-window rule.* Each quiet window is measured from the first synthetic chat input and is the longest gap between consecutive first phrases (any origin) that intersects the window. The same rule applied to the baseline log is not available here, so the baseline column is the number published in the baseline record and a small method difference cannot be excluded.
* *Initiative.* The early re-fire spacings were `5.8 s` and `5.7 s` after a silent refusal. The first re-fire was voiced; the second was itself refused and silent (one early re-fire per refusal, no loop). Of the `7` refusals, `5` ended in a silent fallback and `2` did not (the turn was still voiced).

== Host conditions

* Windows 11, NVIDIA GeForce RTX 2070 SUPER 8 GiB, 32 GiB RAM; local profile only. The host was not quiet: a desktop session with many resident applications was running (browsers, chat clients, other agent sessions), the same situation as the baseline's "other load present".
* Before launch: GPU `2,611-3,088 MiB` used by other processes (baseline: `3,663 MiB`), CPU load about `27%`, free RAM about `4.4-6.1 GiB` of `32 GiB`, no `cargo`/`rustc` running. Whether another session built during the hour was not monitored, so it is not excluded.
* *Memory pressure is the likely confounder.* Free RAM stayed at about `2.4-3.6 GiB` during the hour, and the `llama-server` working set fell from `3,091 MB` to `1,397 MB` (see below), which means its pages were evicted by the OS rather than released by the process. This alone can slow direct generation; it was not isolated as the cause.
* All downloads, temp files and caches were kept on a non-system drive; the system drive had less than `2 GiB` free throughout.

== What this run does and does not show

* #545 behaves as designed on a real hour: after a silent repeat refusal the initiative fired again within about `6 s`, once voiced, once refused again, with no runaway re-firing; the initiative spacing minimum drops from `60 s` to `5.7 s` accordingly. It did not change the in-hour voiced initiative count (`48`, same as the baseline).
* #547 gives a usable refusal breakdown (all `7` refusals matched a prior initiative phrase; `5` of those matches had been shown).
* #540 did not visibly help crowd latency in this run: the single crowd route's `route_observation_to_dispatch` was `6,019 ms` against `3,175 ms`. With `n=1` in each run and a loaded host this is neither a regression finding nor an improvement finding; the crowd path is still reached only once per hour by this workload.
* Direct and deferred latency are worse or noisier than the baseline on this host. A repeat on a quiet host (or with host RAM freed) is the falsifying measurement before attributing any of it to code.
* #59 human review: `not reviewed`. The local session log is retained outside Git for that review.
