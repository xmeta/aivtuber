= Local profile quickstart (zero paid dependencies)
:toc:

Issue #220 (S3). This is the operator guide for running the whole performer on one machine with no paid service, no billable API, no SaaS account and no remote credential:

[source,text]
----
chat on stdin / microphone
   -> VAD + Japanese STT sidecar   (Silero VAD, sherpa-onnx ReazonSpeech k2-v2)   127.0.0.1, child processes
   -> floor policy + barge-in      (deterministic, in the app)
   -> local ThinkingEngine         (llama.cpp llama-server, Qwen3-4B-Instruct-2507)  127.0.0.1:18080
   -> local TTS sidecar            (Supertonic 3 int8 via sherpa-onnx)               127.0.0.1:8770
   -> local audio                  (ffplay)
   -> local VRM avatar renderer    (browser page / OBS Browser Source)               127.0.0.1:8765
----

Everything listens on loopback only. A network connection is needed once, to fetch the pinned model and library files (step 1). After that the run needs none, and step 6 shows how to check that.

Design and policy live elsewhere; this page is the procedure. Read `docs/production-runtime.adoc` for every variable's full semantics, `docs/supply-chain.adoc` for the pins and licences, `docs/vts-obs-adapters.adoc` section 6 for the avatar renderer, `docs/provider-conformance.adoc` for the verified llama.cpp / model pair, and `docs/experiments/EXP-0003-japanese-tts-bench.adoc` for the voice choice.

== 0. What you need (build from source)

Using a release archive? Skip to <<download-a-release>>: it needs none of the toolchains below, and `aivtuber-setup local` replaces steps 1, 2 and the starter-audio step.

* Windows 11 x64 or Linux x64. Only these two platforms have pinned engine libraries. *This guide was run end to end on Windows only.* The Linux commands are the same files with the other pinned archive names; the differences are marked, and they were not executed.
* To build: a Rust toolchain (the version in `rust-toolchain.toml`; `rustup` picks it), Node 20 or newer, Bun (`renderer/local-avatar/package.json` pins `bun@1.3.14`), `git`, and `ffplay` from FFmpeg on `PATH` (the default audio player).
* A browser for the avatar page (Chrome or Edge), or OBS Studio (free, GPL) with its Browser Source.
* About 6 GB of disk for downloads (the LLM is 2.5 GB) and about 1.5 GB of build output.
* Hardware. The measured configuration is in <<measured>>: a desktop with an 8 GB discrete GPU and 16 logical CPUs. The LLM can run on the CPU (`--llama-flavor cpu`, leave out `-ngl`), but then it competes with speech recognition and synthesis for the same cores and the measurements below do not apply. There is no guarantee below the measured hardware.

Linux additionally needs ALSA development headers if you build the `mic-capture` feature (a live microphone). `--input-wav` does not need it.

[#download-a-release]
== Download a release (no Rust, no Node, no Bun)

Issues #294 S1 and S2. This is the whole path for a streamer who only wants to run the performer: download, verify, set up, start. Tagged releases publish prebuilt archives for Windows x64 (`aivtuber-local-<version>-windows-x64.zip`) and Linux x64 (`aivtuber-local-<version>-linux-x64.tar.gz`) with a `SHA256SUMS` file beside them. Nothing below needs a Rust toolchain, Node, Bun, git or a C compiler; steps 0 to 2 of this guide are the build-from-source path for a different revision or platform.

*What the archive contains:* `aivtuber-setup` (the first-run command, below), `aivtuber-app`, `aivtuberctl`, `speech-vad-sidecar` (Silero VAD, microphone), `speech-stt-worker`, `local-tts-sidecar`, `twitch-chat-ingress`, `youtube-chat-ingress`; the pinned sherpa-onnx and ONNX Runtime libraries beside them (leave them there: the sidecars refuse to run if they are missing or changed); the avatar page at `renderer/local-avatar/dist`; the starter reaction pack at `examples/starter-reaction-pack`; `README.txt` and the third-party licence files. *It contains no model weights, voice files or avatar model*: `aivtuber-setup local` fetches them, each verified against its pinned SHA-256.

*You need:*

* Windows 11 x64 or Linux x64, about 6 GB of free disk (the language model alone is 2.4 GiB), and a network connection for the first run only.
* FFmpeg with `ffplay` and `ffmpeg` on `PATH`. Windows: `winget install Gyan.FFmpeg`, then open a new terminal. Linux: `sudo apt install ffmpeg`. (`ffplay` plays the voice; `ffmpeg` encodes the starter reaction audio. Setup warns, and tells you the command, if either is missing.)
* A browser (Chrome or Edge), or OBS Studio with a Browser Source, to show the avatar.
* A GPU with a Vulkan driver is optional. Without one the language model runs on the CPU and the measurements in <<measured>> do not apply.

=== The steps

1. Download the archive for your platform and `SHA256SUMS` from the Releases page.
2. Verify the archive *before* unpacking it.
+
Windows (PowerShell), run in the download folder:
+
[source,powershell]
----
$name = "aivtuber-local-<version>-windows-x64.zip"
$want = (Select-String -Path .\SHA256SUMS -Pattern ([regex]::Escape($name))).Line.Split(" ")[0]
$got  = (Get-FileHash ".\$name" -Algorithm SHA256).Hash
if ($got -ieq $want) { "checksum OK" } else { "CHECKSUM MISMATCH: do not unpack or run this file" }
----
+
Linux:
+
[source,sh]
----
sha256sum -c SHA256SUMS --ignore-missing     # must print: aivtuber-local-<version>-linux-x64.tar.gz: OK
----
3. Unpack and work from the unpacked directory: `Expand-Archive .\<archive>.zip .` then `cd` into the new folder (Windows), or `tar -xzf <archive>.tar.gz` then `cd` (Linux). Choose a location whose path has no spaces (the speech sidecar's arguments are split on whitespace).
4. Optional: see the plan without any network or file change.
+
[source,sh]
----
./aivtuber-setup local --dry-run        # Windows: .\aivtuber-setup.exe local --dry-run
----
5. Run the setup once. It downloads about 2.8 GB, so it takes a while on a slow line, and it can be interrupted and run again: a finished file is kept, a half-finished one resumes.
+
[source,sh]
----
./aivtuber-setup local                  # Windows: .\aivtuber-setup.exe local
----
6. Start everything. This runs llama-server on loopback, waits for it, then runs the app in the foreground; type chat lines in that terminal (or use the microphone), and Ctrl+C stops both.
+
[source,sh]
----
./aivtuber-setup start                  # Windows: .\aivtuber-setup.exe start
----
7. Open `http://127.0.0.1:8765` in the browser (or add it to OBS as a Browser Source). The first answer after start can take several seconds while the model loads.
8. Before you stream: replace the sample avatar (`renderer/local-avatar/dist/model.vrm`) with a model you have the right to broadcast, and put the disclosures that setup printed (section 8) where viewers see them.

=== What `aivtuber-setup local` does

Each step is skipped if its result is already on disk and matches its pin, so the command is safe to re-run after a failure or to repair a damaged file.

. Checks `ffplay`, `ffmpeg` and a Vulkan loader. A missing one is a warning with the fix, never a failure; run the command again after you fix it. With Vulkan present it fetches the GPU build of llama.cpp (`-ngl 99`), otherwise the CPU build.
. Downloads and verifies, into `local-assets/` beside the programs: llama.cpp `b12224`, the Qwen3-4B Q4_K_M model, the Silero VAD model, the ReazonSpeech k2-v2 int8 speech model, the Supertonic 3 int8 voice, and the sample VRM (placed at `renderer/local-avatar/dist/model.vrm` unless a file is already there). Every URL is HTTPS; every file has an exact pinned size and SHA-256; a redirect to plain HTTP is refused; a mismatch deletes the partial file and stops. Archives are unpacked by the program itself with path-traversal and symbolic-link checks and size limits; there is no `tar`, `unzip` or script involved.
. Speaks the six starter reaction lines with the bundled `local-tts-sidecar` and encodes them with `ffmpeg` to `examples/starter-reaction-pack/audio/starter/`, with `PROVENANCE.json` (the same step as <<starter-audio>>).
. Writes `local-profile.env` (the variables of step 4 of this guide, with a fresh random pseudonym key and control secret) and never overwrites an existing one unless you pass `--force`. The file holds secrets: do not share it.
. Prints the licence and disclosure duties of what it fetched (the OpenRAIL-M voice disclosure, the ReazonSpeech provenance note, the avatar's licence) and the exact start command.

[cols="2,5",options="header"]
|===
|Option |Meaning
|`--dry-run` |Print the plan, the duties and the start command. No network, nothing written.
|`--offline` |No network. Verifies what is on disk, makes the starter audio, writes the env file. Fails and lists what is missing.
|`--force` |Replace an existing `local-profile.env` (new secrets).
|`--llama-flavor vulkan\|cpu` |Override the GPU detection.
|`--skip llama,llm,vad,stt,tts,avatar,audio` |Leave steps out (a model you already have, for example).
|`--assets DIR` |Where the downloads go (default `local-assets` beside the programs; no spaces in the path).
|`--env-file FILE`, `--root DIR`, `--llama-port N` |Env file location, the unpacked directory, the llama-server port (default 18080).
|===

`aivtuber-setup start --env-file FILE --dry-run` prints the llama-server and app commands it would run. The same pins are in one file, `packaging/local-profile-pins.json`, which the setup binary embeds and `scripts/fetch-local-profile.mjs` (the source-build path) reads, so the two can not drift (`docs/supply-chain.adoc` section 11).

=== If something goes wrong

[cols="2,4",options="header"]
|===
|Message |Fix
|`sha256 mismatch` |The download was corrupted or the upstream file changed. Run the command again (a bad partial file is deleted); if it repeats, do not work around it: report it with the file name.
|`ffplay was not found` / `ffmpeg was not found` |Install FFmpeg as above, open a new terminal, run `aivtuber-setup local` again. Without `ffplay` nothing is audible; without `ffmpeg` the cached reactions have no audio.
|`no Vulkan loader was found` |It runs on the CPU. Update the GPU driver (Windows) or install `libvulkan1` and a Vulkan driver (Linux), then `aivtuber-setup local --llama-flavor vulkan`.
|`port 18080 is already in use` |Another program listens there. Stop it, or change `AIVTUBER_SETUP_LLAMA_PORT` and the port in `AIVTUBER_OPENAI_ENDPOINT` in `local-profile.env`.
|Windows SmartScreen "protected your PC" |The programs are not code-signed. The checksum in step 2 is how you know the file is the one the release built.
|`does not look like an extracted release archive` |Run `aivtuber-setup` from the unpacked folder, or pass `--root`.
|===

*Known limitations of the archives:*

* *Not code-signed.* The Windows programs are unsigned; macOS is not built. Code signing and installers are a later decision (#294), not part of these archives.
* The Linux programs need the system libraries `libasound2` (microphone) and `libssl3` (Twitch chat), and a glibc at least as new as the build host's (Ubuntu 22.04).
* Each archive is smoke-tested in CI on the platform it was built for: every program starts, the sidecars verify the bundled libraries and refuse an unpinned model directory, and `aivtuber-setup` prints its plan offline and refuses `--offline` with nothing fetched. *The full path from a downloaded archive to a spoken reply on a clean Windows machine has not been run end to end by CI*: the setup steps were run against the real hosts from a development machine (downloads, extraction, starter audio), and a clean-machine run is the remaining #294 check.
* The licence and disclosure duties of section 8 apply unchanged. The archive's `THIRD-PARTY-*` files cover only what it contains.

== 1. Fetch the pinned assets (network needed once)

(Source-build path; a release archive uses `aivtuber-setup local` instead, which reads the same pins.) `scripts/fetch-local-profile.mjs` downloads and SHA-256-verifies everything and extracts it under one directory. Every pin (URL, SHA-256, exact size) is read from `packaging/local-profile-pins.json`, the single source shared with `aivtuber-setup local`; the script *calls* `scripts/fetch-sherpa-onnx.mjs` (engine libraries, STT model, TTS model) and `renderer/local-avatar/smoke/fetch-model.mjs` (sample VRM), which read the same file, so no digest is kept twice. A mismatch deletes the partial file and stops.

[source,sh]
----
node scripts/fetch-local-profile.mjs /path/to/local-assets          # Windows default: the Vulkan llama.cpp build
node scripts/fetch-local-profile.mjs /path/to/local-assets --llama-flavor cpu   # Linux default: CPU build; Vulkan build: --llama-flavor vulkan
----

The last lines print the absolute paths the next steps use (`LLAMA_SERVER`, `LLM_GGUF`, `VAD_MODEL`, `SHERPA_ONNX_ARCHIVE_DIR`, `STT_MODEL_DIR`, `TTS_MODEL_DIR`, `AVATAR_VRM`). `--skip llama,llm,vad,sherpa-lib,stt,tts,avatar` omits steps you already have. Re-running is cheap: files that already match their pin are kept.

On Windows the script extracts with the system `tar.exe`; an earlier GNU `tar` on `PATH` (Git Bash) cannot read zip files and reads `I:\path` as a remote host, which is why it does not use whatever `tar` is first.

If you prefer the individual steps, they are `node scripts/fetch-sherpa-onnx.mjs lib|model ...` (see its header), `node renderer/local-avatar/smoke/fetch-model.mjs`, and the downloads recorded in `docs/provider-conformance.adoc` (llama.cpp, GGUF) and `docs/production-runtime.adoc` (Silero VAD).

=== Replace the sample avatar

The sample VRM is a pixiv test model for checking the pipeline. Before you stream, use a model you have the right to broadcast (see `docs/vts-obs-adapters.adoc`, "Model and rights"). Copy it to `renderer/local-avatar/dist/model.vrm` in step 2.

== 2. Build

[source,sh]
----
export SHERPA_ONNX_ARCHIVE_DIR=/path/to/local-assets/sherpa-lib     # mandatory: without it the crate downloads unchecked binaries
cargo build --release --locked -p aivtuber-adapters \
  --features silero-vad,mic-capture,sherpa-stt,sherpa-tts \
  --bin speech-vad-sidecar --bin speech-stt-worker --bin local-tts-sidecar
cargo build --release --locked -p aivtuber-app --bin aivtuber-app

cd renderer/local-avatar
bun install --frozen-lockfile --ignore-scripts
bun run build                                   # writes renderer/local-avatar/dist
cp /path/to/local-assets/avatar/VRM1_Constraint_Twist_Sample.vrm dist/model.vrm
cd ../..
----

PowerShell: `$env:SHERPA_ONNX_ARCHIVE_DIR = "D:\local-assets\sherpa-lib"`, and `Copy-Item` for the model. `--locked` is required by the repository (do not refresh `Cargo.lock`). Cold release builds took about 4 minutes (the speech features) plus 1 minute (the app) on the measured host.

The default workspace build compiles none of the speech features and needs no model. The binaries land in `target/release/`. On Windows the `sherpa-onnx` and `onnxruntime` DLLs are placed beside the sidecar executables by the build; the sidecars check them against their SHA-256 pins at every start and refuse to run if they do not match. On Linux the sidecars are linked with `$ORIGIN` rpath, so the libraries must stay beside them.

`mic-capture` is only needed for a live microphone. Leave it out if you will feed a WAV file.

== 3. Start llama-server on loopback

[source,sh]
----
/path/to/local-assets/llama/bin/llama-server -m /path/to/local-assets/llm/Qwen3-4B-Instruct-2507-Q4_K_M.gguf \
  --host 127.0.0.1 --port 18080 --alias qwen3-4b-instruct-2507 -c 4096 -ngl 99
----

`--host 127.0.0.1` is the point: llama-server defaults to loopback, and the app refuses any other endpoint in the local profile. `-ngl 99` offloads every layer to the GPU (Vulkan on Windows, or `--llama-flavor vulkan` on Linux); drop it on a CPU-only build. The port is your choice (8080 was in use on the measured host, so 18080 is used here). Wait until `curl http://127.0.0.1:18080/health` answers. The first request after start can take several seconds (model load, shader compile); later ones are sub-second to first token.

llama-server prints a warning that no API key is set and that CORS allows all origins. Both are acceptable *only because the listener is loopback*. Do not bind it to another address; if you must serve other machines, that is a different (non-local) deployment that this profile will refuse.

== 4. Configure and start the app

The app is configured entirely by environment variables. The block below is the complete set for the full local path. It contains no key: there is none to set.

[source,sh]
----
# profile and Thinking (llama-server)
export AIVTUBER_MODE=local
export AIVTUBER_GENERATIVE_ENABLED=true
export AIVTUBER_OPENAI_AUTH=unauthenticated-loopback          # explicit; allowed for a loopback endpoint only; no key may be set
export AIVTUBER_OPENAI_ENDPOINT=http://127.0.0.1:18080/v1/responses
export AIVTUBER_OPENAI_MODEL=qwen3-4b-instruct-2507           # must equal --alias
export AIVTUBER_OPENAI_MODEL_VERSION=Q4_K_M
export AIVTUBER_OPENAI_BACKEND_NAME=llama-server
export AIVTUBER_OPENAI_MAX_OUTPUT_TOKENS=96                   # see "Reply length" below

# required by every profile
export AIVTUBER_MEMORY_PSEUDONYM_KEY_HEX=<64 hex characters>  # e.g. openssl rand -hex 32; keep it local
export AIVTUBER_CONTROL_SECRET=<exactly 32 characters>        # the avatar/operator authority; never commit it

# pack, audio
export AIVTUBER_PACK_ROOT=/path/to/your/pack-copy             # a directory you own: cp -r examples/starter-reaction-pack ...
export AIVTUBER_AUDIO_ROOT=/path/to/audio                     # must exist; generated/ is created below it

# local TTS (supervised child)
export AIVTUBER_TTS_ENDPOINT=http://127.0.0.1:8770/v1/synthesize
export AIVTUBER_TTS_SIDECAR=target/release/local-tts-sidecar
export AIVTUBER_TTS_SIDECAR_MODEL_DIR=/path/to/local-assets/supertonic/sherpa-onnx-supertonic-3-tts-int8-2026-05-11
export AIVTUBER_TTS_SIDECAR_AMPLITUDE_VISEMES=true            # mouth movement from the audio envelope

# speech input (supervised children): live microphone
export AIVTUBER_SPEECH_SIDECAR=target/release/speech-vad-sidecar
export AIVTUBER_SPEECH_SIDECAR_ARGS="--model /path/to/local-assets/vad/silero_vad_op18_ifless.onnx --language ja"
export AIVTUBER_SPEECH_STT_WORKER=target/release/speech-stt-worker
export AIVTUBER_SPEECH_STT_MODEL_DIR=/path/to/local-assets/k2v2
export AIVTUBER_SPEECH_CONVERSATION=true
export AIVTUBER_SPEECH_FLOOR=true
export AIVTUBER_SPEECH_BARGE_IN=true

# local avatar
export AIVTUBER_AVATAR_OUTPUT=local
export AIVTUBER_LOCAL_AVATAR_PORT=8765
export AIVTUBER_LOCAL_AVATAR_PAGE_DIR=renderer/local-avatar/dist

# untrusted-input ceiling (recommended for anything that takes public text)
export AIVTUBER_INGRESS_MAX_TRUST=untrusted
export AIVTUBER_INGRESS_SOURCE_CLASSES=public_chat,speech

cargo run --release --locked -p aivtuber-app --bin aivtuber-app
----

Notes that matter:

* *Paths with spaces* are not supported in `AIVTUBER_SPEECH_SIDECAR_ARGS` (split on whitespace). Use a path without spaces.
* *No microphone yet?* Add `--input-wav FILE.wav --pace realtime --stt-wait-ready-ms 90000` to `AIVTUBER_SPEECH_SIDECAR_ARGS` (a PCM WAV; the sidecar mixes down and resamples to 16 kHz mono, tests cover 48 kHz stereo; the last flag makes it wait for the STT model before reading the file, so the first clip is not skipped). It goes through the same VAD, STT, floor and routing as the microphone; there is no shortcut around the untrusted ingress. When the file ends the sidecar exits and the app logs `speech_sidecar: degraded: sidecar exited` and carries on with typed chat. For a microphone, use `--list-devices` to see names and `--input-device NAME`.
* *Do not set* `AIVTUBER_VOICE_MODEL` unless you also have cached assets for that voice. It names the voice the cached pack was authored for (default `example-voice-v1`); a different name makes every cached descriptor that names a voice incompatible and cached reactions find nothing. The app warns about this at start (`pack_readiness: WARNING ... voice_model_mismatch=N`, naming the voice the descriptors expect and the one configured). The synthesizer's own identity is recorded separately in the provenance (`model_alias=supertonic-3-int8`).
* *Floor and barge-in.* `AIVTUBER_SPEECH_FLOOR` requires `AIVTUBER_SPEECH_CONVERSATION`; `AIVTUBER_SPEECH_BARGE_IN` requires the floor. With the floor on, a spoken turn is answered only after the speaker has been silent for 800 ms (`AIVTUBER_SPEECH_FLOOR_TAKE_TURN_SILENCE_MS`, 700 to 1000). A user who speaks over the avatar for 400 ms stops the playing reply (`speech_barge_in:` log line).
* *Reply length.* Left at its default the model may write several hundred characters, which is over 30 seconds of speech and can exceed the TTS sidecar's 12 s synthesis deadline (`local-tts-sidecar: deadline_exceeded`; the reply degrades to a non-verbal reaction). `AIVTUBER_OPENAI_MAX_OUTPUT_TOKENS=96` kept replies to 5 to 15 seconds of audio on the measured host.
* *English brand words (#222).* A starter lexicon reads `YouTube`, `Twitch`, `VTuber`, `OBS`, `Discord`, `AI` and about forty similar words as katakana before the voice sees them, and the chat window still shows the original spelling. To add your persona's words or fix a reading, write a file in the format of `docs/production-runtime.adoc` ("Text that is not spoken, and how words are read") and set `export AIVTUBER_SPEECH_LEXICON=/path/to/my-lexicon.json` (it is merged over the starter list; `AIVTUBER_SPEECH_LEXICON_DEFAULTS=false` turns the starter list off). The app refuses to start if the file is invalid, and prints `speech lexicon: ...` at start. The log line `speech_projection: ... projection_passthrough_latin=N` counts English words that went to the voice as written; those are the ones worth adding.
* *Phrase mode (default for this profile).* A reply is split into phrases and each is gated, synthesized and committed on its own, so the first phrase plays while the second is synthesized and the 12 s synthesis deadline applies to one phrase, not to the whole reply (#83 S1; <<phrase-mode>>). `AIVTUBER_PHRASE_MODE=buffered` returns to one commit per reply; `AIVTUBER_PHRASE_TTS_TIMEOUT_MS` (default 12000) bounds one phrase. The log shows `generated replies: phrase mode` at startup and one `phrase_response` line per reply.
* *Token streaming (opt-in, #83 S2).* `AIVTUBER_THINKING_STREAM=on` streams the Thinking reply and starts speaking phrase 1 before the model has finished; see docs/production-runtime.adoc for the bounds and the differences from buffered phrase mode. It stays off by default until it has been measured against a real llama-server; against a stub it cut first audio from 634 ms to 387 ms at a 25 ms-per-delta cadence.
* *Cached starter audio.* `examples/starter-reaction-pack` carries descriptors but no audio files (`audio://starter/*.opus`); the cached path plays whatever is under `$AIVTUBER_AUDIO_ROOT/starter/`. Generate them once with the sidecar you built, as described in <<starter-audio>> (one command). Without them an `intent` event is accepted and scheduled but nothing is audible, and the app says so at start (`pack_readiness: WARNING ...`).
* *Cached reactions and the avatar profile.* The pack targets `AIVTUBER_AVATAR_PROFILE` (default `example-live2d-v1`). The local renderer accepts the same commands, so the default works unchanged.

On start the app prints, among others (nothing secret): the OpenRAIL-M voice notice, `tts_sidecar: ready ...`, `thinking: endpoint=http://127.0.0.1:18080 auth=unauthenticated-loopback backend=llama-server`, `composition profile: profile=local ... fallback=deterministic_local`, `aivtuber-app ready: indexed=8 usable=8 preloaded=8`, the floor, barge-in and conversation lines, `speech_sidecar: started`, `speech-stt-worker: ready`, and `local avatar renderer URL ...`.

[[starter-audio]]
=== Starter reaction audio (once, after the build)

The starter pack is descriptors only. (A release archive does this inside `aivtuber-setup local`; the command below is the source-build equivalent and writes the same files.) This one command speaks each descriptor's `speech.text` with the sidecar you just built (the pinned Supertonic 3 int8 model, language `ja`, the text-derived seed of `speech_tts::text_seed`, speaker 0) and encodes the result to the `audio://starter/*.opus` files the descriptors name. It needs `ffmpeg` with libopus (the same FFmpeg that provides `ffplay`).

[source,sh]
----
node scripts/synthesize-starter-audio.mjs \
  --sidecar target/release/local-tts-sidecar \
  --model-dir /path/to/local-assets/supertonic/sherpa-onnx-supertonic-3-tts-int8-2026-05-11
----

It writes six Opus files and `PROVENANCE.json` under `<pack>/audio/starter/` (the app's default audio root, ignored by the repository; pass `--audio-root DIR` and export the same `AIVTUBER_AUDIO_ROOT` to put them elsewhere). The provenance records the model alias and bundle digest, speaker, the seed rule, the SHA-256 of every WAV and Opus file, and the OpenRAIL-M notice; it holds no timestamp, so the same model bundle and FFmpeg build reproduce it byte for byte. `reaction.neutral` is speechless and needs no file. The voice identity is unchanged: descriptors expect `example-voice-v1`, which is the default `AIVTUBER_VOICE_MODEL`, so leave that variable unset and the next start reports no `pack_readiness` warning.

Decision (#289): the audio is generated on the operator's machine, not committed. The weights are OpenRAIL-M and this project does not redistribute them or audio made with them, generated media is never committed here, and the step reuses the pinned sidecar so the voice is exactly the one used for replies. The disclosure duty in section 8 applies to this audio when you broadcast it.

=== Optional voice: VOICEVOX instead of Supertonic (issue #295)

Supertonic stays the default. If you prefer a VOICEVOX character voice, run the VOICEVOX ENGINE yourself and let the app talk to it through a built-in loopback bridge. The engine is a separate program (LGPL-3.0, or a separate licence from its authors): this repository neither links nor bundles it, and the release archives do not contain it.

. Download and start the engine from https://voicevox.hiroshiba.jp/ (or https://github.com/VOICEVOX/voicevox_engine) so that it listens on loopback, normally `http://127.0.0.1:50021`.
. Pick a speaker id. `curl http://127.0.0.1:50021/speakers` lists every character and its styles; the `id` of the style you want is the value to use. *There is no default character*, and the app refuses to start without one.
. Read the terms of the character you chose (see <<voicevox-terms>>) and decide what credit line you must show.
. Replace the `# local TTS (supervised child)` block of step 4 with:

[source,sh]
----
export AIVTUBER_TTS_BACKEND=voicevox
export AIVTUBER_VOICEVOX_ENDPOINT=http://127.0.0.1:50021    # loopback http:// origin only
export AIVTUBER_VOICEVOX_SPEAKER=3                          # the style id from /speakers: required, no default
export AIVTUBER_VOICEVOX_CREDIT="VOICEVOX:ずんだもん"        # required: the credit line your character's terms ask for
# optional
export AIVTUBER_VOICEVOX_TIMEOUT_MS=12000                   # total budget for one synthesis (default 12000)
export AIVTUBER_VOICEVOX_AMPLITUDE_VISEMES=true             # mouth movement from the audio envelope (default off)
----

Do not set `AIVTUBER_TTS_ENDPOINT` or `AIVTUBER_TTS_SIDECAR` with it (the app says so and stops). The app starts a bridge on an ephemeral loopback port inside its own process, and the existing TTS adapter talks to that: the bridge turns each request into `POST /audio_query` and then `POST /synthesis` on the engine, writes the WAV under `AIVTUBER_AUDIO_ROOT/generated/`, and answers with the same contract the Supertonic sidecar uses. At start it logs the engine origin, the speaker, the credit line and a terms notice (the spoken text is never logged). The engine does not have to be running at that moment: a synthesis that cannot reach it, gets a non-2xx answer or exceeds the timeout fails like any TTS failure, and the viewer sees the non-verbal reaction (#291) while the performer carries on. Phrase mode (#83) works unchanged: each phrase is one bridge call. The same text projection as for Supertonic runs first, so URLs and emoji are never sent to the engine (ADR-0004 D-5).

[#voicevox-terms]
==== VOICEVOX terms and credit (yours to follow)

* The VOICEVOX software terms: https://voicevox.hiroshiba.jp/term/ . They require a credit line showing VOICEVOX was used, and require you to pass the terms on to anyone you give the audio to.
* *Every character has its own terms and credit line*, in the form `VOICEVOX:<character name>` (for example `VOICEVOX:ずんだもん`). Some characters are non-commercial, or need prior confirmation or individual contact for commercial or corporate use. Each character's page (linked from the VOICEVOX site and from the engine's `/speakers` data) is the authority; EXP-0003 section 3.2 summarises the ones it read, and that summary can be out of date.
* The runtime cannot show the credit on your stream. Put the configured line where viewers see it (stream description or an overlay text), and keep the AI-generated-voice disclosure as well.
* Whether an AI persona with her own identity should speak with a third-party mascot's voice is a product decision. The project ships no default for it.

==== What is deterministic

EXP-0003 synthesized the same text repeatedly with one engine build (0.26.1, CPU), one character and default parameters, and got byte-identical audio in 50 of 50 replies, in one process and across processes. VOICEVOX has no seed. Treat this as an observation of that build, not a guarantee: another engine version, voice library, hardware backend or parameter can change the audio. The bridge's audio cache is keyed by the text and the speaker id, not by the engine version, so delete `AIVTUBER_AUDIO_ROOT/generated/` after you upgrade the engine or its voice libraries. The bridge never changes the engine's speed, pitch or intonation parameters (it only makes the output mono).

=== Optional: let her see the game (screen perception, issue #90)

Off by default, and not for every machine. The "perception profile" runs one `llama-server` with a multimodal model (Qwen3-VL-4B-Instruct Q4_K_M and its projector) that serves both the Thinking replies and one short screen caption every 10 seconds. **It needs about 12 GB of VRAM** for the whole local stack (model, renderer, speech sidecars, desktop). On an 8 GB card the measurements (EXP-0004c) showed a run that fit and an identical run that spilled into system memory, with captions taking 12 s and speech getting slower; that card class stays on structured telemetry only. If you try it anyway, the app measures this for you: a latency probe at start and every minute suspends perception, and `aivtuberctl status` says why, instead of letting the stream stutter.

. Start the multimodal server instead of the default model (loopback only, two slots so a caption never blocks a reply):
+
[source,sh]
----
llama-server -m Qwen3VL-4B-Instruct-Q4_K_M.gguf --mmproj mmproj-Qwen3VL-4B-Instruct-Q8_0.gguf \
  --host 127.0.0.1 --port 8081 --parallel 2 -c 8192 -ngl 99
----
. In OBS, note the exact name of the one source to read (for example your game capture) and enable obs-websocket on `127.0.0.1` with a password.
. Add to the app's environment (`AIVTUBER_MODE=local` is required; everything stays on loopback):
+
[source,sh]
----
AIVTUBER_PERCEPTION=true
AIVTUBER_PERCEPTION_OBS_SOURCE="Game Capture"
AIVTUBER_PERCEPTION_VLM_ENDPOINT=http://127.0.0.1:8081/v1/chat/completions
AIVTUBER_OBS_PASSWORD=...        # your obs-websocket password
----
. Start the app, then turn it on from the console: `aivtuberctl perception-on` (and `aivtuberctl perception-off` to stop it; it takes effect before the next capture). `aivtuberctl status` shows `status` (`off`, `probing`, `active`, `suspended`), why it was suspended, and how often a capture waited for Thinking or speech.

What you should know before enabling it:

* Frames are read from OBS (downscaled by OBS to 768x432), held in memory for one model call and discarded. Nothing is written to disk or to the log, and nothing leaves the machine.
* The caption is untrusted text the model read off your screen. URLs and credential-looking strings are removed, it is at most 240 bytes, and it is only ever offered to Thinking inside a delimited "untrusted" slot. In this release the caption is collected and bounded but not yet given to Thinking (ADR-0007 S2), so enabling perception does not change what she says yet.
* She does not capture while she is thinking, speaking, or hearing you speak, and never more often than every 5 seconds (default 10).
* A native Japanese read of the captions and a run on a 12 GB card are still manual checks; treat it as experimental.
* Not covered by this quickstart: webcam capture (out of scope), per-window capture (one OBS source only).

== 5. Open the avatar, then talk to it

*Avatar.* Copy the `local avatar renderer URL` from the app's stderr (`http://127.0.0.1:8765/?token=...`) into a browser, or into an OBS Browser Source (width and height of your canvas, "Shutdown source when not visible" off). The URL carries a per-launch secret: do not paste it into issues or shared logs. The token changes on every start. A missing or broken `model.vrm` shows as `disconnected` and the reason is in the page's console. See `docs/vts-obs-adapters.adoc` section 6 for OBS and for the security properties.

*Typed chat* is one Event Envelope per line on the app's stdin. For example:

[source,json]
----
{"schema_version":"0.2.0","event_id":"evt-1","correlation_id":"corr-1","sequence":1,"observed_at":"2026-11-10T12:00:00Z","source":"local-smoke","source_class":"public_chat","plane":"content","trust_level":"untrusted","kind":"chat.message","actor_id":"viewer:1","priority_hint":null,"payload":{"text":"こんにちは！今日は何をして遊ぶ？"}}
----

Free text (no `intent`) goes to the local Thinking engine; `"intent":"reaction.agree"` in the payload takes the cached path. Use a fresh `event_id` and a rising `sequence` per line. Text must be UTF-8: on Windows, pipe from a program that writes UTF-8 (a PowerShell 5 pipe re-encodes it and llama-server rejects it as `ill-formed UTF-8`; PowerShell 7 or a Node/Python writer is fine). When stdin closes the app shuts down and its supervised children exit with it.

For a real stream, put chat in front of it with `twitch-chat-ingress` (`docs/production-runtime.adoc`, "Twitch chat sidecar"); it is anonymous and read-only, and a Twitch connection is of course a remote connection, so it is outside the "no network" check below.

*Speech.* Speak into the microphone, or use `--input-wav`. Expect, in the log, `speech_conversation: final chars=N final_age_ms=...` when the app has a transcript and the floor lets the turn through, then `local-tts-sidecar: ok chars=N audio_ms=...`, and the avatar's mouth moving while `ffplay` plays the reply.

*Emergency stop.* `aivtuberctl` stops or mutes through the authenticated operator endpoint independent of every model path (`docs/production-runtime.adoc`, "Operator control").

== 6. Verify that nothing leaves the machine

Do this while the system is running and a reply has been spoken, so every process has opened its sockets.

[source,powershell]
----
# Windows: every socket of the runtime's processes that is not loopback (expected output: nothing)
$p = (Get-Process aivtuber-app, llama-server, speech-vad-sidecar, speech-stt-worker, local-tts-sidecar -ErrorAction SilentlyContinue).Id
Get-NetTCPConnection | Where-Object { $p -contains $_.OwningProcess -and $_.State -ne 'Bound' } |
  Where-Object { $_.RemoteAddress -notin '127.0.0.1', '::1', '0.0.0.0', '::' -or $_.LocalAddress -notin '127.0.0.1', '::1' }
Get-NetUDPEndpoint | Where-Object { $p -contains $_.OwningProcess }      # expected: nothing (these processes use no UDP)
----

[source,sh]
----
# Linux: sockets of the runtime's processes; every Local/Peer address must be 127.0.0.1 or [::1]
ss -tanpH | grep -E 'aivtuber-app|llama-server|speech-vad|speech-stt|local-tts'
ss -uanpH | grep -E 'aivtuber-app|llama-server|speech-vad|speech-stt|local-tts'     # expected: nothing
----

Expected: listeners on `127.0.0.1` only (llama-server 18080, the TTS sidecar 8770, the avatar host 8765, and the app's connections between them). On Windows the app also shows `Bound` rows with local address `0.0.0.0` and no peer; they are not listeners and not connections, and the check above excludes them (a `Listen` row on a non-loopback address would still be reported).

*The browser is not part of the runtime.* A general-purpose browser makes its own background connections to its vendor even when headless. In the measured runs an unrestricted Edge held connections to remote addresses while showing the avatar page, and Edge kept one of them even with a proxy flag; the avatar page itself requested only `http://127.0.0.1:8765` and same-origin `blob:` URLs (its CSP is `default-src 'self'`). A Chromium started with `--proxy-server=http://127.0.0.1:9 --proxy-bypass-list="127.0.0.1;localhost"` (a proxy that goes nowhere) held no external socket at all; OBS Browser Source was not checked; or disconnect the network. All of these were observed and are recorded in <<measured>>. The PowerShell check above was validated with a negative control: a throwaway Node listener on `0.0.0.0` is reported by it.

*The profile refuses remote endpoints.* A non-loopback Thinking or TTS endpoint, or a missing authentication choice for a remote Thinking endpoint, stops the app at start-up before any connection is made (checked on the measured build):

[source,text]
----
profile "local" is loopback-only but the thinking endpoint is not a loopback address; point it at 127.0.0.1/[::1]/localhost or select the "full" profile
profile "local" is loopback-only but the tts endpoint is not a loopback address; point it at 127.0.0.1/[::1]/localhost or select the "full" profile
Authentication: Thinking endpoint requires an API key; set AIVTUBER_OPENAI_API_KEY, or explicitly set AIVTUBER_OPENAI_AUTH=unauthenticated-loopback for a loopback-only endpoint
----

For the strongest check, disconnect the machine from the network (or block outbound traffic with your own firewall rule) *after* step 1 and run the whole path. This guide did not change any firewall or network setting; the evidence above is observation of sockets, not a deny rule.

== 10. Measured on one host

Date 2026-11, issue #220 S3. One Windows 11 desktop that was also running other desktop software (system CPU was about 30% and the GPU about 35% busy with none of these processes working, so every figure below includes background load; this is not a quiet-machine benchmark). CPU: an 8-core, 16-thread 3.6 GHz-class part from 2019; 32 GB RAM; an 8 GB discrete GPU from 2019; Windows 11 x64. Release builds of the commit that carries this page; llama.cpp `b12224` Vulkan with every layer on the GPU and a 4096-token context; STT and TTS on 4 CPU threads each; `ffplay` for audio; the renderer page in headless Chromium 153 (1280 by 720, WebGL on the GPU through Direct3D 11) showing the sample VRM. All of the processes of section 4 were running at once for the whole run, with the floor and barge-in on.

*Input.* Spoken input: 10 Common Voice ja clips (the EXP-0002 sample of `examples/benchmarks/stt`: seeded, CC0, 16 kHz mono, trimmed to the voiced part, 2.6 to 7.8 s), concatenated with 14 s of silence between them and fed through the sidecar's `--input-wav ... --pace realtime`, which is the same VAD, STT, floor and routing path as a microphone. A live microphone was not used. Typed chat: 8 envelopes on stdin (5 during the silent lead-in of the speech file, 3 after it ended, for the failure rows). The harness (a Node driver, a 1 Hz PowerShell sampler and a log analysis script, written for this run) is not in the repository.

*What was measured.* End of speech is the end of the VAD segment (the covered audio of the final minus the 500 ms segment tail; the clip schedule gave the same figures to within 0.2 s). Player started is the moment the app launched the audio player process (a small shim logged it and then ran `ffplay` unchanged); the sound itself starts a little after that (process start and device open), which was not measured.

Run 2 (Edge) had one 3-second dip to 19 to 22 fps with nothing attributable in the process samples; it did not recur in runs 1, 3 and 4. The avatar host sent 854 sequenced commands in run 4 and the page reported no error; the mouth opened (`aa` up to 0.77) during speech and expressions followed the generated reply.

=== Phrase mode against buffered mode (#83 S1)

Date 2026-11, issue #83 S1, the same host as above but a *debug* build of the app and a *stubbed Thinking endpoint*. No llama-server binary was available on the machine and none was downloaded, so Thinking was a loopback stub that returns a fixed hand-written Japanese reply after a fixed 0.6 s (the LLM time measured in run 4); it is the same in both modes and cancels out of the comparison. Everything else was real: the app, the supervised `local-tts-sidecar` (Supertonic 3 int8, `AIVTUBER_TTS_SIDECAR_AMPLITUDE_VISEMES=true`), the scheduler and `ffplay` (run at volume 0 through a logging shim; the player started time is the shim's START line). Typed events, so there is no floor wait and no STT. The ten replies are 40 to 60 characters, three sentences each (5 to 10 s of speech), typical of a 96-token reply. One event every 26 s, ten events per mode, buffered first, then `AIVTUBER_PHRASE_MODE=phrase`. The driver and the stub are not in the repository.

The first phrase starts about 1.0 s earlier at the median (41 percent), which is the whole-reply TTS time minus the first phrase's TTS time. Completion is not worse (it is a little earlier, the first phrase starts earlier and the per-phrase synthesis stays ahead of playback). Between consecutive phrase clips the player start times were within -24 to +14 ms of the previous clip's audio duration (19 pairs), so phrases are chained to within the process start jitter of `ffplay`; an acoustic gap measurement was not made (no loopback capture), only this timing.

*Long replies.* A 317 character reply: buffered first audio 11.6 s (the sidecar needed 11.0 s of its 12 s deadline), phrase mode 1.6 s. A 458 character reply: buffered hit `local-tts-sidecar: deadline_exceeded chars=458` after 12.6 s and nothing was spoken; phrase mode started speaking after 1.6 s and committed all 16 phrases (`end=Completed`). In that run the cap of 16 phrases merged a 141 character tail into the last phrase, whose 4.9 s synthesis could not hide behind the 2.7 s phrase before it, a single 2.2 s gap (`underruns=1 max_gap_ms=2241`); the default cap is now 32 phrases. A newer event arriving while a long reply was still being spoken ended the first reply after 12 of its 15 phrases (`end=Partial { cause: Superseded }`) with no later phrase committed.

Limits of this evidence: one host, a debug app build, ten replies written by hand, a stub for Thinking (so the real model's reply lengths and any markdown or line breaks are untested here), no microphone (so barge-in was covered by unit and app tests, not by a live run), and `ffplay` process playback, whose per-phrase start cost is hidden only because the player start times were chained from the logical clock.

=== Failure behaviour (run 4 and the first run)

* *llama-server stopped, then a free-text line (as first measured):* accepted, nothing spoken and no avatar command (`lastSeq` did not move) and no log line. That was a gap, closed by #288: the route now names `reaction.neutral`, the starter pack carries two speechless variants of it, and each failed Thinking call plays one on the avatar and prints a `generation_fallback:` line. The behaviour is pinned by tests against a fake loopback Thinking server (timeout, refused connection, invalid and empty output, a refused reply); it has not been re-measured against a real llama-server. The app and avatar kept running.
* *Then a cached `intent` line, with llama-server dead:* played 0.14 s after the event.
* *TTS sidecar killed, then a cached `intent` line:* `tts_sidecar: exited; speech degrades to non-verbal reactions ...` was logged and the cached reaction played 0.11 s after the event.
* *Barge-in:* in every run two replies were still playing when the next clip began (the replies are long); each was stopped by the confirmed barge-in, 0.39 to 0.55 ms (8 events in 4 runs) from the decision to the stop command, `HardStopped` (the `ffplay` process is killed), the avatar reset, and the new turn was answered.
* *A reply of 396 characters* (run 1, default cap) exceeded the sidecar's 12 s synthesis deadline (`deadline_exceeded`); the next request saw the engine still busy and was dropped. With the cap of 96 tokens it did not recur in three runs.
* *The WAV ended:* `speech_sidecar: degraded: sidecar exited`, then typed chat continued.
* *Shutdown:* closing stdin ended the app with exit code 0, and no runtime process survived it (checked in all four runs).
* *Not exercised live:* killing the VAD sidecar or the STT worker in the middle of a turn, a live microphone, OBS Browser Source, a Linux host, a CPU-only llama.cpp, and a machine with fewer than 16 threads. The supervisor tests cover the first.
