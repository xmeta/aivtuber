= Operational SLOs and Error Budgets (issue #71)
:toc: left
:toclevels: 2

Operational objectives for the running runtime, and the report that says
whether it met them.

This is a different question from link:performance-goals.adoc[Performance
Goals and Baselines], and conflating the two is how a proxy metric becomes a
target. #58's regression budget answers:

> Did this change materially worsen the current system?

An operational SLO answers:

> Is the current runtime delivering an acceptable level of service over a
> session / stream hour?

A change can improve relative performance while the product still misses its
operational objective, so the two contracts are separate types, separate
configuration, and separate reports. `benchmarks/budgets.json` is a per-PR
regression budget; `examples/slo/slo-targets.json` is an absolute operational
objective. Nothing reads both.

The indicator vocabulary itself lives in
`crates/telemetry/src/operational_slo.rs`, which owns the catalog, the window
model, attribution, and error budgets. This document owns the policy: what may
be counted, what may not, and what a target has to prove before it exists.

== The three properties the report cannot get wrong

=== Absence of evidence is never a pass

Every indicator result carries a status, and only `met` counts as a pass:

[cols="1,3",options="header"]
|===
|Status |Meaning

|`met`
|target met on at least the sample floor

|`missed`
|target missed on at least the sample floor

|`uncalibrated`
|measured, and no target exists yet. The observed value is published as
calibration evidence

|`no_data`
|the eligible denominator was empty. Not 0%, not 100%, not a pass

|`insufficient_samples`
|samples exist but fewer than the indicator's sample floor

|`not_yet_measured`
|the objective is declared, but the artifact does not carry the evidence to
reconstruct its denominator
|===

A run where nothing has been calibrated reports a verdict of `incomplete`,
which is deliberately not `ok`. This matters most for the indicators nobody has
targeted yet: an unmeasured objective must never be mistaken for a satisfied
one in a dashboard or a release checklist.

The report's own verdict is the aggregate of those statuses, and it is
deliberately hard to read as a pass:

[cols="1,3",options="header"]
|===
|Verdict |Meaning

|`ok`
|every objective was decided (or had legitimately nothing to say) and every
decided objective met its target

|`breach`
|at least one decided objective missed

|`incomplete`
|nothing breached, but at least one objective's evidence is still unresolved —
uncalibrated, under-sampled, or not measurable from this artifact

|`uncalibrated`
|nothing was decided and nothing is outstanding either
|===

`ok` requires the *whole* catalog to be resolved. One met objective while
`safety.stale_dispatch_count` is still `not_yet_measured` is `incomplete`, not
`ok`: otherwise a dashboard would read "every calibrated objective passed" as
"the runtime is operating within its objectives" at exactly the moment the
zero-tolerance evidence is missing.

Every status that is neither a decision nor a legitimate absence of data counts
as unresolved, and `SloStatus::is_unresolved()` lists them explicitly:
`uncalibrated`, `not_yet_measured` and `insufficient_samples`. The last one is
easy to forget and is the reason the list lives in one place — "fewer samples
than the floor" is not the same as "nothing outstanding", and treating it as
such would reopen the same hole this rule exists to close. `no_data` is *not*
outstanding: an objective with an empty denominator has said everything it can
say.

=== Zero-tolerance invariants are not SLOs

Security, authorization, and bounded-state objectives are not probabilistic.
A stale post-stop dispatch, an unauthorized privileged action, and a retention
bound violation have no allowable rate, so they carry no ratio target and no
error budget. `SloTargets::validate` refuses a target file that tries to give
one, and the report emits no `error_budgets` entry for an invariant even if one
somehow existed.

This is the same separation link:product-objectives.adoc[Product Objectives]
draws between hard guardrails and scoreable objectives, applied at the
configuration layer instead of only in prose.

=== A target must cite the measurement it came from

A target entry is a ratio plus a `baseline` block naming the artifact, value,
and represented stream hours it was calibrated from. A target without it is
rejected, and a target file whose `catalog_version` does not match the build
evaluating it is rejected too. The second rule matters more than it looks:
changing an indicator's numerator or denominator without bumping
`SLO_CATALOG_VERSION` would silently reinterpret every threshold ever written
against the previous definition.

The baseline itself is held to the same standard, because a target file is only
as trustworthy as the measurement it cites. `baseline.value` must be a finite
ratio in `[0, 1]`, `stream_hours` may not be `0`, and a `schema_version` that is
present must match the report contract this build emits. An impossible baseline
would not fail any later evaluation; it would simply be quoted forever as the
justification for the number.

The checked-in `examples/slo/slo-targets.json` therefore ships with an empty
`targets` map, and a test fails if a numeric target is added without its
evidence. That is the current honest state of the project, not an oversight.

=== One direction, stated once

`SloTarget::target` is always a **minimum conforming ratio**: `conforming /
eligible`, higher is better. Indicators are therefore named and described as the
conforming rate, not as a failure rate.

[cols="1,1",options="header"]
|===
|Indicator |Numerator

|`availability.event_to_first_visible_within_target`
|events whose first-visible latency was within the configured threshold

|`availability.event_to_first_audio_within_target`
|events whose first-audio latency was within the configured threshold

|`availability.speech_presence_rate`
|events that produced a user-visible output, or stayed silent for a declared
reason

|`reliability.fallback_delivery_rate`
|provider-failure events that still delivered a user-visible outcome

|`reliability.deadline_adherence_rate`
|deadline-bearing events whose deadline was not exhausted

|`reliability.generative_budget_admission_rate`
|events admitted into the generative budget rather than denied

|`quality.semantic_reuse_correctness`
|reviewed events labelled correct
|===

An earlier draft called three of these `*_rate` while their `numerator` text
described the failures, which made a target such as `0.99` ambiguous: the same
number meant "at most 1% bad" to the reader and "at least 99% good" to the
evaluator. One direction removes the ambiguity, and a test asserts that no
measured indicator publishes failure phrasing.

== Windows

Windowing is over the *logical* stream timeline. `EventObservation` records the
event's `stream_offset_ms` — its position on the workload timeline, relative to
the start of the evaluated run; nothing here reads the wall clock, so the same
fixture produces the same windows on a slower machine. That also keeps
replay-relevant reporting on the monotonic/logical ordering rule the rest of the
runtime already follows.

Two clocks exist in a replay, and conflating them is a trap:

* the *replay pacer*, which drives the runtime one virtual second per event so a
  benchmark finishes quickly;
* the *workload timeline*, which is the scenario's own declared phase timing.

`replay-benchmark --scenario` therefore carries each event's position on the
workload timeline through the fixture as `stream_offset_ms`, and records *that*
in the observation. A checked-in fixture that predates the field falls back to
the pacer. Without this, an 80-minute scenario collapses to roughly the event
count in seconds and the report silently under-reports how many stream hours it
stood for.

[cols="1,3",options="header"]
|===
|Window |Definition

|`session`
|one run of the runtime: one replay/scenario run, or one live operator
session

|`stream_hour`
|one represented stream hour, `[n * 3_600_000, (n + 1) * 3_600_000)` of
logical stream offset

|`rolling_stream_hours`
|consecutive stream hours, `--rolling-window-hours N` (default 3)
|===

The hour buckets partition the session: every retained observation falls in
exactly one, and the test that pins it asserts the buckets sum back to the
session count. The bucket count is derived from the workload's declared
duration as well as its last observation, so a run whose last event arrives
early still reports every stream hour it represented.

An artifact with no recorded offsets degrades to a single session window and
says so in `limitations` rather than inventing hour boundaries from the event
index. A run shorter than one stream hour reports one window and says *that*
instead. Those are different problems and the report distinguishes them.

Rolling windows only exist when the run is long enough to contain them. An
80-minute scenario produces rolling windows only at `--rolling-window-hours 1`,
which is exactly the situation a reader needs stated rather than smoothed over.

== Attribution: external failure vs runtime degradation

The runtime cannot guarantee an external provider's uptime. It can own the
quality of its own degradation. The report keeps those apart per miss:

[cols="1,3",options="header"]
|===
|Attribution |Meaning

|`external_provider`
|a provider was unavailable and the runtime still delivered a user-visible
outcome. The cached/non-verbal fallback did its job

|`runtime_handling`
|a provider was unavailable *and* the runtime produced no user-visible output.
This is the runtime's own failure

|`unattributed`
|a declared reason outside the known slug set, so the project cannot say whose
failure this was
|===

The split uses the closed `fallback_reason` slug set the runtime already emits.
`timeout`, `unavailable`, `rate_limited`, `overloaded` and `authentication` are
provider-side; `low_confidence`, `policy_override`, `operator_override`,
`budget_exhausted` and `invalid_request` are deliberate runtime decisions, which
the tally records separately as `runtime_policy_decisions` so nothing silently
disappears. Anything outside the set is counted as `unattributed`, not dropped
and not optimistically reclassified.

Attribution is scoped to the indicator's own denominator. Each indicator declares
one classifier that decides whether an event is outside its denominator, conforms,
misses, or is merely *unscored*, and the report uses that single definition for
the ratio, the miss set and the budget spend. An event outside an indicator's
denominator therefore cannot appear in its miss attribution: an unrelated
provider failure cannot be credited to
`reliability.deadline_adherence_rate` just because that event happened during
the same window. It is still attributed at the run level, where it belongs.

This is what lets `reliability.fallback_delivery_rate` be the objective it
should be. A provider outage with a working fallback keeps that objective
green, so an outage the runtime handled does not manufacture a breach. An
outage the runtime did *not* survive is a miss attributed to the runtime, which
is the signal worth paging on.

=== Unscored is not Missed

A latency sample measured before any `threshold_ms` has been calibrated is
*eligible but unscored*. It counts toward the denominator — that is the evidence
the threshold is chosen from — and it is reported in the `unscored` column, but
it is not a conformance and not a miss. The report therefore says
`status: uncalibrated`, `value: null` and an empty `miss_attribution` for that
row, instead of attributing the sample to a provider failure it may have nothing
to do with.

This is why the classifier has four states rather than three. "No threshold yet"
is neither "passed" nor "failed", and collapsing it into either one corrupts the
contract in a different direction each time: as `Conforms` it invents a pass, as
`Misses` it invades a miss set and the error budget. `SloMeasurement::misses()`
is `eligible - conforming - unscored` for the same reason.

== Error budgets and their limits

A budget exists only for a probabilistic objective that was actually decided.
`allowed_misses = floor((1 - target) * eligible)`, and misses are always
`eligible - conforming - unscored`, so the indicator and the budget can never
disagree about what was spent and an uncalibrated sample is never charged as a
spend. Uncalibrated, empty, and under-sampled windows produce no budget rather
than a budget of zero.

Error-budget thinking does not apply to the zero-tolerance invariants. That is
enforced in code, not by convention: see above.

== Breaches, actions, and the after-action review

Every indicator in the catalog declares its action path:

* `raise_incident` — create or raise an incident;
* `disable_experimental_route` — turn off the experimental route or profile;
* `switch_conservative_profile` — fall back to the cached/reflex profile;
* `open_optimization_issue` — file a reliability/optimization issue;
* `block_promotion` — block promotion from experimental to default.

Alerting on every noisy single sample is explicitly not the policy. A missed
window is a `breach`; it becomes an `aar_candidates` entry only after
`persistent_miss_windows` consecutive misses *within one window series* (default
3), which is the shape
link:after-action-review.adoc[After-Action Review] and
link:current-constraint.adoc[Current Measured Constraint] consume when they
reprioritise. Zero-tolerance invariants bypass the persistence threshold, since
there is no acceptable streak to wait for.

"Within one series" is load-bearing. A session aggregate, an hourly bucket and a
rolling bucket are different observations of the same runtime; counting their
misses in one streak would let a two-hour run manufacture a three-hour streak
out of `session + hour 0 + hour 1`. Rolling windows are keyed by their span, so
a 3-hour and a 6-hour window never share a streak either.

== Experimental traffic

An experimental or shadow route is evaluated with
`--plane experimental`. The report is still a real measurement, but it carries
`counts_toward_active_slo: false`, and the Markdown summary says in words that
it is excluded from the active user-facing SLO. A consumer cannot accidentally
promote it, and a reviewer does not have to remember which run was which.

== Running it

[source,shell]
----
# a replay fixture (or omit for the checked-in smoke fixture)
cargo run --locked -p aivtuber-app --bin replay-benchmark -- \
  examples/benchmarks/replay-comparison.json target/aivtuber-benchmarks

# or a #70 versioned scenario
cargo run --locked -p aivtuber-app --bin replay-benchmark -- \
  --scenario examples/scenarios/chat-burst-10x.json

cargo run --locked -p aivtuber-app --bin slo-report -- \
  --report target/aivtuber-benchmarks/04-full-generative.json \
  --targets examples/slo/slo-targets.json \
  --out target/aivtuber-slo/slo-report.json \
  --markdown target/aivtuber-slo/slo-summary.md \
  --provenance scenario-replay

# pool a history of reports into calibration evidence (no targets)
cargo run --locked -p aivtuber-app --bin slo-baseline -- \
  target/aivtuber-slo/2026-10-01/slo-report.json \
  target/aivtuber-slo/2026-10-02/slo-report.json \
  target/aivtuber-slo/2026-10-03/slo-report.json \
  --out target/aivtuber-slo/baseline-proposal.json \
  --markdown target/aivtuber-slo/baseline-proposal.md

# latency probe step: measure a candidate boundary over each run, then pool
cargo run --locked -p aivtuber-app --bin slo-report -- \
  --report target/aivtuber-benchmarks/04-full-generative.json \
  --probe-latency availability.event_to_first_audio_within_target=250 \
  --out target/aivtuber-slo/probed-run.json
cargo run --locked -p aivtuber-app --bin slo-baseline -- \
  target/aivtuber-slo/probed-run-1.json target/aivtuber-slo/probed-run-2.json
----

Without `--targets` the report publishes measured values and target-free latency
percentiles, and the verdict stays `incomplete`. `--fail-on-breach` makes a
breach exit non-zero for a pipeline that wants to gate on it; it is off by
default, because an operational objective is not a PR gate.

== Choosing a target

A single run is a data point, not a baseline. `slo-baseline` is the tool that
closes that gap: it reads a *history* of `slo-report` outputs — the #58
measured runs — and pools them into per-indicator calibration evidence. It
emits evidence, never a target. For a ratio objective the proposal carries the
pooled `conforming / eligible` value in exactly the `BaselineEvidence` shape a
target entry must cite, so the target is copied from a measurement instead of
improvised.

The pooling is deliberately conservative, and each rule is enforced, not
assumed:

* **One compatibility series.** Every contributing report must share
  `mode + dataset_id + config_version + seed` — the #58 baseline boundary in
  link:performance-goals.adoc[Performance Goals and Baselines]. A history that
  spans two series is refused, not merged, and the report names the series it
  pooled so the boundary is auditable.
* **Distinct runs only.** Byte-identical reports are counted as duplicates: a
  file passed twice is a retry, not a second measurement. Fewer than two
  distinct runs (`MIN_BASELINE_RUNS`) produce no proposals at all — one run
  calibrates nothing.
* **Exact time.** Represented stream time is summed exactly; a partial hour
  never rounds up to one. Two-second runs are two seconds of evidence, and
  sub-hour histories omit `stream_hours` rather than claiming a full hour.
* **Active plane only.** An experimental report is excluded, exactly as it is
  excluded from the active SLO.
* **One report contract.** A `schema_version` or catalog version this build
  does not implement fails closed.

=== The latency calibration cycle

A latency objective has a chicken-and-egg problem the ratio objectives do not:
its conforming ratio does not exist until a `threshold_ms` is chosen, and the
threshold is chosen *from* the measurements. Two steps close the cycle, and
both are measured:

. Pool the target-free history with `slo-baseline` and read the worst-observed
  percentiles: they are the evidence a candidate boundary is chosen from.
. Re-run `slo-report` over each run with
  `--probe-latency <indicator-id>=<threshold-ms>`, which evaluates the
  objective *at* that boundary, and pool the probed reports with
  `slo-baseline`. The proposal now carries the measured conforming ratio at
  that boundary as a valid `BaselineEvidence` — the first latency target is
  constructible entirely from measured artifacts.

A probe is a measurement tool, not evidence: `SloTarget::threshold_probe` is
refused in a targets file, so a boundary can never be written down without the
measured ratio to justify it. Probed histories must share one boundary; ratios
measured at two different thresholds are refused, not averaged.

The procedure is deliberately boring:

. Run the benchmark over a #70 scenario workload (and, when it exists, the #40
  fault overlay) and produce an SLO report with no targets.
. Repeat it, and pool the runs with `slo-baseline`. One run calibrates
  nothing; repeated runs are what turn a measurement into a baseline.
. Read `latency_calibration` for the target-free p50/p95/p99/max, and the
  indicator table for the measured ratios.
. For latency objectives, run the probe step above. For every objective,
  choose a ratio that is a *product* decision, not a number the fixture
  happened to produce.
. Add the entry with its `baseline` block — copied from the proposal, which
  names the dataset, revision, and series it was measured over — and review
  the file like code.
. Re-run and confirm the verdict. A target that is immediately red is a
  measurement problem, not a reason to loosen the target.

The `baseline` block in a target entry is copied from an `slo-baseline`
proposal rather than written by hand, and the target ratio is a product
decision made *above* the measured value — the proposal never prescribes it.
The provenance is durable: the block itself carries the dataset, revision,
config, mode, seed, and series identity, so a target remains auditable after
the proposal file is gone. Repeated nightly runs of the same revision are what
turn one measurement into a baseline, exactly as
link:performance-goals.adoc[Performance Goals and Baselines] requires for #58.

== What this does not cover yet

The catalog deliberately reports these objectives as `not_yet_measured` with
the missing evidence named, rather than pretending to measure them:

* `safety.stale_dispatch_count`,
  `safety.unauthorized_privileged_action_count`,
  `resource.retention_bound_violation_count` — the counters exist in the
  benchmark-result invariant map and the runtime audit log, but as *assertions*,
  not as per-event measurements. `replay-benchmark` writes a literal zero there;
  building an SLO on that would be building it on a constant.
* `availability.event_admission_success_rate` — the denominator is *offered*
  events, and only admitted events are retained.
* `operability.operator_stop_responsiveness_within_target` — no operator
  stop/mute fixture is driven by the replay benchmark.

The engagement, burst, and naturalness indicator families named in the issue
(#74–#77, #78/#79, #81–#89) are not in the catalog yet, because their
denominators depend on those capabilities and several deliberately must *not*
be framed as "respond to everything" objectives. A healthy runtime may
intentionally ignore most benign low-value chat under load.
