= Continuous Benchmark Gate (issue #58 — Phase A–E)
:status: Implemented (result contract + comparator + budgets + PR CI gate + scheduled resource tier + history/trends)
:date: 2026-09-30

The workload the gate measures comes from link:stream-scenarios.adoc[versioned
stream scenarios (#70)]. `replay-benchmark --scenario <path>` generates the
stream from a seeded scenario instead of loading a checked-in event trace, and
the scenario id and version become the result's `dataset_id`, so an incompatible
scenario change starts a new comparison baseline rather than reusing an old one.

The scenario format is shared with the soak, retention and quality suites, so it
carries only its own representability ceiling. The 10 events/minute that the
cached replay path can actually play is a property of *this* consumer, measured
against the starter pack and scheduler; `replay-benchmark` checks it up front
(`validate_playability_for_cached_replay`) and refuses a denser scenario by name
before any work happens, rather than aborting mid-run with `Rejection::Cooldown`.

== 1. Scope

This note documents the continuous benchmark loop from issue #58:

* *Phase A — result contract*: a versioned, machine-readable benchmark
  result document validated by `schemas/benchmark-result.schema.json` in CI.
* *Phase B — comparator*: `benchmark-compare`, which evaluates base vs head
  results against repository-controlled budgets and fails the job on a
  configured regression or hard-invariant violation.
* *Phase C — PR CI integration*: `.github/workflows/benchmark-gate.yml`
  benchmarks the exact base SHA and head SHA in one job/runner and enforces
  the comparator verdict.
* *Phase D — scheduled resource tier*: `resource-bench` runs the high-volume
  logical-time soak (Tier 3) nightly and emits contract results whose
  bounded-state findings are hard invariants.
* *Phase E — history and trends*: trusted main/nightly results are persisted
  to the `benchmark-data` branch and summarized as trend Markdown.

== 2. Result contract

`crates/app/src/bin/replay-benchmark` now emits, next to the existing
comparison-suite documents, one `*-result.json` per comparison mode
conforming to the schema:

* `schema_version` — currently `"1"`; incompatible versions are rejected
  rather than silently compared.
* identity: `benchmark_suite`, `mode`, `dataset_id`, `git.commit`
  (+`base_commit` for comparisons).
* history provenance: `recording.run_id` + `recording.recorded_at`
  (+ diagnostic-only `recording.attempt`), appended by
  `scripts/benchmark-record.mjs` when a trusted job stores the result on
  `benchmark-data`; benchmark producers never emit it. `run_id` is GitHub's
  re-run-invariant run id, so a re-run of one run is idempotent while
  distinct runs of the same revision accumulate (see section 6).
* reproduction metadata: OS/arch/rust/bun/profile, `config_version`,
  `asset_version`, `index_version`, `retriever_version`, model IDs,
  `seed`, `stream_duration_ms`, and `cost_model_version` whenever cost
  metrics are present.
* `metrics` — flat map with unit-explicit names
  (`cached.first_audio.p95_ms`, `routing.route_decision.p95_us`,
  `routing.llm_calls_per_100_events`, `semantic.wrong_reuse_rate_pct`, ...)
  and sample counts.
* `invariants` — hard correctness counters
  (`reliability.stale_dispatch_count`,
  `reliability.unauthorized_privileged_action_count`,
  `reliability.deterministic_replay_mismatch_count`,
  `resource.retention_bound_violation_count`,
  `resource.invalid_route_transition_count`).

CI validates valid and invalid fixtures via `check-jsonschema` in the
schema job.

== 3. Comparator and budgets

`benchmark-compare <base.json> <head.json> [budgets.json] [out-dir]`, or with
repeated runs per side (issue #180):

`benchmark-compare --base <base.json>... --head <head.json>... [budgets.json] [out-dir]`:

1. loads and validates both results (schema version, identity metadata);
2. refuses to compare across differing `benchmark_suite`, `mode`,
   `dataset_id`, `config_version`, or `seed`;
3. computes improvement-positive deltas per metric;
4. applies the suite-scoped budget file — `benchmarks/budgets.json` for the
   replay-comparison suite and `benchmarks/budgets-resource-soak.json` for
   the resource-soak suite (each result must carry the invariants its suite
   actually evidences; every budgeted invariant present in a result is
   required in both sides of the comparison):
   * `direction` `lower`/`higher`,
   * `warn_regression_percent` / `fail_regression_percent`,
   * `warn_absolute_change` / `fail_absolute_change`,
   * `min_samples` — the floor applies to the *pooled* sample count of the
     side being judged; below it the metric reports `ungated` with a warning
     naming the pooled count and the floor (issue #180);
5. when a side contributes repeated runs (issue #180), aggregates them first:
   metrics by the **median** value across runs (outlier resistant), hard
   invariants by the **maximum** (a violation in any run fails), sample counts
   summed, and the observed per-side min/max recorded as a diagnostic
   `run_range` in the table and report. Aggregation refuses — rather than
   silently averaging — when the runs of one side disagree on the measured
   `git.commit`, on the exact metric/invariant key set (checked in both
   directions), or on the comparison boundaries; and an *unknown* pooled
   `sample_count` keeps a `min_samples` floor binding instead of failing
   open;
6. enforces exact hard invariants (any value above `max` fails the gate);
7. prints a Markdown table (metric / base / head / delta / base run range /
   head run range / status) for the PR job summary and writes
   `gate-report.json` + `gate-summary.md`;
8. exits non-zero on `fail`.

Verdicts:

* *pass* — all budgeted metrics within budget, invariants clean;
* *warning* — a budgeted metric breached only its warn threshold;
* *fail* — a fail threshold breached or any hard invariant violated.

Metrics without a budget entry are reported as `ungated` with a warning but
never gate. This is deliberate (#58 "noise calibration"): timing thresholds
become strict only after runner variance is measured; correctness/state
invariants are strict from day one.

== 4. Workflow

PR CI (Phase C, implemented) runs on pull requests that touch `crates/`,
the lockfile, or benchmark inputs:

```text
resolve base SHA (GitHub API)
→ checkout exact PR head SHA → build head replay-benchmark binary
→ checkout base SHA → build base replay-benchmark binary
→ re-checkout exact PR head SHA (comparator + budgets + fixture from the PR)
→ add clean worktrees at the base and head SHAs (result provenance)
→ REPEATS interleaved runs, each side in its own worktree → results/{head,base}/
→ benchmark-compare --base ... --head ... → Job Summary + artifacts
→ assert measured revisions == resolved base/head SHAs
→ enforce verdict (exit status)
```

* Both revisions are the exact reviewed SHAs: the PR head is checked out
  explicitly (the pull_request default `refs/pull/<n>/merge` is a synthetic
  merge commit, not the reviewed revision), and the comparator/budgets run
  from a second head checkout so a PR's own budget changes gate itself —
  intentional regressions therefore require the reviewed budgets edit
  (issue #58 Phase C acceptance).
* Each revision is measured by its own prebuilt binary so base and head can
  be run *interleaved* on one runner (issue #180). Sequential
  base-then-head runs let runner drift land entirely on one side of the
  comparison; A/B/A/B interleaving shares that drift between both sides.
* Both revisions run the *reviewed* fixture and comparator, so a PR that
  edits the fixture or the budgets compares like-for-like under its own
  reviewed measurement definition.
* Each side runs in **its own clean git worktree** checked out at the
  revision it was built from, so the producer's `git rev-parse HEAD`
  resolves to the revision actually under test and results carry that exact
  SHA with no `+dirty`. Doing it by working directory rather than by an
  environment override matters: the base binary is built from the base
  revision, so any producer-side flag introduced by this change would not
  exist in the binary it is meant to identify. Benchmarks are written outside
  the worktrees, which keeps them clean. The `Assert measured revisions match
  the resolved SHAs` step fails the job unless `gate-report.json` carries the
  exact base and head SHAs the job resolved, so this provenance cannot
  silently regress again.
* Both revisions are measured on the same runner under the identical
  fixture/seed/config boundaries, so latency deltas are relative to the
  base measured moments earlier — not to a stale cross-runner history
  record (issue #58 engineering principle 1).
* The Job Summary always contains the metric table, even when the gate
  fails, because summary/artifact publication precedes verdict enforcement.
* Security boundary: the `pull_request` job runs with `contents: read` only.
  Untrusted forked code never receives credentials capable of modifying
  benchmark history; trusted-main persistence is Phase E, on main only.
* The comparator is deterministic: the same inputs always produce the same
  verdict, so gate decisions are reviewable after the fact from the uploaded
  JSON.

Accepting a regression intentionally means editing the suite's budgets file
(`benchmarks/budgets.json` or `benchmarks/budgets-resource-soak.json`) in the
same PR — the change is reviewed like code.

== 5. Phase D — scheduled resource benchmark (Tier 3)

`crates/hardening/src/bin/resource-bench` runs the deterministic logical-time
soak workload (`run_core_soak`, default 576k events ≈ eight logical stream
hours at 20 events/second) and converts the existing mid-vs-final
`GrowthFinding` comparison into contract results:

* retained-state sizes become `resource.*_count` metrics;
* `configured_limit_exceeded` findings become the
  `resource.retention_bound_violation_count` hard invariant;
* `lifetime_growth_detected` findings become the
  `resource.non_plateau_state_count` hard invariant (the #50–#53 plateau
  property, gated exactly);
* throughput and (Linux-only, `/proc`-sourced) peak RSS are reported as
  context metrics — RSS is diagnostic only, never a gate.

`resource-bench` exits non-zero when either hard invariant is violated.

`.github/workflows/resource-bench.yml` runs it nightly (03:00 UTC) and on
`workflow_dispatch`, publishes a metrics/invariants job summary, uploads
results as 90-day artifacts, and records the trusted result to the
`benchmark-data` branch (Phase E). A 5k-event smoke in the `rust` CI job
keeps the contract output verified on every PR. The wall-clock soak and
failure-injection tier remains owned by #40; its results can reuse this
result/history contract.

== 6. Phase E — history and trends

Trusted results are persisted on the orphan `benchmark-data` branch:

* `data/<suite>.<series>.jsonl` — one contract document per line, grouped
  into compatibility series and deduped on
  (suite, mode, commit, `recording.run_id`) with the last line winning.
  `run_id` is GitHub's re-run-invariant run id, so re-running the *same*
  workflow run (any `run_attempt`) is a no-op, but repeated runs of the same
  revision *accumulate*: nightly observations of an unchanged main are the
  raw material for runner-variance calibration. One invocation may record
  several compatibility boundaries at once (record-main stores all four
  replay modes of one run); each lands in its own series.
* `<series>` encodes the comparator's compatibility boundary —
  `mode` + `dataset_id` + `configuration.config_version` +
  `configuration.seed` — plus a short stable hash. Results from different
  datasets, configs, or seeds get separate data and trend files and are
  never rendered into one table, so incompatible workloads are not silently
  compared across a boundary bump.
* `trends/<suite>.<series>.md` — generated tables for the key metrics
  (first-audio p95, first-visible p95, wrong-reuse rate, LLM calls/100
  events, retained state, throughput) plus per-run invariant status. Each
  table's heading states its compatibility boundary and the table has a
  `run` column.

Writers are limited to jobs that run repository-owned code: the `record-main`
job (push to main only) for replay results and the nightly resource bench.
Both serialize through the `benchmark-data-append` concurrency group. The
recorder (`scripts/benchmark-record.mjs`) operates in an isolated git
worktree so it never touches the main checkout, and pull_request jobs keep
`contents: read` only — untrusted forked code cannot write history.
Recording jobs pass `--run-id "run-${{ github.run_id }}"` (re-run-invariant;
`--attempt ${{ github.run_attempt }}` is recorded as diagnostic metadata
only), and the recorder refuses to run without a run identity so retries and
repeated observations can always be told apart.

Trend views are informational. Gating decisions always come from the
machine-readable comparator. Baseline/target methodology, budget rationale,
and the regression-investigation procedure live in
link:performance-goals.adoc[Performance Goals and Baselines].

== 7. Reaction-quality companion evidence

The #58 comparator remains the quantitative benchmark/invariant gate.
When a routing, reuse, generation, or other reaction-policy change also needs
human quality evidence, #151 provides a separate companion report rather than
adding subjective labels to the benchmark metric contract.

After +benchmark-compare+ writes +gate-report.json+, a completed pairwise review
session can render both evidence classes together:

[source,shell]
----
bun run quality:review -- report examples/evaluation/reaction-quality-review/development-example.json target/benchmark-gate/gate-report.json target/reaction-quality-review
----

The resulting +quality-summary.json+ retains the review dataset/protocol and
base/candidate identities, individual-evidence aggregates, the explicit quality
guardrail interpretation, and the selected Keep/Expand/Narrow/Revert/Defer/Stop
decision. +quality-summary.md+ shows the same quality evidence beside the #58
metric deltas.

This composition is intentionally not a new scalar gate. Benchmark invariants
remain hard deterministic constraints, quantitative proxy budgets retain their
existing comparator semantics, and human quality labels remain offline evidence.
If the review interpretation is +regression+, the companion report explicitly
blocks an unqualified product-improvement claim even if the #58 proxy verdict
passes. No report output can promote a candidate policy or mint runtime authority.

== 8. Issue #180 — routing-decision calibration

`routing.route_decision.p95_us` used to be gated at `warn 20%` /
`fail 40%` over a p95 of 3 fixture events whose absolute values are
single-digit microseconds. The noise band of that measurement is wider than
the entire failure budget, so the required check failed on unrelated PRs
(PR #179: `base=3.0000 | head=5.0000 | -66.7% | failed` on a comparator
that executed none of that PR's code).

Measured on one machine, same fixture, same lockfile, debug profile — the
run-to-run spread of a *single* run of one unchanged build:

[source,text]
----
24 sequential runs, routing.route_decision.p95_us (µs):
7 6 6 6 7 5 7 6 6 8 5 6 5 7 7 12 5 5 6 5 8 8 5 7      (median 6, range 5–12)
40 sequential runs, same build:
7 6 9 5 7 5 5 7 5 8 9 8 6 6 7 6 7 6 9 7 6 6 10 6 8 5 6 5 7 5 6 6 6 5 6 6 7 7 5 5  (median 6, range 5–10)
----

A 2x range inside one build.

*Why this metric and not the others.* Across 64 runs of one build, every
other gated metric was bit-identical run to run
(`cached.first_audio.p50_ms` = 83, `p95` = 112, `p99` = 112,
`cached.first_visible.p95_ms` = 33, `routing.llm_calls_per_100_events` = 0,
`semantic.wrong_reuse_rate_pct` = 0) — they are replay-clock measurements
(`at_ms` differences in `crates/runtime/src/cached_playback.rs`), so their
run-to-run noise is zero and their percent budgets are meaningful.
`routing.route_decision.p95_us` is the one gated metric measured against the
**wall clock** (`Instant::elapsed()` in `crates/app/src/lib.rs`), which is
exactly why it — and only it — was gated on uncalibrated noise.

Two changes follow from that evidence:

* *The gate no longer decides this metric from one run.* The workflow
  benchmarks both revisions 7 times, interleaved, and the comparator takes
  the **median** across runs with the observed min/max reported as
  `run_range`. Measured over 8 independent interleaved batches of 7 runs per
  side with byte-identical binaries, every batch produced the same verdict
  (`PASS`, exit 0); the largest base↔head median delta observed was 2 µs,
  against a 3 µs warn budget and 6 µs fail budget.
* *The budget is absolute, and the sample floor binds the pooled
  measurement.* `routing.route_decision.p95_us` is now
  `warn_absolute_change: 3` / `fail_absolute_change: 6` (µs) with
  `min_samples: 15`. 15 samples is more than one 3-event fixture pass
  produces (3), so a single-run comparison reports `ungated` with a warning
  instead of deciding on three samples; the workflow's 7 runs pool 21. A
  percent budget is not expressible at this magnitude — 20% of 6 µs is
  1.2 µs, less than the spread of one unchanged build.

Controlled regression experiment (not a code guess): a deliberate ~120 µs
busy-wait added to `IntentRoutePlanner::route`, binary rebuilt, same
interleaved 7-run protocol:

[source,text]
----
base median 12 µs (run range 9–15)  head median 133 µs (run range 130–142)  → failed, exit 1
base median 12 µs (run range 9–15)  head median 132 µs (run range 129–137)  → failed, exit 1
base median 12 µs (run range 9–15)  head median 133 µs (run range 130–137)  → failed, exit 1
----

A deliberately *small* regression (a 10 µs busy-wait, below the 2x noise
range of a single run) also fails every batch: `12 → 21 µs`, `12 → 21 µs`,
`12 → 22 µs` → `failed`, exit 1. The gate still catches a real routing
regression; it just no longer fails on noise.

Hard invariants were never affected by any of this: they aggregate by
maximum, so a violation in any run still fails the gate.

*Provenance.* Each side is measured in its own clean worktree at the revision
under test. Without that, a runtime `git rev-parse HEAD` stamped both sides
with the PR head (and `+dirty`), which the first CI run of this branch
actually did — `base=3a59ae97...+dirty head=3a59ae97...+dirty` while the
resolved base was `91c4a7e4...`. An environment override was rejected as the
fix: the base binary is built from the base revision and therefore cannot
contain a flag introduced by this change (the assertion caught exactly that
bootstrap failure on the next run). The workflow now asserts that
`gate-report.json` carries the exact resolved base and head SHAs, so
misattributed evidence fails the job instead of being uploaded.

*Unchanged consumers.* The other suites still work through the same CLI:
`resource-bench` results compared with `benchmarks/budgets-resource-soak.json`
PASS with exit 0 in the single-run positional form, and
`bun run quality:review` still renders the #180 gate report (its `metrics`
array only gained the diagnostic `base_range`/`head_range` fields).

== 9. Verification

* `benchmark_gate` telemetry unit tests (21 in
  `crates/telemetry/src/benchmark_gate.rs`; 39 in the `aivtuber-telemetry`
  crate as a whole): improvement/ok/warning/fail paths, higher-is-better,
  absolute thresholds on small denominators, min_samples gating,
  invariant violation overrides improvements,
  incompatible dataset/schema detection, ungated reporting, markdown
  summary, JSON round-trip, plus the #180 repeated-run cases — median/max
  aggregation, pooled sample counts meeting a floor one run cannot,
  an ungated-with-reason warning below the floor, repeated identical runs
  keeping one verdict, inconsistent metric sets and config boundaries
  rejected, empty run lists rejected — plus runs measuring different
  revisions rejected, an unknown pooled sample count keeping the floor
  binding, and later-only metric or invariant keys rejected in both
  directions.
* comparator CLI unit tests (4): the original positional form is unchanged,
  default budgets/output paths, the repeated `--base`/`--head` form collects
  every run, and incomplete/unknown argument forms are rejected.
* hardening tests (11 run in normal CI; 13 defined, 2 credential-gated
  live conformance): soak plateau detection, plus the Phase D contract
  mapping — clean soaks map to zero invariants, growth findings map to
  non-zero invariants with details, results round-trip through the
  comparator's parser.
* reaction-quality bun tests (8): deterministic A/B assignment, reviewer-packet
  identity blinding, tamper rejection, base/candidate normalization,
  disagreement preservation, both-unacceptable retention, quality-regression
  claim blocking, and benchmark companion rendering.
* recorder bun tests (18): run-id identity keying (attempt excluded), retry
  idempotence vs repeated-observation accumulation, stable ordering,
  compatibility-series splitting (dataset/config_version/seed/mode
  boundaries), collision-free series file stems, trend rendering with the
  boundary heading and run column, invariant status flags, metric filtering.
* end-to-end: `replay-benchmark` emits contract results; comparator PASSes
  identical results (exit 0) and FAILs an artificially regressed result
  (first-audio p95 +78%, stale dispatch 3) with exit 1.
* end-to-end (#180): 8 independent interleaved batches of 7 runs per side
  with identical binaries all return the same verdict (PASS, exit 0); the
  same protocol FAILs (exit 1) on injected routing regressions of +10 µs and
  +120 µs. See section 8.
* end-to-end (Phase D): `resource-bench` emits `resource_soak` contract
  results; comparator PASSes identical results with the resource budgets and
  FAILs an artificially non-plateauing head with exit 1.
