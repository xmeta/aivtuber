= Native Audio Backend Evidence Spike (#101)

== Decision

Keep the existing process-player backend as the production default for now, and retain the native Rust backend as an opt-in experimental path behind the existing `AudioPlayer` boundary.

The Windows measurements show a large reduction in backend start, stop, and consecutive-handoff proxy latency for a persistent `rodio` device stream. They do not measure acoustic first-audible latency, real VTuber clip formats, or device-loss recovery well enough to justify replacing the default globally.

Revisit the default when #58/#83 can add acoustic/on-device first-audio and phrase-continuity measurements on the actual deployment profile.

== Compared implementations

Process baseline::
`ProcessAudioPlayer` resolves `audio://` under the configured root and starts `ffplay` for each playback. Production behavior is unchanged. A tracked-start helper exposes the child only to the benchmark so process spawn and stop can be measured without duplicating validation logic.

Native candidate::
`RodioAudioPlayer` is available when the `native-audio-spike` feature is enabled (it is no longer Windows-gated, see "Device and deployment behavior"). It opens one default output stream and keeps *one persistent `Player`* on its mixer (#83 S3d, see "Phrase continuity"). It remains an `AudioPlayer`; no device handle enters domain/replay state.

== Measurement setup

Evidence file: `../examples/benchmarks/audio-backend-windows-2026-09-28.json`.

Environment used for the recorded run:

* Microsoft Windows 11 Pro, version 10.0.26200, build 26200, x86_64.
* `ffplay` 9.0.2 as the process backend.
* `rodio` 0.22.2 with the Windows playback feature.
* 30 repetitions per distribution.
* synthetic silent PCM S16LE mono 48 kHz WAV files: 120 ms for start/handoff and 2 s for stop.
* process playback used `-volume 0`; native input samples were zero, so the measurement did not intentionally emit audible program material.

The benchmark command is:

[source,powershell]
----
$env:AIVTUBER_AUDIO_BENCH_REPETITIONS="30"
cargo run --locked -p aivtuber-adapters --features native-audio-spike \
  --bin audio-backend-benchmark -- target\audio-backend-benchmark-windows.json
----

The start metric is a *backend-return proxy*, not microphone/acoustic first-audible time: process = validated `spawn()` return; native = validated decode plus mixer enqueue return. Stop measures `kill()+wait()` for `ffplay` and `Player::stop()` for rodio. Handoff measures the second backend start after the first short clip reaches its backend-complete condition.

== Results

All latency values below are microseconds.

[cols="2,1,1,1,1,1,1"]
|===
|Metric |Backend |p50 |p95 |p99 |min |max
|Start proxy |process / ffplay |5972 |8767 |13517 |5534 |13517
|Start proxy |rodio |499 |747 |791 |458 |791
|Stop |process / ffplay |2020 |2806 |4617 |1789 |4617
|Stop |rodio |4 |10 |10 |2 |10
|Consecutive handoff proxy |process / ffplay |6514 |14347 |14438 |5966 |14438
|Consecutive handoff proxy |rodio |685 |897 |1025 |594 |1025
|===

Cold-path observations:

* process cold start proxy: 9242 us;
* opening the native default device stream: 77293 us;
* first native playback after stream initialization: 901 us.

This makes persistent device initialization part of the native-backend requirement. Reopening the device for every reaction would erase a substantial part of the measured benefit.

== Resource observations

The harness records coarse Windows process snapshots; they are diagnostic observations, not a controlled CPU/memory benchmark.

* sampled `ffplay` child: about 15.8 MB working set and 15.8 MB private bytes;
* benchmark host before the run: about 12.0 MB working set / 1.84 MB private bytes;
* benchmark host after the run: about 12.5 MB working set / 2.27 MB private bytes.

The host process includes the benchmark code and persistent native stream, so the before/after difference must not be interpreted as rodio-only memory. A future default-backend decision should use isolated steady-state CPU/memory profiling.

== Cancellation and continuity

The native candidate exposes local `stop()` over the currently active player. The benchmark shows that this local operation is much cheaper than terminating and reaping an external process at the measured boundary.

The current `AudioPlayer` production interface remains intentionally authority-free. Operator stop/mute is still decided by the application/security/scheduler path; a native audio object does not receive `AuthenticatedControl`.

The handoff proxy favors the persistent native stream, but the #101 spike did not measure the gap between waveforms. #83 S3d adds that measurement for the part that is deterministic; see the next section for what it does and does not establish.

== Phrase continuity (#83 S3d)

Decision (supervisor, #83): wrap rodio 0.22.2 (already in `Cargo.lock`). Rejected: kira (a second cpal and symphonia, and its own clock would be a second timing authority beside the scheduler), web-audio-api-rs (too heavy), oddio (unmaintained since 2023). A custom cpal ring buffer stays the fallback if the falsifier below fails; it did not.

Design::
* `RodioAudioPlayer` keeps one `Player`. A continuation phrase (phrase seq > 0 of a phrased reply, carried as `AudioPlaybackCommand::continuation` and `AudioPlayRequest::continuation`) is `append`ed behind the audio in flight. rodio's queue then starts it on the sample after the previous source ends, with no per-phrase player creation or stop.
* The queue is bounded: at most `MAX_QUEUED_PHRASES` (3) phrases, playing plus queued. A fourth is refused with `EngineErrorKind::Overloaded` and counted (`refused_queue_full()`); nothing already queued is dropped.
* Speed is applied to each source (`Source::speed`), not to the player, so a continuation at another speed does not retune the phrase already playing.
* A fresh (non-continuation) request replaces what still plays, as before; a drained player is reused.
* The app releases a continuation command to a backend that declares `AudioPlayer::supports_gapless_queue()` (`AudioOutput::gapless_queue()`) `AUDIO_LOOKAHEAD_MS` (250 ms, a constant) before its logical `at_ms`. `ProcessAudioPlayer` does not declare it and keeps the hand-over at the logical start.
* The logical clock is unchanged (ADR-0004 D-6): `Started` is written by the scheduler at the logical `at_ms`; backend acceptance during the lookahead strengthens only the basis of `Finished` and never emits `Started`.
* Operator stop and barge-in end the shared player through the existing `AudioOutput::stop` primitive inside the 100 ms `AUDIO_STOP_BOUND`: queued-ahead phrases are dropped at the instant of the call (a source that has not produced a sample yet yields nothing), the audible phrase fades, the player is dropped, and the next `play` builds a new player. `Player::clear` is never called (it blocks until the queue drains) and nothing is appended to a stopped player (`append` blocks then too). The scheduler cancels the queued-ahead phrases as `Cancelled` (reached `committed`) in the speech lifecycle.

Measured (device-free, `cargo test --locked -p aivtuber-adapters --features gapless-queue --test gapless_queue -- --nocapture`; the queue runs on rodio's offline mixer and the test pulls it sample by sample, so the numbers are exact, not timed):

[cols="3,2"]
|===
|Case |Result
|Two mono 48 kHz WAVs A (4800 samples of 0.25) and B (3600 samples of -0.5), B appended as a continuation
|A occupies indices 0..4799, B's first sample is at index 4800: *0 samples between them*; B is intact (3600) and silence follows
|Three phrases (1000, 777, 2001 samples)
|no zero sample anywhere in the 3778-sample chain; each value appears exactly its length
|Contrast: the second phrase handed over 736 samples after the first one ended (what a hand-over at the logical start does)
|1024 samples (21.3 ms) of silence before it starts: the arrival delay plus up to one 1024-sample idle span of rodio's queue; the detector is able to see a gap
|Bound
|the 4th request is refused with `Overloaded`, counted once, queue still 3
|Stop with a 120 ms fade, two phrases queued ahead
|call returns in 88 microseconds (offline mixer; on a device 58 microseconds in `audio_stop`); neither queued phrase produces a sample; silent after the fade; the next play is audible on a new player
|Speed 0.5 on the continuation
|phrase A intact (4800); B starts immediately behind it and plays at about half its length (rodio's resampler: 2400 expected, 2656 observed in a probe), so exactness is claimed at speed 1.0 only
|===

What this establishes: with the next phrase already appended, rodio's queue plus mixer introduce no silence at the boundary *in the sample stream*, for 16-bit mono WAV at 48 kHz and a sink at the same rate, and the lookahead makes "already appended" the normal case. It also establishes the stop semantics above against the real queue code.

What it does not establish (needs a manual DAC-level measurement, see the PR for #83 S3d):

* the gap at the *speaker*: cpal's callback buffering, the host API (WASAPI shared mode) and the driver sit after the mixer; a loopback or microphone capture of two chained phrases is needed to confirm zero gap there;
* Opus/other codecs (only WAV was used; a decoder that reports a different span length could add padding);
* sample-rate conversion cases (phrase rate different from the device rate, speed other than 1.0);
* drift between the logical timeline and the device: a phrase's logical end is `start + duration_ms` as reported by TTS, while the device plays the actual samples, so a phrase whose file is longer or shorter than its reported duration shifts the audible chain relative to the logical one (`Started` is logical by design; no drift correction exists);
* the stop latency to silence at the speaker (the call returns at once and the fade is at most 150 ms, but the device buffer after it is not measured);
* a preemption that cancels a queued continuation inside its 250 ms window: the already handed-over phrase is not recalled (operator stop and barge-in are handled because they stop the whole player).

== Device and deployment behavior

Windows::
The feature build and live benchmark succeeded against the default Windows output device. `RodioAudioPlayer::new` fails with an unavailable error when the default stream cannot be opened. Device-loss reconnect is a *known gap*: nothing rebuilds the stream after device removal or a default-device change (a play then keeps appending to a player whose device is gone). It must be closed before the native backend can become the default.

Features and other platforms::
Two opt-in features, neither in a default build. `gapless-queue` enables rodio *without* its `playback` feature: the device-free `GaplessQueue`, which builds and tests on any host with no ALSA headers (CI runs its clippy and the falsifier). `native-audio-spike` adds rodio's `playback` (cpal) and `RodioAudioPlayer`/the benchmark; cpal needs ALSA development headers on Linux exactly like `mic-capture`, so default CI does not build it. The Windows-only gate was removed from the code in #83 S3d, but `native-audio-spike` has been built and run on Windows only; Linux and macOS device behavior is unverified.

Fallback::
The process backend remains available and remains the production default. Failure of the optional native experiment therefore does not remove the existing operational path.

== Dependency and runtime risks

* `rodio` pulls platform audio/runtime dependencies when native playback is enabled.
* audio device availability and latency are environmental and observational, not replay inputs.
* one persistent stream is required for the measured low start cost; device lifecycle becomes a long-lived adapter responsibility.
* real OPUS/generated assets and actual deployment devices were not exercised by this synthetic WAV benchmark.
* acoustic onset, underrun/glitch behavior, and phrase-boundary perceptual gaps remain unmeasured.

== Reproduction and verification

Default CI does not require a native audio device:

[source,text]
----
cargo test --locked -p aivtuber-adapters
----

The optional implementation can be type-checked without changing the application default. The recorded live evidence was produced on Windows:

[source,text]
----
cargo check --locked -p aivtuber-adapters --features native-audio-spike \
  --bin audio-backend-benchmark
----

The benchmark output is intentionally a checked-in evidence snapshot; fresh local results belong under `target/` until reviewed and selected for an evidence update.

== Revisit conditions

Reconsider replacing the process default when at least one of these produces new evidence:

* #58 shows audio backend startup is material in the end-to-end latency budget;
* #83 needs phrase-level gap/continuity below what process playback can provide (the sample-stream part is now measured, see "Phrase continuity"; the DAC-level part is not);
* an acoustic loopback/microphone measurement confirms the proxy advantage at first audible output;
* production device-loss/reconnect tests establish a robust persistent-stream lifecycle;
* isolated CPU/memory measurements reveal a material regression or advantage.
