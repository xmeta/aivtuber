= Research and Design Register
:toc:
:toclevels: 2

This register maps external research and mature open-source implementations to aivtuber design questions.

It is not a second roadmap and it does not authorize implementation.
GitHub issues remain the source of truth for ownership, milestone, priority, blockers, and acceptance criteria.

Use this register to avoid:

* rediscovering the same paper or repository in later AI-assisted sessions;
* copying an external architecture without checking local constraints;
* turning benchmark numbers from a different population/workload into aivtuber production thresholds;
* treating GitHub popularity as evidence that a dependency fits deterministic/replay/security requirements.

== Status semantics

Repository issue labels distinguish implementation and design work:

* +status:agent-ready+ -- dependencies are satisfied for implementation work.
* +status:blocked+ -- implementation must not start until the named blocker is resolved.
* +status:design-ready+ -- architecture, research, evaluation design, interface design, or assumption review may proceed; this does *not* authorize code implementation.

An issue may be both +status:blocked+ and +status:design-ready+.

== Research-to-project workflow

[source,text]
----
external paper / OSS pattern
        |
transfer hypothesis
        |
linked GitHub issue
        |
bounded architecture / evaluation design
        |
local replay / benchmark / shadow evidence
        |
keep | narrow | defer | reject
        |
implementation only when dependencies/readiness permit
----

For high-consequence assumptions, use #61.
For experiment evidence, use #58-#60 and #64.
For third-party dependency decisions, use link:reuse-first.adoc[Reuse-First Library and Reference-Implementation Matrix] and #100.

== Current design-ready queue

The following groups are suitable for architecture/research progress even when implementation is blocked or intentionally deferred:

* #104 -- marginal-value routing and thinking-budget contract;
* #105 -- temporal/causal/epistemic memory model and retrieval evaluation;
* #106 -- speculative preparation and commit-barrier contract;
* #107 -- continuous listening-performance state and evaluation;
* #108 -- failure-attribution result schema and evaluator ordering;
* #219/#220 -- OSS avatar and zero-paid local-first product baseline;
* #221/#222 -- dynamic ActionWindow and provider-neutral speech lifecycle/pronunciation contracts;
* #90/#92/#93 -- future perception, speech-turn observations, and media/speaker boundaries.

Design work should produce bounded types, ownership boundaries, acceptance criteria, scenario/evaluation definitions, or assumption records.
It should not silently create runtime dependencies or production code while the issue remains implementation-blocked.

== Research applicability checklist

When adding a paper or OSS pattern to this register, record or verify:

. Is the source a peer-reviewed paper, preprint, official documentation, or repository?
. What language, modality, population, workload, and hardware did it evaluate?
. Which *pattern* is expected to transfer to aivtuber?
. Which reported result should *not* be assumed to transfer?
. Which local issue owns validation?
. What local replay/benchmark/shadow evidence would keep, narrow, or reject the idea?
. Does the idea preserve bounded state, replay, privacy, authority, and graceful degradation?
. Is a mature library/reference implementation available before custom infrastructure is written?

Prefer primary papers and official repositories/docs.

== Maintenance

Update this register when:

* a research-derived idea becomes a dedicated issue;
* a candidate is rejected or materially narrowed;
* a newer paper/repository changes the design assumption;
* implementation evidence resolves a transfer hypothesis;
* a dependency/reuse decision moves to link:reuse-first.adoc[the reuse-first matrix].

Do not copy large issue bodies into this document.
The register should stay a concise map from external evidence to local validation work.
