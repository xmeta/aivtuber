= EXP-0002: Japanese speech-to-text engine bench (#92 S3a)
:toc:
:toclevels: 2

This is a durable experiment record in the link:README.adoc[Durable Experiment Records] format.
It is the evaluation slice S3a of #92: it chooses a local Japanese speech-to-text (STT) engine by measurement before any implementation (S3b).
It contains measurement and throwaway scripts only: no production code, no new dependency in the repository, no model, binary or audio committed.
It follows link:EXP-0001-japanese-turn-observation-bench.adoc[EXP-0001] (VAD and turn-end) and the merged S1 (observation contract) and S2 (speech-activity sidecar with a bounded +PreRoll+ hook).

== 1. Record

[source,text]
----
Decision question:
  Which local, permissively licensed Japanese STT engine, and which integration path from Rust
  without build-time network downloads, should #92 S3b implement, producing partial and final
  transcripts from the S2 VAD segments plus pre-roll?

Context / baseline:
  S2 ships speech-vad-sidecar (Silero v6 via tract, raw edges, bounded PreRoll, clock-stamped
  observations over a supervised child-process pipe). docs/reuse-first.adoc names sherpa-onnx
  ("wrap or sidecar; conformance/benchmark first") for local speech inference and says the
  framework license does not imply the model license. Baseline for "good enough" is not fixed
  (no SLO); the comparison is between candidates and against real time.

Hypothesis / expected outcome (exploratory, no numeric threshold pre-registered):
  A sherpa-onnx Japanese model gives usable accuracy at a real-time factor far below 1 on CPU;
  Whisper-family models are more accurate but too slow on CPU for partials.
  Expected going in: a streaming Japanese model exists in sherpa-onnx (one does, but it is not the ReazonSpeech
  zipformer, which is offline; section 6.3).

Guardrails:
  Code and weights must be permissively licensed, checked separately, and training-data terms
  recorded; no build-time network download in the integration path; no raw audio retained or
  sent anywhere; transcripts are untrusted content, never authority; a slow engine must never
  sit in the scheduler/frame loop; partial transcripts must be bounded.

Decision-changing evidence:
  CER on a few hundred clips with documented normalisation; latency (final call, first partial);
  RTF, load time, RSS; determinism; license table; Rust integration cost with cargo deny.

Cheapest informative test:
  CPU runs of each candidate on the same seeded Common Voice ja clips (section 4), one fresh
  process per run, plus a license/provenance read and a throwaway Rust build of the leading path.

Dataset/workload:
  Common Voice 22.0 ja, test split, 400 clips (1471 s of segments, mean 3.7 s, max 10.4 s), seeded sample,
  trimmed to a VAD-like segment (0.30 s before and 0.50 s after speech). Most sherpa-onnx engines ran all 400;
  Qwen3-ASR, Omnilingual, Nemotron 160 ms and the padded Nemotron runs 150; Vosk small 200, Vosk big 60, Whisper-family 150 (kotoba q5_0 on CPU: 60), always the first clips of the order. Gold = Common Voice sentence verbatim.

Commit/base/head:
  Branch docs/92-s3a-japanese-stt-bench from origin/main 636fc58a (docs and scripts only).
  Benchmark scripts: examples/benchmarks/stt/.

Profile/config fingerprint:
  CPU only. Offline engines: greedy / default decoding, 4 threads unless stated (Whisper: 8 threads).
  Whisper: whisper-server, language ja, temperature 0, default greedy decoding, no timestamps, no GPU.
  Segment: 0.30 s pre-roll, 0.50 s tail around an energy-defined speech span (section 4.2).

Seed:
  20261109 (clip selection and bootstrap intervals).

Asset/index/compiler version:
  Not applicable (no repository assets, replay index or compiler involved).

Provider/model versions:
  Section 3.

Toolchain:
  Python 3.13.12, numpy 2.5.4, scipy 1.18.1, soundfile 0.14.0, psutil 7.2.2, RapidFuzz 3.14.6,
  sherpa-onnx 2.0.1 (Python wheel), vosk 0.3.45 (isolated venv outside the repo);
  whisper.cpp prebuilt CPU binary (nightly b5454, contains v1.9.5); Rust 1.98.1, cargo-deny 0.20.2.

Other relevant environment:
  x86-64 desktop CPU (Zen 2 class, 8 cores / 16 threads), Windows 11 Pro, discrete GPU present but unused
  for the CPU tables. Run date 2026-11-09. Single machine, one run per configuration.

Exploratory unknowns:
  Everything in sections 5-8. No confirmatory criterion was fixed before the results were read.

Confirmatory success/guardrail criteria:
  None (the question is a selection among candidates).
  Criterion version / recorded-at: not applicable.

Actual:
  Sections 2 and 5-8.

Evidence artifacts:
  Scripts are committed (examples/benchmarks/stt/). Per-run outputs (JSON per run with per-clip text and
  timings) are local only and not committed; the tables in this record are the retained evidence.

Noise / uncertainty / missing evidence:
  Section 10. In short: read speech with noisy labels, one machine, intervals are wide, partials are
  emulated for offline engines, GPU not measured (or measured separately, section 6.6), one corpus.

Expected-vs-actual difference:
  The expected streaming ReazonSpeech zipformer does not exist (the one streaming Japanese-capable sherpa-onnx model, Nemotron 3.5, was clearly less accurate here). Whisper-family models were too slow on CPU
  (RTF 0.76-3.0, seconds per segment) as expected, but were not clearly more accurate than the CPU transducers on this
  read speech, and on a GPU they were as fast as the transducers. Vosk big was competitive in accuracy.

Likely explanation:
  The ReazonSpeech Japanese models are offline-only; Whisper pads every input to a 30 s window; on short read
  sentences with noisy labels the accuracy spread among strong models is within the measurement noise. The first two
  statements are mechanical, the third is a limitation of the data (section 10).

Decision:
  Narrow.
  Carry sherpa-onnx + ReazonSpeech k2-v2 int8 (CPU, prefix re-decode for partials) into the S3b design, with parakeet-ja
  as the configurable accuracy option and a Whisper GPU tier deferred; Nemotron streaming only as a watched option;
  reject SenseVoice (license), Moonshine (license), Vosk, Qwen3-ASR, Omnilingual, Dolphin, CPU Whisper and sherpa-rs. Conditional on the ReazonSpeech corpus question (section 12, Q1) and on the supervisor
  choices Q2-Q5. This is a recommendation, not a decision.

Follow-up / owning issue:
  #92 S3b (implementation). Open questions: section 12.

Revisit condition:
  A real conversational Japanese test set with permissive terms, or a streaming Japanese model with a clean
  license, or a clarified ReazonSpeech corpus license, or a sherpa-onnx crate release that drops the
  non-allowlisted build-time dependencies, or a CPU/GPU target change.

== 2. Result summary

All numbers are measured here unless marked as vendor-reported.
Accuracy is measured on read speech with noisy labels (section 10): use the ordering and the intervals, not the absolute CER.

* *Two native streaming Japanese engines exist, and neither is the ReazonSpeech zipformer.* ReazonSpeech k2-v2 is an offline transducer (section 6.3). The sherpa-onnx catalogue does contain a streaming Japanese-capable model, NVIDIA Nemotron 3.5 ASR Streaming 0.6B (multilingual, cache-aware RNN-T; an early survey of this work missed it, see section 11), and Vosk is a streaming Kaldi engine. Nemotron's partials are append-only (100% of them were a prefix of the final text) but its first partial came about 1.1 s after speech onset and its accuracy on this read speech was clearly worse than the offline transducers (below).
* *"Streaming" with an offline model* means re-decoding a growing prefix every 0.5 s: for ReazonSpeech k2-v2 int8 one call cost p50 102 ms / p95 246 ms (4 threads), and the first non-empty partial arrived about 236 ms after speech onset (bounded by the 0.5 s grid, not by the model). Only about 59% of such partials were a prefix of the final text, so they are revisable, not stable.
* *Accuracy on read speech* (same first 150 clips, CER with 95% bootstrap interval): NeMo parakeet-tdt_ctc-0.6b-ja int8 10.3% (8.0-12.6), ReazonSpeech k2-v2 fp32 12.0% (9.0-15.4), SenseVoice 12.9% (10.7-15.3), whisper.cpp large-v3-turbo q5_0 13.1% (10.4-16.1), k2-v2 int8 14.3% (10.1-19.3), whisper medium q5_0 15.6%, Dolphin small 17.7%, whisper small 21.6%, Nemotron 560 ms 21.6% (with tail padding; 24.7% without), Qwen3-ASR 21.7%, Nemotron 160 ms 26.0%, Vosk small 27.8%, Omnilingual 300M 32.9%. On the full 400 clips the order of the sherpa-onnx engines is the same: parakeet 15.2%, k2-v2 fp32 16.9%, SenseVoice 17.6%, k2-v2 int8 18.6%, Dolphin 21.6%, ja-en zipformer 21.5%, Nemotron 560 ms 29.0% (no tail padding). Paired against k2-v2 int8 on 400 clips: parakeet -3.3 pp (interval -5.5 to -1.4) and k2-v2 fp32 -1.6 pp (-3.1 to -0.4) are better; Nemotron +10.5 pp (+8.0 to +12.9), Dolphin +3.0 (+0.5 to +5.5) and the ja-en zipformer +3.0 (+0.2 to +6.0) are worse; SenseVoice is not distinguishable (-1.0, -3.2 to +1.0). Absolute CER is pessimistic (noisy labels, orthographic scoring; section 10).
* *CPU cost, final call on a whole segment* (mean segment 3.7 s): k2-v2 int8 RTF 0.039, p50 123 ms, p95 289 ms, load 4.1 s, peak working set 548 MB; parakeet RTF 0.102, p50 323 ms, 938 MB, load 9.1 s; SenseVoice RTF 0.053; Dolphin 0.078; k2-v2 fp32 0.046 but 1050 MB; Qwen3-ASR 0.37 and 1987 MB; Nemotron 560 ms 0.23-0.30 and about 830-890 MB, 160 ms 0.68-0.86. Whisper-family models on 8 CPU threads need *seconds per segment regardless of its length* (30 s window): small 2.9 s (RTF 0.76), medium q5_0 7.4 s (1.9), large-v3-turbo q5_0 12.0 s (3.0), kotoba-whisper v2.0 q5_0 11.8 s (2.9, 60 clips). They cannot do partials or real-time finals on this CPU.
* *GPU, reported separately* (whisper.cpp CUDA 12.4 build, RTX 2070-class GPU): kotoba-whisper v2.0 fp16 p50 144 ms / p95 201 ms (RTF 0.038), large-v3-turbo fp16 157 / 237 ms (RTF 0.042), load about 20 s, roughly 1.8-1.9 GB of GPU memory above the idle baseline; CER 13.6% and 11.5% on the first 150 clips, within noise of the CPU transducers. Re-decoding partials on the GPU costs p50 143-154 ms (first partial about 330 ms after onset). Contention with the avatar renderer was not measured.
* *Determinism:* the same input in the same process gave the same text on every re-run for every sherpa-onnx model (100 of 100 for the 400-clip runs) and every Whisper run; a fresh process gave identical text on 400 of 400 clips; changing the thread count of the int8 k2-v2 model changed the text on 3 of 400 clips (1 thread) and 1 of 400 (8 threads), so replay must pin the thread count. Vosk small was *not* repeatable within a process (46 of 50).
* *Pre-roll matters:* with a 300 ms pre-roll the k2-v2 int8 CER on 200 clips was 14.8%; cutting the segment to start 150 ms before the energy-defined onset gave 16.8%, 100 ms 18.9%, at the onset 22.1%, 100 ms after it 23.3% (section 6.5). A streaming model additionally needs trailing zeros before +input_finished()+ to flush its last chunk (Nemotron 560 ms: 23.8% without, 20.9% with 1 s of padding, 100 clips).
* *Licenses (section 3.2):* sherpa-onnx, whisper.cpp and Vosk code are Apache-2.0 / MIT. *Non-permissive or non-standard:* SenseVoice weights (custom FunASR license with a forfeiture clause), Moonshine ja weights (non-commercial community license; not run). *New to the project:* Nemotron's OpenMDW-1.1 (permissive in substance). *Unverified:* the ja-en zipformer weights, Vosk's training data (its README reports CSJ test sets), Whisper's, Qwen3-ASR's, Dolphin's and Omnilingual's training data. *Risks to decide:* ReazonSpeech k2-v2, parakeet-ja and kotoba-whisper descend from the ReazonSpeech corpus, whose gate demands use under Japanese Copyright Act Article 30-4 only (whether that follows the weights is not determined here); Nemotron's card lists Common Voice 8.0 as training data, our test corpus.
* *Rust integration (section 7):* the new official +sherpa-onnx+ crate 2.0.1 (Apache-2.0) built offline in 91 s from a SHA-256-pinned library archive and reproduced the Python text on 100 of 100 clips, but its build script downloads without a checksum unless two environment variables are set, and it fails the repository's +cargo deny+ license gate on two build-time-only crates (+bzip2-1.0.6+, +CC0-1.0 OR MIT-0+). +sherpa-rs+ fails on MPL-2.0. +whisper-rs+ passes +cargo deny+ but needs cmake, a C/C++ toolchain and libclang, and could not be built on this machine.
* *Recommendation:* sherpa-onnx with ReazonSpeech k2-v2 int8 as the default CPU engine for partial and final transcripts, in the S2 supervised-sidecar pattern; parakeet-ja as the accuracy option on the same runtime; Nemotron streaming is the one to watch if append-only native partials matter more than accuracy (not recommended now); a Whisper-class tier on GPU as an optional later slice; reject SenseVoice, Moonshine, Vosk, Qwen3-ASR, Omnilingual and CPU Whisper. *Conditional on the ReazonSpeech corpus question (Q1).* Details in sections 8 and 9.

Findings that need a decision from the project owner:

* *Non-permissive or non-standard:* SenseVoice weights (custom FunASR license with a conduct-forfeiture clause) and Moonshine ja weights (Moonshine Community License: free only for research, non-commercial use and organisations under US$1M annual revenue). Neither adopted; Moonshine not run. Nemotron's OpenMDW-1.1 is permissive in substance but new to this project.
* *Unverified:* the ja-en zipformer weights license; the Vosk ja models' training data; Whisper's training data; the training data of Qwen3-ASR, Dolphin and Omnilingual; the license of the third-party Qwen3-ASR ONNX export.
* *Contamination risk:* Nemotron's card lists Common Voice 8.0 among its training data (our test corpus is Common Voice 22.0).
* *Training-data terms:* every top accuracy candidate (ReazonSpeech k2-v2, parakeet-ja, kotoba-whisper) descends from the ReazonSpeech corpus, whose gate requires agreeing to Japanese Copyright Act Article 30-4 use. The weights carry Apache-2.0 / CC-BY-4.0 licenses, but nobody here has determined whether the corpus terms follow the weights. This is the principal licensing risk and is listed in section 12.

== 4. Dataset and method

=== 4.1 Clips

Common Voice 22.0 ja test split; clips present in the extracted archive with at least 2 up-votes and no down-vote (6276 candidates, the same count as EXP-0001), one clip per +sentence_id+, decoded duration 1.0-12.0 s, seeded shuffle (20261109), first 400 kept.
The mp3 is decoded and resampled to 16 kHz mono (+scipy.signal.resample_poly+).

=== 4.2 Segments, standing in for S2 VAD output

Each clip is trimmed to start 0.30 s before the first 20 ms frame above max(-50 dBFS, peak RMS - 35 dB) and end 0.50 s after the last such frame, and written as 16-bit PCM.
This stands in for "Silero segment plus pre-roll plus silence tail" without involving the VAD, so a VAD error (late onset, early cut) is not part of these numbers; section 6.5 measures what a clipped onset costs separately.
The speech onset is about 0.30 s into every segment by construction, which is how "time after speech onset" is computed.

=== 4.3 Text normalisation (identical for gold and hypothesis)

. NFKC (full/half width, compatibility forms), lower-case.
. Remove every character whose Unicode category is punctuation (+P*+), symbol (+S*+), separator (+Z*+) or control/format (+C*+).
. Nothing else is rewritten: no kana/kanji conversion, no numeral conversion, no word list.

*CER* is micro-averaged: total Levenshtein distance over total reference characters (+rapidfuzz+), reported with a 95% bootstrap interval over clips (2000 resamples, seed 20261109).
A secondary column collapses every run of digits and kanji numerals (+0-9〇一二三四五六七八九十百千万億兆+) into one placeholder, so that choosing "25" versus "二十五" does not count as an error; it also hides real digit errors and is never used instead of the primary figure.
Paired differences are computed on the same clips with a paired bootstrap.

=== 4.4 What is timed

* *Final call latency:* wall time of one transcription call on the complete segment (Python +perf_counter+). For offline engines this is the time from "segment complete" to "final text", on top of whatever silence the VAD needed to close the segment. For Whisper it includes one HTTP round trip over loopback and 16-bit WAV encoding.
* *Partials:* offline engines have no partial output; they are emulated by re-decoding the growing prefix every 0.5 s of audio, which is what an integration would have to do. Vosk produces partials natively; it is fed 100 ms chunks. "First partial after speech onset" is the audio time of the first non-empty partial minus the onset (0.30 s) plus the cost of that call. For the emulated engines it is bounded below by the 0.5 s step grid, not by the model.
* *RTF* is the sum of final call times over the sum of segment durations. It is below 1 when the engine keeps up in real time.
* *Load time:* constructing the recognizer in-process; for Whisper, spawn of +whisper-server+ until it answers. *Peak RSS* is the peak working set of the process holding the model (the server child for Whisper). Python and numpy are part of the in-process figure.
* *First call* is the first transcription after load (lazy initialisation); three more calls warm up and are not recorded.

=== 5.4 Reading the accuracy tables

* The intervals are wide and the clips are short read sentences; the *ordering* of the engines is the only claim. "Paired difference" is the difference in micro CER on the same clips with a paired bootstrap; negative is better than k2-v2 int8.
* Heavy tails dominate: on the 400-clip set the worst 10% of clips carried about 46% of the total edit distance of k2-v2 fp32, and 23 clips exceeded 50% CER on each of the four engines first run (k2-v2 int8 and fp32, ja-en zipformer, parakeet; probable wrong labels or unusable audio, kept in the figures). The "clips with CER > 50%" column is a robustness view: k2-v2 fp32 35, parakeet 32, SenseVoice 43, k2-v2 int8 41, ja-en 55 of 400.
* The number-insensitive column barely moves the figures (by under 1 point for every engine), so numeral spelling is not what separates the engines here.
* *Within noise of each other (first 150 clips):* k2-v2 int8, k2-v2 fp32, SenseVoice, whisper large-v3-turbo (CPU and GPU), kotoba-whisper (GPU), whisper medium. *Distinguishable from k2-v2 int8:* parakeet (better, -4.1 pp, interval -8.7 to -0.1), Vosk small (worse, +13.4 pp), whisper small (worse, +7.2 pp). The int8 quantisation of k2-v2 cost 1.6-2.3 pp against fp32 (interval -3.1 to -0.4 on 400 clips) for half the memory.
* *Vosk big* (60 clips): 15.2% against 13.8% for k2-v2 int8 on the same clips (difference +1.4 pp, interval -5.3 to +7.0), i.e. competitive on read speech, at 1.7 GB resident and with unresolved training-data provenance (section 3.2). Vosk small is far worse (23.7% on the same 60).
* *Whisper:* accuracy grows with model size (small 21.6%, medium q5_0 15.6%, large-v3-turbo q5_0 13.1% on 150 clips; kotoba-whisper v2.0 q5_0 10.8% on the first 60 clips against 13.8% for k2-v2 int8 there, not distinguishable). Quantisation to q5_0 was not compared with fp16 on CPU; on GPU the fp16 turbo was 11.5% against 13.1% for the CPU q5_0 on the same 150 clips (within noise).
* *Newer sherpa-onnx models:* Dolphin small (CTC, 644 MB) 21.6% on 400 clips, +3.0 pp against k2-v2 int8 (interval +0.5 to +5.5), RTF 0.078; Qwen3-ASR 0.6B int8 (LLM-style decoder, 1987 MB, load 13.6 s) 21.7% on 150 clips (+7.4 pp, interval +2.8 to +11.5) and the engine logged repetition loops that it truncated; Omnilingual 300M CTC v2 32.9% on 150 clips (+18.6 pp). None is a candidate on these numbers.
* *Nemotron 3.5 streaming:* the 560 ms export gave 29.0% on 400 clips without tail padding (+10.5 pp, interval +8.0 to +12.9; 90 clips above 50% CER, 32 empty outputs) and 21.6% on the first 150 clips with 1 s of trailing zeros (+7.3 pp, interval +2.9 to +11.4; 7 empty outputs); the 160 ms export was worse again (26.0% with padding, +11.7 pp). Without trailing zeros a streaming model never decodes its last, incomplete chunk, so the padding is part of a correct integration (section 6.5). The residual empty outputs and the gap to the offline transducers were not diagnosed (language option, export, domain, or all three). Nemotron's card lists Common Voice 8.0 among its training data, so this corpus should if anything flatter it.

* The sherpa-onnx transducers answer a 3-4 s segment in about 0.1-0.3 s on 4 CPU threads (k2-v2 int8 p50 123 ms, p95 289 ms, max 393 ms over 400 clips). The time from the end of speech to the final text is therefore the VAD silence needed to close the segment (EXP-0001: end detected a median 61 ms late; the S1 fallback waits 800 ms before an irreversible turn-take, which is a separate policy) plus this call, minus whatever speculative work was done during the silence. The call cost grows roughly with segment length (RTF 0.04), so a 10 s segment costs about 0.4 s.
* *Threads:* k2-v2 int8 at 1 / 4 / 8 threads: RTF 0.057 / 0.039 / 0.048 (p50 176 / 123 / 158 ms). More threads than 4 did not help on these short segments. One thread still keeps up in real time with 17 times headroom, which matters when TTS, the renderer and an LLM client share the CPU (their cost was not measured).
* *Memory:* peak working set includes the Python interpreter and numpy (38 MB before any model was loaded). k2-v2 int8 was 275 MB right after load and grew to 548 MB while decoding (runtime buffers), parakeet went from 720 to 938 MB; a native sidecar would be a little smaller. fp32 k2-v2 doubles it (1050 MB) for a 1.6-2.3 point CER gain; parakeet-ja is 938 MB with a 9 s load.
* *Whisper on CPU:* the fixed 30 s encoder window makes the final call cost almost independent of the segment length (small p50 2.9 s at 8 threads and 4.4 s at 4; large-v3-sized models 12 s). RTF above 1 means the engine cannot keep up with a continuous stream; Whisper models are therefore not candidates for partials or low-latency finals on this CPU. Shortening the window (+-ac+) was not tried (limitation L9).
* *Vosk:* the small model's RTF (0.8, repeated at 0.7 on a second run) was far worse than the big model's (0.14), which also reports its own tail cost: the last 100 ms chunk plus the final result took p50 25 / p95 173 ms (small) and 115 / 298 ms (big), so for a streaming engine the speech-end-to-final latency is small once the model keeps up; the small model does not keep up.
* The first call after load was as fast as the later ones for every sherpa-onnx model (no lazy-initialisation penalty), but loads took 1.5-9 s, so the model must be loaded at sidecar start, not at the first utterance.
* One Whisper-small call took 11.6 s while a Rust build and an archive extraction were running (section 11), probably because of that load; that maximum is not representative.
* *Nemotron 3.5 streaming on 4 CPU threads:* RTF 0.23 (560 ms chunks, no padding) to 0.30 (with 1 s padding) and 0.68-0.86 for the 160 ms export (smaller chunks mean more encoder calls); 833-889 MB resident; load 2-10 s. It is a 0.6B model: about 6-22 times the CPU cost of the k2-v2 transducer (RTF 0.23-0.86 against 0.039) for lower accuracy here.

* *Offline engines emulated as streaming:* a partial is a full re-decode of everything since the segment start. The k2-v2 int8 call cost p50 102 ms / p95 246 ms across the growing prefixes (parakeet p50 269 ms / p95 684 ms), well inside a 0.5 s step; the largest was 379 ms. The first non-empty partial at 236 ms after onset is the 0.5 s grid (audio time 0.5 s, 0.2 s after onset) plus one decode; a 0.25 s step would roughly halve it at twice the decode load.
* *Partials are not stable.* Only 52-59% of the non-empty sherpa-onnx partials were a prefix of the last partial's text (after normalisation), and 40-62% for Whisper (8 clips; 4 for kotoba); Vosk's native partials were 82-86%. Earlier text is rewritten as audio arrives. Consumers must treat a partial as a replaceable guess (section 9).
* *Vosk* streams natively with 100 ms chunks: first non-empty partial about 1.1 s (small) / 1.2 s (big) after speech onset, much later than the 0.2-0.3 s of the emulated offline transducers; its per-chunk cost is small (p50 1 ms) for the big model. That latency is a property of its decoding (it emits words when confident), not of this harness.
* *Whisper* partials cost a whole 30 s window decode each (3-12 s on CPU), so the emulation is not usable; the column is shown only to document that. On the GPU build a partial costs about as much as a final (p50 143-154 ms, section 6.6) and the first partial arrives about 330 ms after onset.
* *Nemotron 3.5 streaming (native):* partials were append-only (100% were a prefix of the final text, about 40 per clip at a 100 ms feed), a property the offline engines do not have. The cost is latency: the first non-empty partial came about 1.1 s after speech onset for both the 560 ms and the 160 ms export (p95 1.6-1.7 s), later than the 0.2-0.3 s of the emulated k2-v2 partials, and the per-chunk cost is small (p50 0 ms when a chunk needs no decode, p95 144 ms at 560 ms). After the last audio the model needs its trailing padding processed: last chunk plus 1 s of zeros plus finish took p50 285 ms (560 ms export) and 782 ms (160 ms export).

=== 6.5 Cost of a clipped onset (pre-roll sensitivity)

ReazonSpeech k2-v2 int8, 4 threads, first 200 clips, segment start moved relative to the energy-defined speech onset (section 4.2; every segment normally starts 300 ms before it):

[cols="2,2,3",options="header"]
|===
|Segment starts |CER % |95% CI

|300 ms before the onset (the normal segment) |14.8 |11.2-19.1
|150 ms before |16.8 |13.3-21.3
|100 ms before |18.9 |15.2-23.0
|50 ms before |20.4 |16.7-24.7
|at the onset |22.1 |18.4-26.3
|50 ms after (onset already lost) |23.9 |20.1-28.3
|100 ms after |23.3 |19.9-27.4
|150 ms after |26.2 |22.6-30.5
|200 ms after |28.1 |24.2-32.6
|300 ms after |31.9 |28.0-36.0
|===

Reading:

* The recogniser is sensitive to a clipped onset: starting at the energy onset instead of 300 ms earlier costs about 7 points, and each further 100 ms of lost speech costs roughly 2-3 more. The energy rule fires at 35 dB below the peak frame, so the true acoustic onset is earlier than "the onset" here, and the shifts are not a one-to-one model of VAD lag; the shape, not the exact values, is the finding.
* EXP-0001 measured Silero's onset p50 at 48 ms and p90 at 112-144 ms after an energy-defined start, with 12.7% of utterances above 100 ms. With no pre-roll, utterances whose onset is reported late would be cut roughly like the 0 to +100 ms rows (22-24%); with the S2 default of 300 ms the lead-in absorbs a lag of that size. *A pre-roll of 300 ms (the S2 default) is the least this table supports*: the curve has not flattened at 300 ms, and whether a longer pre-roll still helps was not tested because the clips were trimmed to 300 ms of lead-in. The S2 hard ceiling is 2 s.
* The segment must also carry a silence tail after the end edge (0.5 s here); a tail-length sweep was not run.
* *Streaming models need trailing zeros.* A cache-aware streaming model decodes in fixed chunks and never decodes the last incomplete chunk unless it is padded before +input_finished()+. Nemotron 3.5 (560 ms export) on the first 100 clips: 0 s padding 23.8% CER (95% CI 19.7-28.5, 7 empty outputs), 0.3 s 21.5%, 0.66 s 21.0%, 1.0 s 20.9% (16.9-25.3, 5 empty), 1.5 s 20.9%. The tail of a segment (the S2 silence after the end edge, plus up to about 1 s of padding added by the transcriber) is therefore a first-class parameter of a streaming integration. A tail-length sweep for the offline models was not run.

== 9. Proposed integration shape (for S3b; not decided here)

Consistent with S2: a supervised child process, bounded queues, drop-newest, degrade to "no transcripts" without blocking the scheduler, no raw audio retention, no restart without an operator decision.

[source,text]
----
VAD sidecar (S2, unchanged edges)                    STT worker                          runtime (app)
  mic -> 16 kHz -> Silero edges ---+
  PreRoll (<= 2 s, in memory) -----+--> segmenter --> bounded queue (1-2 segments) --> decode loop
                                        start edge: copy PreRoll tail (>= 300 ms)        partial every ~500 ms of audio
                                        accumulate until end edge + tail                  final once on end edge + tail
                                        hard cap per segment (e.g. 30 s), then force-final
                                                                                          |
                                                              one JSON line per revision  v
                                                              stdout (separate pipe) --> SpeechTranscriptTracker
                                                                                          (bounded, untrusted content)
----

. *Same supervised-sidecar pattern.* The transcriber is part of, or a child of, the S2 speech sidecar so that the raw audio never crosses a process boundary that the app does not own: the sidecar already owns the microphone, the 16 kHz stream and the +PreRoll+ ring. Two variants, to be decided in S3b (open question Q3): (a) a transcriber thread inside +speech-vad-sidecar+ behind a cargo feature; (b) a second child, +speech-stt-worker+, spawned by the sidecar and fed PCM over its stdin pipe, so a model crash cannot take the VAD down. Variant (b) keeps the heavy model out of the VAD process at the cost of one local pipe of 16 kHz PCM (32 kB/s).
. *Segment source.* A segment starts at a VAD start edge and takes the newest +PreRoll+ samples (the measured default is 300 ms; EXP-0001's onset-lag p90 was 112-144 ms and section 6.5 shows what each lost millisecond costs). It ends at the end edge plus a silence tail. A minimum speech duration for transcription (the raw edges have none) and a maximum segment length (the models are limited to about 30 s) are STT-side policy. Pre-roll and segmenter buffers are in memory, bounded, never written to disk, and have length-only +Debug+ output.
. *Partials.* While a segment is open the worker re-decodes the accumulated audio at most every ~500 ms (the measured per-call cost is a fraction of that, section 6.2) and emits a *partial* only when the text changed. The queue between capture and decoder holds at most one pending decode; if the decoder falls behind, partial requests are *dropped* (never queued) and the final always wins. The decoder never runs on the audio-capture thread, never in the scheduler or frame loop.
. *Wire shape (proposal, schema-first per AGENTS.md).* A new normative schema +schemas/speech-transcript.schema.json+ with positive and negative fixtures, then Rust domain types, in the style of +speech-observation+: +segment_id+ (monotonic per sidecar run), +revision+ (monotonic per segment), +kind+ (+partial+ or +final+), +text+ (bounded characters, bounded batch bytes), +language+ (declared, never inferred), +covered_audio_ms+ and +observed_at_ms+ on the runtime timeline (the end of the audio the text covers, same clock handshake as S2), +engine+ (model id, sha256 of the model files, +calibrated+-style flag: an engine score, if any, is a provider value), and an explicit +complete=false+ on partials. No audio, no PCM, no word timings in the first slice. The schema carries no source class, plane, trust or priority field: the receiving ingress assigns them.
. *Trust.* Transcribed speech is content from a microphone speaker: source class +speech+, plane +content+, trust +untrusted+, like the S1 observations; it cannot mint a privileged-control capability or a durable-memory permit even when the operator speaks, and the model's output is data. The operator ceiling +AIVTUBER_INGRESS_SOURCE_CLASSES+ applies before parsing, as for observations. A transcript that says "ignore your rules" is just text.
. *Partial versus final.* Only a *final* may become conversation input to Reflex or Thinking, and only through the normal normalizer and bounded typed request path. A *partial* is incomplete content: it may feed observation-style policy (for example to hold the floor while the user is still talking) but must not start a reply, and must be superseded by revision, never appended. Section 6.2 measured that only about half of the partials are prefixes of the final text, so a consumer must not assume stability.
. *Failure policy.* Same as S2: a child that exits, closes stdout, sends 32 consecutive invalid lines, or exceeds its decode deadline degrades to "no transcripts", is counted once as provider unavailable, and is not restarted automatically. A hung decode is cancelled by a per-segment deadline in the worker; a hung child that stops emitting is *not detected* without a heartbeat (the S2 limitation), which S3b should add for this child. The deterministic silence fallback of S1 keeps working without any transcript.
. *Pins and provenance.* The worker takes model file paths from operator configuration and refuses to start unless every model file (and, if dynamically loaded, every engine library) matches a SHA-256 pinned in the binary, as S2 does for the Silero model. Transcript lines record the model id and hash so replay and audit can tell engines apart. No build step downloads anything; the library archive is fetched and hash-checked by a separate documented step.
. *Replay and metrics.* Transcript lines are replayable with logical time like speech observations (fixture files, no microphone or model); metrics are bounded counters and histograms: decode latency per final, queue drops, partials per segment, final-after-end latency, rejected lines by reason.
. *Privacy.* No raw audio retention beyond the in-memory ring and the open segment; no transcript persistence in the sidecar; durable memory writes stay behind their own non-serializable permit.

== 10. Limitations

. *L1, read speech, one speaking style.* Common Voice is single-speaker read sentences recorded on contributors' own devices. It has no conversation, fillers, backchannels, overlap, stream-game background or the long, loud, fast speech of a streamer. CER on it says little about absolute performance on VTuber audience or operator speech.
. *L2, noisy gold.* Common Voice labels contain typed romaji, English words, rare place names and sentences whose text does not match the audio. On the 400-clip set 23 clips exceeded 50% CER on each of the first four engines run (k2-v2 int8 and fp32, ja-en zipformer, parakeet); these are probable label or audio faults and were *kept* in the primary figures (the scripts offer +--drop-common-bad+ as a view). The absolute CER is therefore pessimistic and the ordering is the only claim.
. *L3, orthographic CER.* Japanese has several correct spellings (kanji versus kana, okurigana, numerals). Counting a correct but differently spelled word as errors penalises every engine, some more than others (an engine trained on one corpus's spelling conventions is favoured). The normalisation removes only punctuation and width differences. No reading-based (kana) CER was computed.
. *L4, possible training-data overlap.* Common Voice text and audio may have been in the training data of some candidates (Whisper, SenseVoice); this was not checked. ReazonSpeech-derived models were trained on Japanese TV speech, which is a different domain.
. *L5, segments are not VAD output.* The segment boundaries come from an energy rule (section 4.2), not from the Silero sidecar, so late onsets, early cuts and false segments are not part of these numbers (section 6.5 gives the onset sensitivity of one engine only).
. *L6, partials of offline engines are emulated* by re-decoding prefixes every 0.5 s, and the "time to first partial" is bounded by that grid. A tuned step would change it. Whisper partials were measured on 8 clips only.
. *L7, sample sizes.* 400 / 200 / 150 / 60 clips depending on the engine; the intervals in section 5 are wide (the 95% interval on a CER of 15% spans roughly 10 to 19 points at n = 150-200) and clips share sentences structure and contributors. Differences under about 3-4 points are not distinguishable here except where a paired interval says otherwise.
. *L8, one machine, one run per configuration, a Python driver.* A Zen 2-class 8-core desktop CPU, Windows 11, 8 threads for CPU Whisper and 4 for the others. Native bindings may be a little faster; other CPUs, laptops, Linux and macOS were not measured. The Rust binding was run only to compare text (100 clips) and its timing was not recorded as a benchmark (it ran concurrently with a Whisper run).
. *L9, Whisper configuration.* +whisper-server+ with default decoding (greedy, best-of 2) and temperature 0, no prompt, no VAD, no audio-context shortening (+-ac+), no word timestamps. Whisper always processes a 30 s window; shortening it (+-ac+) trades accuracy for speed and was not tried. The binary is a nightly build, not a tagged release.
. *L10, Vosk partials.* The Python wheel was fed 100 ms chunks; the small model's measured real-time factor (0.8, and 0.7 on a repeat run on an idle machine) was far higher than the big model's (0.14); this was not investigated and may be a property of this wheel or of the small model's lookahead decoding rather than a harness artefact. Its same-process repeat differed on 4 of 50 clips while two separate processes agreed on 60 of 60; not explained.
. *L11, license reading is partial.* See section 3.2: the ja-en model's license, Vosk's training data, Whisper's training data, the ReazonSpeech corpus terms as applied to model weights, and pip dependencies were not resolved or audited. Nothing here is legal advice.
. *L12, no GPU path for sherpa-onnx.* Only the Whisper CUDA binary was tried (section 6.6); contention with the avatar renderer on the same GPU was not measured.
. *L13, no confirmatory criterion.* Nothing here is a pass/fail against a pre-stated threshold; do not use these numbers as SLOs.
. *L14, Nemotron configuration.* Run with +language=ja+ set per stream, greedy decoding, default sherpa-onnx streaming settings, a 100 ms feed, and (in the padded runs) 1.0 s of zeros before +input_finished()+; the padding length was probed on 100 clips only (0 / 0.3 / 0.66 / 1.0 / 1.5 s gave 23.8 / 21.5 / 21.0 / 20.9 / 20.9% CER). Its worse-than-offline accuracy may be a property of this export or setting; the empty outputs (7 of 150) were not diagnosed. The 560 ms run on 400 clips was done *without* padding; the padded runs cover 150 clips.
. *L15, models not run.* Moonshine ja (license), Cohere Transcribe, FunASR-Nano, Dolphin base, the Omnilingual 1B models, the sherpa-onnx whisper exports and the ESPnet/NeMo ReazonSpeech models were not measured; the catalogue (500 assets) may contain further Japanese-capable models that a keyword listing did not show.

== 11. Protocol deviations

* *The expected streaming ReazonSpeech zipformer does not exist* (+reazonspeech-k2-v2+ is an offline model); partials of offline models are emulated by prefix re-decoding. Vosk was added as a native streaming Japanese engine.
* *Late correction of the candidate survey.* The first reading of the sherpa-onnx +asr-models+ listing stopped at the first 40 +streaming+ names and concluded that no streaming Japanese model exists, and a first version of this record said so. A review of the full 500-asset listing found Nemotron 3.5 ASR streaming (multilingual, Japanese included) and several newer multilingual offline models (Qwen3-ASR, Dolphin, Omnilingual, Moonshine ja, Cohere Transcribe, FunASR-Nano). Nemotron (two chunk sizes), Qwen3-ASR, Dolphin small and Omnilingual 300M were then downloaded, pinned and run; the record was rewritten. Moonshine ja was read for its license and not run (non-commercial). Cohere Transcribe (1.7 GB, gated upstream), FunASR-Nano and the others were not run.
* *Nemotron was run twice:* first without trailing padding (400 clips for the 560 ms export, 150 for the 160 ms export), then, after the first results showed 32 empty outputs, a padding probe (100 clips) and padded runs on 150 clips. Both are reported.
* *Run sizes differ by engine:* 400 clips for most sherpa-onnx engines (150 for Qwen3-ASR, Omnilingual and the Nemotron 160 ms and padded runs), 200 for Vosk small, 60 for Vosk big and for kotoba-whisper q5_0, 150 for the other Whisper runs (CPU cost, always the first clips of the same seeded order); paired comparisons use common clips. A first plan of 200 Whisper clips was cut to 150, and kotoba q5_0 to 60, after the first runs showed 7-12 s per clip. Vosk big was cut from 200 to 60 when a partial run showed it was slow.
* *Whisper binary:* release v1.9.5 ships no binary assets; the nightly +b5454+ (v1.9.5 plus later commits) was used instead of building from source. A source build through +whisper-rs-sys+ failed here for lack of a C/C++ compiler (section 7). The vendored whisper.cpp inside that crate is 1.8.3.
* *SenseVoice archive:* the first smoke run used the 2025-09-09 sherpa-onnx SenseVoice asset, which is a Cantonese fine-tune and transcribed Japanese as Chinese; it was replaced by the 2024-07-17 asset before any reported run.
* *Parakeet:* the sherpa-onnx export contains only the CTC head of the TDT+CTC model; the TDT transducer was not run.
* *ja-en zipformer:* run, but its license could not be read (section 3.2).
* *Concurrency:* the Rust build and run, a +cargo deny+ run and an extraction of a 0.7 GB archive ran while the Whisper-small run was in progress; the Rust steps used idle priority and two jobs. One Whisper-small call took 11.6 s (p95 3.5 s), probably from that load; the reported p50 is robust to it, the maximum is not. The other timings were taken while only light shell commands ran.
* *Common Voice from a third-party mirror* (as in EXP-0001); the official distribution was not accessed.
* *Repository search:* tgrep 1.0.11 was installed and the checkout indexed, but lookups in specific known files (docs, +Cargo.lock+, +deny.toml+, the S2 sources) were done with grep and sed in the shell rather than tgrep; none was a repository-wide content search that the two tools could disagree on. External pages and release metadata were read with the fetch, curl and gh tools.
* *GPU:* run only for Whisper (CUDA build of the same nightly); the first download of the 0.7 GB CUDA archive over the release URL returned HTTP 504 repeatedly and was fetched with +gh release download+ instead (sha256 identical to the one pinned in +fetch_assets.py+). sherpa-onnx GPU builds were not run.
* *Kotoba fp16 and turbo fp16 on CPU were not run* (about 40 minutes each); kotoba-whisper was measured on CPU as q5_0 only (60 clips) and on GPU as fp16. +large-v3-turbo+ fp16 was downloaded for the GPU run only.
* *Whisper-small at 4 threads* was run on 40 clips only, to show thread scaling.

== 12. Open questions

. *Q1, ReazonSpeech corpus terms (blocking for adoption of any ReazonSpeech-derived weights).* The corpus gate requires agreeing to use the data solely for Japanese Copyright Act Article 30-4 purposes. The k2-v2 weights are Apache-2.0 and parakeet-ja is CC-BY-4.0, but does the corpus condition follow the weights into a product that ships them (and, for a VTuber, into commercial streaming use)? The project owner should decide whether to accept the risk, obtain a legal reading, or restrict the first slice to a model with clearer provenance. Until then the recommendation below is *conditional*.
. *Q2, model choice for the default.* ReazonSpeech k2-v2 int8 (fast, small, Apache-2.0) or parakeet-ja (better in this set by a paired margin whose interval just excludes zero, 2.5 times slower, about 940 MB, CC-BY-4.0 attribution)? The measurements support either; the decision depends on the CPU budget next to TTS, the avatar renderer and the LLM client (not measured), and on Q1.
. *Q3, process shape.* Transcriber thread inside +speech-vad-sidecar+ (no audio crosses a pipe) or a separate +speech-stt-worker+ child (a model crash cannot take VAD down; PCM crosses a local pipe)? Section 9 prefers the second for fault isolation; the first is simpler. Decide in S3b with the S2 sidecar owner's input.
. *Q4, native library packaging.* Official +sherpa-onnx+ crate (two allowlist additions to +deny.toml+, build-time-only crates, a CI rule to always set +SHERPA_ONNX_ARCHIVE_DIR+) or our own +libloading+ FFI with runtime SHA-256 pins (one new crate, we own the unsafe surface)? Either needs the pinned library archive for each supported OS/arch (only Windows x64 was exercised).
. *Q5, transcript wire shape.* A new +speech-transcript+ schema (proposed in section 9) or an +EventEnvelope+ kind? The S1 reasoning (signals do not ride the content queue) argues for a separate pipe for partials; final transcripts are content and eventually become +EventEnvelope+ content after the normalizer. Where is the boundary, and who owns the revision/supersede semantics?
. *Q6, text policy for partials.* May partial text influence floor decisions (for example hold the floor while the user is still talking) or only the final? A partial that says "stop" must not stop anything (model output is data); the operator stop stays on its independent path.
. *Q7, a Japanese conversational test set.* All accuracy here is read speech. A permissively usable, human-transcribed Japanese conversation or streaming-speech set (the same blocker as EXP-0001 11.1 item 1) is needed before CER numbers can be treated as predictive; none was found.
. *Q8, Whisper-class accuracy tier.* Is a slow high-accuracy second pass (GPU or a few seconds of CPU per utterance, final-only) wanted after the fast partial/final path, for example for logging or for correcting the first final? It would be a separate decision with its own latency budget; nothing here measures its benefit on real speech.
. *Q9, punctuation, inverse text normalisation and kana/kanji policy.* The engines differ (SenseVoice and Whisper add punctuation; the transducers do not). Where does text normalisation for downstream Reflex/Thinking live, and is a reading (kana) form needed for matching?
. *Q10, native streaming versus prefix re-decode.* Nemotron gives append-only partials that never need superseding but starts late (about 1.1 s), costs roughly 6-22 times the CPU and was less accurate here; the offline transducers give early (about 0.25 s) but revisable partials at a small fraction of the CPU. Which property does the floor policy (#81) actually need from a partial? If append-only partials are needed, is a later streaming Japanese model, or a diagnosis of the Nemotron gap, worth a follow-up evaluation?
