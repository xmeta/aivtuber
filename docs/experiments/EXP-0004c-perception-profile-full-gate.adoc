= EXP-0004c: Perception profile with the full local profile running (#90, follow-up to EXP-0004b)

:toc:
:toclevels: 2

This is a durable experiment record in the link:README.adoc[Durable Experiment Records] format.
It is the first gate that link:EXP-0004b-single-multimodal-model.adoc[EXP-0004b] left open (its section 7): repeat the memory and latency-probe check of the opt-in "perception" profile (one `llama-server` with Qwen3-VL-4B-Instruct Q4_K_M plus projector, `--parallel 2`, `-c 8192`) with the avatar renderer and the STT and TTS sidecars running.
Scripts only (`examples/benchmarks/vision/`, extended with `--attach` and a `captions` command): no production code, model, binary or image is committed.

== 1. Record

[source,text]
----
Decision question:
  With the whole local profile running (app, supervised TTS and STT sidecars, VAD sidecar, avatar page in a browser),
  does the perception profile still show no VRAM spill, and a Thinking first-token p95 at or below about 1.5x the
  Qwen3-4B baseline of EXP-0004b (0.386 s, so about 0.58 s)?

Context / baseline:
  EXP-0004b measured 6.9 GB peak of 8.2 GB without the sidecars and the renderer and extrapolated about 0.5 GB of
  headroom with them. Baseline p95 0.386 s is Qwen3-4B alone (EXP-0004b section 4.1).

Hypothesis / expected outcome:
  Headroom is thin; the sidecars are CPU engines, so the extra VRAM is the renderer's. Expected: passes, narrowly, or
  spills.

Guardrails:
  Loopback only; invented viewer text and synthetic frames only; the Thinking GGUF of the default profile was not
  downloaded; nothing committed except scripts and this record; spill judged by a latency probe and Thinking latency,
  not by free VRAM.

Decision-changing evidence:
  Total GPU memory with everything resident, the latency probe before and after, Thinking first-token p50/p95 alone and
  with captions every 10 s (with and without the yield gate) and every 5 s, caption latency, and a TTS and STT round.

Cheapest informative test:
  One resident-stack run of the EXP-0004b `mux` workload attached to the already running server.

Dataset/workload:
  As EXP-0004b: 30 Japanese Thinking requests 2.5 s apart per condition, 30 synthetic 768x432 frames, describe-v1
  prompt, 96 max tokens, seed 1234. TTS and STT rounds use the app's own path (section 4).

Commit/base/head:
  Branch docs/90-exp-0004c-full-profile-gate from origin/main at e5fa3d23 (#315).

Profile/config fingerprint:
  llama-server b12224 Vulkan: Qwen3VL-4B-Instruct-Q4_K_M + mmproj Q8_0, -c 8192 --parallel 2 -ngl 99, alias
  qwen3-vl-4b-instruct, AIVTUBER_OPENAI_MODEL set to that alias. The app, sidecars and env file are the output of
  `aivtuber-setup local` (--skip llm) from this checkout; STT 4 threads, TTS 4 threads (as the quickstart).

Seed / asset versions / toolchain:
  Seed 1234. Pins from packaging/local-profile-pins.json (sherpa-onnx 2.0.1, ReazonSpeech k2-v2 int8, Supertonic 3
  int8, Silero VAD). Release build of this checkout; Python 3.13; Edge (Chromium 157) headless for the avatar page.

Other relevant environment:
  Same Windows 11 desktop, 8 GB WDDM GPU, as EXP-0004/0004b, shared with other desktop software. That software held
  2.36 GB when the experiment started and 2.71 GB when it ended (section 3). 2026-11-11, one machine.

Confirmatory criteria (supervisor, issue #90):
  Go if no spill and Thinking first-token p95 at most about 1.5x the Qwen3-4B baseline; otherwise the perception
  profile needs about 12 GB of VRAM.

Actual / expected-vs-actual:
  Sections 2 to 5. Two identical resident-stack runs disagreed: the first passed, the second showed the spill signature.

Decision:
  No-go on 8 GB (section 6): record that the perception profile needs about 12 GB of VRAM.

Follow-up / owning issue:
  #90 (S1b scope, ADR-0007 wording; those are the supervisor's).

Revisit condition:
  A GPU with 12 GB, a desktop that leaves clearly more than 2.7 GB free of other use, a smaller multimodal model, or a
  llama.cpp build with a smaller KV/compute buffer.
----

== 2. Result summary

* *Memory.* Qwen3-VL-4B at two slots adds about 4.4 GB (6,825 MiB total after load against 2,362 MiB before). The whole stack added about 0.2 to 0.25 GB more (the renderer's browser; the CPU sidecars added no VRAM), giving 6.8 to 7.1 GB in most runs and 7.45 to 7.6 GB in one, on a card with 8.19 GB.
* *Run 1 (resident stack, 6.8 GB):* no spill signature. Probe 68 ms before and 59 ms after. Thinking first-token p95 with captions: 0.511 s at 10 s (1.32x of 0.386 s), 0.496 s with the yield gate (1.29x), 0.476 s at 5 s (1.23x). But Thinking *alone* was slower and noisier than in EXP-0004b (p50 0.67 s, p95 1.64 s, last seven requests 1.2 to 2.6 s), with no explanation found.
* *Run 2 (same stack, 7.5 GB, the desktop holding more memory):* spill signature. Idle probe 179 ms (the EXP-0004b value was 59 to 86 ms), Thinking alone p50 1.51 s and p95 4.19 s (11x of 0.386 s), p95 5.17 s with captions at 10 s, caption p95 12.2 s and maximum 17.2 s. The yield-gate condition later in the same run recovered (p95 0.434 s) and the post-run probe was 71 ms, so the degradation came and went inside one run.
* *Speech sidecars still work but are slowed by caption load.* TTS real-time factor (synthesis time over audio length) median 0.38 with captions off and 0.54 with captions every 10 s, with one phrase taking 9.5 s for 2.4 s of audio (the sidecar deadline is 12 s). STT final latency about 300 ms alone; with captions running, five of seven finals stayed near 300 ms and two took 1.6 s and 6.5 s.
* *Verdict:* does not meet the gate (section 6).

== 4. Thinking and captions with the stack resident (run 1)

Method: the app (from `aivtuber-setup local` output, with `AIVTUBER_OPENAI_MODEL` set to the server alias) ran against the perception server with the VAD sidecar reading a 10-minute silent WAV, so the STT worker, TTS sidecar and VAD were loaded and idle; Edge headless showed the avatar page (an established connection to the avatar port was confirmed). `vision_bench.py mux --attach` then ran the EXP-0004b workload against the same server.

Caption JSON was valid in every condition (100%); S1a-valid 29% to 50% raw, 100% after the producer repair; scene agreement 100%. In run 2 caption latency p95 was 12.2 s at 10 s and 4.7 s at 5 s, past ADR-0007's 3 s deadline. The loaded rows of run 1 are fast while "Thinking alone" is slow; that order is the reverse of EXP-0004b, so these numbers are noisy and the "alone" row of run 1 and run 2 is the clearest sign of the machine being short of memory, not an effect of captions.

== 5. TTS and STT rounds (through the app)

TTS: typed chat to the app (six lines, 26 s apart), `local-tts-sidecar: ok` lines (synthesis time against audio length):

[cols="3,1,1,1",options="header"]
|===
|Condition |Phrases |Real-time factor range |Slowest phrase

|Stack and server idle, no captions (6 replies) |14 |median 0.38; 0.29 to 0.74, one 1.13 |4.96 s for 4.4 s of audio
|Captions every 10 s in the background (7 replies) |16 |median 0.54; 0.24 to 0.84, one 3.97 |9.46 s for 2.4 s of audio
|===

EXP-0003 and the quickstart measured 0.24 with the 2.9 GB model; here the median is 0.38 even without captions (with a larger spread), on a machine that is also running the browser and a 4B model. The 9.5 s phrase is inside the 12 s sidecar deadline but is a tail an operator would hear as a long pause; it coincided with a caption job.

STT: eight clips of Supertonic-generated Japanese (2.1 to 4.4 s each, 6 s of silence between them) through `speech-vad-sidecar --input-wav ... --pace realtime` and the real worker; recognition correctness was not scored (no reference text). The app's `final_age_ms` (final text to routing): idle 300 to 314 ms (7 of 8 finals reached the router; one was not routed in either run and was not investigated); with captions every 10 s: 299 to 308 ms for five finals, then 1,564 and 6,515 ms. Worker load 2.5 to 3.3 s. Real microphone input was not used (the build has no `mic-capture`).

The end-to-end event-to-first-phrase time was not derived: the app's `phrase_response` commit times use its own clock and could not be aligned to the driver's send times.

== 6. Verdict

[cols="3,4,2",options="header"]
|===
|Gate criterion |Result |Verdict

|No spill |Run 1: no signature (probe 68 / 59 ms) at 6.8 GB. Run 2: signature (probe 179 ms; Thinking alone p95 4.2 s; captions p95 12 s) at 7.5 GB. The state depends on what else holds GPU memory.|Not met reliably
|Thinking first-token p95 at most 1.5x of 0.386 s (0.58 s) |Run 1 with captions: 0.48 to 0.51 s (1.23x to 1.32x). Run 1 alone: 1.64 s. Run 2: 0.43 s (gate condition) to 5.17 s. |Not met in 4 of 8 cells
|TTS and STT still meet their own latency |TTS median 0.38 idle (0.24 before), 0.54 under captions with a 9.5 s phrase; STT 300 ms idle, 1.6 s and 6.5 s under captions |Degraded under captions
|===

*No-go on this class of machine: the perception profile needs about 12 GB of VRAM.* On this 8 GB card with the desktop's 2.4 to 2.7 GB it sits at the edge of the card (6.8 to 7.1 GB, 7.5 GB when the desktop grows), where one run was healthy and the next was not; a profile that works only while other software stays small is not one to ship as a supported setting. ADR-0007's structured-telemetry-only class for 8 GB hardware stays. The decision to document 12 GB as the requirement is the supervisor's.

Limits:

* One machine; two resident-stack runs; 30 requests per cell, so every p95 is the 28th to 29th value. The two runs disagreed, which is the finding; no third run was made to chase the cause.
* The reason for the +0.7 GB difference between runs 1 and 2 is not established. Candidates are other desktop software and the Edge instance (restarted between runs, headless, D3D11); neither was isolated. Total-used memory cannot attribute it.
* The stack was idle (silent audio) during the bench; real speech, floor/barge-in activity and avatar commands from an active performer were exercised only in the separate TTS and STT rounds, which had captions but not the 30-request Thinking workload on top.
* Thinking requests came from a Python client straight to llama-server, not through the app's `/v1/responses` path.
* The avatar page was headless Edge on this GPU; its frame rate was not measured and OBS was not used.
* Synthetic frames, no capture, no sidecar redaction path: this record does not re-test S1b code (none exists).
* The STT clips are synthetic speech, not people.

== 7. Setup-command dogfooding (#294 S2)

`aivtuber-setup local` was run from a release-like directory assembled from this checkout's release build (the five executables, the sherpa libraries the build placed beside them, `renderer/local-avatar/dist`, `examples/starter-reaction-pack`) with `--skip llm --assets <dir>`. There is no source-build equivalent of `--root`, so the directory had to be assembled by hand (`scripts/package-release.mjs` does this from build outputs and was not tried).

* *Worked:* `--dry-run` printed an accurate plan; the real run fetched llama.cpp b12224, the VAD, STT and TTS files and the sample VRM, verified every SHA-256, synthesized the six starter files with the bundled sidecar, wrote `local-profile.env`, and exited 0 with no error text. The generated env started the app with the supervised TTS sidecar unchanged.
* *Friction 1: no way to choose another model.* The env, `aivtuber-setup start` and the pins are hard-wired to Qwen3-4B (`AIVTUBER_OPENAI_MODEL=qwen3-4b-instruct-2507`, `AIVTUBER_SETUP_LLAMA_GGUF=...Qwen3-4B-Instruct-2507-Q4_K_M.gguf`, no `--mmproj` and `--parallel` support). After `--skip llm` the env points at a file that does not exist; the perception profile needed a hand-started llama-server and a manual `AIVTUBER_OPENAI_MODEL` override. S1b needs a profile switch in the setup binary (model, mmproj, `--parallel`, `-c`, alias).
* *Friction 2:* the generated env holds absolute scratch paths; fine, but the setup output does not say that `--skip llm` leaves the env's model path dangling.
* *Friction 3 (supervision, not setup):* the app's `tts_sidecar: ready ... load_ms=` printed 1.4 s, 17 s and 60 s on three starts with the same files (the sidecar's own `load_ms` was 1.1 to 7.3 s); the cold starts coincided with the other desktop software and a freshly killed browser. With stdin-driven shutdown (`AIVTUBER_*` speech `--input-wav` runs) an app that takes a minute to start can have its stdin closed before the sidecar starts; the sidecar then logged `speech-stt-worker: exit OutputClosed` with 0 segments. This is a harness race, not a product bug found, but a slow start is visible only in that log line.
* *Friction 4:* a build without `mic-capture` makes `speech-vad-sidecar` exit with `speech-vad-sidecar: microphone capture needs the mic-capture feature; use --input-wav` and the app logs `speech_sidecar: degraded: sidecar exited (exit code: 1); no speech observations`. The message is clear; release archives are presumably built with the feature, which this check did not exercise.
* No setup bug that corrupted a download, wrote a wrong file or failed was found.
