= ADR-0003: Local OSS VRM renderer behind a loopback avatar adapter
:status: Proposed
:date: 2026-11-08

== Context

Issue #219 asks for a zero-paid-dependency local avatar path (VRM 1.0 / MToon, transparent output, expression / look-at / viseme, neutral/reset, health, restart without stale replay) that keeps the provider-neutral avatar contract, scheduler, replay and authority boundaries in Rust. VTube Studio stays an optional adapter (see link:../vts-obs-adapters.adoc[VTS/OBS adapters]).

The issue is +status:design-ready+: this ADR records a candidate decision, a proposed process boundary, and the evidence from a throwaway spike. It does not authorize production implementation. Nothing from the spike is committed; only the numbers and the design are recorded here.

Current code that the design must fit:

* +AvatarAdapter::execute(&AuthorizedAvatarAction)+ in +crates/domain/src/interfaces.rs+, where +AvatarAction+ is a stringly typed +{ action, parameters: BTreeMap<String, f64> }+;
* the production composition path in +crates/app+, which calls +AvatarOutput::execute(&AvatarPlaybackCommand)+ with the typed variants +Expression { preset, intensity }+, +Gesture { preset, amplitude }+, +Gaze { target }+, +Viseme { viseme, weight }+, each carrying a +generation+ (+crates/runtime/src/cached_playback.rs+);
* the VTS output in +crates/app/src/outputs.rs+ that maps these variants to hotkeys / injected parameters;
* assumption A-VTS-001 (link:../assumptions.adoc[Assumption Register]): reconnect must not replay stale avatar commands.

== Hard constraints

* Model/generated output is data; the renderer cannot mint operator/tool authority. Renderer-to-host messages are untrusted, bounded data and never feed authorization.
* Each avatar command still passes through +authorize_avatar_action+ (+Capability::AvatarControl+) before it reaches the adapter, exactly as for VTS.
* No raw renderer, VRM node or expression names in +aivtuber-domain+ or in scheduler/replay decisions. They may appear only inside the renderer profile.
* The control transport binds to loopback only; remote exposure is opt-in and authenticated (issue #219).
* Reconnect, reload or renderer restart cannot replay stale avatar commands (A-VTS-001, issue #219).
* Retained state on both sides is explicitly bounded (no unbounded outbound queue).
* No production runtime CDN; dependencies are bundled and pinned.
* High-level decisions are outside the renderer's 30-60 Hz loop; the renderer only interpolates/blends.
* Avatar model licenses are independent of the code license and must be surfaced to the user.

== Assumptions

No existing assumption ID covers renderer choice. Proposed new assumptions (to be added to the register if this ADR is accepted):

* A-VRM-001: Chromium-based browser surfaces (OBS Browser Source / CEF, Tauri WebView2) can run WebGL2 with an alpha canvas and honor a transparent page background. Verified here only in desktop Edge/Chromium headless; OBS and Tauri were not run.
* A-VRM-002: +@pixiv/three-vrm+ 3.x keeps VRM 1.0 + MToon support and stays MIT and maintained. Revisit on the conditions below.

== Alternatives considered

. Status quo: VTube Studio only (rejected for the baseline: requires an external application; issue #219).
. Adopt +@pixiv/three-vrm+ (Three.js) as a bundled library inside an aivtuber-owned renderer page (wrap).
. Sidecar a Godot process with V-Sekai +godot-vrm+.
. Custom renderer: rejected without evaluation; contradicts the reuse-first rule and both candidates already cover VRM 1.0 / MToon.

== Evidence

All of the following is *executable spike evidence from one Windows 11 machine*, throwaway code kept outside the repository. Categories: spike = observed local behavior; spec = vendor docs/metadata; unverified = listed under Known limitations.

=== Spike setup

* +three+ 0.187.0 and +@pixiv/three-vrm+ 3.5.5, exact-pinned, bundled with Vite 8.0.3 (no CDN; the page only talks to 127.0.0.1).
* Test host (Node 24.19.0, +ws+ 8.22.1) standing in for the Rust host: serves the bundle and the control WebSocket on 127.0.0.1.
* Browser: Microsoft Edge 156.0.4314.58 driven by +playwright-core+ 1.65.0 (+channel: 'msedge'+). Playwright's own bundled Chromium was not downloaded or used.
* Software rendering mode: +--disable-gpu --use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist+. The page reported WebGL renderer "ANGLE ... SwiftShader Device (Subzero) ... SwiftShader driver". GPU mode: default flags, NVIDIA RTX 2070 SUPER (D3D11 via ANGLE).
* Model: VRM1_Constraint_Twist_Sample.vrm (10,776,032 bytes, SHA-256 12C2B97E...631A2 as hashed on this machine), 1280x720 canvas.

Notes on these numbers:

* "Cold" start is not decomposed. The model fetch+parse+first frame account for roughly 0.25-0.45 s; the remaining ~1.5 s of navigation-to-ready was not attributed (browser page start, 0.76 MB script evaluation and WebGL init are candidates). Three samples per mode is a smoke measurement, not a distribution.
* The command latency is *command sent by the host to the renderer's ack, sent after the render() call of the frame that includes the applied target*. It excludes compositor presentation, OBS capture/encode and display latency. The renderer additionally interpolates toward the target with a 60 ms time constant, so the visible change completes over roughly 150 ms after the first frame; this is a design parameter, not a measured one. On software GL the latency is one frame (~110 ms) and is dominated by frame time, not by the protocol.
* A "pixel changed" probe (framebuffer read-back, ack on first changed pixel) was also run but is *not reported as evidence*: spring-bone motion made pixels change between frames even with idle motion disabled (screenshot noise floor in the mouth region about 1,100 pixels), so the probe could not separate the command from background motion. Visible-change evidence is instead: (a) the renderer's own VRM expression values read after each command (+happy=1+, +aa=1+, +oh=0.8+, gaze target 35/10 degrees, all returning to zero after +reset+), and (b) a manual look at one screenshot showing the smiling, open-mouth +joy+ expression. A pixel-diff regression test would need spring bones frozen or a mouth-only region with fixed seeds; not done.

=== Functional results (SwiftShader and GPU runs agree)

* Transparent output: canvas created with +alpha: true+, +setClearColor(0, 0)+, body background computed +rgba(0, 0, 0, 0)+. A Playwright screenshot with +omitBackground+ had alpha 0 at all four corners and 726,071 fully transparent pixels of 921,600 (opaque 193,242; partial/anti-aliased 2,287) in the SwiftShader run; GPU run: 725,475 / 193,886 / 2,239. The same page screenshotted without +omitBackground+ is white (headless default); transparency is what the page offers, and consumers must request it.
* All five commands worked end to end: expression (+joy+ to +happy+), gaze (+away+), viseme (+A+ to +aa+, +O+ to +oh+, single active viseme), gesture (+nod+ bounded head rotation), +reset+. Unknown presets and raw VRM names sent on the wire (+happy+) were rejected with +unknown_preset+; raw VRM names exist only in the renderer profile.
* Restart: after +page.reload()+ the new page announced a fresh epoch, started with all expression values at zero and gaze at zero, +last_seq+ 0. The test host then replayed the three pre-reload commands verbatim as soon as the new +hello+ arrived; all three were rejected +stale_epoch+ and state stayed neutral. Within the new epoch a repeated +seq+ was rejected +stale_seq+. A forced WebSocket drop without reload produced a third epoch and neutral state after +ready+. In both runs a command written to the terminated socket was lost, not delivered after reconnect.
* WebSocket hardening on the test host: the server listened on 127.0.0.1; an upgrade with a foreign +Origin+, a missing +Origin+, or a wrong token returned HTTP 403; matching origin + token connected.

=== Finding that changed the design

After a reconnect without reload, the renderer's internal targets were reset immediately but the VRM expression values only changed on the next rendered frame. A host that reads state at +hello+ sees stale values. The spike therefore announces +ready+ only after the first neutral frame of the new epoch has rendered, and the host must treat +hello+ as "not ready yet".

== Decision

Proposed, for the supervisor to accept or reject:

. *Renderer candidate:* adopt +@pixiv/three-vrm+ + Three.js as the baseline, reuse mode *wrap*: a project-owned renderer page that bundles exact-pinned dependencies and exposes only the project's command protocol. +godot-vrm+ is not selected; it is recorded as "reference only / benchmark first", reopened by the revisit conditions. The comparison is desk-only and does not prove three-vrm is better.
. *Process boundary:* the Rust runtime owns a loopback HTTP+WebSocket listener (+LocalAvatarAdapter+). The renderer page (OBS Browser Source, a Tauri WebView, or a local browser) is the WebSocket *client*, so a browser page needs no listener and the same URL works in OBS. The Rust side stays authoritative for ordering, authorization and freshness.
. *Epoch and sequence:* the renderer mints a random epoch per page load and per WebSocket connection and resets to neutral. The host stamps every command with the epoch it learned from +hello+ and a per-epoch strictly increasing +seq+ starting at 1. The renderer rejects a command whose epoch differs from its own or whose +seq+ is not greater than the last accepted one, and acks each command (+applied+ or +rejected+ with a typed reason). The host keeps no outbound queue across connections and only issues commands derived from the current scheduler state/generation after +ready+.
. *Health/readiness:* +hello+ (protocol version, epoch, profile id, model identity: SHA-256 + VRM spec + name), +ready+ (after first neutral frame), periodic +health+ (fps, last seq, frame counter). The host treats missing +ready+ or heartbeats as +Unavailable+ using monotonic timing; this never blocks the deterministic performer.
. *Model/profile identity:* the +hello+ model hash and +profile id+ feed the existing avatar compatibility identity used by the asset store (see Open questions for the exact field).
. *Wire DTOs* stay adapter-private (renderer protocol schema + fixtures next to the adapter) and are not added to +aivtuber-domain+.

=== Proposed protocol sketch (spike shape, not a final schema)

[source,text]
----
renderer -> host:  hello  { proto, epoch, profile, renderer{three}, model{sha256, vrm_spec, name} }
                   ready  { epoch, frame }            # after first neutral frame of this epoch
                   health { epoch, fps, last_seq, frame }
                   ack    { epoch, seq, status: applied|rejected, reason? }
host -> renderer:  cmd    { epoch, seq, op: expression|viseme|gaze|gesture|reset, ...typed args }
----

Host state machine: +Disconnected -> Connected(hello) -> Ready(epoch) -> Disconnected+. On +hello+: drop in-flight commands, reset +seq+, verify profile/model compatibility. On socket close: forget the epoch; +send+ with no ready renderer returns +Unavailable+ and buffers nothing. Hardening: 4 KiB max message, one renderer connection (newest wins in the spike), +Origin+ equal to the served origin, per-launch random token on the WebSocket URL.

== CI strategy without a GPU

* Do not make GPU rendering part of the required-gate. Gate on: (a) Rust-side protocol/state-machine tests against a scripted in-process fake renderer (epoch/seq refusal, no replay, bounded in-flight, +Unavailable+ semantics); (b) renderer unit tests of the mapping and clamping logic with a stub +expressionManager+, no WebGL; (c) a JSON fixture set of commands and expected acks.
* Optional, non-blocking smoke job: headless Chromium forced to SwiftShader (flags above) loads the bundle, waits for +ready+, sends the commands, and asserts: renderer-reported VRM values, nonzero count of opaque pixels, alpha 0 at corners, restart-neutral behavior. This worked on the spike machine at about 9 fps, so assertions must be state-based and tolerant, not pixel-exact.
* Not verified: a Linux CI container. The spike ran Edge 156 on Windows 11 with SwiftShader forced; WSL Ubuntu was present but untouched. Playwright's bundled Chromium (browser download) was not used and its headless shell may differ. Verify on the actual CI image before promising a gate.
* The npm/bun supply chain for the renderer is not covered by +cargo deny+ (+docs/supply-chain.adoc+ does not mention npm/bun); see Open questions.

Model:

Its embedded VRM 1.0 metadata: author pixiv Inc., +licenseUrl+ https://vrm.dev/licenses/1.0/, avatarPermission +everyone+, commercialUsage +corporation+, modification +allowModificationRedistribution+, allowRedistribution true, credit not required, antisocial/hate usage disallowed. == Consequences

=== Positive

* One web surface serves OBS Browser Source, the planned Tauri shell, and CI smoke tests.
* Renderer is a thin interpolator; authority/ordering stay in Rust. Stale-command refusal is enforced on both sides without relying on a queue.
* Small dependency surface (15 MIT packages, 187 KB gzip JS).

=== Costs / trade-offs

* Adds a JS toolchain and a protocol to maintain next to Rust.
* Software-GL latency (~110 ms) makes CI unsuitable for timing assertions.
* Spring-bone motion makes pixel-exact tests unreliable.

=== Known limitations

* OBS Browser Source was not run; transparency was verified only through headless Chromium screenshots and page/canvas attributes. OBS's CEF behavior, color/alpha handling and its frame-rate setting are unverified.
* Tauri/WebView2 was not run. WebGPU was not tried (WebGL2 only).
* Linux and GPU-less container rendering unverified (see CI strategy).
* Gesture/motion: only two procedural head gestures and idle sway were tried; no VRMA animation clips, no body motion library.
* Latency does not include presentation, OBS capture or audio sync. Lip-sync to real audio was not tested; visemes were driven by hand.
* Expression override interaction (a happy expression blocking mouth visemes per the model's override settings) was not examined.
* Soak, memory growth, and context loss recovery were not tested.
* The godot-vrm comparison is metadata/README only.
* Only one model was tried.

== Staging and rollback

. Define the neutral vocabulary and a private protocol schema + fixtures; implement the Rust state machine against a fake renderer. No renderer needed.
. Add the renderer bundle behind a feature/profile flag next to the VTS output; selection per profile. VTS stays the default until the local path passes the acceptance criteria.
. Rollback point: remove the profile; no domain type changes if the protocol stays adapter-private. Becomes expensive once the neutral vocabulary and compatibility identity enter asset-store packs.

== Revisit conditions

* OBS Browser Source or Tauri WebView2 fails to render the transparent bundle.
* The Linux CI smoke cannot run under software GL.
* +@pixiv/three-vrm+ loses maintenance, changes license, or drops VRM 1.0 / MToon.
* Motion needs (VRMA clips, physics, full-body) exceed what the Three.js path delivers cheaply; then benchmark +godot-vrm+ for real.
* A required behavior needs the render loop to take decisions.

== Open questions for the supervisor

. *Integration point:* implement +AvatarOutput+ (typed +AvatarPlaybackCommand+, used by the app) and/or +AvatarAdapter+ (stringly +AvatarAction+)? The existing VTS adapter encodes actions as strings (+hotkey.trigger:<id>+, +parameters.inject+); a local adapter could add typed actions instead.
. *Neutral vocabularies:* expression/gesture presets and visemes are free strings today (VTS uses +A I U E O N+; issue says aa/ih/ou/ee/oh). Where is the canonical list defined, and does a pack/asset declare which profile it needs (asset-store +viseme_mapping+ is the likely home)?
. *Generation:* should +generation+ be sent on the wire so the renderer can drop older generations on its own, or stay Rust-only?
. *State after reconnect:* the spike resets to neutral on every new epoch and relies on the scheduler to re-issue. Should the renderer instead hold the last pose for a bounded time on a socket drop (visible freeze vs visible snap to neutral)?
. *Command TTL:* should commands carry a renderer-side expiry (monotonic ms from receive) to drop frozen-in-transit commands, or is epoch+seq enough?
. *Gaze:* keep symbolic targets only (matches schema) or add numeric/normalized targets?
. *Wire contract home:* is an adapter-private protocol schema acceptable, or should it live under +schemas/+ as normative to satisfy the schema/domain change order?
. *Supply chain:* how are npm/bun renderer dependencies gated (lockfile, license, advisories) given +cargo deny+ does not cover them?
. *Multiple renderer connections:* newest wins (spike), or reject a second renderer?
. *Which process serves the page and holds the per-launch token:* the Rust runtime directly, or the Tauri shell?
