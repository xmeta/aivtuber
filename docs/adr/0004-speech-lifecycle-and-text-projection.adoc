= ADR-0004: Provider-neutral speech lifecycle and deterministic display-to-speech text projection
:status: Proposed
:date: 2026-11-08

== Context

Issue #222 asks for two provider-neutral speech-output contracts:

. an explicit speech *lifecycle* (Prepared / Committed / Started / Boundary / Finished / Cancelled) whose truth is owned by the scheduler/audio execution path, so that a TTS provider reporting "synthesis done" is never read as "audibly finished" (consumers: #81 floor control, #83 phrase streaming, #84 coherent intent, #92/#93 participant-speech observations, replay and telemetry);
. a deterministic, offline *projection* from the display text that was gated and logged to the speech text that is sent to TTS (for example 約束 to やくそく, or OpenAI to オープンエーアイ), with a bounded per-persona lexicon and a projection identity that participates in asset and replay compatibility.

The issue is +status:design-ready+: this ADR records a candidate decision, the measured evidence, a code-reading of today's lifecycle truth, and open questions. It does not authorize production implementation. Nothing from the spike is committed; only the numbers and the design are recorded here.

Current code that the design must fit (all on +main+ at the time of writing):

* the output gate runs before TTS: +GenerativePipeline::run_with_output_gate_and_fallback_deadline+ gates the reply at +crates/generative/src/lib.rs:768+ and builds the +SpeechRequest { text, style }+ at +:788+; the app revalidates the same text again before scheduling (+crates/app/src/lib.rs:1854-1895+, see link:../security-threat-model.adoc[security threat model]);
* +SpeechRequest+, +SpeechArtifact+ and +SpeechProgress+ in +crates/domain/src/interfaces.rs:50-70+ carry no display/speech distinction and no identity;
* +SpeechTrack.text+ stores only the display text (+crates/asset-store/src/lib.rs:51-60+, filled at +crates/generative/src/lib.rs:470+); +AssetCompatibility+, +RuntimeCompatibility+ and +AssetIdentity::stable_key+ (+crates/asset-store/src/lib.rs:99-109+, +550-556+, +649-699+) are the existing place where voice model and viseme mapping already gate reuse;
* the scheduler (+crates/scheduler/src/lib.rs+) is a pure logical-time state machine; audio is handed to an +AudioOutput+ at +crates/app/src/lib.rs:2435+ with no completion path back.

== Hard constraints

* The output/publication gate applies before anything irreversible; the projection must not become a way around it (issue #222; link:../security-threat-model.adoc[security threat model]).
* Model, Jev and generated output are data, never runtime authority. A pronunciation lexicon is operator-owned configuration; it cannot be written from chat, from model output, or from a TTS provider.
* The projection must not introduce new semantic claims: every character of +speech_text+ must be derivable from the gated +display_text+ plus lexicon entries and constant rule tables (issue #222: "it is a rendering/pronunciation projection, not a second free-form generation step").
* The baseline must work offline with no Python, no network service and no paid TTS feature (issue #222, local-first requirement).
* Replay-relevant decisions use monotonic or logical ordering, not wall-clock ordering. Retained state (lexicon, spans, lifecycle logs, queues) is explicitly bounded.
* Provider-specific wire DTOs and provider speech events stay behind adapters; the domain exposes a provider-neutral contract only.
* The scheduler/audio execution path owns public lifecycle truth. A cancelled future phrase must never be reported as spoken. Jev/LLM must not run in the frame/motor loop.
* Dependency additions must pass +cargo deny --locked check+ against the repository +deny.toml+ (AGENTS.md, link:../supply-chain.adoc[supply chain]).

== Assumptions

No existing assumption ID covers pronunciation or playback-completion truth. Proposed new assumptions (to be added to the link:../assumptions.adoc[Assumption Register] if this ADR is accepted):

* A-SPEECH-001: A deterministic lexicon plus rule layer is sufficient for the product's own names, game terms, brand words, numbers and symbols; context-dependent homographs (生物, 人気, 辛い) are not solved by any evaluated analyzer and are handled by lexicon override or left to the TTS. Evidence: this ADR (small, single-annotator sample).
* A-SPEECH-002: A TTS backend's own Japanese frontend reads ordinary kanji correctly enough that the baseline projection need not rewrite ordinary text. *Unverified here*: no TTS engine was run (see Limitations); this is the principal falsifier for the implementation phase.
* A-SPEECH-003: Output-adapter return values (+spawn+ returned, mixer enqueue returned) are a backend-return proxy and not acoustic first-audible time, consistent with A-AUDIO-001 and link:../audio-backend-spike.adoc[Native audio backend spike].

== Alternatives considered

. *Status quo*: send the gated display text to TTS and let the vendor read it; infer completion from the TTS duration on the logical clock. Rejected as the end state: no deterministic fix for names/brands, projection and completion are not replay-visible, and the scheduler reports +Completed+ even for commands that were muted, dropped late or failed (see the lifecycle table).
. *Rule layer plus lexicon only (analyzer-free)*: project-owned, zero third-party dependency, rewrites only spans that need it. Adopted as the baseline (Stage 1).
. *Add a local morphological analyzer to read ordinary text*: wrap one of jpreprocess, lindera, vibrato or sudachi.rs behind a project-owned trait. Adopted only as an optional second stage (Stage 2), per TTS profile, because the analyzer choice was within measurement noise after the rule layer and each candidate has a supply-chain cost (below).
. *Cloud pronunciation service or vendor markup dialect (SSML, vendor dictionaries)*: out of scope and prohibited by the issue's non-goals.
. *Second generative pass to rewrite text for TTS*: prohibited by the issue's non-goals and by the derivability constraint.
. *Lifecycle inferred from provider events* (for example a vendor "speech finished" callback): rejected; provider events are normalized in adapters into a three-value output observation and only the scheduler owner turns them into public lifecycle.

== Evidence

Categories used below: *spike* = observed local behaviour (throwaway code, not committed); *documented* = vendor docs or source reading, not run; *unverified* = listed under Limitations.

=== Method

* Harness: std-only Rust library (so analyzer footprints are not polluted) plus one tiny binary per candidate, rustc 1.98.1, release profile with thin LTO, Windows 11, one machine. The lexicon, rule layer and scoring are shared code; only the +tokens(text)+ adapter differs per candidate.
* Candidate configurations (7): jpreprocess 0.15.0 + naist-jdic; lindera 6.2.0 + ipadic; lindera 6.2.0 + unidic (mecab 2.1.2); vibrato 0.5.3 + ipadic; vibrato 0.5.3 + unidic-cwj-3.1.1 compact; sudachi.rs v0.7.0 (+5de0410b6edfd428fc510cc9763440772e9619d5+) + SudachiDict 20261015 core; same + small.
* Dataset: 106 items written by the spike author (no third-party text) over eight categories: kanji words (12), homographs needing context (16), numbers/dates/counters/units (23), English and brand words (18), emoji and kaomoji (9), symbols and URLs (6), names (9), game terms (13). Each item has a gold hiragana reading, optionally several accepted alternatives (for example じっぷん or じゅっぷん). 20 of the items are flagged "L": one of the 19 lexicon entries was designed to cover them; the other 86 are "held-out" for the lexicon.
* Metric: exact match after normalisation (katakana to hiragana, punctuation and symbols removed, prolonged mark and o+u / e+i spellings folded to vowel repetition) and mean character error rate. Kana-only tokens are passed through unchanged; only tokens containing kanji, digits or Latin are replaced by the analyzer's reading.
* Pipelines: *Raw* = analyzer only; *With lexicon* = lexicon longest-match substitution first; *With rules* = lexicon, then the deterministic rule layer (numbers with 29 kanji, Latin and symbol units, ALLCAPS acronym spelling up to 5 letters, emoji, kaomoji, URL removal, a few symbols), with the resolved kana spliced inline so the analyzer still sees the whole sentence ("FullIn" in the harness).
* Two later blind sets were written after the rules were frozen and never used for tuning: *blind1* (35 items, number units and Latin forms outside the rule tables) and *blind2* (30 items; written after a rule-mode change made in response to blind1, and its units mostly overlap the rule table, so it checks rule logic, not unit coverage).

Reading the table honestly:

* The "main, with lexicon and rules" column is *not* a held-out estimate: the rule layer and lexicon were written looking at this set. It shows the ceiling of the approach, not expected field accuracy.
* The lexicon column measures plumbing: of the 20 designed-for items, 18 to 20 are right after the lexicon alone on every candidate (the others also contain digits or acronyms that need the rule layer); it says nothing about coverage of unseen names. Held-out items are unchanged by the lexicon (identical held-out counts before and after on every candidate).
* On blind1, the project-written number/counter rules *lost* to jpreprocess's built-in OpenJTalk rules (jpreprocess Raw 33/35 versus 24-25/35 for the other six configurations with the hand-written rules, and 27/35 for jpreprocess itself when the hand-written rules were applied in front of it). A mode that leaves numerals and kanji counters to the analyzer and keeps only Latin-unit, acronym, emoji, URL and symbol rules ("Min" in the harness) restores jpreprocess to 31/35 on blind1 and 27/30 on blind2. Differences between candidates on blind2 (26 to 28 of 30) are within sampling noise.
* The single discriminating, reproducible difference is unit/counter coverage: OpenJTalk's NJD rules cover far more counters than the 22-entry table written for the spike, and sound changes are carried in the pronunciation field. The hand-written table is the weakest part of the rule layer and should not be extended without evidence.
* Segment-split rule application (resolved text isolated from the analyzer) was strictly worse than inline splicing on blind1 and blind2 (for example sudachi core 23/35 versus 25/35 and 23/30 versus 27/30): cutting the sentence at an override boundary loses the analyzer's context (+5分間休む+ became ごふんマヤスム). Inline splicing is the recommended mechanism.

Failures that no candidate fixes (main set, with lexicon and rules): 生物 as なまもの (H07), 人気 as ひとけ (H11), 辛い as からい before カレー (H13), and the kaomoji +(*^o^*)+ (the heuristic requires non-alphanumeric inner characters). 一日中 as いちにちじゅう fails on six of seven configurations (jpreprocess passes) and 上手 as かみて on three. These are context-dependent; the project can only fix them with a lexicon entry or by leaving the span to the TTS.

=== What a deterministic rule layer must cover regardless of the analyzer

Observed Raw failures common to every analyzer except where noted:

* *Numbers, dates, counters, units*: ipadic returns digits unread (0/23 numbers); unidic/sudachi read single digits but not multi-digit or counter sound changes (3 to 6 of 23). Only jpreprocess reads them (21/23 main, 33/35 blind1) and still misses unit symbols (+100m+, +36.5℃+). A rule layer for symbol units, percent, decimals and width folding is needed even with jpreprocess; kanji counters can be delegated to jpreprocess (see above).
* *Latin script*: brand words (OpenAI, GitHub, VTuber, YouTube, Twitch, Discord) fail everywhere except where a dictionary happens to contain them (SudachiDict core knows OpenAI and Python). ALLCAPS acronyms (AI, GPU, USB, PC, HP, S) are fixed by a 26-letter spelling table. Unknown mixed-case words (Python, Wi-Fi, React, iPhone, Switch) stay wrong on every candidate and need either a lexicon entry or an explicit policy (leave to TTS, spell out, or flag).
* *Emoji, kaomoji, URLs, hash and wave-dash symbols*: analyzers either leave them or, in jpreprocess, spell a URL out letter by letter. They are deleted (or replaced by a configured literal) by rules, not read.
* *Width normalisation* of full-width digits and Latin letters before matching.
* *Names and game terms* (星乃ひかり, 魔導核, 剛力丸): on Raw the candidates read 9 to 13 of 13 game terms and 7 to 8 of 9 names; the failures are the designed fictional items (for example vibrato with UniDic read 月城アカリ as ガツジョウ...). Adding the 19 lexicon entries raised the main-set total by 6 (sudachi.rs core) to 12 (ipadic-based) items (18 to 20 of the 20 designed items are right with the lexicon alone); held-out items did not change. The lexicon is for the product's own vocabulary, not for general names.

=== Dependency findings from +cargo deny+

Run per candidate against the repository +deny.toml+ with a pruned +Cargo.lock+ (spike crates excluded from the conclusions; the harness crates themselves report "unlicensed", which is an artifact). Results are in the comparison table. Consequences for the repository policy:

* jpreprocess and vibrato both need advisory exceptions (+docs/supply-chain.adoc+ requires reason, owner and revisit condition). jpreprocess: +bincode+ 2.0.1 and +unsafe-libyaml+; vibrato: +bincode+, +instant+, +paste+.
* sudachi.rs cannot enter the graph without an +allow-git+/+allow-org+ entry or vendoring, because +unknown-git = deny+.
* lindera is the only candidate with a clean +cargo deny+ result, but its +embed-*+ build scripts download dictionary tarballs over HTTPS at build time (verified with MD5 only), which conflicts with offline and reproducible builds and adds a build-time TLS stack (+ureq+, +rustls+, +ring+). The offline alternative (build the dictionary with the Lindera CLI from a pinned source archive and load it at runtime) was not tried.
* jpreprocess with its default bundled-dictionary feature would add a build-time +reqwest+/+aws-lc-sys+ download. == Decision

This section is the *candidate* decision for the supervisor; the open questions below list what remains undecided.

=== D1. Projection architecture: two stages, rule layer and lexicon are project-owned

* *Stage 1 (baseline, required, no new third-party dependency)*: a project-owned +custom+ rule layer and bounded lexicon, analyzer-free, that rewrites only the spans that need it. Reuse-first record: +custom+, because no evaluated crate offers a bounded and versioned lexicon with replay identity, a derivability audit and the output-gate ordering this repository requires; the only generic mechanism involved (longest-match scan) is small. Earlier modes do not fit for the same reasons.
* *Stage 2 (optional, enabled per TTS profile that lacks a usable Japanese frontend)*: analyzer-assisted reading behind a project-owned trait that maps a string to non-overlapping (range, reading) pairs. Recommended implementation: *wrap* jpreprocess 0.15.0 with a runtime-loaded, hash-pinned naist-jdic (so no build-time network), because it is the only candidate that brings counter and numeral rules, is small, and is on crates.io under BSD-3-Clause. This is *conditional on the supervisor accepting two advisory exceptions* (RUSTSEC-2025-0141, RUSTSEC-2024-0449) with owner and revisit date, or on upstream removing the dependencies. Lindera 6.2.0 with an offline-built dictionary is the fallback if exceptions are refused. Vibrato and sudachi.rs are rejected for now (see comparison); revisit conditions below.
* The spike supports *not* choosing an analyzer on accuracy: after the rule layer the seven configurations are within noise on the blind sets, and the residual errors are shared context-dependent homographs. Operational fit (counter coverage, size, advisories, build-time network, source policy) is what separates them.

=== D2. Contract and invariants

Proposed provider-neutral domain types (names are implementation choices):

----
SpeechTextProjection
  display_text      the gated text; the only text the publication policy reasons about
  speech_text       what is sent to TTS
  identity          ProjectionIdentity (below)
  spans             bounded list of (display range, speech range, origin)
  outcome           Identity | Projected | Fallback(reason)

origin  = Passthrough | Rule(rule_id) | Lexicon(entry_id) | Analyzer(token index)
----

Invariants, each testable and independent of the analyzer:

. *Order*: projection runs after the output gate and its revalidation, and before the +SpeechRequest+ is built (between +generative/src/lib.rs:774+ and +:788+). The public-output policy is evaluated on *both* +display_text+ and +speech_text+; if +speech_text+ is rejected the outcome is +Fallback(GateRejected)+ and +speech_text = display_text+ (already allowed). Projection can never turn a rejected display text into an allowed speech text.
. *Derivability*: the spans cover +speech_text+ with no gaps; +Passthrough+ spans equal the input substring byte for byte; +Rule+ spans equal the pure rule applied to the input substring; +Lexicon+ spans equal the reading of an entry whose surface equals the input substring, naming entry id and revision; +Analyzer+ spans equal the dictionary reading of that token. A verifier re-runs the projection and compares (projection is pure and deterministic), so verification needs no trust in the analyzer.
. *Charset and size*: +speech_text+ may contain only hiragana, katakana, the prolonged mark, ASCII punctuation, and characters passed through from the input; no Latin word unless passed through by policy; length at most 3x the input and at most a fixed cap; otherwise +Fallback(TooLong)+.
. *Deletions are allowed, insertions are not*: emoji, kaomoji and URLs may be deleted. Replacement text may only come from a lexicon entry or from a constant rule table (for example the 26 letter names, or a configured URL placeholder); it never comes from model output.
. *Authority*: lexicon entries and the active rule/analyzer profile are operator-owned configuration loaded through the local operator path. Public chat, Jev, the LLM and the TTS provider cannot add, edit or select them; model-suggested corrections (the "pronunciation correction labels" metric) are proposals that need an operator action, in the same spirit as the durable-memory write permit.
. *Failure mode*: any projection failure degrades to +speech_text = display_text+ with a typed +Fallback+ reason and a metric; it never blocks the deterministic performer and never calls a network service. No generative reading hints are accepted from the model in this design.

=== D3. Rule layer and lexicon design with bounds

* *Lexicon*: per persona or project profile, a list of (surface, reading, optional note) entries applied by longest match before the analyzer, with the resolved kana spliced inline (spike evidence: inline beats isolating the span). Latin entries need an ASCII-letter boundary on both sides; matching is on the width-folded input.
* *Bounds (proposed)*: at most 2,048 entries and at most 131,072 bytes of UTF-8 in total per profile; surface 1 to 32 Unicode scalar values; reading 1 to 64 scalar values, restricted to hiragana, katakana and the prolonged mark; no duplicate surfaces; at most 4 active profiles (persona, project, platform, session). The projector accepts at most 2,000 characters per call. Measured: 2,067 entries / 75,004 bytes cost about 30 µs extra per sentence with a linear-scan prototype.
* *Rule layer (analyzer-independent)*: width folding; emoji and kaomoji deletion; URL handling; ALLCAPS acronym spelling up to 5 letters; symbol units (percent, degree, metre, gram and their prefixed forms), decimals, thousands separators; a short symbol table (ampersand, multiplication sign). Kanji counters and plain numerals are *not* hand-written when jpreprocess is the Stage-2 analyzer; with no analyzer they are left to the TTS and recorded as not projected. Every rule has a stable +rule_id+ and a version.
* *Out of the box policy for unresolved Latin words*: pass through unchanged and count as +unprojected+ (the spike showed that letter-spelling a word such as Python is worse than leaving it to the TTS); the lexicon is the remedy.

=== D4. Projection identity, replay and asset compatibility

The projection identity is a canonical, length-prefixed key in the style of +AssetIdentity::stable_key+ (+crates/asset-store/src/lib.rs:674-699+):

----
projection = rules:<rules_version> | analyzer:<name>-<version> or "-" |
             dictionary:<name>-<version>+<sha256> or "-" |
             lexicon:<profile-id>@<revision>+<sha256> | scope:<overrides_only|full>
----

* *Asset compatibility*: add an optional +speech_projection+ component beside +voice_model+ and +viseme_mapping+ in +AssetCompatibility+, +RuntimeCompatibility+ and +AssetIdentity+, and add resolved +speech_text+ beside +text+ in +SpeechTrack+. Both the JSON schema (+additionalProperties: false+) and the Rust types (+deny_unknown_fields+) reject unknown fields, so old readers cannot ignore the new fields: this is an incompatible wire change under +docs/domain-contract.adoc+ ("old readers can safely ignore") and needs a +schema_version+ bump of the performance asset schema (0.1.0 to 0.2.0), following the schema-first change order in AGENTS.md. Open question Q3.
* *Compatibility rule (proposed)*: a change of rules version, analyzer or dictionary identity is a hard incompatibility for assets that carry pre-rendered audio; a change of lexicon revision marks only assets whose recorded spans reference a changed entry as stale. A stale asset is playable but not eligible for semantic reuse until regenerated. Open question Q4.
* *Replay*: the lifecycle +Prepared+ event and the telemetry record the projection identity and a digest of +speech_text+; replay consumes the recorded +speech_text+ and does not re-run the analyzer, so replay does not depend on analyzer or dictionary availability. Re-projection is a separate regression test.

=== D5. Lifecycle contract and single owner

Smallest provider-neutral type (domain crate; names are implementation choices):

----
SpeechLifecycleEvent
  seq        per-process monotonic sequence (ordering; not wall clock)
  at_ms      scheduler logical time in milliseconds
  speech     SpeechRef
  phase      SpeechPhase
  basis      LogicalTimeline | OutputAccepted | OutputDrained   (how the fact was observed)

SpeechRef
  event_id, generation (scheduler attempt id; None until Committed),
  phrase (0-based), final_phrase (bool),
  asset_identity (stable key, includes projection), speech_text_digest

SpeechPhase
  Prepared | Committed | Started | Boundary { offset_ms }
  | Finished
  | Cancelled { reason: SpeechCancelReason, reached: BeforeCommit | Committed | Started }

SpeechCancelReason
  OperatorStop | Muted | Preempted | Superseded | SchedulerRejected(kind)
  | StaleOrLate | GenerationCancelled(stage) | OutputFailure | Shutdown | GateRejected

OutputObservation (adapter-normalized input, three values)
  Accepted | Drained | Failed(kind)
----

* *Single owner*: a +SpeechLifecycleLog+ inside the scheduler crate is the only constructor of +SpeechLifecycleEvent+ and the only writer of +seq+. The scheduler's own transitions (+schedule_at+, +advance_to+, +stop_all+, +cancel_queued+, safe-boundary preemption) write Committed, logical Started, Boundary, Finished and Cancelled with reasons. The composition root's +dispatch_audio+ and the output adapters are *reporters*: they pass +OutputObservation+ values back into the scheduler (and call +prepare+ for Prepared); they do not emit events. Provider-specific signals (process exit, +Player::empty+, a vendor "finished" callback) are mapped to +OutputObservation+ inside adapters and never cross the boundary.
* *Truth rules*: +Finished+ is emitted only when the logical end has passed *and* no failure, mute or drop was recorded for that generation; +basis+ says whether a drain was observed. A cancelled or never-started future phrase is reported +Cancelled+, never +Finished+. TTS success emits +Prepared+ only. Muted, late-dropped and failed commands emit +Cancelled+ with a reason instead of vanishing.
* *Phrase and finality*: +phrase+ and +final_phrase+ are explicit from day one; a single-phrase reply is phrase 0 and final. #83 later emits phrase 0..n; the end of a non-final phrase is +Finished+ (with +final_phrase+ false) followed by +Started+ of the next phrase, and +Boundary+ is reserved for declared safe points inside a phrase.
* *Boundedness*: live state is a map keyed by generation, bounded by scheduler live items; terminal records share the scheduler history ring; the outbound queue is bounded and only +Boundary+ may be coalesced or dropped. A slow consumer detects loss through +seq+ gaps and re-synchronizes from a snapshot of the live map and recent ring, so it does not need provider events (#81).
* *Privacy*: events carry digests and identities, not text, consistent with the causal-trace rule of no free-text fields.
* *Metrics* map directly: committed-to-started latency (Committed vs Started +at_ms+), started-to-finished duration, cancellation before/after commit (+reached+), incomplete-versus-final mismatches (+seq+ and +final_phrase+ checks), pronunciation override use and projection failures (+origin+ and +outcome+).

=== Supervisor decisions

Recorded after review; the ADR status remains Proposed.

. *D-1 (scope)*: Stage 1 only. The project-owned custom lexicon plus rule layer is the baseline. Stage 2 (an analyzer) is deferred until a TTS-in-the-loop test shows the target TTS mis-reads ordinary kanji, that is, until A-SPEECH-002 is measured. Reason: after the rules the analyzers are within noise on the blind sets, and the projection's job is overrides, which the lexicon and rules do. This supersedes the Stage 2 recommendation in D1; the jpreprocess wrap there is retained only as the first candidate to re-evaluate.
. *D-2 (supply chain)*: No advisory exceptions now. When Stage 2 triggers, re-evaluate jpreprocess at its then-current release (0.16 or later) against +cargo deny+ first. lindera is acceptable only with an offline, hash-pinned dictionary build and no build-time network. vibrato and sudachi.rs stay rejected for now. The mecab-ipadic / ICOT and SudachiDict-provenance questions need answers only if one of those is reconsidered.
. *D-3 (schema)*: +speech_text+ and +speech_projection+ will bump the performance asset schema to 0.2.0 as a schema-first change in the implementation issue, with a migration note. It is incompatible because of +deny_unknown_fields+. No schema change is made in this ADR's pull request.
. *D-4 (compatibility)*: A projection mismatch is stale but playable, not a hard incompatibility (this replaces the hard/soft split in D4). Cached audio still carries the meaning; it is re-synthesized lazily and the event is counted. In addition, an operator-forced invalidation per lexicon entry is provided, for when a wrong reading must stop immediately (for example a name).
. *D-5 (defaults)*: URLs are not spoken: dropped from +speech_text+ and kept in the display text. Emoji and kaomoji are dropped from +speech_text+. Unknown Latin words pass through unchanged to the TTS and are counted as +projection_passthrough_latin+ so the lexicon can be grown from evidence.
. *D-6 (basis)*: The logical-timeline Started/Finished with an explicit +basis+ is acceptable for #81 initially. #81 must read +basis+ and must not treat +LogicalTimeline+ as audible.
. *D-7 (naming)*: The ambiguity of "generation" (scheduler attempt id versus +GenerationCancellationToken+ attempts) is recorded and resolved in the implementation issue. Nothing is renamed now.

=== D6. What is explicitly not decided here

Which analyzer ships if Stage 2 triggers, and whether Stage 2 is needed at all for the chosen baseline TTS (A-SPEECH-002). Schema policy, compatibility, defaults, basis and naming are decided in Supervisor decisions above; the remaining questions are under Open questions.

== Consequences

=== Positive

* Names, game terms and brand words become a deterministic, auditable, offline fix with a measured per-sentence cost of a few tens of microseconds, independent of any TTS vendor feature.
* The scheduler stops equating "TTS duration elapsed" with "spoken": muted, dropped, failed and preempted speech become typed lifecycle facts that #81, #83 and #84 can consume without provider events, and that replay and telemetry can record.
* Projection identity enters the same compatibility mechanism as voice model and viseme mapping, so a lexicon or analyzer change cannot silently reuse stale audio.

=== Costs / trade-offs

* A new, versioned lexicon artifact with an operator workflow, a rule table to maintain, and (for Stage 2) a dictionary to pin, hash and ship with attribution.
* An incompatible performance-asset schema change (new optional fields rejected by old readers) with the full schema/fixture/parity/replay update cycle.
* The scheduler gains a return path from audio output; the audio adapters need to expose acceptance, drain and failure, which the process player currently discards.
* Stage 2 introduces dependency exceptions or a build-time-network workaround, and an extra 40 to 280 MB of memory depending on the choice.

=== Known limitations

. *Sample size and annotator*: 106 + 35 + 30 items, one annotator (the spike author); gold readings were not independently reviewed. Per-candidate differences of a few items are noise.
. *Rules tuned on the main set*: the rule-layer columns on the main set are optimistic. Only blind1 was a coverage test; blind2 mostly reuses units already in the rule table. The "Min" rule mode was introduced after seeing blind1, so blind1 is contaminated for that mode and only blind2 is clean for it.
. *No TTS in the loop*: reading correctness was judged against kana gold, not against what a TTS engine pronounces. Whether kana-only output harms accent and prosody for the baseline TTS, and whether the TTS already reads ordinary kanji well enough that Stage 2 is unnecessary, is unmeasured (A-SPEECH-002).
. *Kana projection side effects*: rewriting whole sentences to kana discards kanji word-boundary and accent hints; the proposed default scope is overrides only for that reason. Deleting emoji removes tone cues; this is a deletion, not a claim, but it changes delivery.
. *Heuristics*: the kaomoji detector fails on faces containing letters (+(*^o^*)+), and the acronym rule would spell English words written in capitals (for example NASA).
. *Homographs are not solved* by any candidate (生物, 人気, 辛い); only lexicon entries or TTS context help, and a lexicon entry is context-free.
. *Platform and determinism*: one Windows machine, warm file cache, no cold-start or cross-OS/CPU timing, no concurrent load test; byte-identical output was shown within one build only. Maximum latencies include scheduler noise. One dependency build (+aws-lc-sys+ under the default jpreprocess feature) failed in the scratch environment; a long build path is suspected but was not confirmed, and the runtime-file dictionary path avoided it.
. *Not exercised*: native user-dictionary support was run only for vibrato; the vibrato BCCWJ-derived remap terms, the lindera offline dictionary build, jpreprocess 0.16.0-rc0, sudachi.rs plugin loading and the user-dictionary build tools were not examined.
. *Bug candidate (own issue)*: on the generated path the asset is inserted into the hot cache (+crates/app/src/lib.rs:1898+) before the scheduler accepts it (+:1900+); a scheduler rejection (duplicate event, cooldown, priority) then surfaces as +AppError::Playback+ and leaves an orphaned hot-cache asset with synthesized audio that was never committed. Found by code reading, not reproduced.
. *Lifecycle design is code-reading only*: no lifecycle code or prototype exists; the proposal is checked against the code by citation, not by running it. Real audible-start and drain behaviour of the process and native players remains a proxy measurement (A-AUDIO-001).

== Staging and rollback

. *Shadow*: compute the projection and lifecycle events alongside the current path, record identity and spans, send the unchanged display text to TTS. No behaviour change.
. *Lifecycle first*: add the lifecycle log and the output-observation return path (adapters report acceptance, drain, failure) before any projection change, because #81 and #83 need it independently. Rollback: ignore the events.
. *Stage 1 projection behind a profile flag*, per persona, default off; the asset schema bump lands with this step.
. *Stage 2 analyzer* behind a second flag and only after the falsifier.

Rollback is cheap until audio is generated and cached with projected text (assets then carry +speech_projection+ and become incompatible if reverted). After that, rollback means regenerating those assets or reverting to the display text, which remains valid because projection is additive.

== Revisit conditions

* jpreprocess removes or replaces +bincode+/+unsafe-libyaml+ (for example in 0.16.0), or its release line stalls.
* Lindera ships an offline, hash-pinned dictionary build path, or the repository accepts a build-time-network exception.
* Vibrato clears the +argmin+/+bincode+ advisories; sudachi.rs is published to crates.io or the sources policy gains a vetted allow entry; SudachiDict provenance (Hatena, Mozc, station list) is clarified.
* A TTS profile with a weak Japanese frontend becomes the baseline (#220), making Stage 2 mandatory.
* The falsifier shows kana projection harming prosody, or the baseline TTS already reads names correctly, making Stage 1 lexicon use rare.
* #83 phrase streaming or #106 commit barrier changes where commit happens or how phrases are identified.
* A privacy or security review finds that speech text needs its own retention class.

== Implementation notes

=== Issue #222 S1: text projection and lexicon (implemented)

Decisions D-1 to D-5 were implemented as decided; the operator-facing description is in docs/production-runtime.adoc ("Text that is not spoken, and how words are read"). Where the code differs from the candidate design above:

* *Projection type.* +SpeechTextProjection+ carries +display_text+, +speech_text+, +identity+ and a counts-only +report+. The +spans+ list and the +outcome+ field of D2 are not built: derivability is tested by projecting again, and the typed +Fallback(reason)+ outcomes stay the existing +PolicyOverride+ fallback (nothing speakable, or the gate rejecting the projected text). They belong with the lifecycle work (S2) if a consumer needs them.
* *Identity.* +rules:<v>|lexicon:<id@revision;...>+<sha256>+ (or +lexicon:none+); no analyzer or dictionary component because Stage 2 is deferred (D-1). The hash covers the effective merged entries, not the file bytes.
* *Lexicon bounds.* As proposed in D3 (2048 entries, 131072 bytes, surface 1 to 32, reading 1 to 64 kana), with at most 4 merged layers. The per-entry +source+ field is required so provenance of every reading is recorded; the starter lexicon is self-authored and copies no third-party dictionary.
* *Rule layer.* Only the D-5 deletion rules and the lexicon exist. The ALLCAPS acronym spelling, symbol and unit rules of D3 are not implemented; unknown Latin words pass through and are counted as +projection_passthrough_latin+ (D-5).
* *Asset schema.* 0.2.0 as in D-3 (+speech.speech_text+, +compatibility.speech_projection+). 0.1.0 assets stay readable (a reader needs the 0.1.0 shape only for fields it does not use), which is a deliberate softening of "incompatible": the writer emits 0.2.0, new readers accept both, old readers refuse 0.2.0. The default compiler version was decoupled from the schema version constant so the bump did not invalidate cached assets.
* *D-4.* +AssetCompatibility::speech_projection_is_stale+ implements stale-but-playable as a pure predicate. Lazy re-synthesis and its counter, and operator-forced invalidation per entry, are not built (S2).
* *Order.* The gate sees display, projected (only when something changed) and display again last, per reply and per phrase; this keeps the #286 commit-barrier contract.
