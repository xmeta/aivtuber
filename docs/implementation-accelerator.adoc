= Implementation Accelerator
:toc:
:toclevels: 3

This document reduces repeated discovery work for open aivtuber issues.
It is a start-here map, not a second roadmap and not an implementation authorization source.

Snapshot date: 2026-10-04.

Live GitHub issue milestone, priority, blockers, and status labels remain authoritative.
Before implementation, read the complete issue, +AGENTS.md+, the smallest relevant authoritative docs, and link:reuse-first.adoc[the reuse-first matrix].

== 1. How to use this document

For an implementation issue:

. confirm +status:agent-ready+ on GitHub;
. start from current +origin/main+;
. run +tgrep+ from the repository root;
. inspect the local start-here files below before designing a new module;
. inspect the named OSS/reference implementation before writing generic infrastructure;
. implement the smallest vertical slice listed here unless newer issue evidence narrows it;
. run the cheapest falsifier early;
. record adopt / wrap / sidecar / partial reuse / reference only / benchmark first / reject for external mechanisms.

A row is intentionally compact. The issue body owns acceptance criteria and security constraints.

== 7. Concrete upstream reference map
=== 7.1 MCP and Rust agent orchestration

Official MCP Rust SDK: https://github.com/modelcontextprotocol/rust-sdk

As of this snapshot, +rmcp+ implements the current stable MCP 2026-07-28 protocol while retaining compatibility with earlier releases.
It already covers tool discovery/invocation, resources/prompts, OAuth features, subscriptions, long-running tasks, response caching, and multiple transports.
For #193, prefer +client+ plus only the transport/auth features the vertical slice actually needs; avoid enabling a broad feature set by default.

Useful upstream files:

* +README.md+
* +crates/rmcp/README.md+
* +ROADMAP.md+ for conformance/health claims
* +docs/OAUTH_SUPPORT.md+ when remote authenticated MCP becomes necessary

Rig: https://github.com/0xPlaygrounds/rig

Useful upstream files for #193:

* +crates/rig-agent/README.md+ -- +AgentRun+ is a steppable serializable sans-IO state machine;
* +examples/agent_run_stepping/src/main.rs+ -- demonstrates host-controlled IO/tool execution between agent steps;
* +examples/README.md+ entry +agent_with_approval_policy+ -- useful HITL/policy reference;
* +crates/rig-rmcp/README.md+ -- +McpTool+, +McpClientHandler+, dynamic tool-list synchronization, raw/structured MCP result preservation.

This makes the preferred spike stronger than a generic "try Rig": keep Rig's run/tool mechanics below the aivtuber capability and verification gates.
Do not add a second orchestration framework merely to gain approval/resume mechanics until this fit is disproved.

=== 7.2 Realtime voice and turn handling

LiveKit Agents: https://github.com/livekit/agents

Useful reference implementation details:

* +livekit-agents/livekit/agents/voice/turn.py+ exposes interruption options including false-interruption timeout/resume;
* +livekit-agents/livekit/agents/voice/agent_activity.py+ contains recovery checks;
* +livekit-agents/livekit/agents/voice/turn.py+ and voice-session code contain preemptive-generation options;
* its documented turn layer distinguishes turn detection, endpointing, interruption, and preemptive generation.

Transfer to aivtuber as state-machine/test ideas, not as scheduler authority.
In particular, #81 can model TentativeInterrupt -> ConfirmedInterrupt / FalseInterrupt -> Resume while still honoring scheduler safe points.

Pipecat: https://github.com/pipecat-ai/pipecat

Useful upstream file:

* +src/pipecat/audio/turn/smart_turn/local_smart_turn_v3.py+ -- local ONNX end-of-turn analyzer;
* +src/pipecat/turns/user_turn_strategies.py+ -- integration strategy.

Smart Turn v3 is a better first local turn-projection candidate than writing a custom model.
Benchmark Japanese/multilingual behavior locally before promotion.

sherpa-onnx: https://github.com/k2-fsa/sherpa-onnx

Useful upstream file:

* +rust-api-examples/README.md+ includes a microphone example combining Silero VAD with a Japanese ReazonSpeech Zipformer recognizer.

For #92, first measure normalized observation latency and Japanese accuracy from a sidecar/wrapper.
Do not pull raw audio/model state into the deterministic domain contract.

=== 7.3 VTuber / embodiment references

Use it to derive #83 test cases around punctuation, first-fragment latency, per-segment TTS failure, and interruption.

AIRI: https://github.com/moeru-ai/airi

=== 7.4 Long-term memory

Hindsight: https://github.com/vectorize-io/hindsight

The current OSS server exposes retain/recall/reflect over HTTP and has a built-in MCP endpoint.
Useful upstream files:

* +hindsight-api-slim/hindsight_api/api/mcp.py+ -- MCP tool exposure and bank scoping;
* +hindsight-docs/docs-integrations/local-mcp.md+ -- local MCP usage.

For #105, Hindsight is now a first-class benchmark/sidecar candidate, especially because #193 can supply an MCP client boundary.

Graphiti: https://github.com/getzep/graphiti

Useful upstream file:

* +mcp_server/README.md+ -- temporal graph operations, hybrid search, episode/entity management, FalkorDB/Neo4j deployment.

Its MCP server is described upstream as experimental, so prefer a benchmark/spike and explicit removal fallback rather than a mandatory baseline dependency.

Letta: https://github.com/letta-ai/letta

Use as a stateful-agent identity/memory-lifecycle reference.
The active source has moved to +letta-ai/letta-code+; do not build new integration against retired V1 server code.

=== 7.5 Agent tracing and evaluation

OpenTelemetry GenAI semantic conventions:

* https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md
* https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md

The current development conventions include agent/workflow/plan and +execute_tool+ spans.
For #108/#193, add an optional mapping/export layer rather than replacing +TraceStage+ or storing prompt/output content by default.

Phoenix: https://github.com/Arize-ai/phoenix

Phoenix is an OpenTelemetry-based OSS tracing/evaluation system with datasets, experiments, annotations, and an MCP endpoint.

=== 7.6 Full-duplex spoken-agent evaluation

Full-Duplex-Bench-v3: https://arxiv.org/abs/2604.04847

The 2026 v3 benchmark adds real human disfluency plus multi-step tool-use tasks.
The transferable pattern for aivtuber is the scenario taxonomy, especially:

* hesitation / false start / correction / restart;
* interruption and turn-taking under real speech;
* chained tool use while speech input is disfluent;
* separate accuracy, latency, and turn-taking outcomes.

Use these as #70/#92/#193 synthetic/replay scenario classes.
Do not copy reported latency or accuracy numbers into aivtuber SLOs.

== 8. Cross-issue implementation shortcuts

=== 8.1 Prefer fixture-first contracts

For #72/#80/#81/#84/#88/#90/#92/#191, define the smallest bounded domain fixture before live providers.
A fixture lets replay/security tests land without waiting for UI, microphone, game, or model integration.

=== 8.2 Separate recommendation, policy, authorization, and execution

Use the existing project pattern:

[source,text]
----
model / Jev / external observation
        -> recommendation/data
        -> deterministic project policy
        -> authenticated capability when required
        -> adapter/executor
        -> observed result
        -> verification
----

This prevents #74/#76/#81/#90/#92/#193 from each inventing their own trust model.

=== 8.3 Reuse one evidence pipeline

Prefer extending #58/#59/#64/#65 artifacts over introducing per-feature metrics stores.
A new behavioral feature should normally identify:

* one deterministic/replay fixture;
* one quantitative counter/latency/resource measure;
* one human-review label if perception/naturalness matters;
* one promotion condition or explicit reason no promotion is needed.

=== 8.4 Sidecars are acceptable when they isolate heavy runtimes

Python/C++/ONNX ecosystems are not a reason to reimplement mature algorithms in Rust.
For Graphiti/Hindsight, LiveKit/Pipecat, or speech models, a bounded sidecar is acceptable when:

* input/output is typed and bounded;
* process/network failure degrades independently;
* deadlines and reconnect are explicit;
* raw private media/content is not retained by default;
* the sidecar cannot mint project authority;
* deterministic replay uses normalized recorded observations instead of the live service.

=== 8.5 Record negative reuse decisions

A rejected library decision is useful future context.
Record the exact reason and revisit trigger, for example:

[source,text]
----
Candidate: Pipecat Smart Turn v3
Decision: reference/sidecar only
Why: Python/ONNX runtime is acceptable outside core; no reason to port model logic.
Revisit: if measured IPC overhead exceeds the #92 observation deadline.
----

This avoids repeatedly re-running the same research.

== 9. Revalidation

External OSS details above were checked on 2026-10-04.
Revalidate before dependency adoption when:

* the upstream repository has materially changed;
* the referenced file/path disappeared;
* license or model-weight terms changed;
* the project is archived/unmaintained;
* the issue becomes implementation-ready substantially later;
* a local benchmark disproves the assumed fit.

GitHub issue metadata remains the execution source of truth even when this document names an implementation order.

== 10. Issue-start checklist

Copy this mental checklist rather than creating a new planning document for every issue:

[source,text]
----
1. git status --short --branch
2. read complete issue + milestone/labels
3. git fetch origin; branch from origin/main
4. tgrep the named local start-here symbols/files
5. read authoritative security/domain/architecture docs touched by the change
6. inspect the named upstream candidate at the current revision
7. record reuse decision
8. write the smallest failing/replay/security fixture
9. implement one vertical slice
10. run targeted checks, then full relevant validation
11. update this accelerator only when new evidence would save future work
----

When a row conflicts with a later issue decision, the issue wins and this document should be updated in the same or a follow-up PR.
