= Jev Reflex Routing Contract
:toc:

== 1. Role

Jev is used as the default *Reflex Brain*: a low-latency structured decision engine between deterministic rules and the generative LLM.

The domain layer depends on a generic `DecisionEngine` interface. Jev-specific request/response types remain inside the adapter.

== 2. What Jev decides

A single reflex evaluation should batch independent atomic judgments when possible.

Recommended decisions:

[cols="1,1,2"]
|===
|Decision |Type |Meaning

|response_route
|choice
|`silent | reaction | cached | template | llm`

|reaction
|choice
|Semantic reaction family, not raw animation parameters

|gesture
|choice
|Gesture family or `none`

|attention_target
|choice
|`camera | chat | game | speaker | away`

|interrupt
|boolean probability
|Whether current performance should be interrupted

|cache_reuse
|boolean probability
|Whether the retrieved candidate is sufficiently appropriate

|importance
|ordinal score
|Working-memory/event priority

|emotion_intensity
|ordinal score
|Strength of expression
|===

The Jev adapter may map these concepts to Jev primitives such as Choice, Score, and Noul. The core does not depend on primitive names.

== 5. Policy remains deterministic

Jev returns evidence for decisions. Final execution policy lives in code.

Example:

[source,text]
----
if operator_override:
    obey_operator()
else if interrupt_probability >= 0.95 and scheduler.safe_interrupt_point:
    interrupt()
else if interrupt_probability >= 0.70:
    interrupt_at_next_phrase_boundary()
else:
    keep_current_performance()
----

Do not put irreversible policy solely inside a probabilistic model.

== 6. Route policy

Initial thresholds are hypotheses and MUST be calibrated using recorded sessions.

[source,text]
----
exact cache hit            -> cached
semantic candidate + reuse probability >= T_reuse
                           -> cached
route = template           -> template
route = llm                -> llm
low confidence             -> deterministic fallback
timeout                    -> deterministic fallback
----

== 7. Candidate selection

Do not expose a very large asset library as one flat decision.

[source,text]
----
semantic embedding / metadata filter
              |
            Top-K
              |
              v
         Jev reranker
              |
          final asset
----

The retrieval layer finds plausible candidates; Jev decides contextual suitability.

== 8. Timeout budget

The ReflexDirector must have a strict deadline. A timeout is a normal control-flow event, not a fatal error.

Record:

* decision latency
* timeout count
* fallback route
* chosen route
* confidence
* downstream outcome

== 9. Calibration dataset

Store replayable decision records with privacy controls:

[source,text]
----

typed_context_snapshot
retrieval_candidates_with_rank_similarity

----

These records support threshold calibration and future replacement/comparison of Jev with local models.

== 10. Anti-patterns

Do not:

* call Jev at 30-60 Hz;
* ask it to output raw Live2D parameter values per frame;
* use one opaque "overall quality" score where atomic decisions can be measured;
* route every chat message into an LLM after Jev;
* treat probability as certainty;
* make the system unusable when Jev is unavailable.

== 11. Current System One wire contract and Rust production path

The production Rust adapter in `crates/reflex` targets the current TypeSafe System One API:

[source,text]
----
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer <API_KEY>
Content-Type: application/json
----

The request contains exactly the System One concepts `state`, string-valued `model`, and caller-named `questions`. The routine reflex bundle uses Choice questions for route/reaction/gesture/attention, Noul questions for interruption and cache reuse, and two-level Score questions for normalized importance and emotion intensity. When semantic candidates exist, a separate Choice question selects an explicit asset id or `none`.

The response records the concrete returned `model`, named `answers`, and `usage` token counts. The requested model alias and returned concrete model remain separate evidence fields.

=== 11.1 Compact state

Routine reflex requests do not contain an arbitrary transcript/history field or free-form top-level state map. The Rust adapter serializes the versioned `ReflexContext` (`PerformerSnapshot`, `StreamSnapshot`, `RecentInteractionSnapshot`) plus the normalized current event and bounded Top-K `RetrievalSnapshot`. Candidate rank and similarity are preserved with each asset id. The request/context schema versions are included in compact state, and a byte cap is applied before transport.

=== 11.2 Semantic retrieval

`SemanticIndex` performs deterministic cosine Top-K retrieval over versioned precomputed embeddings. The production builder consumes the compatibility-checked `AssetStore` snapshot and excludes incompatible assets, missing embeddings, and embeddings from a different model/version. It performs no network I/O.

Replay evidence records:

* candidate asset id, compatibility-stable asset identity, rank, and similarity;
* retriever version;
* embedding model and model version;
* deterministic index snapshot version;
* asset compiler compatibility version;
* similarity metric;
* deterministic tie-break rule.

Equal similarities are ordered by asset id. The index snapshot version is deterministic for the same retriever/model/compiler metadata, stable asset identities, and vectors. L0 promotion does not alter the index. Successful AssetStore reindex + rebuild reflects descriptor additions/removals, while a failed transactional reindex preserves the prior candidate snapshot.

A Jev-selected cached candidate carries the retrieval-time asset identity through policy/execution. The production playback path resolves the candidate through `AssetStore` again and rejects it if that identity has changed, preventing a stale semantic decision from silently playing a different same-id asset.

=== 11.3 Evidence, policy, execution

The Rust path keeps three separate stages:

[source,text]
----
DecisionEvidence
      |
      v
PolicyDecision
      |
      v
ExecutedDecision
----

A cached route is executable only when Jev explicitly selects a Top-K candidate and the deterministic cache-reuse threshold passes. Model evidence cannot directly execute an asset.

Full replay records retain measured latency. Deterministic replay fingerprints normalize observational wall-clock latency while preserving every decision-affecting field.

=== 11.4 Deadline and retries

One absolute reflex deadline covers request serialization, transport attempts, retry backoff, response parsing, and normalization.

* Jev HTTP endpoint configuration and the exported HTTP transport both validate the parsed URL and require a valid HTTPS host with no embedded username/password; string-prefix checks do not establish a secure destination. Direct transport callers cannot bypass this policy. Requests do not follow redirects. A 307/308 redirect could replay the bounded, curated event/context request body to a different HTTPS host, even if the HTTP library strips the bearer token. Redirect responses are treated as provider errors and cannot carry a decision into the scheduler.
* Jev HTTP responses are limited to 1 MiB before JSON deserialization. A larger response is rejected rather than truncated; the pure response parser enforces the same limit for fuzz, replay, and mock transport callers. Oversized provider output cannot produce a decision.
* HTTP 401/403 fails as authentication without retry.
* HTTP 400/422 fails as invalid request without retry.
* HTTP 429 and 529 use bounded exponential backoff only while deadline budget remains.
* transport timeout maps to the deterministic timeout fallback;
* transport unavailability maps to the deterministic unavailable fallback.

The generic Rust `DecisionEngine` implementation runs blocking HTTP work on a worker thread and propagates cooperative cancellation. No Jev transport is part of the scheduler/frame loop.

=== 11.5 Benchmark boundary

Run:

[source,shell]
----
cargo bench -p aivtuber-reflex --bench routing
----

The benchmark compares deterministic-only policy evaluation with semantic retrieval plus System One request/response normalization through an in-process mock transport. It measures local routing overhead and intentionally excludes external network/model latency.

On the development machine used for the Issue #8 implementation, one representative run measured approximately:

[source,text]
----
deterministic-only policy:                 19.3 ns/op
semantic retrieval + Jev adapter boundary: 28.4 us/op
----

These numbers are diagnostic rather than a cross-machine performance guarantee.

== 12. Burst micro-batching (issue #78, S1 and S2)

A per-comment Jev call does not survive a chat burst, and the local profile runs without Jev at all. `aivtuber_reflex::BurstEngine` (`crates/reflex/src/burst.rs`) groups admitted public chat into small bounded batches _only while chat is bursting_, selects a Top-K deterministically, and gives every admitted comment exactly one terminal outcome. S1 is the library plus its falsifier; S2 wires it into `process_content_bytes` behind `AIVTUBER_CHAT_BURST_MODE` (default off) with deferred replies (12.6).

=== 12.1 Lanes

Lane choice uses only the structure the normalizer assigned, never what a payload or hint claims.

[cols="2,3",options="header"]
|===
|Event |Disposition
|Control or system plane |`Immediate`: never delayed by, queued behind or counted in a batch
|Content non-chat (donation, game, speech) |`Immediate(NonChatKind)`: existing per-event path
|Content plane carrying an authorization claim, an operator kind or an operator source class |`Refused`: content cannot claim a bypass, and the claim is not promoted
|`chat.message` while chat is quiet |`QuietPassthrough`: no wait, nothing held
|`chat.message` while bursting |`Batched`
|===

A viewer-supplied `priority_hint` is ignored for ranking (and counted in `priority_claims_ignored`), so untrusted text cannot self-escalate into the Top-K.

=== 12.2 Adaptive window and flush reasons

Chat is "bursting" once `burst_enter_count` arrivals fall inside `window_ms` (a bounded ring of arrival instants). The engine owns no clock, thread or timer: every instant is a caller-supplied monotonic millisecond value, and a regressing value is clamped and counted. Flush reasons are derived from event time, sequence and configuration only:

* `count`: the pending batch reached `max_candidates`;
* `bytes`: the next candidate would exceed `max_bytes` of retained bytes;
* `window`: `opened + window_ms` elapsed. The batch is stamped with that logical deadline, not the poll instant, so replay records do not depend on polling cadence;
* `shutdown`: `shutdown()` flushes the partial batch and resolves everything without consulting a ranker, so a partial batch cannot deadlock shutdown.

=== 12.3 Request, ranking seam and fairness

`BatchEngagementRequest` carries the shared `ReflexContext` once, at most `request_candidates` (hard cap 16) bounded candidates (text truncated to 256 bytes on a UTF-8 boundary, identifiers at most 256 bytes) and a `CapacityEnvelope`. It is `Serialize`-only and Rust-internal: it defines no JSON Schema, so it cannot become a second implicit wire contract. The provider shape of the Jev batch call lives only in `crates/reflex/src/jev_batch.rs` (section 12.8).

`BatchRanker` is the seam behind the reflex boundary. Its answer is only an ordering suggestion: ids outside the request or repeated are ignored, and the deterministic policy then re-applies Top-K, the per-batch actor cap and the per-actor cooldown. A ranker can therefore neither add a candidate nor revive a suppressed one; any ranker failure falls back to the deterministic order (`ranking_source = ranker_fallback`).

The deterministic order is local score (a caller-supplied `0..=1000` value such as retrieval similarity), then arrival sequence.

=== 12.4 Terminal outcomes

Each admitted comment ends in exactly one of: `selected{rank}`, `quiet_passthrough`, `not_selected_capacity`, `suppressed_actor_cooldown`, `suppressed_actor_batch_cap`, `shed_pending_overflow`, and, with audience aggregation on (12.7), `represented_by_aggregate{signal}`. `BurstMetrics::invariant_violations` counts any observation of `admitted != terminal + pending + ready` and must be zero.

=== 12.5 Configuration (`BurstConfig`) and metrics

Every field is validated, never clamped.

[cols="2,1,3",options="header"]
|===
|Field |Default (hard cap) |Meaning
|`window_ms` |1500 (5000) |Longest a candidate waits; also the burst-density window
|`burst_enter_count` |4 (64) |Arrivals inside the window that start batching; at least 2 so quiet chat never waits
|`max_candidates` |32 (64) |Count flush bound
|`max_bytes` |16 KiB (32 KiB) |Retained-byte flush bound
|`max_ready_batches` |4 (16) |Flushed batches awaiting resolution; the oldest is shed with terminal accounting beyond it
|`top_k` |3 |Comments selected per batch (at most `request_candidates`)
|`max_per_actor` |1 |Selected comments per actor per batch (at most `top_k`)
|`actor_cooldown_ms` |10000 |Logical time before an actor can be selected again; `0` disables
|`request_candidates` |12 (16) |Candidates shown to a ranker
|`max_tracked_actors` |1024 (4096) |Remembered cooldowns; the oldest stamp is evicted deterministically
|===

Metrics (`BurstMetrics`): `ranker_calls_per_comment()` (a per-comment design is 1.0), flush counts by reason, candidate wait (`wait_ms_total`, `wait_ms_max`, `mean_wait_ms()`), observational ranker wall time, shed batches, high-water marks and the terminal counters.

=== 12.6 Live wiring and deferred replies (issue #78 S2, issue #75 S1)

With `AIVTUBER_CHAT_BURST_MODE=true`, `ProductionApp::with_chat_burst` composes a lane (`crates/app/src/chat_burst.rs`) in front of the per-event path. Without it `process_content_bytes` is exactly the per-event path.

* *Bypass.* Control/system traffic never reaches the lane (content ingress refuses it). A content event that is not a chat message (donation, game, speech) takes the unchanged per-event path at once, even while the performer is busy. Content that claims control authority is refused by admission or by `BurstEngine` and is never promoted.
* *Quiet chat and selected comments* are answered at once when the performer is available, otherwise they wait in a bounded deferred inbox. Replies that the Top-K does not select get their burst terminal outcome and are never spoken.
* *Local score.* The engine's `local_score_milli` is a deterministic text heuristic (a question scores higher, a short-but-not-trivial comment higher than a one-word reaction, a comment of one or two repeated characters scores zero). It only orders untrusted comments among themselves and cannot buy a bypass or a gate. With `AIVTUBER_CHAT_BURST_RETRIEVAL_SCORE` the heuristic is augmented by the existing semantic index, and a Jev `BatchRanker` can reorder each batch (section 12.8); both are default off, and without them the lane resolves with no ranker exactly as before.
* *Typed reply timing.* `aivtuber_scheduler::ResponseTiming` is `Immediate`, `WhenAvailable`, `BeforeDeadline` or `NoReply`, carried by a `ResponseDisposition` (earliest time, expiry, supersession key, reason code). It is Rust-internal and `Serialize`-only: no `Deserialize`, no JSON Schema, so it is not a second implicit wire contract. S1 produces `WhenAvailable`; `BeforeDeadline` (a hard deadline that sorts ahead of `WhenAvailable`) is implemented and tested in the inbox for later donation/acknowledgement slices.
* *Busy state is a trusted input.* `ReplyAvailability` is built by the composition root from the operator mute flag, the scheduler's speech lifecycle (`speech_lifecycle().metrics().live > 0`, #308) and the generation runtime. No event field is an input and the type has no `Deserialize`: chat can neither claim an idle performer (to jump the queue) nor a busy one (to starve replies). The conversational floor (#81) is not an input in S1.
* *Bounded inbox.* `DeferredInbox` holds at most `capacity` items (default 32, cap 256), at most `per_actor_cap` (default 2) per `(source, actor)`, with an expiry horizon of at most `max_ttl_ms` (default 60 s, cap 10 min). A reply's time-to-live (`reply_ttl_ms`, default 20 s) is measured from the comment's *arrival*, so a comment that waited in a batch, or whose window was polled late, is never answered after it went stale. A full inbox evicts the item that would expire first; an actor at their cap has the newcomer rejected; a repeated event id supersedes its earlier deferral (the supersession key is the event id only until #80 provides topics).
* *Revalidation before dispatch.* Immediately before a deferred reply dispatches: expiry is swept (an item is stale at `expires_at_ms <= now`), availability is re-read, and `SecurityRuntime::revalidate_deferred_content` re-runs the structural content gate (validity, plane, kind, authorization claim, ingress ceiling, payload cap). The re-run consumes no rate token and no queue slot and can only refuse. Erased actors and operator-stopped items are removed from the inbox, so no later poll can return them.
* *Terminal outcomes.* Every comment that enters the lane ends in exactly one `ChatOutcome`: `dispatched_now`, `dispatch_failed`, one of the four burst non-selection outcomes, `represented_by_aggregate` (12.7), `erased_before_selection`, `cancelled_before_selection`, `shutdown_before_selection`, `expired_before_dispatch`, or `deferred(<dispatched | expired | superseded | erased | operator_cancelled | revalidation_refused | dispatch_failed | evicted_for_capacity | rejected_actor_cap | rejected_invalid | shutdown_dropped>)`. `ChatBurstMetrics::invariant_violations` counts any observation of `admitted != terminal + inbox.offered + held + in_flight`; tests require zero, and it is never repaired silently.
* *Operator control is independent.* Stop and mute use the authenticated ingress and `handle_control_reporting`, never the lane. Operator stop cancels every held and deferred reply with an explicit outcome at once (nothing queued before a stop speaks after it); mute holds replies until they expire. The daemon loop drains operator requests before it services the lane, and a lane step is bounded by the inbox capacity plus one batch.
* *Erasure (#305).* A viewer or operator actor erase cancels that actor's deferred replies (`erased`), marks their batched comments so they resolve as `erased_before_selection` and never speak, and drops their cooldown from the engine. Candidates already inside a pending batch keep their actor id until the batch resolves (at most one window), which is not edited so the exactly-one-outcome accounting is not broken.
* *Replay.* The lane reads only the caller's monotonic `at_ms`; the same input trace produces byte-identical terminal records (`take_chat_burst_records`, a ring of 256 of event id, logical time and outcome).

Falsifier (`crates/app/src/tests/chat_burst_tests.rs`): the #78 100x burst (2060 events, 1849 admitted chat comments) replayed through `process_content_bytes` against a performer that is busy most of the time, with operator stops during the burst, leaves every admitted comment with exactly one terminal outcome, dispatches no reply later than its time-to-live after arrival, and applies each operator stop synchronously with an empty inbox afterwards. A second run without stops and with a 1 s time-to-live exercises expiry.

Audience aggregation (#79 S1) is section 12.7.

Not yet: #79 semantic/topic grouping and windowed trends across batches, #80 topic features, #58 cost comparison, an immediate non-verbal acknowledgement with a deferred spoken reply, the conversational floor as a busy input, and an operator no-interruption window (needs a new authenticated control action, which is a wire change).

=== 12.7 Audience-signal aggregation (issue #79, S1)

A burst is mostly the same few reactions or the same remark repeated. With `AIVTUBER_CHAT_AUDIENCE_MODE=true` (default off; requires `AIVTUBER_CHAT_BURST_MODE=true`, otherwise startup is refused) `BurstEngine` groups a resolving batch into audience signals before ranking (`crates/reflex/src/audience.rs`). Without the flag, or in quiet chat (nothing waits to be grouped), behaviour and replay bytes are exactly as before: `BatchReplayRecord::audience_signals` is omitted from the encoding when empty.

*Safety ordering.* The universal guard (`guard_text`) sees every candidate before any grouping. A text that looks like a threat, scam, targeted abuse (term lists plus any @-mention), a link, a control/prompt-injection phrase, or that may have been cut by the 256-byte candidate bound is never absorbed and stays an individual candidate. Plain-duplicate coalescing additionally refuses texts with digits (amounts, addresses, codes) and texts longer than 80 characters. The guard is recall-oriented and can only *prevent* absorption: it never suppresses, deletes or acts on a message, so a false positive costs a missed aggregation. It is not a moderation policy (#76/#77). Known residual: an obfuscated threat that evades every list and is repeated verbatim by at least `min_cluster_size` viewers from at least `min_unique_actors` actors is absorbed, but its member ids stay in the replay record and its text still reaches the performer path through the carrier exactly as an unaggregated copy would.

*Two layers, no semantics.* (a) Exact or normalized duplicates: equal after full-width to ASCII, katakana to hiragana, lowercasing, whitespace and decoration removal (`! . ~ ー` and similar) and repeated-character folding; (b) a small reviewed reaction-family table (laughter 草/w/lol, good game gg/wp, praise, congratulation, greeting, cheer, surprise, sympathy, thanks, Japanese and English). A text matches a family only if it is composed entirely of that family's tokens (`wwww草` is laughter, `gg that was close` is nothing). Table and guard lists are folded at first use, versioned by `AUDIENCE_METHOD_VERSION`, and changed only by reviewed code. There is no topic/semantic grouping (#80), no ANN and no learned model.

*A crowd needs more than one voice.* A group becomes a signal only with at least `min_cluster_size` members (default 3, 2 to 16) and `min_unique_actors` distinct actors (default 2, at most the cluster size; anonymous events share one slot). One account repeating itself is not inflated into an audience.

*`AudienceSignal`* (Rust-internal, `Serialize`-only, versioned `0.1.0`; no JSON Schema and no `Deserialize`, so it is not a wire contract): window (the batch's logical open and flush instants), class (`reaction{family}` or `repeated_text`), method (`exact_duplicate`, `normalized_duplicate`, `reaction_family`) and method version, count, unique-actor estimate (exact inside one bounded batch), intensity (share of the batch, 0 to 1000), trend (second half of the window against the first: `rising`, `steady`, `falling`, `unknown` for a zero-length window), at most 3 representative event ids and a confidence prior per method (1000, 900, 850; a prior, not a calibrated probability). It holds no viewer text and no actor identifiers.

*One crowd-level candidate.* The first member in arrival order is the *carrier*. It is ranked in place of the cluster with its actor cleared (a crowd has no single actor, so the per-actor cap and cooldown neither apply to it nor are stamped by it) and with a local score of the cluster's best member score plus 20 per extra member, capped at +300 and at 1000, so a crowd cannot buy bypass of any gate. Its `BatchEngagementRequest` entry carries `represents: <count>`. The other members are never shown to a ranker and cannot be revived by one; they end as `represented_by_aggregate` (`TerminalOutcome::RepresentedByAggregate{signal}`, `ChatOutcome::RepresentedByAggregate`). The carrier itself ends with whatever the crowd candidate gets (selected and dispatched or deferred like any selected reply, or not selected). Exactly-one-outcome accounting is unchanged: `admitted = terminal + held`, with represented members as one more terminal category; the invariant counters must stay 0.

*Metrics.* `BurstMetrics`: `audience_signals`, `audience_carriers`, `audience_members_represented`, `audience_below_threshold` (eligible but below the thresholds) and `audience_guarded` by reason. `ChatBurstMetrics` mirrors signals, represented and guarded totals and counts dropped signals. The app keeps the last 64 signals in a bounded ring (`ProductionApp::take_audience_signals`); the daemon logs each as ids and counts only, plus an `chat_burst: audience signals=... represented=... guarded=...` line.

*Configuration.* `AIVTUBER_CHAT_AUDIENCE_MODE` (default off), `AIVTUBER_CHAT_AUDIENCE_MIN_CLUSTER` (default 3, 2 to 16) and `AIVTUBER_CHAT_AUDIENCE_MIN_ACTORS` (default 2, at most the cluster size). Out-of-range values refuse startup, never clamp.

*Erasure (#305).* Membership is computed at resolution from the candidates still in the batch, so an actor erased while batched is still counted in that batch's signal; an erased or cancelled carrier is not dispatched and its members keep their `represented_by_aggregate` outcome (each comment still has exactly one outcome). Signals hold no actor identifier.

Falsifiers (`crates/reflex/tests/audience_falsifier.rs`, `crates/app/src/tests/chat_burst_tests.rs`): a burst with six laughter reactions, four `gg`, one threat, one scam link and one real question yields two signals; the threat, scam and question stay individual candidates and are selected; each member has exactly one terminal outcome (8 represented, invariant 0); replay bytes are identical across runs and independent of polling cadence; a ranker sees one actor-less crowd candidate per cluster and cannot revive an absorbed member; the 100x burst stays fully accounted with aggregation on.

Deferred: semantic/topic grouping and conflicting explicit threads (#80), cross-batch windows, trends and decay, coordinated-spam moderation actions (#76/#77), feeding a signal into the router or a Jev prompt, and an operator-visible crowd view.

=== 12.8 Retrieval score and Jev batch ranker (issue #78, S3)

Both are default off, act only inside the burst lane, and refuse startup when requested without `AIVTUBER_CHAT_BURST_MODE=true`.

*Retrieval-augmented local score* (`AIVTUBER_CHAT_BURST_RETRIEVAL_SCORE`, `crates/reflex/src/chat_score.rs`). The lane's score for a comment is `(3 * heuristic + retrieval) / 4`, where `retrieval` is the rounded milli cosine similarity of the comment's best match from the *existing* `SemanticIndex::search` (the index the Reflex pipeline queries; the reflex and full profiles reuse theirs, the local and cached profiles build the same starter index from the pack). The query vector comes from `ReactionAxisEmbedder`, which maps a bounded text onto the starter-semantic axes already defined by `payload_intent_axis` (a question is a thinking prompt, a surprise reaction a surprise, any other reviewed reaction family of `reaction_family` an agreement-style reaction, everything else spreads over every axis). The retrieval component therefore measures how well the curated library covers the comment; the heuristic stays dominant. There is no model, no second retrieval implementation, and no viewer text leaves the process.

* *Deterministic and replay-stable.* The embedding is a pure function of the text, the search is the index's deterministic Top-K, the similarity is rounded to an integer, and the budget runs on the caller's monotonic `at_ms`.
* *Bounded.* At most `AIVTUBER_CHAT_BURST_RETRIEVAL_LOOKUPS` (default 64, at most 1024) searches per logical window (the burst window), and the index is capped at 4096 assets. Past the budget a comment keeps its heuristic score.
* *Falls back to the current score.* No embedding, a search error, an exhausted budget, or no usable index at startup (logged) yields the heuristic unchanged. A heuristic of zero (spam) stays zero and the result stays within `0..=1000`, so retrieval cannot buy a gate or revive spam; it only orders untrusted comments among themselves.

*Jev batch ranker* (`AIVTUBER_CHAT_BURST_JEV_RANKER`, `crates/reflex/src/jev_batch.rs`). Requires `AIVTUBER_MODE=reflex` or `full`, where a Jev adapter and key are already composed (a Jev-free local profile refuses startup instead of silently ignoring the flag). It implements `BatchRanker` over the existing `JevAdapter` transport, endpoint, key, HTTPS-only/no-redirect policy and response-size ceiling.

* *One call per batch.* The engine calls the ranker at most once per flushed batch, the lane at most once per `resolve_ready` step, and never at shutdown. There is no per-comment call and no retry or backoff: a single attempt bounded by `AIVTUBER_CHAT_BURST_JEV_RANKER_DEADLINE_MS` (default 250, at most 1000). The call runs on the daemon step that services the lane, never in the frame/motor loop. After 3 consecutive failures the ranker short-circuits (no network) for the next 8 calls, counted in batches rather than wall time.
* *Bounded typed input.* The request is built from the validated `BatchEngagementRequest` (at most 16 candidates, text at most 256 bytes, `ReflexContext` validated, compact state within the adapter's `max_state_bytes`). Each comment gets a local slot (`c00`, `c01`, ...); actor identifiers and event ids are not sent. Comment text appears only as a JSON string under `state.comments[*].text`, and the question text names it untrusted data to score, never an instruction.
* *Score questions, not free text.* The provider answers one System One `score` question per slot. The answer set must be exactly the requested slots and each a well-formed score in `0..=1`. An unknown, missing or extra slot, a wrong type, an out-of-range number, invalid JSON or an oversize body is `BatchRankFailure::Malformed`; a timeout is `Timeout`; a transport error or non-200 status is `Unavailable`. Every failure falls back to the deterministic order (`ranking_source = ranker_fallback`).
* *Reorder only.* The product is an ordering of the request's own candidates (score descending, ties in request order). The engine then re-applies Top-K, the per-batch actor cap and the per-actor cooldown, and audience carriers keep their cleared actor, so the provider cannot add a candidate, revive a suppressed one, change trust or bypass fairness. The path holds no capability or permit, and nothing from the provider is serialized back as authority. The seam carries no per-candidate hints.
* *Egress.* The reflex and full profiles already send each event's payload to Jev; the ranker sends the bounded text of at most 16 shortlisted comments per batch, without actor ids. It is a separate opt-in because it is a separate egress decision.

Falsifier (`crates/reflex/tests/burst_falsifier.rs`): the 100x burst through the real `JevBatchRanker` over a scripted transport that also injects HTTP 503 and invented-slot answers makes at most one request per flushed batch (well under 0.1 per comment), keeps every question set inside the request ceiling, leaves every admitted comment with exactly one terminal outcome, and replays byte-identically whatever the poll cadence.
