= Assumption Register
:toc:
:toclevels: 2

This register captures architectural and external assumptions whose failure could invalidate implementation or operational decisions.

It is intentionally human-readable.
GitHub issues, executable tests, provider conformance results, and ADRs remain the evidence/ownership sources.

== Status vocabulary

* *Invariant* -- repository policy/security boundary; changing it requires an explicit architecture/security decision.
* *Verified* -- currently supported by executable repository evidence or an authoritative protocol guarantee.
* *Needs validation* -- plausible/current design assumption, but local/provider evidence is incomplete.
* *Invalidated* -- known false; linked design/implementation must be reviewed.
* *Retired* -- no longer relevant because the owning design was removed/replaced.

A mock proving the repository behaves a certain way does not prove a hosted provider behaves the same way.

== Register fields

Each important assumption should record:

* stable assumption ID;
* statement;
* subsystem/owner;
* status;
* evidence/source;
* last verified repository revision/date when practical;
* validating test/fixture or conformance probe;
* consequence if false;
* revisit/invalidation trigger;
* related issue/ADR.

Do not record secrets, private user data, or raw provider credentials.

== Current assumptions

=== A-CTRL-001 -- Serialized authorization is not runtime authority

*Subsystem:* security / control plane

*Status:* Invariant

*Statement:* Serialized +AuthorizationContext+ and model/provider output are audit/data only. Privileged runtime actions require non-serializable +AuthenticatedControl+ minted by authenticated local control ingress.

*Evidence:*

* +docs/security-threat-model.adoc+
* +crates/domain/src/control.rs+
* privileged adapter interfaces in +crates/domain/src/interfaces.rs+
* runtime/control tests using +AuthenticatedControlCommand+

*Consequence if false:* Public/model content could forge privileged control.

*Revisit when:* Only through an explicit security-boundary redesign and corresponding threat-model/fixture changes.

*Related:* ADR-0001, #14, #56.

=== A-MEM-001 -- Durable memory requires explicit write authority

*Subsystem:* security / adaptation

*Status:* Invariant

*Statement:* Public content may participate in bounded working context, but durable memory writes require the non-serializable +MemoryWritePermit+ issued by the runtime write gate.

*Evidence:*

* +docs/security-threat-model.adoc+
* +docs/memory-adaptation.adoc+
* +crates/runtime/src/lib.rs+ (+MemoryWritePermit+)
* +crates/adaptation/src/lib.rs+

*Consequence if false:* Prompt injection/public content could poison durable memory without the intended gate.

*Revisit when:* Only through an explicit memory-authority/privacy redesign.

*Related:* #51, #105, #114.

=== A-MEM-002 -- Durable retained memory stays in the low thousands of entries

*Subsystem:* adaptation / persistence

*Status:* Needs validation

*Statement:* Approved durable memory per installation stays within the bounds of link:adr/0008-cross-session-memory-persistence.adoc[ADR-0008] section 3.2 (2,048 entries, about 1.6 KiB worst case each, 16 MiB on disk), so a bounded single file and a linear scan suffice and no embedded database or full-text index is justified by volume.

*Evidence:*

* +docs/adr/0008-cross-session-memory-persistence.adoc+ (analytic size estimate from the configured claim/topic bounds; not measured)
* +crates/adaptation/src/lib.rs+ (+WorkingMemoryConfig+ bounds; linear-scan +relevant+)

*Consequence if false:* A linear scan or single-file snapshot could miss its retrieval latency or write budget, and the database/sidecar options rejected in ADR-0008 would need reassessment.

*Revisit when:* Retained entries exceed about 5,000; #283 shows a lexical or semantic retrieval need a linear scan cannot meet; or measured entry sizes differ materially from the estimate.

*Related:* #282, #105, #283.

=== A-MEM-003 -- No production path writes durable memory yet

*Subsystem:* app / adaptation

*Status:* Retired (#306)

*Statement:* At `main` `b9efb0f5`, +ProductionApp::remember_working_memory+ and +remember_durable_memory*+ were called only by tests, hardening soaks and evaluation runners. Cross-session continuity therefore had no producer.

*Retirement:* ADR-0008 Q1 landed in #306: the app's post-turn consolidation step (+crates/app/src/memory_writer.rs+) writes stream-level performer facts under a runtime-minted permit when +AIVTUBER_MEMORY_WRITER+ is enabled (default off). Continuity has a producer behind an opt-in switch, and the ADR-0008 Q4 falsifier is runnable from the +memory_writer_metrics+ counters. The assumption no longer holds, so it is removed from the active set; the ADR-0008 need test stays valid only for viewer-attributed persistence, which this writer does not produce.

*Related:* #282, #105, #306.

=== A-VTS-001 -- Reconnect does not justify stale avatar-command replay

*Subsystem:* VTube Studio adapter / output freshness

*Status:* Verified

*Statement:* A command that failed or became stale before VTube Studio reconnect must not be replayed solely because connectivity recovered.

*Evidence:*

* +crates/app/src/lib.rs+ test +avatar_reconnect_does_not_replay_failed_due_commands+
* VTS reconnect policy implementation in +crates/adapters/src/vts.rs+

*Consequence if false:* Old expressions/motions could execute after their conversational moment, producing incorrect or unsafe performer behavior.

*Revisit when:* VTS adapter architecture/protocol changes, or a third-party VTS client is introduced.

*Related:* #66, #100.

=== A-LLM-001 -- "OpenAI-compatible" does not imply identical behavior

*Subsystem:* Thinking provider adapters

*Status:* Repository normalization fixture-verified; provider/model-specific live behavior still needs validation

*Statement:* Providers exposing an OpenAI-compatible API may differ in structured output, streaming order, finish reasons, cancellation, rate limits, prompt caching, reasoning controls, and model identity semantics.

*Evidence:* Provider documentation, repository normalization contracts, +examples/conformance/openai-responses.json+, and the versioned #66 compatibility matrix. Live provider/model evidence remains opt-in and version-specific.

*Consequence if false assumption is ignored:* Mocks may remain green while production provider behavior drifts.

*Revisit when:* A provider/model/API version changes, #66 conformance evidence lands, or the provider gateway changes.

*Related:* #61, #66, #104.

=== A-LLM-002 -- A loopback endpoint is a sufficient trust boundary for unauthenticated Thinking

*Subsystem:* Thinking provider adapters / `local` composition profile

*Status:* Needs validation (one llama.cpp release and one model observed manually; policy enforced by tests)

*Statement:* A Thinking endpoint whose host is `127.0.0.0/8`, `::1`, or `localhost` resolving only to loopback is on the operator's machine, so it may run without a credential when the operator names that policy explicitly (`AIVTUBER_OPENAI_AUTH=unauthenticated-loopback`). Other local processes and users on the same host are inside this boundary: any of them can use the inference server. A `localhost` lookup is checked at startup and repeated by the HTTP client at connect time.

*Evidence:* `crates/adapters/src/openai.rs` tests (remote host, off-loopback resolution, missing key, no `Authorization` header), `local_profile_free_text_reaches_loopback_thinking_and_plays` in `crates/app/src/lib.rs`, and the manual llama-server check in `docs/provider-conformance.adoc`.

*Consequence if false:* A rebinding or hosts-file change could redirect curated chat text to a remote host without a credential. Remote hosts are never accepted unauthenticated, and the loopback check precedes any request.

*Revisit when:* Multi-user hosts or containers share the loopback namespace, a reverse proxy fronts the server, a non-`localhost` name needs to be allowed, or the llama.cpp Responses endpoint changes.

*Related:* #220, A-LLM-001.

=== A-LLM-003 -- One warm-up request makes the first real Thinking request fit its timeout on a local llama-server

*Subsystem:* Thinking warm-up / `local` composition profile (#333)

*Status:* Needs validation (the cold-start cost is measured; the fix is pinned by tests against a fake slow loopback server, not yet re-measured against a real llama-server)

*Statement:* The first request to a cold llama-server spends most of its time loading and evaluating the prompt (19.4 s against a 15 s timeout on a CPU-only host); the next request reuses the cached prompt prefix and takes about 2 s. One internal request built by the same request builder, sent at startup, pays the cold cost once. A real request that overlaps it queues behind it on a single-slot server and is given the warm-up's remaining time.

*Evidence:* The #333 timings; `crates/app/src/tests/thinking_warmup_tests.rs` and `crates/adapters/src/openai/warmup_tests.rs`.

*Consequence if false:* The first reply falls back on timeout as before (typed, visible, counted); nothing else is affected because the warm-up output is discarded and its failure is only logged. A server with several slots, or one that evicts the cache, may still be cold for a real line.

*Revisit when:* The default prompt or model changes (the cached prefix changes), the server runs without prompt caching, or `AIVTUBER_OPENAI_TIMEOUT_MS` defaults change.

*Related:* #333, #294, A-LLM-001.

=== A-TTS-002 -- A loopback-only unauthenticated TTS sidecar is a sufficient boundary for local speech

*Subsystem:* local TTS sidecar / `local` composition profile

*Status:* Needs validation (one model, one host observed manually; the policy is enforced by tests)

*Statement:* `local-tts-sidecar` binds only a loopback address, requires a loopback `Host` header and `Content-Type: application/json`, bounds every input, runs one synthesis at a time and takes no credential. Other local processes and users on the same host are inside this boundary: any of them can make it synthesize text, and one that holds the single synthesis slot can delay replies (a denial of speech, never of the performer). The audio the app plays is only what a generation result of its own names, resolved under the audio root by the player's existing traversal rules, so a stranger's request cannot make the app play anything.

*Evidence:* `crates/adapters/src/speech_tts/server.rs` tests (non-loopback bind and `Host`, content type, bounds, busy), `crates/adapters/tests/tts_sidecar_supervisor.rs`, and the manual end-to-end run recorded in the S2b pull request.

*Consequence if false:* A local attacker could burn CPU, fill the generated-audio directory up to its byte cap or keep the voice busy. Text synthesized for a stranger is not curated chat text and is not logged (log lines carry counts and timings only).

*Revisit when:* Multi-user hosts or containers share the loopback namespace, a reverse proxy fronts the sidecar, a second backend (VOICEVOX) is added, or the sidecar must serve a non-loopback client.

*Related:* #220, A-LLM-002, A-TTS-001.

=== A-TTS-003 -- A loopback VOICEVOX ENGINE run by the operator is a sufficient boundary for the optional VOICEVOX voice

*Subsystem:* VOICEVOX bridge / `local` composition profile (issue #295)

*Status:* Needs validation (the engine was driven by EXP-0003 on one host; the bridge is tested against a fake engine only)

*Statement:* The bridge accepts a loopback `http://` engine origin only, with no credentials, path or query, and never follows a redirect or uses a proxy. The engine is trusted to be the VOICEVOX ENGINE the operator started; it is not authenticated, so another local process listening on that port could answer instead. Its answers are treated as data: the query JSON is passed back as an opaque object (with only `outputStereo` set) and the WAV is parsed strictly (16-bit PCM, mono, bounded size and rate) and re-encoded by the sidecar server. The credit line is the operator's configuration; the runtime logs it but cannot make it visible to viewers.

*Evidence:* `crates/adapters/src/speech_tts/voicevox.rs` tests (loopback validation, bounds, strict WAV, failures never carrying text or URL), `crates/app/src/tests/voicevox_tts_tests.rs`, EXP-0003 sections 3.2 and 7 for the engine's terms and its measured repeatability.

*Consequence if false:* A local process on the engine port could feed bounded audio into the voice path (never a command: audio is data and plays only through the generation result that named it). A stale audio cache after an engine or voice-library upgrade would replay old audio for the same text and speaker, because the cache key does not contain the engine version.

*Revisit when:* the engine is not on this host, a character's terms change, the cache key must include the engine version (probe `/version`), or EXP-0003's determinism result stops holding for a newer engine.

*Related:* #220, #295, A-TTS-001, A-TTS-002.

=== A-TTS-004 -- An explicit, operator-opted HTTPS egress to Aivis Cloud is an acceptable exception to the loopback-only local profile

*Subsystem:* Aivis Cloud bridge / `local` composition profile (issue #327)

*Status:* Needs validation (one live synthesis recorded in the pull request; otherwise tested against a loopback fake)

*Statement:* The local profile is otherwise loopback-only. `AIVTUBER_TTS_BACKEND=aivis-cloud` is the single exception: it sends the projected speech text of each reply (never raw chat, never memory, never the key in any log) to the Aivis Cloud API over TLS, only when the operator selects it, and the app says so at start. The synthesizer accepts an `https://` origin (or loopback `http://` for test fakes), no credentials, path or query, and never follows a redirect, so the bearer key cannot be forwarded. The key is a `SecretString` read from `AIVIS_API`. The service's audio is data: it is parsed strictly (16-bit PCM mono, bounded size and rate) and re-encoded by the sidecar server. The loopback profile check still sees only the loopback bridge; the egress is bounded by this one synthesizer, not by a generic provider allowlist.

*Evidence:* `crates/adapters/src/speech_tts/aivis_cloud.rs` tests (origin rules, bearer header, `use_ssml=false`, status mapping, bounds, redaction, no redirect), `crates/app/src/aivis_bridge.rs` and `crates/app/src/tests/aivis_cloud_tts_tests.rs`, and the live smoke.

*Consequence if false:* Reply text, which can quote a viewer, reaches a third party the operator did not intend; a leaked key spends the operator's credits. Credits exhausted or the service down degrade the voice to the visible non-verbal fallback, never the performer. The audio cache key does not contain a service-side model version, so a silent model update can leave stale cached audio.

*Revisit when:* a second cloud provider is added (then a typed egress allowlist is warranted instead of one synthesizer), the service's terms or data handling change, replies could carry content the operator does not want sent out, or the cache key must carry a service model version.

*Related:* #220, #295, #327, A-TTS-001, A-TTS-003.

=== A-AUDIO-001 -- Current process-player startup cost is acceptable until measured otherwise

*Subsystem:* audio output

*Status:* Invalidated

*Statement:* The existing external process-player backend is operationally acceptable for the current production profile; native audio is not assumed better without measurement.

*Evidence:* #101 Windows evidence in link:audio-backend-spike.adoc[Native audio backend spike] and +../examples/benchmarks/audio-backend-windows-2026-09-28.json+ shows materially lower backend-return start/stop/handoff proxies for a persistent rodio stream than per-playback ffplay. This does not yet prove lower acoustic first-audible latency or better phrase continuity.

*Consequence if false:* Process startup may materially hurt first-audio latency or phrase continuity. The spike confirms the startup mechanism is non-negligible at the measured backend boundary, so the process path should not be treated as latency-equivalent to native playback.

*Revisit when:* #58 provides end-to-end/acoustic first-audio evidence, #83 measures phrase continuity, or native device-loss/reconnect behavior is validated well enough to reconsider the production default.

*Related:* #58, #83, #101.

=== A-SPEECH-OBS-001 -- Adapter observation times map onto the runtime timeline within a small skew

*Subsystem:* speech observation (#92)

*Status:* Needs validation

*Statement:* A speech adapter can stamp `observed_at_ms` on the same monotonic (or replay logical) timeline the runtime uses for `now_ms`, to within `max_future_skew_ms` (default 50 ms). The contract carries no clock-offset negotiation. Defaults of 160 ms (activity max age, from ADR-0005's stalled-feed measurement), 400 ms (turn-end score max age, unmeasured; must exceed model inference p99 plus polling cadence) and 800 ms (fallback silence, EXP-0001, synthetic pauses) are not validated on real dialogue.

*Evidence:* EXP-0001 section 7, ADR-0005; executable: `speech_observation` and `speech_replay` tests in +crates/runtime+.

S2 measurement (`speech-vad-sidecar`, see the Speech sidecar section of `docs/production-runtime.adoc`): with the app's warm-up re-sync, the stamp-to-arrival lag of a model-free probe edge over a pipe was median 0.3 ms and at most 0.9 ms (one run had a 25 ms outlier; first line alone, without warm-up, 11 to 18 ms stale), always non-negative within rounding, inside the 50 ms skew. Real VAD edges arrive about 38 ms after their stamp (frame start plus the 10 ms chunk plus inference), inside the 160 ms age limit. Same-host, two monotonic clocks; the device-buffer latency before the capture callback is not measured.

*Consequence if false:* A mis-mapped timeline makes every observation stale (rejected, counted as `stale_age`) or future-dated, so the floor sees no speech and the deterministic fallback stays at `no_speech`; nothing blocks.

*Revisit when:* acoustic and device-buffer latency is measured with a loopback rig, a sidecar runs on another host or clock domain, or a real labelled Japanese dialogue set exists (EXP-0001 11.1 item 1).

*Related:* #81, #92, ADR-0005.

=== A-SPEECH-STT-001 -- A re-decoded offline recognizer gives usable partials and finals on a CPU shared with the renderer

*Subsystem:* speech transcripts (#92 S3b)

*Status:* Needs validation

*Statement:* Re-decoding the open segment with an offline recognizer (ReazonSpeech k2-v2 int8 through sherpa-onnx, 4 CPU threads) about every 500 ms of audio keeps up in real time and yields final text within about 130 ms of the end of the covered audio, early revisable partials (not prefix-stable: about 59% of partials are a prefix of the final, EXP-0002 6.2) and engine text that the pipeline passes on unmodified. The 500 ms end-of-speech tail, the 250 ms minimum speech, the 300 ms pre-roll, the 1500 ms partial age and floor-hold limits and the 10 s final age limit are measured or chosen on read speech and a synthetic floor, not on conversation (decision Q7 accepted this as a limitation).

*Evidence:* EXP-0002 6.1 and 6.2; the end-to-end measurement in the Speech transcripts section of `docs/production-runtime.adoc` (8 clips, this host, final after covered audio p50 127 ms, max 179 ms, identical text in 3 runs); executable: `speech_transcript`, `speech_transcript_replay` (crates/runtime) and `speech_stt` (crates/adapters) tests.

*Consequence if false:* On a host that cannot keep up, partial requests are dropped (counted) and finals arrive late; a final older than 10 s is rejected (`stale_age`); a decode past its deadline ends the worker and the transcript path degrades to nothing while VAD edges and the deterministic fallback carry on. Nothing blocks the scheduler.

*Revisit when:* a real-conversation check (decision Q7) is run, the renderer and an LLM client are measured concurrently, a second platform is pinned, or a streaming Japanese model with a clean license appears (EXP-0002 section 8).

*Related:* #92, EXP-0002, ADR-0004, ADR-0005.

=== A-THINK-001 -- Reasoning is disabled server-side and the reply prompt names the reply language

*Subsystem:* local profile Thinking model (llama-server, +crates/setup+, +compact_generation_input+)

*Status:* Validated on one machine

*Statement:* With Gemma 4 E4B QAT as the default local Thinking model, +llama-server --reasoning off+ and the generation-prompt sentence "Write the reply in the same language as the input text." together yield non-empty replies in the viewer's language.

*Evidence:* #318 comments, EXP-0004b 27 Japanese text cases (llama.cpp b12224 Vulkan, RTX 2070 SUPER): Gemma 4 with the instruction and +--reasoning off+ answered 0/27 in a non-Japanese language and 0 empty (p50 412 ms, about 2.6 GB VRAM). Without the instruction 9/27 replies were English. With reasoning on, 27/27 replies were empty because reasoning used the whole 96-token budget. Qwen3-4B-Instruct-2507 answered 1/27 in Chinese. One run, one machine, one language.

*Consequence if false:* Replies are empty (reasoning on) or in the wrong language, and the performer falls back to canned behavior or speaks the wrong language.

*Revisit when:* the pinned llama.cpp or model changes, a non-Japanese audience is supported, +--reasoning+ semantics change, or a wider language sample shows drift.

*Related:* #340, #318, #357.

_#357 note:_ the premise now holds per model. +reasoning = off+ is written into every section of the router preset that +aivtuber-setup start+ generates, so a model switched to from the panel gets the same setting as the default. The Qwen3-4B-Instruct-2507 evidence above is the one 1/27 off-language sample; an operator who installs it with +--with-model+ accepts that. Streaming Thinking was measured with Gemma only (EXP-0005); it stays on after a switch because the env file chose it, and this is not separately measured for Qwen3-4B.

== Relationship to ADRs

An ADR captures a substantial decision and alternatives.
This register captures facts/expectations that the decision depends on.

One ADR may depend on multiple assumptions, and one assumption may affect several decisions.

If an assumption is invalidated, do not silently rewrite history in an accepted ADR. Record the changed evidence, then supersede/amend the decision explicitly when needed.
