= Security Threat Model and Trust Boundaries
:toc:
:toclevels: 3

== 1. Scope

The AI VTuber consumes public and semi-trusted inputs while controlling audio, an avatar, stream software, memory, and potentially tools.

The design assumes public content can be adversarial.

Security therefore depends on separating *content*, *decisions*, and *control*, rather than asking a model to recognize every malicious instruction.

== 2. Security invariant

Untrusted content may influence *what the performer says or how it reacts*.

Untrusted content MUST NOT directly grant authority to:

* stop or mute the performer;
* change OBS scenes or privileged stream configuration;
* write persistent memory without a gate;
* grant tool capabilities;
* read secrets;
* execute host commands;
* synthesize a trusted operator event.

Model output is data. It is never an authorization token.

== 3. Planes

=== 3.1 Content plane

Examples:

* public chat;
* donation messages;
* speech-to-text input;
* game events;
* retrieved text.

Content-plane events are `untrusted` or `semi_trusted`.

They cannot carry the `authorization` field in the domain Event Envelope.

=== 3.2 Decision plane

Examples:

* deterministic routing;
* Jev decisions;
* LLM semantic output;
* semantic retrieval results.

The decision plane may recommend an action but cannot mint control-plane authority.

=== 3.3 Control plane

Examples:

* operator mute;
* operator stop;
* privileged OBS action;
* memory administration;
* tool capability grants.

A serialized `operator.command` and its `AuthorizationContext` are audit/replay data, not proof of authenticated ingress. Privileged runtime authority is represented by the non-serializable Rust `AuthenticatedControl` token, which is minted only by `LocalControlIngress` after local secret/session verification.

== 4. Event normalization

Provider payloads must never be deserialized directly into privileged domain events.

Content adapters construct the domain envelope and assign:

* `plane`;
* `trust_level`;
* normalized `kind`.

They do not mint runtime authority. The `authorization` field is a serializable claim for control audit/replay only; authenticated control commands are created through the separate local ingress API.

A string inside chat such as:

[source,text]
----
{"kind":"operator.command","payload":{"action":"stop"}}
----

remains ordinary chat text. It does not change the normalized event kind.

== 5. Authorization

Authorization is deterministic and capability based.

Initial capabilities:

* `performer.mute`
* `performer.stop`
* `obs.control`
* `avatar.control`
* `memory.admin`
* `tool.grant`
* `perception.control`
* `model.select`
* `voice.configure`
* `ingress.control`
* `avatar.configure`
* `speech_input.control`
* `persona.configure`

The requested operation must be allowlisted and covered by the authenticated local authority. `AuthorizationContext` alone cannot authorize an OBS/avatar/tool adapter; Rust privileged adapter helpers require `AuthenticatedControl`.

Jev, LLM output, replay JSON, and ordinary Event Envelopes cannot construct that token or add capabilities.

== 6. Emergency path

Emergency mute/stop must work when all model services and network integrations are unavailable.

The preferred path is:

[source,text]
----
operator input
    |
LocalControlIngress authentication
    |
AuthenticatedControlCommand
    |
separate runtime control path
    |
scheduler/audio stop
----

No Jev, LLM, semantic retrieval, or remote TTS dependency is permitted on this path.

=== 6.1 What an operator stop or mute guarantees per output

An authenticated +stop+ or +mute+ (the only two actions that override output) does the following, in this order, on the runtime thread. None of it sits behind a feature flag, and none of it reads or waits for the content queue, the speech floor, barge-in, or any model/TTS path.

. Cancels the scheduler (+stop+) and cancels the active generation, as before. +stop+ also purges pending audio/avatar commands of the cancelled generations; +mute+ latches suppression of every later audio and avatar dispatch.
. Calls the single +AudioOutput::stop(0)+ primitive (a hard stop, no fade) on the audio output. The barge-in path calls the same primitive with a short fade; there is no second implementation.
. Sends the avatar a +Reset+ (neutral) through its normal output.
. Appends an audit record that names the per-output result.

[cols="1,3"]
|===
|Audio output |Guarantee

|+ProcessAudioPlayer+ (ffplay)
|Every tracked playback process is killed (about 2 ms) and reaped off-thread. Reported +hard_stopped+, or +nothing_playing+ when nothing was running.

|Backend with a stop that cannot ramp from outside
|Reported +hard_stopped+.

|Backend without a stop (the +AudioOutput+ default, or a player whose adapter has none)
|Audio that already started plays out. Reported +unsupported+. The record is +operator_audio_stop_unconfirmed+ and never claims success.

|Backend whose stop returns an error
|Reported +failed+ (+operator_audio_stop_unconfirmed+); the adapter health shows the audio error.

|Backend whose stop does not answer within 100 ms (stuck driver)
|The control handler returns anyway; the stop runs on a worker thread and is reported +unconfirmed+. Audio may still be audible. Dispatch never blocks on the stuck output, and a repeated stop does not start a second worker.
|===

Audit records use the +Authorization+ category with decision +operator_audio_stopped+ (the backend confirmed a hard stop or nothing playing) or +operator_audio_stop_unconfirmed+ (anything else), and a detail of tokens only: +audio_stop=<hard_stopped|nothing_playing|unsupported|failed|unconfirmed> avatar_reset=<ok|failed>+. The operator response carries the same tokens. Only a non-serializable +AuthenticatedControl+ minted by +LocalControlIngress+ reaches this path: a wrong secret, a chat message, and a serialized +operator.command+ with an +authorization+ claim do not.

Mute is a latch, not a one-off: after it, audio commands and avatar commands are dropped at dispatch, so the neutral avatar is not re-animated.

== 7. Prompt injection containment

Prompt injection is treated as a data-flow problem.

Controls:

. Keep system/operator policy outside untrusted text.
. Mark untrusted content structurally before model calls.
. Never concatenate secrets into model state.
. Do not execute tool-like text emitted by viewers or models.
. Require typed tool requests plus deterministic authorization.
. Treat retrieved web/document content as untrusted unless explicitly elevated by policy.
. Record the origin and trust level of memory candidates.
. Require a separate memory-write gate.
. Treat text read off the screen by a vision model (ADR-0007) as untrusted observation: at most one delimited item of at most 512 bytes in a Thinking request, never memory, TTS or Reflex input; a perceived scene (rank 4) may inform context but can never set busy, deferral or interruptibility, which only a trusted source (OBS state through the operator-owned scene table, rank 1 to 3) may do (`SceneContextSnapshot`, #88).

== 8. Memory poisoning

Long-term memory is an attack surface.

A memory candidate records:

* source event id;
* trust level;
* keyed pseudonymous actor id where appropriate;
* normalized claim;
* expiry/retention policy;
* write decision.

Public chat SHOULD NOT become durable identity/fact memory solely because an LLM repeats it.

Claim provenance must not silently become epistemic authority.

Retained entries carry a write-time epistemic class (fact/claim/observation/experience/opinion) derived only from the source class and trust level the security runtime assigned *and* whether the retained claim is the source event's own text; the class and the vocabulary version it was derived under are stored on the entry and never recomputed. A memory-write permit proves the source event was authorized, not that an arbitrary sentence supplied alongside it was verified, so such a claim MUST NOT be treated as a verified fact. The claim binding is judged on the full text of both sides, after the same normalization and before storage byte truncation, so a case/whitespace rewrite never changes whether the retained claim is the event's own and content appended to the event's claim never inherits its provenance. A claim classed as a verified fact whose own text exceeds the storage byte bound MUST be rejected before storage rather than stored truncated, because dropping the negation or qualifier that bounded it would make the retained copy assert something the runtime never observed; weaker classes assert nothing and keep the truncation semantics. An untrusted viewer assertion remains a viewer claim unless a separate trusted verification/update policy explicitly changes its class; LLM repetition, summarization, semantic similarity, or graph linkage alone MUST NOT promote a claim to verified fact. The class is not authorization and never feeds a gate.

Targeted erase only reduces retained data and has its own non-serializable `MemoryErasePermit` (issue #305, ADR-0008 D-Q7): operator erase requires authenticated `memory.admin`; a viewer may erase only the pseudonym derived from their own envelope's `source` and platform-asserted `actor_id`, by an exact chat command, rate-limited per pseudonym. Read visibility is revoked before removal, and the report always names the copies the runtime cannot prove erased (sidecars, provider logs, generated assets, broadcast output, backups).

Deletion/expiry semantics also apply to future relation metadata: an edge or summary MUST NOT become a covert archive of content that retention policy removed.

The Rust production path enforces this with a non-serializable `MemoryWritePermit`: `SecurityRuntime::authorize_memory_write` can mint the permit only for an allowed system source or authenticated `memory.admin` authority. `crates/adaptation` accepts public content into bounded working memory, but its durable-write API requires that permit and stores only a pseudonymous actor identifier.

The operator can view and replace the operator memory seed while the app runs (issue #402) without a new capability: the actions `memory.seed.get` and `memory.seed.set` map to the existing closed `memory.admin`, are reachable only from the authenticated local ingress (panel `POST /api/memory-seed/get|set` behind the per-launch token, same-origin and JSON checks, body bound checked before it is read; `aivtuberctl memory-seed` behind the control secret) and from nothing on the chat, model, Jev or tool paths (tests: an ingress without the capability, a wrong secret, an app without live editing, a chat line naming the action and the panel path for `memory.export` all change nothing). A set is parsed and bounded by the seed parser and admitted entry by entry through the operator-seed permit before anything changes, written atomically, and only then replaces the previous seed entries; a refusal or a failed write leaves the file and the live entries unchanged. Entries stay operator-written, actorless, trusted performer claims; the seed text is never logged, audited or placed in status or the support bundle (a test asserts a marker claim is in none of them; only the entry count and the content hash are). Under the hybrid profile the entries relevant to a reply are part of the cloud request, which the panel states before a save.

The permit also carries the source event's own claim text so a consumer can perform that binding check. That text is retained content: the permit's debug representation MUST NOT print it (only whether the event carried a claim plus a redaction marker), so debug/tracing output is not a content-disclosure path.

Actor pseudonyms are cryptographic correlation identifiers, not anonymous identities. Production derives them with HMAC-SHA-256 under a deployment-only key, domain-separated by key version and source/provider namespace. The key is never serialized into Event Envelopes, replay fixtures, telemetry, memory records, or model context. Rotating the key/version intentionally makes historical pseudonyms unlinkable unless an operator performs an explicit controlled migration.

== 9. Rate limiting and backpressure

Each external source has independent:

* queue limits;
* event-rate limits;
* maximum payload size;
* timeout policy.

Overflow degrades by dropping/coalescing low-priority content rather than blocking operator commands.

The default Rust stdin boundary is bounded before parsing: raw records use the same `max_envelope_bytes` limit as `SecurityRuntime`, oversized records are drained without retaining the full line, and the pre-runtime queue is a bounded `sync_channel` sized from the runtime content-queue limit. Queue saturation drops the newest raw record with an observable metric instead of accumulating unbounded input or blocking the producer.

Public content then enters the Rust runtime through byte-aware per-source token buckets and a bounded content queue. Payload caps are measured as serialized UTF-8 bytes. Authenticated emergency control bypasses that content queue entirely, so content flood/backpressure cannot starve mute/stop.

== 10. Secrets

Secrets must not appear in:

* Event Envelope payloads;
* Jev state;
* LLM context;
* replay fixtures;
* telemetry;
* error logs.

Adapter configuration references secret identifiers; it does not copy secret values into domain state. Rust control secrets use redacted `Debug`, and telemetry/public-output paths apply a configured `SecretRedactor` before emitting text.

Outbound provider egress: the local profile is loopback-only except the opt-in Aivis Cloud TTS backend (#327, assumption A-TTS-004), which sends only projected reply text to an HTTPS origin, holds its key (`AIVIS_API`, or the key file of #360) as a redacted `SecretString`, never follows a redirect, and never logs the key or the spoken text. Since #360 the operator can switch to it, and back, at runtime from the panel: that switch is a new egress decision point, taken only through the authenticated `voice.configure` operator action with an explicit egress confirmation (section 15.1). The model search and the key check are the only other calls to that service; neither sends reply text, and the search sends no credential.

Crowd routing (#79 S2, `AIVTUBER_CHAT_CROWD_MODE`, default off) consumes only clusters the audience guard already admitted and adds no absorption path: the guard still runs first on every candidate and a flagged text stays an individual candidate. Its route comes from the engine's own record (never a payload field or a model) and a viewer cannot name an asset group. The crowd summary placed in a reply context is a closed-vocabulary typed value with counts: no member text, no actor id, no authorization claim, and no path to the operator or control plane, a capability, a permit or the memory writer. A non-verbal crowd reaction plays through the same performer path as any intent (mute, operator stop and the scheduler apply), and a deferred crowd carrier is revalidated by the content gate before it dispatches. The cross-batch window holds a class, a count and a fixed-size hash, never text, and is bounded and expired by logical time.

The opt-in Jev chat-batch ranker (#78 S3, `AIVTUBER_CHAT_BURST_JEV_RANKER`, reflex and full profiles only) sends the bounded text of at most 16 shortlisted comments per batch, without actor ids, through the existing Jev adapter. Its answer is data: slot-keyed scores that can only reorder the batch's own candidates, after which Top-K, the actor cap and the cooldown are re-applied; any malformed, unknown, extra or late answer falls back to the deterministic order. It holds no capability or permit, so it needs no authenticated control path.

=== 10.1 Hybrid profile: remote Thinking behind a typed egress allowlist (#364)

`AIVTUBER_MODE=hybrid` is the `local` route graph (no Jev, no semantic retrieval, loopback TTS/avatar/sidecars/OBS) with one exception to loopback-only: the Thinking role may be a remote HTTPS provider (OpenRouter, ADR-0009, assumption A-LLM-004). The profile check is a per-role policy, not a generic allowlist:

* *Only Thinking may leave the machine.* TTS, the TTS sidecar, VOICEVOX, scene-context OBS and the perception model stay loopback-only exactly as under `local`; a non-loopback endpoint for any of them fails startup with the role named and the URL not echoed. The existing opt-in Aivis Cloud TTS exception (section 10 above) is unchanged and independent: it is taken the same way under `hybrid` as under `local`.
* *Exact host, HTTPS, Bearer.* A non-loopback Thinking endpoint must parse as `https://`, with no userinfo, a DNS name (never an IP literal), the default port 443 (or the port written in the configured allowlist value), and a host that equals an allowlist entry after lowercasing the parsed URL host: `openrouter.ai` when `AIVTUBER_THINKING_PROVIDER=openrouter`, plus the single host named by `AIVTUBER_THINKING_EGRESS_HOST` when set. There are no wildcards and no suffix matching, so `openrouter.ai.attacker.example`, `sub.openrouter.ai` and `openrouter.ai@attacker.example` are all refused. It requires `Bearer` authentication; `unauthenticated-loopback` against a remote host is refused by the profile check and, independently, by the adapter constructor.
* *The egress variable is hybrid-only.* `AIVTUBER_THINKING_EGRESS_HOST` set under any other profile is a startup error, so it cannot silently widen `local`.

*What leaves the machine.* Every generated reply sends the bounded, typed Thinking request to the allowlisted host: the fixed instruction and the projected text of the triggering event, which can be a viewer's chat message or transcribed speech, plus the bounded `ThinkingRequest` context the compact generation input projects (curated context items, which can include approved memory, scene text and, when the operator wrote one, the character sheet of section 10.3). Nothing is sent for deterministic intent playback or for an event that is not routed to Thinking. The startup log states the egress host (host only: no scheme, path, key or text) and that chat and reply text are sent to it, mirroring the Aivis Cloud notice. Operators streaming viewer text to a third-party model are responsible for their own platform and privacy obligations; OpenRouter's `provider.data_collection` is sent as `deny` by default (#363) so routed upstream providers are asked not to retain or train on the prompt, and `AIVTUBER_OPENROUTER_DATA_COLLECTION=allow` is an explicit operator choice.

With both the hybrid Thinking egress and the Aivis Cloud TTS opt-in active, reply and viewer-derived text leaves the machine by two independent paths: the Thinking prompt to the Thinking host, and the projected speech text to Aivis Cloud. Each is separately opted in and separately announced at startup.

*Key handling.* The key is `AIVTUBER_OPENAI_API_KEY`, held as a redacted `SecretString`, sent only in the `Authorization` header of requests to the validated endpoint, never in a log, startup line, error or telemetry, and never forwarded: the HTTP client follows no redirects, so a 3xx from the provider cannot carry it to another origin.

*Model output stays data.* A remote model is no more trusted than a local one. Its reply passes the same typed parse, the same publication containment gate (section 11) and the same scheduler admission as a local reply; it can mint no capability or permit and cannot reach the control plane. A stronger or hostile remote model changes the quality of the data, not the authority it holds. A compromised or misbehaving provider can still return unwanted text, which the gate does not moderate (section 11), and can log the prompt; that is the residual risk the operator accepts by selecting `hybrid`.

*Failure.* A refused, slow, rate-limited, unauthorized or out-of-credit provider degrades like any Thinking failure: the typed non-verbal reaction, never a frozen performer. Operator emergency control does not depend on the provider.

=== 10.2 Voice input is opt-in and switchable by the operator (#396, #397, #400)

*Threat.* Up to v0.1.6 `aivtuber-setup start` opened the OS default capture device at every start in both the local and the hybrid profile. That is an unannounced ambient-speech path: whatever the device carries (a microphone, or on a streaming mixer whatever is routed to its input) is transcribed, answered as untrusted conversation input and able to barge-in over the performer, and under the hybrid profile each routed final is sent to the cloud Thinking host as the triggering event text (section 10.1). The operator had not turned voice input on, and the hybrid disclosure did not say the microphone was listening.

*Mitigation.* Voice input is off unless turned on. `aivtuber-setup start` passes `AIVTUBER_SPEECH_INPUT_SETTINGS`, and the app starts the speech sidecar only if that file is a well-formed `enabled: true`; with it off no capture device, VAD or STT process exists. The file is local operator-owned data treated as untrusted input: read bounded (512 bytes, like the model settings file), strictly parsed, and every failure (missing, unreadable, oversized, malformed, wrong type, unknown field) reads as off, so a damaged file can never turn the microphone on. Start-up always prints whether voice input is on or off (not hidden by quiet mode), and says that transcribed speech goes to the cloud model when Thinking is remote. The file confers no authority: speech finals stay untrusted `speech` content on the same normalizer path as before.

*Live switching (#400).* The operator can turn voice input on and off while the app runs, from the panel (+POST /api/speech-input+ with +{"enabled": true|false}+ and nothing else, strict +deny_unknown_fields+: no device, program, argument, trust level or source class) or +aivtuberctl voice-input on|off+. Both are the operator actions +speech_input.enable+ and +speech_input.disable+ under a new closed capability, +speech_input.control+ (+Capability::SpeechInputControl+; the schema enum, the TypeScript reference, the public-output control terms, +capability_for_action+). It goes through exactly the verification of stop and mute: the constant-time secret check, the capability minted by +LocalControlIngress+, an audit record per request with a fixed phrase (never a program path or a device name), on the panel's own queue so a switch can never sit in front of a stop or a mute. *Who can hold it:* only the operator endpoint's ingress, and only when the launcher composed voice input (a speech sidecar is configured and +AIVTUBER_SPEECH_INPUT_SETTINGS+ names the state file); an app run directly does not offer it. It is not reachable from model, Jev, tool or chat output, from the transcript of what the microphone hears, or from a viewer: the control terms are replaced in public output, an event cannot carry a capability it did not get from the authenticated local ingress (fixtures +examples/events/invalid/forged-speech-input-control.json+ and +examples/security/chat-claims-speech-input-control.json+), and the capability cannot raise trust: what the sidecar hears is admitted as untrusted +speech+ content under the operator's ingress ceiling, exactly as when it was started with the app. The sidecar and its configuration (program, arguments, models) are fixed at start by the operator's environment; a request can only start or stop that one configured child. *Enable* spawns a fresh sidecar and writes the state file as enabled only after the spawn succeeded; a spawn failure is a typed refusal and changes nothing. A later sidecar failure is reported as failed in the status and does not rewrite the file. *Disable* always succeeds and is immediate: the sidecar is stopped, the speech trackers drop every speaker, partial transcript and pending final of the old instance (a bounded +clear+, counted as +cleared_by_operator+, no fabricated end-of-speech event), the feed heartbeat and the handled barge-in run are forgotten so no barge-in can be confirmed from stale edges, every final the floor was holding for a speaker is discarded and counted (+dropped_by_operator+ in +speech_floor_metrics+, printed under quiet like the other drop counters), so nothing heard before the switch is answered or sent to a model (under the hybrid profile, to the cloud) after +off+, and the choice is written as disabled. A write failure of the state file is reported in the answer, not hidden, and the new state still applies.

*Capture device and duplex (#396).* Two more operator actions under the same closed capability, +speech_input.device+ and +speech_input.duplex+ (panel: +POST /api/speech-input/device+ with +{"device": "<name>"|null}+ and +POST /api/speech-input/duplex+ with +{"duplex": "half"|"full"}+, strict bodies on the same queue; +aivtuberctl voice-input device NAME|--default+ and +duplex half|full+). This changes the earlier statement that a request can name no device: the device action names a *capture device by its name*, and nothing else. The name is data, not authority: it is accepted only as one bounded argument (1 to 128 bytes, no control characters), and once the sidecar has reported its devices only a name it listed is accepted, so a request cannot make up a device, a program, a path or an argument (the name becomes the single value after +--input-device+ of the fixed, operator-configured sidecar command line, replacing any configured one). The device action restarts the one configured sidecar on the new device after stopping the old one (so no two hold a capture device or the speech model), and clears the speech state like enable. Device names are operator-local data: they are shown in the panel and +aivtuberctl status+ and saved in +local-speech-input.json+, never sent to a model, never part of the support bundle or of a public output, and *never in an audit record or an answer* (fixed phrases only; the sidecar's own stderr line, which is the operator's terminal, keeps the name). The duplex action is a boolean-like choice with no side effect beyond the gate below. *Half duplex (the default)* drops, before the floor, a final whose segment started while performer audio played or within 400 ms after it ended (counted in +dropped_during_playback+), so an echo of the performer's own playback is never held, routed or sent to a model, and it disables voice barge-in. It only removes input and an interruption path, never grants anything; the operator stop and mute are unaffected. The playback intervals come from the scheduler's speech lifecycle events only; a lost event never extends the gate (open units are forgotten on a +seq+ gap).

*Residual.* The state file is writable by any local process or user that can write the install directory (the same trust as the env file, which names the programs to run); a local writer can turn voice input on for the next start, as before. Disabling stops the sidecar with a hard kill; the speech-recognition worker is the sidecar's own child and ends when the sidecar's pipes close (read in code, see +docs/production-runtime.adoc+; only the pipe mechanism is tested, with a stand-in worker, not the real worker). Device choice and self-echo handling are later slices of #396. The app run directly without the variable keeps the previous behaviour and has no switch.

=== 10.3 The operator's character sheet is bounded configuration, rendered as delimited data (#404)

*Threat.* A text the operator writes (a character sheet: name, pronoun, tone, personality) is placed in every generated reply's Thinking request so the model can speak as that character. The risks are that the text becomes an instruction channel that outranks the runtime's rules, that it is used to smuggle authority (a capability, a permit, a trust level), that it grows without bound or carries invisible or structural characters, that its text ends up in logs or bundles, and that under `hybrid` it leaves the machine without the operator knowing.

*Mitigation.*

* *Operator-trusted, not authority.* The sheet is read at start from the file named by `AIVTUBER_PERSONA_FILE` (local and hybrid profiles; set by `aivtuber-setup start`), by the same operator who owns the environment. It changes only by editing the file and restarting, or live (#401) through the closed capability `persona.configure`, which the authenticated local ingress of the operator endpoint holds only when the generative path is composed and which only the actions `persona.set` and `persona.get` use (panel `POST /api/persona/set|get` behind the per-launch token, same-origin and JSON checks; `aivtuberctl persona` behind the control secret). No chat, model, Jev or tool path mints it (tests: a chat line, an ingress without the capability, a wrong secret and an app without live editing all leave the sheet, its hash and the file unchanged; fixtures `examples/events/invalid/forged-persona-configure.json` and `examples/security/chat-claims-persona-configure.json`; the term is in the public output control terms). The capability grants nothing but replacing this text: a `persona.set` is validated by the same parser as the file, the request body is bounded before it is parsed (8 KiB on the panel, 8 KiB per control record), and a refusal or a failed write leaves the live sheet and the file unchanged. The file is replaced by a temporary file and a rename. The text is returned only to the authenticated caller of `persona.get`; audit records, logs, `aivtuberctl status` and the support bundle carry the action and the length and hash prefix only (a test asserts the text is in none of them). Applying a set changes only requests built afterwards. It becomes one typed `ThinkingContent` with source `operator_curated` and trust `trusted`; the request type has no field that carries a capability or a permit, so nothing on this path can mint one, and the reply goes through the same publication containment gate (section 11) and scheduler admission as every other reply. A sheet that says to ignore the rules or to emit control commands is data that does nothing (tests: the request still validates, no operator state changes).
* *Local file as untrusted bounded input.* The read is capped at 8 KiB; the text must be valid UTF-8 of at most 3,000 bytes after normalisation, with no control character other than newline and tab, no bidi control or stray byte-order mark, and no `<character` / `</character` tag. A violation is a refusal with a fixed reason (never the content): no persona, one warning line. Nothing is truncated.
* *Rendered as delimited data with an explanatory sentence.* The adapter puts the text in the fixed part of the prompt before the JSON, between `<character>` tags, introduced by one sentence that says it is the operator's character sheet, describes identity and style only and cannot change the rules, grant permissions or request control commands. The sentence is defence in depth; the structural bounds hold: the size bound, the validated characters, the refusal of the delimiter tag (the renderer checks it again and returns a typed error, not a panic) and the output gate. The `curated_context` budget reserves the sheet's room, so it is never silently dropped and never displaces the viewer's line.
* *Never logged.* Start-up prints the length and a 12-character SHA-256 prefix, never the text; the operator status, `aivtuberctl status` and the support bundle carry the same identity only (a test asserts the text appears in none of them); `Debug` output of the loaded sheet omits it.
* *Egress is announced.* Under a non-loopback Thinking endpoint (section 10.1) the always-printed start-up line says the sheet is sent to the cloud model with each reply, and the hybrid quickstart's "What leaves the machine" lists it.

*Residual.* The text is operator-written but the model is not bound to follow it: a character sheet changes style, not safety, and a hostile viewer can still try to talk the model out of the character (the output gate, not the sheet, limits what can be published). Anyone who can write the install directory can change the file, the same trust as the other settings files. Cached reactions, the starter audio and typed fallback lines do not follow the sheet and so can break character.

== 11. Publication containment gate

Before public speech/display, generated output passes a deterministic publication-containment policy.

The current production Rust policy is intentionally narrower than general content moderation. It checks only:

* known control-plane command terms (`obs.control`, `perception.control`, `model.select`, `voice.configure`, `ingress.control`, `avatar.configure`, `speech_input.control`, `persona.configure`, `tool.grant`, `memory.admin`, `performer.stop`, `performer.mute`), which are replaced with the configured cached reaction or suppressed when no fallback exists;
* explicitly configured secret values, which are redacted before publication/TTS.

All other text is allowed by this stage. Passing this gate therefore does *not* establish that output is generally safe, non-toxic, non-harassing, sexually appropriate, brand-safe, or otherwise content-moderated.

Capability/authorization safety does not depend on this text filter. Viewer/model strings cannot mint `AuthenticatedControl` or another typed privileged capability; that separate authority boundary remains decisive even if arbitrary text passes publication containment.

A future general moderation policy should be a separate typed policy stage that may veto publication without gaining capability authority. The current control-term path fails closed: when text contains a control-plane term and no cached fallback is configured, public output is suppressed. Publication suppression does not stop the local scheduler.

=== 11.1 Speculative output is uncommitted data

If a future latency optimization starts model/TTS work before final turn/context commitment, its result remains untrusted/uncommitted data until the deterministic publication path revalidates it.

At minimum:

* source revision/generation identity must still be current;
* cancellation/supersession must be honored locally even if provider cancellation failed;
* the normal publication-containment gate must still run before irreversible publication, independently of any separate general moderation policy;
* a late provider result must not be replayed after a newer event/turn decision replaced it;
* operator emergency control remains independent of speculative provider work.

This separates "compute started" from "permission to publish".

The production generation worker follows this rule directly. It receives only immutable request/fallback data, a cancellation token, and a cloneable side-effect-free public-output policy snapshot. It does not receive Scheduler/AssetStore mutation authority or authenticated control capability. A completed result is revalidated on the composition thread before hot-cache insertion or scheduling, and shutdown/cancellation/supersession fences late completions locally.

=== 11.2 Phrase-level commit is an irreversible boundary (#83)

With phrase mode (`AIVTUBER_PHRASE_MODE`) a generated reply is committed one complete phrase at a time. Each committed phrase is already spoken: a later rejection, failure or cancellation can end the reply, never unspeak it. The invariants:

* the whole reply is evaluated by the publication-containment gate before any phrase is synthesized, so a policy that refuses or redacts any part of it decides while nothing is irreversible; the gate is then applied again to each phrase's own display text, on the worker before synthesis and on the composition thread immediately before that phrase's scheduler commit;
* the composition thread commits a phrase only when its generation is still current, uncancelled and not shut down, and only when the worker's gate decision is for exactly the phrase text and the current policy still publishes exactly that text;
* a phrase that fails any check ends the reply after the previous phrase, with a typed counted cause; it is not retried, a delivered phrase is never replayed, and the reply is never recorded as complete (`PhraseResponseEnd::Partial`);
* partial text or audio cannot reach the scheduler: the only handoff type, `PhraseUnit`, exists only for a phrase that is gated, completely synthesized and compiled into a validated asset;
* operator stop and mute, barge-in and supersession cancel the response, so no later phrase is committed, independent of any model or TTS path.

Streamed replies (`AIVTUBER_THINKING_STREAM`, #83 S3a) cannot gate the whole reply before phrase 0. They use a cumulative-prefix gate instead:

* from phrase 1 on, the candidate phrase is gated joined to the display text of every already-committed phrase, after its own display gate and before projection and synthesis, so a violation that exists only across phrases is stopped before the offending phrase is spoken;
* the joined text is bounded by the reply cap (`StreamPolicy::max_reply_chars`, equal to the adapter's stream cap); a reply that would exceed it is stopped fail-closed, never gated in part;
* a refusal or a redaction of the joined text ends the reply: committed phrases stand, the rest is never synthesized, the end is a `gate_rejected` partial and the output-gate audit records the refusing decision;
* a final whole-reply gate at completion is audit and telemetry only and cannot unspeak anything; a disagreement is counted (`stream_whole_reply_gate_rejected_after_commit`);
* the gate sees phrases re-joined from trimmed text (a space is restored only between two ASCII boundary characters), so separator-sensitive patterns that span a boundary are matched approximately; risky contexts should keep buffered mode.

For risky contexts buffered whole-reply mode remains available and is the default outside the `local` profile.

== 12. Audit and replay

* source event id;
* plane/trust level;
* decision output;
* requested capability;
* authorization result;
* executed action;
* fallback/override reason.

Secrets and raw credentials are never included.

== 15. Local operation panel (loopback web surface, issue #335)

The panel is a browser page and four JSON endpoints served by +aivtuber-app+ on +127.0.0.1+ next to the avatar renderer server (+crates/adapters/src/local_avatar/panel.rs+, +crates/app/src/panel.rs+; operation: docs/production-runtime.adoc). It is new network surface that can stop and mute the performer, so it is held to the control-plane rules above.

=== 15.1 What it is allowed to do

It holds no authority. It validates an HTTP envelope and forwards typed requests (+Chat+, +Stop+, +Mute+, +SelectModel+, and the voice requests of #360) over bounded queues to the composition thread. There:

* stop and mute are the same operator actions +aivtuberctl+ sends and go through the existing verification (the panel presents the control secret as the raw 32 bytes the ingress compares, so a generated 256-bit secret is not narrowed to a text alphabet): constant-time secret comparison inside +LocalControlIngress+, the +performer.stop+ / +performer.mute+ capability mint, the output stop of section 6.1, and the audit records of section 12. The panel is an authenticated client of the operator endpoint that happens to live in the same process; it cannot reach +perception.control+, +memory.admin+ or diagnose, and has no unmute. Of the capability set it can ask for exactly three actions: stop, mute and +model.select+. A serialized claim from the page is never read: the page sends no authorization field and the body parser rejects unknown fields;
* a Thinking model switch (+POST /api/model+, +{"model": alias}+, issue #357) is the +model.select+ operator action, also reachable as +aivtuberctl model <alias>+. It goes through the same verification as stop and mute: constant-time secret check, the +model.select+ capability minted by +LocalControlIngress+ (the operator endpoint's ingress holds it only when the launcher passed a model allowlist, +AIVTUBER_OPENAI_MODEL_CHOICES+), and an audit record (+action=model.select decision=<alias>: ...+, accepted or rejected; an alias that is not shaped like one is audited as +(invalid alias)+, never echoed). The page can only name an alias: the HTTP layer checks its shape (at most 96 characters of +a-z 0-9 . _ -+, optionally +vendor/model[:variant]+ with one +/+ and one +:+ so an OpenRouter id fits, issue #365) and the composition thread refuses anything outside the allowlist with a typed error and changes nothing, so a model name is never a path, a URL or free text, and model output cannot select a model. The choice that survives a restart is one bounded file (+local-model.json+, at most 512 bytes, schema +local-model-settings/1+) read by +aivtuber-setup start+ only after it is checked against the models installed at that start. The capability changes which already-installed local model answers; it cannot install, download or load an arbitrary file. Under the OpenRouter preset (#365) it changes only the +model+ field of the request to the already-allowlisted egress host, from the id list in +AIVTUBER_OPENAI_MODEL_CHOICES+ (at most 8, fixed at startup): the app never fetches OpenRouter +/models+ at runtime, so external data cannot widen the allowlist, and the switch makes no provider call of its own (no spend is triggered by the panel). A switch loads the model on a background thread (the existing Thinking warm-up) and never blocks the composition loop, emergency control or the deterministic performer; a slow or failed load degrades to the typed fallback. Disclosure and audit records of generated replies name the model that was active for that request;
* the voice settings (issue #360) are the +voice.configure+ operator actions (+voice.apply+, +voice.key.set+, +voice.key.remove+, +voice.key.check+, +voice.preview+; +POST /api/voice+, +/api/voice/key+, +/api/voice/key/remove+, +/api/voice/key/check+, +/api/voice/preview+). They go through the same verification as stop and mute (constant-time secret check, the capability minted by +LocalControlIngress+, which the operator endpoint's ingress holds only when the launcher composed the voice settings, and an audit record per action, accepted or rejected) on their own queue, so a slider drag can never sit in front of a stop or a mute. +aivtuberctl+ sends all of them except +voice.key.set+. What the page may send is a bounded, typed patch (+deny_unknown_fields+): backend (+local+ or +aivis+), a model UUID, speaker UUID, style id 0 to 31, four tuning values inside the API's bounds, a credit line (at most 200 characters of plain text) and +confirm_egress+. Enabling Aivis from the local voice is refused without +confirm_egress+, a model, the credit line and a key, and a refusal changes nothing. The audit record carries the validated summary (backend, model, speaker, style, tuning), never the credit line or a key. Model output cannot select a voice: the choice is operator data. The preview speaks one fixed sentence, armed for one operator-queued panel line by event id; a viewer who types the same sentence gets the model.
* the stream-chat connections (issue #361) are the +ingress.control+ operator actions (+ingress.connect+, +ingress.disconnect+, +ingress.key.set+, +ingress.key.remove+; +POST /api/ingress/connect+, +/api/ingress/disconnect+, +/api/ingress/key+, +/api/ingress/key/remove+). They go through the same verification as stop and mute (constant-time secret check, the capability minted by +LocalControlIngress+, held by the operator endpoint's ingress only when the launcher composed chat connections, an audit record per action) on their own queue. +aivtuberctl+ sends all of them except +ingress.key.set+. The request names a platform and a target only (+deny_unknown_fields+): a Twitch login (+[a-z0-9_]{3,25}+, lowercased) or a YouTube video id (11 characters, or taken from a +youtube.com/watch?v=+, +youtube.com/live/+ or +youtu.be/+ link; other hosts, ports, credentials and paths are refused). It cannot name a program, an argument, an environment variable, a trust level, a source class or a source id; the app derives all of those. The audit record carries the platform and the validated target (public names) or a fixed phrase, never the key.
* the avatar choice (issue #362) is the +avatar.configure+ operator actions (+avatar.upload+, +avatar.confirm+, +avatar.select+, +avatar.delete+, +avatar.discard+; +POST /api/avatar/upload+, +/confirm+, +/select+, +/delete+, +/discard+). They go through the same verification as stop and mute (constant-time secret check, the capability minted by +LocalControlIngress+, held by the operator endpoint's ingress only when the launcher composed the avatar store, an audit record per action with the model name and hash) on their own queue. +aivtuberctl+ sends all of them except +avatar.upload+. The capability is deliberately not +avatar.control+, the runtime's motor authority: choosing which file the renderer parses is an operator decision. *The uploaded model is untrusted data that two parsers read.* The app's inspector (+aivtuber_adapters::vrm+) accepts only a fully checked subset of glTF binary: magic, version 2, a total length equal to the file length, a first JSON chunk of at most 8 MiB, aligned in-bounds chunk lengths, at most 16 chunks and one binary chunk, UTF-8 JSON with a VRM extension and a +meta+ object; only the JSON chunk is read into memory. The upload is bounded before it is read (declared length at most 64 MiB, one upload at a time, idle and total deadlines, no chunked body), streamed to a staging file under a name the app generates, and refused with a typed error otherwise; no client-supplied path, file name or URL is ever used (a model is named by SHA-256 or +sample+). Passing the inspector does *not* make a model safe for the second parser, the renderer page (three.js and three-vrm decoding meshes, textures and the VRM extension in the browser or OBS's embedded Chromium); that remains the supply-chain-pinned renderer's job, so the risk is accepted for operator-chosen files and recorded here: only upload models you obtained from a source you trust. The model is served only to a page that presents the per-launch avatar token, under the existing +Content-Security-Policy+ (same-origin connections only), and a model that fails to decode is replaced by the sample rather than leaving the stream blank. Every meta string is untrusted text: only strings and booleans are taken, control characters are removed, lengths are capped (at most 5 authors), the panel renders them with +textContent+ and never as a link, and none is used as a path, a command or a URL to fetch. The licence summary is the file's own statement; the app does not verify it, and the operator confirms before the model is shown.
* voice input (issue #400) is the +speech_input.control+ operator actions (+speech_input.enable+, +speech_input.disable+; +POST /api/speech-input+ with a strict boolean body). They go through the same verification as stop and mute, held by the operator endpoint's ingress only when voice input is composed, with an audit record per action (fixed phrases, no path), on their own queue. +aivtuberctl+ sends both. The enable and disable requests name no device, program or argument: they can only start or stop the one sidecar the operator configured. The device request (#396) names a capture device by a bounded name, accepted only from the list the sidecar reported, and the duplex request is +half+ or +full+; neither can name a program or an argument. Section 10.2 has the clear-on-disable rules.
* the chat sidecars the app starts (issue #361) are a *new untrusted input source started from the panel*, and the panel still cannot raise trust. The app runs the sidecar binary next to its own executable by absolute path with arguments only (no shell), stdin null and the key (YouTube only) in the child's environment, and removes the other secrets it holds (+AIVIS_API+, +AIVTUBER_CONTROL_SECRET+) from that environment. The child's stdout is read through the same bounded record reader as piped stdin (line length = the envelope limit, queue = the content queue limit, newest dropped and counted) on its own thread, and each record is admitted by the same +process_content_bytes+ path, so envelope validation, the plane check, the operator-configured ingress ceiling (+AIVTUBER_INGRESS_MAX_TRUST+, +AIVTUBER_INGRESS_SOURCE_CLASSES+) and the content rate limits apply exactly as to a stdin line. In front of that, a panel-started source has its own fixed ceiling that no environment setting can raise: a record is dropped and counted unless its source is that platform's (+twitch:<login>+, +youtube:live-chat+), its class is +public_chat+ (or +donation+ for YouTube) and its trust is +untrusted+. A compromised or buggy sidecar therefore cannot self-escalate; it can only produce public chat. The composition loop takes at most 8 records per platform per turn and never blocks on a child; a flood fills the bounded queue and is dropped with counters. The child's stderr is read on its own thread through the same bounded reader (512-byte lines, 32 queued), logged at most 20 lines a minute, sanitized (control characters removed, 160 characters) with the key text replaced if it ever appears, and is the only source of the shown last error. A child is killed on disconnect and when the app ends (on Windows the whole tree, by the absolute +System32+ +taskkill+); restarts are bounded (backoff, a cap on consecutive failures).
* the YouTube API key (issue #361): handled like the Aivis key. Entered in the panel (+POST /api/ingress/key+, same redacted body field) or set as +YOUTUBE_API_KEY+, which wins; stored in +local-youtube-key.txt+ (owner-only, atomic); a +SecretString+ held by the controller; handed to the YouTube sidecar's environment only; never in a response, status, log line, audit record or settings file. A test drives the status, Debug output, every response and the audit records with a sentinel, and a hostile sidecar double that echoes the key onto stderr shows it replaced.
* the Aivis API key (issue #360): entered in the panel (+POST /api/voice/key+, body field, password input, trimmed and bounded, no whitespace) or set as +AIVIS_API+, which wins. It is a +SecretString+ from the moment the HTTP layer parses it (redacted +Debug+ on the request type), is written to its own file (+local-aivis-key.txt+, at most 512 bytes) with a temp file created owner-only first and then renamed (mode 0600 on Unix; on Windows +icacls+ by absolute path drops inheritance and grants the owner only), and is used only as the +Authorization+ header of calls to the validated Aivis origin (https, or loopback http for test fakes; no credentials, no redirects). It is never in a response, the published state, a log line, an audit record or the settings file; the operator control socket has no key action, so it cannot land in a command line or a request log. A test drives the status snapshot, the panel state, every operator response, the audit records, +Debug+ output and the settings file with a sentinel key and asserts it appears only in the key file. The page empties the field before the request is answered and keeps no copy. Anyone who can read the key file or the process environment can spend the operator's credits, as for any API key on disk.
* the model search (+POST /api/voice/search+) is the one panel route that reaches the internet. It is answered on the panel's own connection thread, never the composition loop; one at a time (a second is a 429), under a 6 s deadline, to the public list endpoint with no credential, no redirect and a 2 MiB response limit. The answer is untrusted text: it is mapped into a minimal typed DTO (UUIDs and style ids validated, texts cleaned of control characters and length-capped, at most 24 models, 8 speakers and 32 styles per page) and rendered with +textContent+. The search needs the same authenticated, same-origin POST as every state change, and it is off (404) unless the voice settings are composed.
* a chat line is normalized by the composition root, not by the page: source +local-panel+, source class +public_chat+, plane +content+, trust +untrusted+, no +authorization+, admitted by the call a stdin line goes through. It can influence what the performer says exactly as a viewer's chat line can, and nothing more (section 2). A line that looks like +operator.command+ stays chat text (section 4);
* status is read-only: the +aivtuberctl status+ snapshot plus a bounded view of recent spoken replies. Reply text is output that already passed section 11 (or a cached pack line); it is shown with +textContent+, never as markup.

=== 15.2 Attackers considered and the controls

[cols="2,4"]
|===
|Attacker |Control (each has a negative test)

|A web page in the streamer's own browser that sends requests to +127.0.0.1+ (CSRF)
|State-changing requests need +Origin+ equal to the panel origin (a missing +Origin+ is refused), +Content-Type: application/json+ (no form post), and a secret in a custom header. No CORS header is ever sent and +OPTIONS+ is refused, so a cross-origin page can neither pass a preflight nor read a response.

|A web page that rebinds its own DNS name to 127.0.0.1 (DNS rebinding)
|The +Host+ header must equal the exact +127.0.0.1:port+ for every route, including the page; +localhost+, a bare IP and other ports are refused. A rebinding page's requests carry its own name and are refused before anything else is read.

|Anything that learns the URL from a log, a screenshot or a request line
|The secret is only in the URL fragment, which no server or proxy receives, and is never in a query string; a query-string token is ignored (401). The page keeps it in a JavaScript variable (not in storage or a cookie) and removes it from the address bar. The URL is printed to the operator's console only, like the avatar URL, and the app never logs it. The secret is 256 bits, minted per launch from OS entropy, different from the control secret and the avatar token, and compared in constant time.

|A peer on the network
|There is no bind-address option; the listener is +127.0.0.1+ only and +AIVTUBER_PANEL_BIND+ / +_HOST+ / +_ADDR+ are refused at startup rather than ignored.

|A flooding client, a slow client, an oversized request
|Request heads are capped (8 KiB, 2 s), bodies (4 KiB, a declared +Content-Length+ above it is refused unread, chunked bodies are refused), chat text (500 characters, control characters refused), connections (16), authenticated calls (token bucket) and the queues (chat 8, control 4, state 64 KiB). A full queue answers 503; it never blocks the composition thread or grows. Stop and mute have a queue of their own and are served before chat, so content saturation cannot delay them (section 6).

|Script injection through the page
|Server strings are rendered with +textContent+; the page is served with +default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; frame-ancestors 'none'+, +X-Frame-Options: DENY+, +Referrer-Policy: no-referrer+ and +nosniff+. Only +panel.html+ and +assets/+ are served from the page directory (not the avatar page or any model).
|===

=== 15.3 Residual risk and assumptions

* *Chat read from the panel is still hostile text.* A viewer controls every character of what a connected chat delivers (#361). The controls above bound what it can be (untrusted public chat), how much of it gets in, and that it cannot become authority; what the model then says in reply is still model output, filtered by the output gate like any other. The sidecars are the project's own binaries, found next to the app: whoever can replace those files can already run code as the operator, which is outside this model. Closing the app's process abruptly (a kill, not a normal exit) can leave a sidecar running until its next write to the closed pipe; the Windows tree kill of +aivtuber-setup start+ covers the normal launcher path. The API quota of the YouTube key is spent while connected.

* *Another local process or user.* Loopback is reachable by every process on the machine. Such a process still needs the secret; it is shown only in the operator's terminal and the browser the operator opened. A process that can read that terminal, the browser's memory or its history can use it, as it could use +AIVTUBER_CONTROL_SECRET+ for +aivtuberctl+. The secret is per launch, so a stale URL is useless after a restart.
* *The authenticated panel exposes the avatar URL.* The state document includes the avatar page URL with its own token (display authority only: a second renderer connection is refused while one is active, and it can only receive avatar commands). Anyone who can use the panel could already stop and mute.
* *The control secret is in the same process.* The panel presents its raw bytes to +LocalControlIngress+ on the operator's behalf and never sends it to the page; the state document does not contain it. A compromise of the +aivtuber-app+ process is out of scope here, as it is for the control endpoint.
* *Showing the URL again (#388).* The panel URL, with its secret, may be shown again only to someone who already holds operator authority on this machine, and is never written anywhere new. `aivtuberctl panel-url` sends the operator action `panel.url`, which reuses the existing `performer.stop` capability (the operator endpoint's ingress always holds it, only the authenticated local ingress can mint it, and the secret it reveals already carries stop and mute; no new capability). The panel's own request path has no such action, so a page holding the panel secret cannot ask for it again; chat, model, Jev and tool output cannot reach it. The URL is held in memory as a redacted `SecretString`, returned only to the authenticated caller, and the audit record is the bare phrase `panel url shown` (tests: a wrong secret, an ingress without the capability, the panel path, an app without a panel, and a chat line naming the action; a marker secret is in no audit record, status, support bundle or `Debug`). `aivtuber-setup start --open` runs `aivtuberctl panel-url` with the control secret in the child's environment and hands only a loopback `http://127.0.0.1:` URL to the platform opener by absolute path without a shell. *Accepted risk:* that URL is then a process argument of the browser launch, readable by another process of the same user for a moment; such a process could equally read the control secret from the environment, so it gains nothing it did not have. The URL is never put in a log, the support bundle, the env file or a settings file.
* *Browser history.* A browser may record the URL with its fragment before the page replaces it. The secret does not survive a restart.
* *Plain HTTP.* Loopback HTTP is not exposed to the network; no TLS is used or needed for that scope, and none must be added in a way that implies the panel may be reached remotely. Remote exposure remains out of scope (a reverse proxy would defeat the +Host+ and +Origin+ rules and must not be put in front of it).

Revisit if the panel gains any action beyond stop, mute and chat (for example settings, issue #335 S2): each new action needs its own capability decision, an audit record and a negative test, and anything that writes configuration must be validated and must not be reachable by a request that only carries the status secret.
