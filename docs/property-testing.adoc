= Generated property coverage (issue #145)

== Scope

Issue #145 adds `proptest`-generated coverage for the deterministic
scheduler/replay state machines. It deliberately does *not* add parser fuzz
targets (issue #146) or the bounded CI/corpus job (issue #147), so those remain
separable slices of parent #57.

== Where it lives

`crates/scheduler/tests/properties.rs`, an integration test target in the
scheduler crate.

That is the smallest boundary that owns every invariant in scope: `Scheduler`
holds arbitration, preemption, rejection, cancellation, operator stop and
bounded retention, and `ReplayHarness` holds deterministic replay and sink-action
construction. Reaching further out would either duplicate the state machine or
test through a layer that cannot observe the invariant.

Two consequences follow from using an integration target rather than a
`#[cfg(test)]` module:

* the properties exercise the crate's public surface exactly as a consumer sees
  it, so a private helper cannot accidentally become load-bearing;
* `proptest` is a `[dev-dependencies]` entry and never reaches a production
  build. `cargo tree --edges normal` contains no `proptest` node for any
  workspace member; only `--edges dev` does.

`proptest` is declared with `default-features = false, features = ["std",
"bit-set"]`. That keeps the `fork`/`rusty-fork`/`tempfile` process-isolation
machinery out of the dependency graph: shrinking runs in-process, and failing
cases are reproduced from the checked-in regression file instead.

== Invariants covered

Each property is a whole-sequence invariant, so a failure reports the minimal
operation sequence that broke it.

`generated_operation_sequences_preserve_scheduler_invariants` drives up to 40
generated operations (schedule, advance, operator stop, complete-all) against a
generated `SchedulerConfig` and checks, after every single step:

* *Resource exclusivity.* Two plans that conflict — exclusive work against
  anything, otherwise intersecting channel sets — never occupy the same instant.
  The conflict predicate is restated in the test rather than imported, so the
  property asserts the arbitration rule instead of restating the implementation.
* *Rejection atomicity.* A refused schedule leaves the live collection, history,
  metrics, generation counter and logical clock byte-identical. `last_rejection`
  is asserted separately, because reporting the rejection is the documented
  output of a rejection rather than a leaked reservation.
* *Stale-action suppression.* Every live item is reachable through both public
  liveness indexes, and nothing in terminal history remains reachable through
  either. This is what makes a cancelled or stopped audio/avatar action
  undispatchable.
* *Terminal classification.* Completed work has no interior cancellation
  boundary; cancelled work always has one; nothing non-terminal appears in
  history.
* *Bounded retention.* Metrics agree with the actual history, and the ring
  policy never retains more than its configured capacity. `RetainAll` is
  documented to grow without bound, so the capacity bound applies only to the
  ring.

`a_live_event_cannot_be_scheduled_twice` covered the same stale-action concern
from the request side. It has been removed: it asserted that re-requesting a
live event cannot produce a second live generation, but that is not the
scheduler's contract. `Scheduler::schedule_at` accepts a second request for an
`event_id` that is already live and overwrites the event liveness index with the
newer generation. The property's assertion
(`live.plan.generation != accepted.generation`) was therefore trivially true in
exactly the case it was written to catch, so it passed without checking
anything. Asserting the invariant would have meant first making it true, which
is a contract change rather than a test change; until that decision is made the
claim is recorded here instead of being asserted.

Duplicate-`event_id` contract (issue #198), decided and enforced rather than
recorded as a gap:

[source,text]
----
event_id   = logical event identity, at most one live (Queued/Playing) item
generation = scheduling-attempt identity, unique per accepted schedule
----

`Scheduler::schedule_at` refuses a second request for an id that is still live
with `Rejection::DuplicateEvent`. The check runs after logical time has
advanced — which is what retires an already-terminal item and frees its id —
and before any reservation, cooldown or generation is touched, so a rejected
duplicate changes nothing. The id becomes schedulable again once the prior item
is terminal, and that accepted request receives a fresh generation. The check
reads the live collection rather than the event liveness index, so a stale index
entry can never widen the accepted set. `check_liveness_index_consistency`
consequently asserts identity rather than presence: the index has to resolve a
live item's id to *that* item, a terminal entry may only be reachable through a
stale pointer, and a terminal id that legitimately reappeared must resolve to
the newer live item.

`stale_actions_are_never_dispatchable` works at the sink boundary instead of the
scheduler boundary. It asserts that every start action corresponds to an item
that was not cancelled before its logical start, that no generation starts
twice, and that every stop is preceded by a start for the same generation.

`duplicate_live_event_id_is_rejected_atomically` covers the issue #198 contract
above. Its generated steps draw event ids from a pool of three, because the
main suite cannot produce a duplicate at all: `plan_for` derives
`evt-{sequence}` and a sequence never repeats a step, which is exactly why the
contract needed a property of its own. It asserts that a live duplicate is
refused atomically — the refusal moves no generation, reservation or cooldown —
that an id whose item retired becomes schedulable again under a generation that
advances, that no two live items ever share an id, and that the event liveness
index resolves each id to *that* item rather than merely to *something*.

`identical_trace_seed_and_config_are_byte_identical`,
`the_seed_actually_varies_the_replay`, and
`replay_is_independent_of_input_order` cover replay determinism. The first is
the determinism requirement itself; the other two exist because a determinism
property is trivially satisfied by a harness that ignores its inputs. The seed
property sweeps 64 seeds rather than comparing a pair, because two seeds can
coincidentally round to the same millisecond start delay.

== Reproducing and shrinking a failure

Failing cases are persisted to `crates/scheduler/proptest-regressions/properties.txt`
and replayed on every later run, so a regression becomes a checked-in input
rather than something that has to be rediscovered.

To replay *only* the persisted cases:

[source,shell]
----
PROPTEST_CASES=0 cargo test --locked -p aivtuber-scheduler --test properties
----

`cases` counts only *newly generated* inputs: proptest replays every persisted
seed first, those replays are not counted towards `cases`, and only then does
it generate inputs while `successes < cases`. Zero therefore stops the run
after the stored cases and nothing else. Setting `PROPTEST_CASES` to 1 is *not*
replay-only: it replays the stored case and then generates one more. proptest
pins that itself in `persisted_cases_do_not_count_towards_total_cases`, which
asserts that two inputs run at `cases: 1`; an instrumented run of this target
measured 1 input at `PROPTEST_CASES=0` and 2 when it is set to 1. The caveat is
an empty corpus: `PROPTEST_CASES=0` would then generate nothing and pass
vacuously, which is why `scripts/validate.mjs` requires a real `cc <seed>` line
in `crates/scheduler/proptest-regressions/`.

To widen the search while investigating:

[source,shell]
----
PROPTEST_CASES=10000 cargo test --locked -p aivtuber-scheduler --test properties
----

The default is 96 cases per property, which keeps the whole target inside the
normal `cargo test --locked --workspace` gate in a couple of seconds. Widening
is an investigation step, not the committed default.

== What the properties do not guarantee

These properties explore operation sequences against the *current*
implementation. They cannot prove an invariant holds for every possible
schedule, and they say nothing about the interleavings inside the concurrent
shadow orchestration of issue #164, which needs a different mechanism (an FSM
explorer or explicit test hooks) because its ordering properties are about
thread interleaving rather than about reachable scheduler states.

Every property here was verified to be non-vacuous by mutating the scheduler and
confirmating the corresponding failure, including the cases where a mutation
correctly did *not* fail because the property does not claim that behaviour.
== Regression workflow (issue #147)

By default `cargo test --workspace` runs each property with a random seed and
the case count the suite pins itself: `cases: 96` in the `ProptestConfig` of
`crates/scheduler/tests/properties.rs`, so the default is 96 cases per
property rather than proptest's own 256 (`PROPTEST_CASES` overrides that in
turn, which is how CI narrows the run to 64). The seed is *not* pinned outside
CI, so **every PR explores a different space** and no run is reproducible from
the previous one.

Two mechanisms make failures durable:

* *Checked-in regressions.* When a property fails, proptest shrinks the input
  and appends it to `crates/scheduler/proptest-regressions/properties.txt`. That
  file is committed, and proptest replays those cases **before** generating any
  novel input — so they run regardless of the seed. The directory resolves
  relative to the crate root, not the test file.
* *A seeded bounded subset in PR CI.* This command runs twice in
  `.github/workflows/ci.yml`, once as a step inside the required `Rust checks`
  job and once as a standalone `regressions` job:

[source,text]
----
PROPTEST_CASES=64 PROPTEST_RNG_SEED=20261004 \
PROPTEST_MAX_SHRINK_ITERS=4096 \
cargo test --locked -p aivtuber-scheduler --test properties
----

The *gating* copy is the one inside `Rust checks`. `main`'s branch protection
requires exactly three contexts — `Validate schemas and fixtures`,
`Rust checks`, and `Schema and security fixtures` — and the standalone
`regressions` job is not one of them, so a regression failure there would leave
all three green and the pull request mergeable. Duplicating the run inside a
required job makes the failure actually stop the merge without needing a branch
protection change; both jobs share a checkout, so they share
`proptest-regressions/`.

Both copies carry `if: always()` on their `upload-artifact` step. Without it,
Actions' default `success()` condition skips the upload exactly when `cargo
test` exits non-zero — which is precisely when proptest has just shrunk and
persisted a *new* case. The artifact would be reclaimed with the runner.

`scripts/validate.mjs` asserts that the seeded step lives inside a job whose
context name is one of the required checks (it parses the `jobs:` blocks rather
than the whole file, so moving the step back into the non-required job fails
the check), and that at least one real `cc <seed>` persistence line is present
in `crates/scheduler/proptest-regressions/` — a file that exists but is empty or
comments-only does not count as a corpus.

Stable-only and fuzz-free by design. libFuzzer needs nightly, and a second
toolchain channel in `ci.yml` would contradict
`scripts/validate-toolchain-pins.mjs`; the bounded fuzz campaigns live in
`.github/workflows/fuzz.yml`, which is schedule/`workflow_dispatch` only and
never blocks a pull request. `scripts/validate.mjs` asserts the seed, the case
bound, and that the fuzz workflow has no `pull_request` trigger.

=== Bringing a failure back as a regression

1. Reproduce from the recorded seed rather than from memory:

   [source,text]
   ----
   PROPTEST_CASES=64 PROPTEST_RNG_SEED=20261004 \
     cargo test --locked -p aivtuber-scheduler --test properties
   ----

2. Read the `failing step` / `generated sequence` in the failure message, or run
   the property alone with `PROPTEST_CASES=0` to replay stored cases only,
   without generating a single new input.
3. Fix the runtime. Do not edit `proptest-regressions/*.txt` to make the suite
   green — those files are evidence, and deleting a line silently un-arms the
   regression.
4. Commit the regenerated regression file with the fix, so the failing case
   replays on every future run.

=== Verified round

This workflow was exercised end to end rather than described from theory:

* `retire()` was temporarily changed to skip
  `self.live_by_event.remove(&item.plan.event_id)`. The property suite failed
  with `terminal item evt-0 is still reachable by event id`, and proptest shrank
  the failing sequence to three `Schedule` operations and wrote it to
  `crates/scheduler/proptest-regressions/properties.txt`.
* The mutation was reverted and the stored case re-run with
  `PROPTEST_CASES=0`: it passes — persisted replay only, zero generated
  inputs, so the pass does not depend on a lucky fresh case.
* The mutation was re-applied and re-run with `PROPTEST_CASES=0`: it fails
  again with `terminal item evt-0 is still reachable by event id`. At
  `PROPTEST_CASES=0` the generated-case loop body runs zero times, so no fresh
  input existed that could have failed — the failure can only come from the
  checked-in regression, and the file genuinely pins the behaviour.
* The zero-generation claim was measured rather than inferred: an instrumented
  run of `generated_operation_sequences_preserve_scheduler_invariants` counted
  **1** input at `PROPTEST_CASES=0` (the persisted seed) and **2** when
  `PROPTEST_CASES` is set to 1 (persisted plus one generated), matching
  proptest's own `persisted_cases_do_not_count_towards_total_cases`
  assertion. The instrumentation was removed afterwards and the target is
  unchanged.

`crates/scheduler/src/lib.rs` is byte-identical to `main`; the mutation existed
only during those runs.
